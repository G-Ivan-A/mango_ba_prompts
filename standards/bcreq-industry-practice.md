# Индустриальные стандарты BCREQ: что используем, где и как из них выводится структура

Этот файл — SSOT блока «Индустриальные стандарты» на странице
[«Стандарты»](https://g-ivan-a.github.io/mango_ba_prompts/#standards). Он делает
ссылки вида «по BABOK» однозначными: у каждого стандарта указано, какой его пункт
что определяет в BCREQ. Реестр сверенных источников остаётся в
[стандарте отраслевых стандартов](industry-standards-standard.md).

## 1. Выбор стандартов

Согласие со стандартами БА даёт на шаге **Ш-А Анкета**. Молчание или пропуск шага
означает значения по умолчанию; они записываются в журнал решений 8.5.

| Что определяет | По умолчанию | Что может выбрать БА | Параметр |
| --- | --- | --- | --- |
| Термины раздела 1 | Словарь Манго D0 → IREB CPRE Glossary | другой отраслевой словарь со ссылкой | `словарь` |
| Формулировка и группировка ФТ, раздел 3 | BABOK Guide v3 | другой стандарт со ссылкой | `стандарт ФТ` |
| Структура раздела 5 | C4 model | TM Forum ODA или другой стандарт со ссылкой | `альтернативный стандарт` |

Если БА дал ссылку на другой стандарт, ассистент выписывает из него три вещи:
элементы модели, правило «один пункт раздела — один элемент» и способ отметить
покрытие ФТ. Если стандарт закрыт или таких правил в нём нет, ассистент говорит об
этом и предлагает значение по умолчанию. Решение остаётся за БА.

### Группировка ФТ: как «настройка → исполнение → ресурсы и данные» следует из BABOK

Запись остаётся короткой, но каждое слово теперь имеет определение:

| Уровень | Категория BABOK 7.1 | Что значит в разделе 3 | Актор |
| --- | --- | --- | --- |
| Блок | Capability | Одна бизнес-возможность. Название блока — название возможности. | — |
| 1. Настройка | People and Roles | Кто и что настраивает, какие права для этого нужны | Пользователь с правом администрирования |
| 2. Исполнение | Activity Flow | Что происходит в сценарии работы | Оператор, сотрудник, система |
| 3. Ресурсы и данные | Data and Information | Какие данные, отчёты и ресурсы создаёт и использует возможность | Любой |

BABOK задаёт категории, но не порядок. Порядок — договорённость BCREQ: так читает
Заказчик. Категория Rationale в раздел 3 не входит: обоснование живёт в 2.2 и 2.3.
Если категории в блоке нет, её пропускают.

## 3. Раздел 5: выбор между C4 и TM Forum ODA

Оба стандарта дают **метамодель**: набор типов элементов и правило, какой элемент
становится пунктом. Поэтому структура раздела 5 выводится детерминированно и не
зависит от номеров ФТ. Номера ФТ попадают только в скобки покрытия на уровне 5.х.

| | C4 model (по умолчанию) | TM Forum ODA (по выбору БА) |
| --- | --- | --- |
| Что это | Открытая модель описания программной системы | Отраслевая архитектура телеком-оператора |
| Когда подходит | Доработка или новая система Mango; интеграция с внешней системой | Заказчик или внешняя система работает в терминах TMF; продолжение такого документа; сравнительный прогон |
| Метамодель | Person → Software System → Container → Component → Code | Functional Block → ODA Component → Open API |
| Правило пункта L1 ФДР | 5.1 — контекст решения (диаграмма System Context). Далее один пункт 5.х на связь системы с человеком или внешней системой | Один пункт 5.х на затронутый функциональный блок |
| Правило пункта L2 ТС | Один пункт на изменённый Container | Один пункт на затронутый ODA Component |
| Доступ | Открыт | Полные спецификации — участникам TM Forum; Open API открыты, Apache-2.0 |
| Что подключается | — | Словарь D9 в сверку глоссария |

### C4: как получить структуру

1. Назвать систему в рамке (Software System): одну на документ.
2. Выписать людей (Person) и внешние системы, связанные с ней напрямую.
3. Пункт 5.1 — контекст: все элементы шага 2 и связи между ними.
4. Каждая связь — кандидат в пункт 5.х. Связи с одним и тем же элементом можно
   объединить, если они согласуются одним решением.
5. Для каждого 5.х отметить в скобках ФТ, которые пункт покрывает.

Источники: [System Context](https://c4model.com/diagrams/system-context),
[абстракции C4](https://c4model.com/abstractions).

Пример для интеграции с внешней HelpDesk-системой:

```text
5.1. Контекст решения
5.2. Подключение интеграции Пользователем в ЛК (ФТ-01)
5.3. Передача звонков и заявок: ВАТС ↔ внешняя система (ФТ-02, ФТ-03)
5.4. Работа Оператора с заявкой при звонке (ФТ-03, ФТ-04)
```

### TM Forum ODA: как получить структуру

1. Отнести каждое изменение к функциональному блоку ODA: Engagement Management,
   Party Management, Core Commerce Management, Production, Intelligence Management.
   Точный состав зависит от версии ODA: сверьте его с версией, которую назвал БА.
2. Один затронутый блок — один пункт 5.х.
3. На L2 назвать ODA Component и Open API (TMF NNN). Если компонент неизвестен —
   вопрос команде.
4. Для каждого 5.х отметить в скобках ФТ, которые пункт покрывает.

Источники: [ODA](https://www.tmforum.org/oda/),
[компоненты ODA](https://www.tmforum.org/oda/implementation/components-canvas/),
[TMF Open API](https://github.com/tmforum-apis). Состав блоков сверен по вторичным
источникам (GÉANT, 2022); страница `tmforum.org/oda/` автоматическому чтению закрыта.
Нормативное описание блоков — GB1022 ODA Functional Architecture Guidebook.

## 5. Терминология issue #464

| Термин | Определение | Источник |
| --- | --- | --- |
| Однозначность (unambiguity) | Требование нельзя понять по-разному | IREB CPRE Glossary |
| Проверяемость (verifiability) | Выполнение требования системой можно проверить | IREB CPRE Glossary |
| Исполнимость | Результат сверки требования с документацией продукта по шкале Да / Частично / Нет | RUN-0070, RUN-0077, issue #382 |
| Пользователь (user) | В IREB — любой, кто пользуется функциями системы | IREB CPRE Glossary |
| Стейкхолдер (stakeholder) | В IREB — кто влияет на требования или на кого влияет система | IREB CPRE Glossary |

Различие для BCREQ:

- **проверяемость** — свойство формулировки. Её подтверждает возможность оценить
  требование по документации;
- **исполнимость** — результат такой оценки. Она показывает, нужна ли доработка.

Правило «Пользователь — сотрудник с правом администрирования» уже определения IREB.
Это сознательное сужение (класс С3 сверки): оно снимает путаницу ролей настройки и
исполнения и применяется только там, где обе роли есть. Правило
[раздела 1](bcreq-sections/01-glossary.md#пользователь-и-оператор) приведено в
стандарте раздела. «Стейкхолдер» в 2.5 тоже уже IREB: в реестр входят стороны
решения. Сотрудник остаётся актором сценария в 2.1.
