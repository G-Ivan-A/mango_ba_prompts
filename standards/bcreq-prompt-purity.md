# Чистота исполнимых промптов BCREQ

Промпт исполняет модель в чате или IDE-клиенте. Всё, что модель не может
исполнить, — шум, а ссылка на приватный репозиторий ещё и недоступна:
модель либо выдумывает содержимое, либо тратит шаг на ACCESS_GAP. Стандарт
задаёт три класса нарушений, политику размещения содержимого и машинных
сторожей. Мастер стандарта — только эта спица (решение владельца, issue #495,
комментарий 2, п.12); зеркало в runtime не создаётся.

Машиночитаемая часть (контур, словарь кейс-лексики, шаблоны балласта, реестр
кейсов) — [`bcreq-prompt-purity.json`](bcreq-prompt-purity.json). При
расхождении текста и JSON исполняется JSON, расхождение — дефект стандарта.

## 1. Классы нарушений

| Класс | Что | Правило | Пример нарушения |
| --- | --- | --- | --- |
| а | Ссылка на приватный репозиторий `mango_ba_prompts` (абсолютная или относительная ссылка на файл репозитория), голый указатель на файл спицы в тексте промпта (путь `standards/…`, `pr-ops/…`, `scripts/…`, `docs/…` кроме `docs/kb` runtime, «стандарт композиции §N», «README §N») или ссылка на runtime не на закреплённом SHA | ЧП-1 | `[Промпт 0](https://github.com/…/mango_ba_prompts/blob/main/prompts/…)`; «Стандарт каждого раздела — файл `NN-*.md` в standards/bcreq-sections» |
| б | Кейс-лексика: имя внешней системы, имя продукта, ID кейса, параметр профиля продукта, кейс-термин (словарь CT-01…CT-09) | ЧП-2 | «коннектор» в цели AIN-06; amoCRM/API-привязка в общем контракте A-IN |
| в | Балласт: HTML-комментарии и маркеры сборки, отсылки к issue/PR/BL/RUN/ADR и к внутренним RFC/ADR по ID, пометки «по тесту», отчёты сборщика, редакционные оговорки, история изменений (шаблоны BP-01…BP-13) | ЧП-3 | `<!-- Experimental: for BL-156 … -->`; «Редакция по тесту (#427)»; «приоритет у принятого RFC-AIN-001» |

## 2. Правила

- **ЧП-1. Без приватных ссылок.** В исполнимом тексте нет URL и относительных
  ссылок на файлы `mango_ba_prompts`. Нужный для исполнения контракт — в
  runtime `mango-ba-ai-runtime` по закреплённому SHA
  ([реестр справочников](bcreq-runtime-references.md), раздел 1). Контракта
  в runtime нет — задача в бэклог (РТ-N реестра) и строка заглушки
  `[СПРАВОЧНИК ОТСУТСТВУЕТ: <имя>]`, а не ссылка на спицу. Справочное
  (RFC, ADR, отчёты) — вне исполнимого контура: промпт на него не ссылается.
  Снятая ссылка не остаётся голым путём или названием файла спицы
  («в standards/…», «README §2»): правило, которое входит в промпт,
  называется по месту в самом промпте, остальное уходит из текста (правило
  A-SPOKE-PATH; архив — история, к нему не применяется).
- **ЧП-2. Промпт — принцип, не кейс (АД-11).** Правило формулируется через
  класс явления: «внешняя система», «интеграционный компонент», «подсистема
  продукта», «номера телефонии продукта». Конкретный кейс — в golden set
  runtime с трассировкой к правилу (реестр кейсов CR-NN); продуктовый факт
  (профили, состав линейки, параметры) — в справочнике runtime.
- **ЧП-3. Без балласта.** Критерий удаления — влияние на исполнение, а не
  название блока. Удаляемое не пропадает молча: реестр удалений фиксирует
  «что → куда перенесено» (описание PR задачи).
- **ЧП-4. Правка через ССОТ.** Сгенерированные файлы (`prompts/drafts/**`,
  `site/data/*.json`) руками не правятся: правится источник, затем
  пересборка цепочкой из раздела 5. Проекция исполнимого текста —
  `scripts/prompt_purity.py:project` (снимает ссылки на спицу с сохранением
  текста ссылки и служебные HTML-комментарии).
- **ЧП-5. Данные сайта без приватных URL.** `site/data/*.json` хранят пути от
  корня репозитория; ссылку на исходник строит интерфейс (`site/app.js`,
  `repoHref`). Тела промптов в данных сайта подчиняются ЧП-1…ЧП-3.
- **ЧП-6. Версия сайта.** Подготовительные сборки — только patch-серия
  текущего опубликованного minor (2.9.x); версия не убывает. Переход на
  2.10.0 — только после записанной приёмки и явного решения о деплое.

## 3. Политика размещения

| Содержимое | Где живёт | Как попадает в исполнение |
| --- | --- | --- |
| Принцип, правило с ID, стоп-кран, контракт входа/выхода | Текст промпта (ССОТ спицы → сборка) | Напрямую |
| Исполнимый контракт или справочник, нужный модели | runtime по закреплённому SHA | Ссылкой из реестра справочников |
| Кейс (пример, контрпример, конкретная система или задача) | runtime golden set (`golden/prompt-regressions.yaml`, И-12) | Не читается промптом; проверяет исполнение принципа при прогоне |
| Продуктовый факт (профили, состав линейки) | runtime справочник (`taxonomy/product-profiles.yaml`, И-11) | Ссылкой по SHA; до слияния — заглушка З-5 |
| Справочное (RFC, ADR, история, отчёты сборщика) | Спица, вне исполнимого контура | Никак |

## 4. Защита от сверхчистки

Не балласт и сохраняется при чистке (решение владельца, комментарий 2, раздел 3):

- тексты правил с ID (Р, АД, АП, БС, КС, IN/EX/AN/EL/GE/VE/RE), контракты
  входа и выхода, стоп-краны, circuit breakers;
- receipt и «Проверки», «Состояние BCREQ», «Пакет памяти проекта», маркер
  «КОНЕЦ <ID> <версия>»;
- блоки «Итог шага», «На согласование БА», план текущего шага и отчёт о
  чтении БЗ и норм;
- операциональные пояснения: «читай "Промпт ДОЛЖЕН" как "ты ДОЛЖЕН"»,
  UNKNOWN → `[ТРЕБУЕТСЯ УТОЧНЕНИЕ]`, приоритет текста шага над общим блоком
  (служебная рамка блока удаляется, правило приоритета остаётся явно);
- локаторы и цитаты runtime, ссылки на runtime по закреплённому SHA;
- универсальные нормы со значениями, одинаковыми для любой задачи
  (минимальный набор словарей D1, D2, D11): в runtime уходит только
  соответствие «профиль продукта → словари» (CT-09).

Общеупотребительные термины и имя организации-владельца процесса не являются
кейс-лексикой (`generic_allowed` в JSON).

Сторож сверхчистки — `protected_markers` в JSON: число защищённых маркеров
(ID правил, `[ТРЕБУЕТСЯ УТОЧНЕНИЕ]`, ACCESS_GAP, «Состояние BCREQ», «Пакет
памяти проекта», «КОНЕЦ», «Итог шага», «На согласование БА», «Промпт ДОЛЖЕН»,
receipt, стоп-краны) в каждом промпте и черновике не меньше, чем в базе
(снимок `experiments/issue_495/audit/protected-baseline.json`). Исключение —
ID правил, не внесённых в промпты по решению базового стандарта: они
перечислены с причиной в `prompts/drafts/manifest.json` (`excluded_base_rules`).

## 5. Контур и исключения

Контур — `contour` в JSON: тексты промптов (`prompts/*.md`, черновики,
системный трек, 39 стандартов классов), ССОТ A-IN, служебные файлы рядом с
промптами (только класс а) и данные сайта.

- **Архив 2.7.0** (`prompts/archive/**`) — историческая сущность: классы б и
  в, кроме HTML-комментариев, не применяются; файл архива — проекция
  оригинала, хэши опубликованного оригинала сохранены в манифесте.
- **Разметка сайта** (`site/index.html`, `site/app.js`) — интерфейс, а не
  промпт: ссылка «исходник на GitHub» строится интерфейсом и в контур не
  входит.
- **Frontmatter промптов** — метаданные карточки (статус, версия, связи).
  Класс а применяется: ссылки во frontmatter сняты (запись D-12). Классы б
  и в и правила A-PRIVATE-NAME, A-RELATIVE, A-SPOKE-PATH не применяются: путь
  в поле метаданных — не инструкция исполнителю. Сборщики черновиков
  frontmatter не переносят; в комплекте A-IN на сайте файл шага копируется
  целиком вместе с frontmatter — побайтовое совпадение с файлом — критерий
  приёмки #474 («24/24 clipboard byte-equal»), его держат валидаторы #474 и
  #476.

Пересборка после правки ССОТ:

```bash
python3 scripts/bcreq_handoff.py && python3 scripts/build_bcreq_a_in.py \
  && python3 scripts/build_bcreq_step_prompts.py && python3 scripts/build_bcreq_system_track.py \
  && node scripts/generate-pages-data.mjs
```
