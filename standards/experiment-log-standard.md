# Стандарт фиксации экспериментов (Draft v0.1)

> **Статус: Draft v0.1.** Этот стандарт намеренно минимален и **подлежит
> валидации на 2–3 следующих экспериментах**. Если на практике метрик окажется
> мало (или много) — правим стандарт, а не подгоняем эксперименты под форму.
> Открытые вопросы — в конце документа и в `governance/BACKLOG.md`.

## Зачем

Чтобы накопить доказательную базу «какой промпт где недотягивает», каждый
реальный прогон БА должен оставлять **сопоставимый, лёгкий** след. Цель — не
бюрократия, а feedback loop: *прогон → метрики → правка промпта → следующий
прогон*.

Ключевой принцип: **фиксация должна занимать минуты, а не быть проектом**.
Стандарт сознательно НЕ требует заполнять 20 полей перед началом работы. Если
форма мешает — у БА есть право зафиксировать по минимуму (Уровень 0).

## Два уровня фиксации (выбор за БА)

### Уровень 0 — по умолчанию (≈30 секунд): GitHub Issue

Подходит для большинства прогонов и для быстрого старта.

1. Создать issue с лейблом `experiment`.
2. Вставить в тело issue стенограмму чата (или ссылку на неё).
3. Заполнить **ядро метрик** (6 полей ниже) — можно прямо чек-боксами/строками.

Всё. Анализ и решение о правках промптов происходят отдельно (в `docs/analysis/`
или в комментариях issue). Это и есть «право на отказ от бюрократии» в действии.

### Уровень 1 — по запросу: лёгкий Markdown-файл

Нужен, **только** когда прогон становится доказательной базой для:

- перевода промпта `draft → canonical` (README требует минимум один
  зафиксированный прогон), либо
- конкретной правки промпта (как в анализе 1027).

Файл кладётся в `prompts/experiments/` по имени
`[операция]-[ярлык]_[YYYY-MM-DD].md` и использует шаблон ниже.

## Ядро метрик (обязательно на обоих уровнях)

Шесть полей. Заполняются за минуты.

| Поле | Тип | Что значит |
| --- | --- | --- |
| `iterations` | число | Сколько раз прошли цикл «генерация → правка» до приёмки. Прокси трудозатрат. |
| `ba_edits` | число | Сколько ручных правок/вмешательств сделал БА. Прокси «недотянутости» промпта. |
| `quality` | 1–5 | Субъективная оценка качества результата (5 — принял почти без правок). |
| `prompts_used` | список | Какие промпты запускались (id или имена файлов). Связь с библиотекой. |
| `verdict` | enum | `works` / `works-with-edits` / `fails`. |
| `outcome` | 1–2 строки | Что зафиксировано и что чинить дальше. Вход для следующей правки. |

Метрики `iterations`, `ba_edits`, `quality` прямо названы в issue #101 как
ориентир. `quality` субъективна сознательно: на старте важнее скорость фиксации,
чем точность шкалы.

## Шаблон Уровня 1 (копировать целиком)

```markdown
---
status: draft
version: 0.1
updated: YYYY-MM-DD
ai-generated: false
experiment: <короткий-id-эксперимента>
scope: prompts
related_artifacts:
  - "prompts/<запущенный-промпт>.md"
---

# Эксперимент: <название>

## Метрики
- iterations: <N>
- ba_edits: <N>
- quality: <1–5>
- prompts_used: [<id1>, <id2>]
- verdict: <works | works-with-edits | fails>
- outcome: <1–2 строки>

## Что генерировали
<1–3 предложения: задача, какие разделы ТЗ, какой продукт.>

## Что сработало (с цитатами)
- <цитата из чата> — <короткий вывод>

## Что не сработало / правки БА (с цитатами)
- <цитата из чата> — <какую правку пришлось внести вручную>

## Предложения по промптам
- <файл> → <суть правки или ссылка на анализ/PR>

## Вопросы для согласования
- <если есть>
```

> Цитаты из стенограммы обязательны в секциях «что сработало / не сработало» —
> именно они делают вывод доказуемым (тот же принцип, что в анализе 1027).

## Почему именно так (аргументация формата)

- **Два уровня вместо одного.** Богатый формат существующих файлов в
  `prompts/experiments/` отличен для канонизации, но тяжёл для повседневной
  фиксации. Уровень 0 (Issue + чат) снимает порог входа; Уровень 1 сохраняет
  совместимость с принятой практикой и требованием README.
- **Ядро из 6 полей, а не 20.** Достаточно для сравнения прогонов между собой
  (динамика `iterations`/`ba_edits` по экспериментам = есть ли прогресс), но не
  превращается в форму-блокер.
- **Субъективная `quality`.** На объёме 1–3 экспериментов точная рубрика
  преждевременна; уточним шкалу после валидации.

## Пример заполнения (на сессии 1027)

`iterations ≈ 8`, `ba_edits ≈ 12`, `quality = 4`,
`prompts_used = [glossary-context-understanding-stepwise, fr-documentation-stepwise, constraints-documentation-oneshot]`,
`verdict = works-with-edits`,
`outcome` = «промпты отработали; правки P1–P5 по читаемости 4.x.1, канонике
6.1.1–6.1.3 и фильтру избыточных ограничений». Полный прогон по этому стандарту —
[`prompts/experiments/fr-generation-1027-live_2026-06-16.md`](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/prompts/experiments/fr-generation-1027-live_2026-06-16.md).

## Открытые вопросы (валидировать на следующих экспериментах)

1. Достаточно ли 6 метрик, или нужно добавить время/длину результата?
2. Нужна ли формальная рубрика для `quality` (1–5), или субъективной хватает?
3. Где граница между Уровнем 0 и Уровнем 1 — оставить на усмотрение БА или задать
   правило (например, «правишь промпт → заводишь файл Уровня 1»)?
4. Автоматизировать ли подсчёт `iterations`/`ba_edits` из стенограммы?
