# Стандарт README

README — это первый коммуникационный слой проекта или каталога. Он быстро
объясняет, что перед читателем, зачем это существует и куда идти дальше.

Стандарт применим к корневому `README.md` и README внутри каталогов. Цель —
написать полезный README за 5 минут, не превращая его в журнал изменений,
контракт, спецификацию или реестр.

## Назначение

README должен за первые 5 секунд ответить на три вопроса:

- Что это за проект/каталог?
- Какую проблему он решает?
- Чем отличается от других? Уточните, от каких соседних каталогов или
  документов README помогает отличить этот объект.

Если читателю нужно знать историю решений, точный контракт, список всех записей
или полный аудит, README ссылается на соответствующий документ, но не копирует
его содержание.

## Четыре канона

### Канон 1: Коммуникация

README начинается с человеческого контекста: название, краткое описание и
назначение. Первый абзац должен содержать ключевые слова предметной области и
не должен начинаться с технических деталей, таблиц, YAML-полей или истории
миграции.

Минимальный ответ:

- что это за проект/каталог;
- какую проблему он решает;
- чем отличается от соседних каталогов, стандартов, KB, run records или docs.

### Канон 2: Инструкция

README должен объяснять, как использовать каталог или проект:

- быстрый старт с командами, если команды существуют;
- 1-2 коротких примера использования;
- требования к окружению, если без них инструкция не воспроизводится;
- куда писать результат, если каталог связан с процессом выполнения.

### Канон 3: Сообщество

README должен показывать маршрут участия:

- как сообщить об ошибке: создать GitHub Issue с контекстом и ожидаемым
  результатом;
- как предложить код или документацию: Pull Request по правилам
  [`CONTRIBUTING.md`](../CONTRIBUTING.md);
- где читать полную документацию, стандарт или контракт.

Раздел `## Как помочь?` может быть опущен в маленьком внутреннем каталоге, если
рядом уже есть очевидная ссылка на корневый README или `CONTRIBUTING.md`.

### Канон 4: SEO

SEO здесь означает видимость и находчивость, а не рекламный текст:

- ключевые слова должны быть в первом абзаце;
- заголовки должны быть понятными без контекста;
- описание должно занимать 1-2 предложения;
- ссылки должны иметь осмысленные подписи, а не "тут" или "см. выше".

## Обязательная структура

Базовый README использует такую структуру:

```markdown
# Название (что это?)

Краткое описание (1-2 предложения).

## Что это?

## Как использовать?

## Быстрый старт

## Связанные документы

## Как помочь? (опционально)
```

Разделы можно объединять только для очень маленького каталога, но первые четыре
элемента должны оставаться распознаваемыми: название, краткое описание,
`## Что это?`, `## Как использовать?` или `## Быстрый старт`.

## Запрещено

- Не смешивать README с `CHANGELOG.md`: даты, релизные заметки и история
  изменений живут в журнале изменений.
- Не смешивать README с контрактами и спецификациями: точные поля, MUST/SHOULD,
  схемы данных и валидаторы живут в стандартах или `CONTRACT.md`.
- Не смешивать README с реестрами и индексами: длинные списки записей живут в
  `REGISTRY.md`, индексах или generated data.
- Не превышать 200-300 строк без причины. Если README растёт, вынесите детали в
  связанные документы.
- Не начинать с технических деталей без контекста.
- Не дублировать полный текст связанного стандарта, RFC или run-контракта.

## Разделение ответственности

| Документ | Назначение |
| --- | --- |
| `README.md` | Коммуникация: что это, зачем, как использовать, куда идти дальше. |
| `CHANGELOG.md` | Логи изменений: что добавлено, изменено, исправлено и когда. |
| `CONTRACT.md` | Спецификации: поля, схемы, MUST/SHOULD-правила, machine-readable contract. |
| `REGISTRY.md` | Реестры и индексы: списки записей, таблицы, каталоги объектов. |

Если в каталоге уже есть стандарт вместо `CONTRACT.md`, README должен ссылаться
на него как на источник правил. Пример: `runs/README.md` ссылается на
[`standards/runs-contract-standard.md`](runs-contract-standard.md), а не
переопределяет контракт записи.

## Интеграция

- [`standards/cascading-context-loading-standard.md`](cascading-context-loading-standard.md):
  если README часто загружается агентами и становится тяжёлым, рядом создаётся
  `README.executable.md`. Оригинальный `README.md` остаётся full-версией, а
  executable-слой содержит только маршруты и триггеры эскалации.
- Hub RFC #254
  [`research/mango/repository-structure-vision-2026-06.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/mango/repository-structure-vision-2026-06.md):
  README не должен смешивать Definition и Run, governance и operational records,
  стандарт и ADR/RFC. Он ссылается на source-of-truth, но не зеркалит
  `research/` в этом споке.
- [`standards/runs-contract-standard.md`](runs-contract-standard.md): README
  каталога `runs/` объясняет назначение и быстрый старт, а поля `metadata.yaml`,
  структуру `runs/YYYY/RUN-XXXX/` и проверки оставляет run-контракту.
- [`templates/readme-template.md`](../templates/readme-template.md): новый README
  можно начинать с шаблона и удалять неприменимые подсказки.

## Примеры

### Пример хорошего README

````markdown
# Runs

`runs/` — каталог результатов выполнения BA-процессов и промптов. Он отделяет
записи прогонов от определений процессов, стандартов и документации.

## Что это?

Здесь лежат run records вида `runs/YYYY/RUN-XXXX/`.

## Как использовать?

Создайте новый `RUN-XXXX`, заполните `metadata.yaml` и четыре подкаталога.
Точный контракт: `standards/runs-contract-standard.md`.

## Быстрый старт

```bash
python3 scripts/validate_issue_123_runs_contract.py
```

## Связанные документы

- `standards/runs-contract-standard.md`
- `standards/readme-standard.md`
````

Почему пример хороший: первый абзац отвечает "что это" и "зачем", контракт
вынесен в стандарт, команда проверки указана отдельно.

### Пример плохого README

```markdown
# Runs

## metadata.yaml

run_id MUST match RUN-XXXX. process MUST be filled. version MUST be filled.

## Migration registry

| Old path | New path |
| --- | --- |
| prompts/experiments/a.md | runs/2026/RUN-0001/outputs/a.md |

## Changelog

2026-06-20: moved files.
```

Почему пример плохой: README начинается с технического контракта, смешивает
спецификацию, реестр миграции и журнал изменений, но не объясняет назначение
каталога.

## Чек-лист

- [ ] Первый абзац за 5 секунд отвечает: что это, какую проблему решает, чем
      отличается.
- [ ] Есть разделы `## Что это?`, `## Как использовать?`, `## Быстрый старт`,
      `## Связанные документы`.
- [ ] Команды и примеры можно выполнить или понять без чтения истории PR.
- [ ] Для ошибок и вкладов есть маршрут: Issue, Pull Request, полная
      документация.
- [ ] В первом абзаце есть ключевые слова предметной области.
- [ ] README не содержит changelog, полный контракт, длинный registry или
      migration log.
- [ ] Длина обычного README не превышает 200-300 строк.
- [ ] Для тяжёлого README создан `README.executable.md` по каскадному стандарту
      или явно решено, что companion не нужен.
