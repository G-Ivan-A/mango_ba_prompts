# Мета-стандарт раздела 5 «Описание разрабатываемого решения (ОРР)»

> **Метка #420, риск 8.** Название раздела исправлено: ОРР — описание
> разрабатываемого решения, ФДР — функциональный дизайн решения, ТС —
> техническая спецификация. Прежние расшифровки «Описание решения»,
> «функциональное решение», «техническое решение» не совпадали с
> аббревиатурами ([комментарий владельца к PR #422](https://github.com/G-Ivan-A/mango_ba_prompts/pull/422#issuecomment-6560476938)).

> Общие правила, стили и шаблон — в [README](README.md). Носитель —
> [ADR-012](../../docs/adr/2026-10-adr-012-bcreq-meta-standards.md).

## Назначение

Раздел 5 показывает, как будет реализована доработка целиком: каждое ФТ и то, что
нужно для полноты, но не вынесено в раздел 3 (граничные случаи, служебные функции).
L1 ФДР (функциональный дизайн решения) — для согласования, L2 ТС (техническая
спецификация) — для команды разработки.

| Уровень | Определение |
| --- | --- |
| L1 ФДР | Детализация разработки на уровне бизнес-логики, достаточная для однозначного согласования со стейкхолдерами. |
| L2 ТС | Полная детализация разработки на уровне бизнес-логики и внешне наблюдаемых технических параметров: термины, поля, статусы, форматы, известные контракты. Это не архитектура и не системный анализ: у БА нет доступа к архитектуре. Внутреннее устройство остаётся за командой разработки; что БА неизвестно — вопрос команде. |

## Структура: по стандарту, а не по ФТ

Раздел 5 **не строится** по блокам ФТ. Опыт показывает: ФТ-01 не должно соответствовать
пункту 5.1. Структуру задаёт стандарт, который БА выбрал на шаге Ш-А: C4 (по умолчанию),
TM Forum ODA или другой по ссылке. Правила вывода структуры —
в [справочнике стандартов](../bcreq-industry-practice.md#3-раздел-5-выбор-между-c4-и-tm-forum-oda).

Номера пунктов не зависят от номеров ФТ. Покрытие указывается только в скобках на уровне
5.х; пункт **покрывает** ФТ (отношение Satisfy, BABOK 5.1):

```text
5.1. Контекст решения
5.2. Формулировка заявки (ФТ-01, ФТ-03)
```

Совпадение номеров разрешено, но ни из чего не следует. Пункт может не покрывать ни
одного ФТ: контекст решения или служебные функции. Каждое ФТ покрыто хотя бы одним пунктом.

## Необходимо и достаточно

**L1 ФДР (функциональный дизайн решения) — обязателен всегда:**

- Для каждого пункта 5.х — видимое пользователю поведение: кто, где, что делает, что
  получает. Дополнения «→ раздел 5» из раздела 3 описаны здесь же.
- Контекст на уровне C4 L1 (System Context): доработанная система, пользователи,
  внешние системы, направления потоков — схемой или таблицей «участник → что
  передаёт → кому».
- Таблица трассировки ФТ ↔ ОРР (ниже).
- Нет: методов API, форматов, БД, очередей, имён сервисов.

**L2 ТС (техническая спецификация) — по опции уровня:**

- Контейнеры и сервисы на уровне C4 L2 (Container), которые меняются.
- Дельта API: новые и изменённые методы в формате OpenAPI, события — AsyncAPI;
  тип изменения: `добавление | изменение | удаление` и признак обратной
  совместимости.
- Данные: новые сущности и поля, миграция, сроки хранения.
- Доменные подпункты блока L2 ТС — по
  [профилям композиции](../bcreq-composition-standard.md#4-профили-продуктов).

**Достаточно:** каждое ФТ покрыто строкой трассировки; каждая строка L2 ведёт к
строке L1. Описание неизменяемых частей системы — лишнее (Р6).

## Стиль

- L1 — короткий: КС1–КС7 [README §2.1](README.md#21-короткий-стиль-разделы-2-5-l1-6),
  бюджет ≤900 слов без таблицы трассировки.
- L2 — технический [README §2.3](README.md#23-технический-и-табличный-стили-дополнение):
  таблицы и контракты; правила КС2, КС5, КС6. Названия форматов (OpenAPI,
  AsyncAPI) допустимы как технический факт (исключение правила Р5).

## Уровни L1 и L2

БА: «Уровень 1: ФДТ (необходимо и достаточно для согласования)»
[р. 752, Ч-13](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/experiments/issue_387/chat-2026-10-22-23-register.md?plain=1#L47); «Уровень 2: ТС (расширенная, опционально)» [р. 752, Ч-14](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/experiments/issue_387/chat-2026-10-22-23-register.md?plain=1#L48).
В issue #387 уровень 1 назван ФДР; в стандарте используется это название.

Опция уровня задаётся на шаге Ш-А или в шаге 2.6/2.7: `уровень: L1 | L1+L2`.
По умолчанию — `L1`.

| Условие | Рекомендуемый уровень |
| --- | --- |
| Доработка в одном продукте, API не меняется. | L1 |
| Нужна детальная оценка разработки до передачи в команду (разделы 5–8 → оценка, [р. 796, Ч-42](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/experiments/issue_387/chat-2026-10-22-23-register.md?plain=1#L76)). | L1+L2 |
| Меняется публичный API или webhook (продукт API). | L1+L2: дельта OpenAPI/AsyncAPI обязательна |
| ≥2 продуктов со стыковыми ФТ. | L1+L2: стыки описаны контрактом |
| БА явно выбрал уровень. | выбор БА |

Модель рекомендует уровень по таблице, выбирает БА (правило Р3, CB-0.5). При
`L1` блок L2 ТС содержит одну строку «L2 — на стороне команды разработки».

**Опция альтернативного стандарта.** Если по
[условиям композиции](../bcreq-composition-standard.md#3-tm-forum-oda--альтернативный-стандарт)
выбран TM Forum ODA, пункты L1 строятся по функциональным блокам ODA, L2 описывает
компоненты ODA и TMF Open API вместо C4 L2 и собственной дельты OpenAPI. Другой стандарт
БА задаёт ссылкой; ассистент сначала выводит правило пункта и показывает его БА.

### Трассировка ФТ ↔ ОРР

| ФТ | ОРР L1 (пункт) | ОРР L2 (пункт, если есть) | Продукт | Стык |
| --- | --- | --- | --- | --- |
| ФТ-01 | 5.2 | ТС 1 | ЛК | — |
| ФТ-02 | 5.3 | ТС 2, ТС 3 | ВАТС → ЛК | событие ВАТС → настройка ЛК |

> **Метка расхождения #420, риск 2, снята issue #464.** ФТ нумеруются
> ФТ-01, ФТ-02 …, а пункт ФДР называется «5.х Название (ФТ-01, ФТ-02)».
> Номера 5.х задаёт выбранный стандарт, а не порядок ФТ.

Стыковое ФТ (затрагивает ≥2 продуктов) имеет в L1 одно описание, в L2 —
описание каждой стороны стыка и контракт между ними (правило К4
[композиции](../bcreq-composition-standard.md#2-правила-композиции)).

## Паттерны формулировок

| Корректно | Некорректно | Почему |
| --- | --- | --- |
| L1: «Администратор включает передачу текста разговора в настройках интеграции ЛК. После разговора ВАТС отправляет текст в CRM Заказчика.» | L1: «Сервис transcription-gateway публикует событие в Kafka-топик.» | Детали L2 в L1. |
| L2: таблица «метод `POST /webhooks/transcript` · поле `call_id` · тип изменения: добавление · обратная совместимость: да». | L2: «Будет сделан новый метод API для передачи текста.» | Нет контракта и типа изменения. |
| «5.3. Передача заявок: ВАТС ↔ внешняя система (ФТ-02, ФТ-03)» — пункт по связи C4. | «5.1 ФТ-01», «5.2 ФТ-02» — пункт на каждое ФТ. | Структура следует за стандартом, а не за нумерацией ФТ. |
| L1 одним пунктом на стыковое ФТ + L2 по сторонам стыка. | Отдельные разделы «ОРР ВАТС» и «ОРР ЛК», повторяющие одно ФТ. | Раздел 5 распадается по продуктам (правило К3). |
| «L2 — на стороне команды разработки» при опции `L1`. | Пустой блок L2 ТС без пометки. | Неясно, пропуск это или решение. |

## Circuit breakers

| ID | Условие | Действие |
| --- | --- | --- |
| CB-5.1 | Нет согласованных разделов 3 и 4 (Согласование 1 не пройдено). | Остановиться: раздел 5 строится после гейта Согласование 1. |
| CB-5.2 | ФТ невозможно реализовать без изменения, которое противоречит разделу 2.4.2. | Остановиться, вернуть вопрос о границах (возврат в A-CORE). |
| CB-5.3 | Меняется публичный API, а выбран уровень `L1`. | Рекомендовать `L1+L2`, решение за БА. |
| CB-5.4 | Поведение продукта, на которое опирается решение, не подтверждено документацией. | Спросить БА. Нет ответа — `[ТРЕБУЕТСЯ УТОЧНЕНИЕ]`, вопрос в 8.4 и согласованная с БА гипотеза. |
| CB-5.5 | Стандарт раздела 5 не выбран на Ш-А. | Применить C4 и записать выбор по умолчанию в 8.5. |

## Чек-лист валидации

- [ ] Уровень (`L1` или `L1+L2`) указан и выбран БА.
- [ ] Структура выведена из выбранного стандарта; нумерация 5.х не зависит от нумерации ФТ.
- [ ] Скобки покрытия стоят только на уровне 5.х, каждое ФТ раздела 3 указано хотя бы в одном пункте.
- [ ] Каждое ФТ раздела 3 есть в таблице трассировки; нет строк L2 без строки L1.
- [ ] L1 не содержит методов API, форматов, БД и имён сервисов; ≤900 слов.
- [ ] L2 содержит дельту API с типом изменения и обратной совместимостью (если API меняется).
- [ ] Стыковые ФТ описаны в L1 один раз, в L2 — по сторонам стыка с контрактом.
- [ ] Доменные подпункты — только в блоке L2 ТС по профилям композиции.
