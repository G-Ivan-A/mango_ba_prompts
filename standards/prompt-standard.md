# Стандарт промпта

> Предложен на утверждение Пользователю (issue #52). До утверждения —
> рекомендация. Формат — по практике Хаба: обязательства сверху,
> обоснование в конце; нормативный словарь
> [RFC 2119](https://www.rfc-editor.org/info/bcp14)
> (**ДОЛЖНО** / **СЛЕДУЕТ** / **МОЖНО**).

## Стороны и область

Контракт обязывает всех contributors и AI-агентов, создающих или изменяющих
файлы в `prompts/` (включая `prompts/archive/`). Не распространяется на
записи результатов в `runs/` (см. §Тестирование) и `patterns/`
(см. [pattern-standard.md](pattern-standard.md)).

## Обязательства

### Frontmatter — ровно 6 обязательных полей

1. Промпт **ДОЛЖЕН** начинаться с YAML-frontmatter, содержащего ровно
   6 обязательных полей:

   | Поле | Значения | Назначение |
   | --- | --- | --- |
   | `id` | `mango-[операция]-[режим]` (= имя файла + префикс `mango-`) | Уникальный токен для аналитики. |
   | `title` | строка на русском, 2-5 слов | Человекочитаемое название для UI. |
   | `status` | `draft` \| `canonical` \| `archived` | Зрелость промпта. |
   | `version` | semver (`0.1`, `1.0`, …) | Версия содержимого. |
   | `updated` | `YYYY-MM-DD` | Дата последнего изменения. |
   | `temperature` | число (обычно `0.1`) | Рекомендуемая температура запуска. |

   Поля `id` и `title` добавлены поправкой по
   [issue #92](https://github.com/G-Ivan-A/mango_ba_prompts/issues/92).
   `id` **ДОЛЖЕН** быть уникальным и не дублироваться между активными и
   архивными промптами. `title` **НЕ СЛЕДУЕТ** перегружать техническими
   аббревиатурами (кроме общепринятых: ФТ, ТЗ, ASR, UC, US, LLM).

2. `status: archived` — валидное терминальное значение. Архивация
   промпта **НЕ ДОЛЖНА** требовать создания issue: перенос файла в
   `prompts/archive/` + `status: archived` выполняется в обычном PR.
3. Frontmatter **НЕ ДОЛЖЕН** расширяться маппингами и ссылками:
   маппинг паттерн ↔ промпт ↔ процесс живёт централизованно в
   [docs/ba-processes/00-index.md](../docs/ba-processes/00-index.md),
   research-зависимости — в
   [docs/hub-research-dependencies.md](../docs/hub-research-dependencies.md).
4. Provenance-поля (`source_hub`, `source_sha`, `based_on`) **МОЖНО**
   сохранять для мигрированных артефактов; для новых промптов они
   не обязательны.

### Именование

5. Имя файла **ДОЛЖНО** следовать схеме `[домен]-[операция]-[режим].md`
   (kebab-case): операция — из
   [docs/taxonomy.md](../docs/taxonomy.md) (§1, `_` → `-`), режим —
   `stepwise` \| `oneshot` \| `legacy`. Пример: `fr-validation-stepwise.md`.

### Ссылки (формат для RAG)

6. Ссылки на стандарты и глоссарий внутри тела промпта **ДОЛЖНЫ** быть
   Markdown-ссылками с путём от корня репозитория:
   `См. [Глоссарий](standards/GLOSSARY.md)`. Относительные пути
   (`../standards/...`) и голые упоминания без ссылки **НЕ СЛЕДУЕТ**
   использовать — RAG-индексация опирается на единый формат.

### Жизненный цикл

7. Новый промпт **ДОЛЖЕН** проходить временный workflow из
   [CONTRIBUTING.md](../CONTRIBUTING.md): draft → review issue →
   `canonical`.
8. Промпт со `status: canonical` **ДОЛЖЕН** содержать явный раздел
   «ФОРМАТ ВЫВОДА».

### Тестирование

9. Результаты прогонов промпта **СЛЕДУЕТ** фиксировать в
   `runs/YYYY/RUN-XXXX/outputs/` файлом
   `[имя-промпта]-[сценарий]-[YYYY-MM-DD].md`; сам прогон оформляется по
   [контракту runs](runs-contract-standard.md).
   Перевод `draft → canonical` **ДОЛЖЕН** опираться минимум на один
   зафиксированный прогон.

## Нейминг: парс-алгоритм, запрет перегрузки и KB-промпты (ADR-006, issue #97)

> Дополнение по [ADR-006](../docs/adr/006-prompt-naming.md) (issue #97).
> Уточняет правило 5, не отменяя его; 24 существующих промпта не переименовываются.

### Парс-алгоритм имени (справа налево)

Имя `[домен]-[операция]-[режим].md` разбирается так:

1. **режим** = последний сегмент, из множества `{stepwise, oneshot, legacy}`;
2. **операция** = максимальное совпадение предшествующих сегментов с операцией
   из [таксономии §1](../docs/taxonomy.md) (kebab-форма, `solution_design` →
   `solution-design`); операция **МОЖЕТ** быть многословной;
3. **домен** = остаток слева (1-2 сегмента, kebab-case).

Пример: `technical-details-solution-design-legacy` → домен `technical-details`,
операция `solution-design`, режим `legacy`.

### Запрет перегрузки (жёсткое требование ФТ-4)

- **Правило P1.** Имя **ДОЛЖНО** иметь ровно три логические части (домен,
  операция, режим). Четвёртая ось **НЕ ДОЛЖНА** появляться: запрещены суффиксы
  `-kb`, `-rag`, `-v2`, `-simple`, `-new`, `-final`.
- **Правило P2.** Домену **СЛЕДУЕТ** быть ≤2 сегментов.
- **Правило P3.** Версия — в `version`, зрелость — в `status`; в имя их выносить
  **НЕ ДОЛЖНО**.

### KB-промпты — сквозная способность, не ось имени

Доступ к базе знаний — cross-cutting capability. Промпт получает её через
**общий блок цитирования KB** ([kb-standard.md](kb-standard.md),
[ADR-007](../docs/adr/007-kb-standard.md)), а **НЕ** через суффикс `-kb`/`-rag`.
Если основная задача промпта — операция над самой БЗ, он именуется по обычной
схеме с подходящей операцией (например `research`, `governance`, `quality`).

## Обобщение содержимого промпта (issue #413)

> Решение владельца в [#413](https://github.com/G-Ivan-A/mango_ba_prompts/issues/413):
> промпт содержит только паттерны, классы и принципы. Вопросы, значения и
> решения конкретной задачи — уровень исполнения задачи, а не промпта. Правило
> совпадает с защитой АД-11 конституции BCREQ: универсальный промпт содержит
> принцип, а не значения или частное решение из одного кейса.

### Уровни содержимого

| Уровень | Что это | Пример | Где хранится |
| --- | --- | --- | --- |
| Принцип | Норма, верная для любой задачи процесса | «Статус ставит человек» | Промпт |
| Класс | Тип объекта, входа или дефекта с признаками распознавания | Класс ограничения платформы | Промпт, классы процесса ([ADR-015](../docs/adr/2026-10-adr-015-bcreq-manual-classes.md)) |
| Паттерн | Повторяемая форма решения с условиями применения | «Вопрос после поиска»: сначала проверить вход, потом спрашивать | Промпт, [`patterns/`](../patterns/README.md) |
| Кейс | Вопрос, значение, фраза или решение одной задачи | Вопрос ассистента о настройке в конкретной задаче BCREQ | Golden set процесса ([стандарт evals](evals-contract-standard.md)), журнал задачи, `runs/` |

### Правила G1–G5

Обобщение по G1–G5 убирает из промпта признаки конкретного кейса. Оно
**НЕ** разрешает объединять классы промптов, сокращать требования или
упрощать шаги процесса.

- **G1.** Правило в промпте **ДОЛЖНО** быть сформулировано на уровне
  принципа, класса или паттерна.
- **G2.** Промпт **НЕ ДОЛЖЕН** содержать вопросы, значения, фразы и решения
  конкретной задачи. Кейс, из которого выведено правило, **СЛЕДУЕТ** записать
  в golden set процесса или в журнал задачи; в промпт попадает только
  обобщение.
- **G3.** Тело промпта **НЕ ДОЛЖНО** содержать идентификаторы задач и
  прогонов: ID вопросов (`Q-2.1`), задач (`BCREQ-123`), прогонов
  (`RUN-0075`), сценариев (`SC-65`) и ссылки на issue. Происхождение правила
  фиксируется в CHANGELOG, записи прогона или PR, а не в тексте, который
  читает модель.
- **G4.** Перед добавлением правила задай вопрос: «Верно ли это правило для
  любой другой задачи того же процесса?» Ответ «нет» означает кейс (G2).
- **G5.** Существующие нарушения не правятся в треке «Проект». Они
  перечислены в allowlist валидатора и переданы в трек промптов
  ([#411](https://github.com/G-Ivan-A/mango_ba_prompts/issues/411)).
  Allowlist может только уменьшаться.

Проверка G3 и G5 автоматизирована:
[`scripts/validate_issue_413_prompt_generalization.py`](../scripts/validate_issue_413_prompt_generalization.py).
Правила G1, G2 и G4 проверяет ревьюер: признаки кейса — конкретные числа,
имена, настройки и цитаты одной задачи.

## Критерии соответствия (DoD)

- [ ] Frontmatter содержит ровно `id`, `title`, `status`, `version`, `updated`,
      `temperature` (+ опциональные provenance-поля для мигрированных).
- [ ] `id` уникален и совпадает с именем файла с префиксом `mango-`; `title`
      человекочитаем и на русском.
- [ ] Имя файла соответствует `[домен]-[операция]-[режим].md`; операция
      существует в таксономии.
- [ ] Имя не перегружено (P1-P3): три части, без запрещённых суффиксов.
- [ ] Внутренние ссылки — Markdown от корня репозитория.
- [ ] Промпт отражён в маппинге
      [docs/ba-processes/00-index.md](../docs/ba-processes/00-index.md).
- [ ] Промпт содержит паттерны, классы и принципы; в теле нет вопросов,
      значений и идентификаторов конкретных задач (G1–G3).

## Обоснование

- **Без маппингов в frontmatter.** Migration-era frontmatter (с `output_format`,
  `glossary_ref`, `research_dep`) перегружал файлы и дублировал
  централизованные реестры. Минимальный frontmatter снижает трение для БА
  и AI-агентов (решение Пользователя, issue #52); маппинги выносятся в
  `docs/ba-processes/00-index.md` и `docs/hub-research-dependencies.md`.
- **`id` и `title` (issue #92).** Это идентификационные, а не маппинг-поля:
  `id` даёт стабильный токен для аналитики использования, `title` —
  человекочитаемое название для интерфейса GitHub Pages. Они не дублируют
  центральные реестры и не нарушают принцип «без маппингов в frontmatter».
- **`archived` без issue.** Архив — операция низкого риска (файл не
  удаляется); обязательный issue создавал бы лишний процессный шум.
- **RAG-формат ссылок.** Единый предсказуемый формат позволяет резолвить
  ссылки при индексации промптов в RAG без эвристик.
- **Обобщение (issue #413).** Частный случай в промпте занимает контекст,
  смещает модель к одному кейсу и устаревает вместе с задачей. В golden set
  тот же кейс работает как проверка правила и не влияет на другие задачи.
