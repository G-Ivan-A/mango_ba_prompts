# Стандарт композиции стандартов для кросс-продуктовых доработок BCREQ

> Носитель — [ADR-012](../docs/adr/2026-10-adr-012-bcreq-meta-standards.md).
> Мета-стандарты разделов — в [bcreq-sections/](bcreq-sections/README.md).
> Нормативный словарь [RFC 2119](https://www.rfc-editor.org/info/bcp14).

Стандарт отвечает на четыре вопроса issue #387: когда доменный стандарт
применяется к подпункту, а когда ко всему разделу; как сохранить единство
раздела 3 и раздела 5 при 2+ продуктах; как трассировать ФТ ↔ ОРР на стыках.
Он также проверяет гипотезу о специализированных промптах для API и КЦ/ЛК
[р. 796, Ч-41](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/experiments/issue_387/chat-2026-10-22-23-register.md?plain=1#L75).

## 2. Правила композиции

- **К1. Доменный стандарт — к подпункту.** Доменный стандарт **ДОЛЖЕН**
  применяться к подпункту, который описывает один продукт (5.2.x, UC, пункт
  6.2), а не ко всему разделу. Весь раздел подчиняется доменному стандарту,
  только если доработка затрагивает один продукт **и** раздел — L2.
  Так один документ не превращается в «описание по ВАТС» или «по КЦ» — это
  антипаттерн из гипотезы 2 БА [р. 748, Ч-11](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/experiments/issue_387/chat-2026-10-22-23-register.md?plain=1#L45).
- **К2. Раздел 3 — один список.** При 2+ продуктах раздел 3 — **один** список ФТ
  по BABOK, сгруппированный по бизнес-способности (Capability или Feature
  [классификации Mango](product-classification-contract.md#иерархия-классификации)),
  а не по продуктам. Правило 5±2 действует на весь раздел. Доменные термины
  в ФТ — только из раздела 1. Продукт, который реализует ФТ, указывается в
  таблице трассировки раздела 5, не в тексте ФТ.
- **К3. Раздел 5 — единый каркас.** Каркас раздела 5 один для всех продуктов:
  5.1 L1 (C4 L1, общий контекст всех продуктов), 5.2 L2 (C4 L2). Доменные
  стандарты разных продуктов живут в подпунктах 5.2.x и не меняют каркас.
  Отдельные разделы «ОРР ВАТС», «ОРР КЦ» запрещены.
- **К4. Стыковое ФТ.** ФТ, которое выполняется ≥2 продуктами, — стыковое. В
  таблице трассировки раздела 5 оно имеет: одно описание в L1; описание каждой
  стороны в L2; контракт стыка (метод OpenAPI, событие AsyncAPI, протокол
  профиля) с владельцем каждой стороны. У стыкового ФТ есть UC, проходящий
  через оба продукта (раздел 7), и зависимость в 8.2 от команды второй
  стороны.
- **К5. Один термин на стыке.** Если продукты называют одну сущность по-разному
  (ВАТС: «вызов», КЦ: «обращение»), раздел 1 содержит оба термина и их связь.
  Расхождение с индустриальным словарём — блок сверки
  ([01-glossary](bcreq-sections/01-glossary.md#сверка-с-индустриальными-словарями)).
- **К6. Профиль — данные, не промпт.** Профили продуктов (§4) передаются
  промпту как данные (Промпт 0, поле `продукты`). Отдельные промпты по
  продуктам не создаются (§6).
- **К7. Уровень ОРР при 2+ продуктах.** При стыковом ФТ модель рекомендует
  `L1+L2` ([05-solution-description](bcreq-sections/05-solution-description.md#уровни-l1-и-l2)),
  выбор за БА.

## 3. TM Forum ODA — альтернативный стандарт

БА: TM Forum — «не стокль как замещающий, а если его не применяем, то оставить
его как альтернативный» [р. 766, Ч-31](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/experiments/issue_387/chat-2026-10-22-23-register.md?plain=1#L65). Issue #387: сохранить «для
совместимости с legacy», возможно — как замещающую опцию раздела 5.

**Статус:** альтернативный стандарт. По умолчанию не применяется.

**Условия применения** (достаточно одного, решение за БА и фиксируется в 8.5):

| ID | Условие | Пример |
| --- | --- | --- |
| ODA-1 | Legacy-совместимость: доработка продолжает документ или интеграцию, уже описанную в терминах TM Forum (SID, eTOM, ODA). | Старые требования интеграции с биллингом оператора. |
| ODA-2 | Заказчик или внешняя система — оператор связи, работающий по TMF Open APIs или модели SID. | Интеграция ВАТС с BSS оператора через TMF620/TMF622. |
| ODA-3 | Явный выбор БА для сравнительного прогона (тестирование стандарта как замещающего). | Прогон «arc42 + C4» против «ODA» на одной задаче. |

**Что заменяется:** только L2 раздела 5 — компоненты ODA и TMF Open API вместо
C4 L2 и собственной дельты OpenAPI. Словарь D9 подключается к сверке
глоссария. **Что не заменяется:** разделы 1–4, 6–8 и L1 раздела 5.

**Доступность.** TMF Open APIs открыты (лицензия Apache-2.0,
<https://github.com/tmforum-apis>). SID, eTOM и ODA Component specifications
доступны в полном объёме участникам TM Forum. Поэтому основной стек открыт, а
ODA — опция.

**Запрет из аудита Задачи 1.** Роль модели не задаётся через TM Forum или CBAP
(АП1 [аудита](../docs/analysis/2026-10-23-prompts-catalog-audit.md#35-антипаттерны)).
ODA — стандарт содержания, а не роль.

## 4. Профили продуктов

Профиль — набор доменных стандартов и словарей продукта. Профиль подключается,
если продукт есть в 2.5. Домены — по
[product-classification-contract](product-classification-contract.md#-domain-семейство).

| Профиль | Domain Mango | Доменные стандарты (раздел 5.2.x, 6, 7) | Словари сверки | Специфика ФТ |
| --- | --- | --- | --- | --- |
| ЛК (личный кабинет, настройки) | сквозной, владелец — продукт настройки | WCAG — только если доработка меняет интерфейс и Заказчик это требует | D1, D2, D11 | настройка → исполнение (Б3.7) |
| ВАТС | `voice-ucaas` | 3GPP TR 21.905 (терминология), SIP RFC 3261 (сигнализация) | D5, D6 | правила маршрутизации вызова |
| КЦ | `contact-center` | SCXML (сценарии и состояния), ITU-T E.600 (трафик, нагрузка), BPMN (процесс оператора) | D6, D11 | очередь, распределение, статусы оператора |
| РА (речевая аналитика) | `analytics` | — (класс стандарта не выбран: открытого отраслевого стандарта нет, см. [третье мнение](../docs/analysis/2026-10-23-bcreq-standards-third-opinion.md#3-findings)) | D11, D3 | правила анализа, чек-листы качества |
| API / интеграции | сквозной | OpenAPI, AsyncAPI, RFC 9110 | D8 | тип изменения метода; обратная совместимость |
| Оператор связи (опция) | — | TM Forum Open APIs, SID (§3) | D9 | только при ODA-1…ODA-3 |

## 5. Примеры комбинаций продуктов

### 5.1. ЛК + ВАТС: передача текста разговора в CRM

- Раздел 3: одна группа «Интеграция с CRM» (Capability `crm-integration`),
  ФТ 3.1 настройка в ЛК, ФТ 3.2 передача после разговора (стыковое: ВАТС → ЛК
  → CRM). Не «ФТ ЛК» и «ФТ ВАТС».
- Раздел 5: L1 — один контекст C4 L1 (ЛК, ВАТС, CRM Заказчика). L2 — 5.2.1 ЛК
  (настройка, OpenAPI), 5.2.2 ВАТС (событие завершения вызова по профилю ВАТС),
  контракт стыка — событие AsyncAPI.
- Раздел 7: UC «администратор включает → звонок завершён → текст в CRM»
  проходит через оба продукта.

### 5.2. ЛК + ВАТС + КЦ: обратный звонок из очереди

- Раздел 1: «вызов» (ВАТС) и «обращение» (КЦ) — два термина со связью (К5).
- Раздел 3: группа «Обратный звонок» (Feature `callback-scheduling`), 3–7
  ФТ на весь раздел.
- Раздел 5: 5.2.1 ЛК (настройка правил), 5.2.2 КЦ (состояния заявки на
  обратный звонок — SCXML-диаграмма), 5.2.3 ВАТС (исходящий вызов, SIP).
  Стыки КЦ → ВАТС и ЛК → КЦ — с контрактами.
- Раздел 7: граничные кейсы очереди (пустая очередь, все операторы заняты,
  повтор через интервал) по переходам состояний.

### 5.3. ЛК + ВАТС + РА: анализ звонков по чек-листу

- Раздел 3: группа «Контроль качества разговоров» (Capability
  `speech-analytics`); ВАТС — источник записи, РА — анализ, ЛК — настройка
  чек-листа и отчёт.
- Раздел 4: НФТ к задержке анализа и хранению — только из запроса.
- Раздел 5: L2 5.2.x по продуктам; для РА доменного стандарта нет, раздел
  описывается каркасом arc42 + C4 без доменного подпункта (К1, К3).
- Раздел 8.2: зависимость от команды РА.

### 5.4. API + КЦ: новый метод выгрузки статистики операторов

- Раздел 3: ФТ — «Система должна предоставлять внешней системе возможность
  получить …»; метод API не называется в ФТ (Ф4).
- Раздел 5: уровень `L1+L2` обязателен (меняется публичный API); 5.2.1 —
  дельта OpenAPI с типом изменения «добавление» и обратной совместимостью;
  5.2.2 — источник данных КЦ (статусы операторов, ITU-T E.600 для показателей
  нагрузки).
- Раздел 7: граничные кейсы API — пустая выборка, предел страницы, неверный
  период.

### 5.5. Оператор связи (ODA-2): ВАТС + биллинг оператора

- Разделы 1–4 и L1 — как обычно; L2 — компоненты ODA и TMF Open API (§3),
  словарь D9; выбор зафиксирован в 8.5.

## 6. Гипотеза: специализированные промпты для API и КЦ/ЛК

**Гипотеза БА** [р. 796, Ч-41](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/experiments/issue_387/chat-2026-10-22-23-register.md?plain=1#L75): ФТ на API отличаются от ФТ на КЦ или
ЛК; возможно, на раздел нужны несколько типов промптов. **Приоритет** —
антиинфляция.

**Проверка по разделам.**

| Раздел | Отличие API от КЦ/ЛК | Нужен отдельный промпт? |
| --- | --- | --- |
| 1 | другой словарь сверки (D8) | нет — выбор словаря по профилю |
| 2 | нет | нет |
| 3 | субъект ФТ — «внешняя система», а не пользователь; формула та же (Б3.4); ФТ API — последней группой (Б3.7) | нет — правило в стандарте раздела 3 |
| 4 | типичные метрики — время ответа, лимиты запросов; правило «только из входа» то же | нет |
| 5 | L2 обязателен при изменении публичного API; дельта OpenAPI с типом изменения | нет — условие опции уровня (К7, CB-5.3) |
| 7 | граничные кейсы API (пагинация, коды ошибок) | нет — техники ISTQB те же |

**Решение.** Отличия API от КЦ/ЛК — в **данных** (профиль, словарь, опция
уровня), а не в **структуре** раздела. Отдельные промпты по продуктам
дали бы ~5 профилей × 8 разделов вариантов и повторили бы АП5 аудита
(«варианты одной операции расходятся»). Поэтому:

1. Один промпт на шаг; профиль продукта — параметр Промпта 0 (К6).
2. Единственный структурный вариант — ФТ «с нуля» (В-Н, шаг 2.10), потому что
   у него другой фильтр (нет дельты) и другая группировка
   ([03-functional-requirements](bcreq-sections/03-functional-requirements.md#варианты-раздела)).
3. Критерий пересмотра: если в прогонах Задачи 3 одна и та же правка БА
   повторяется только для одного профиля в ≥3 прогонах, профиль выделяется в
   отдельный блок промпта (не в отдельный файл) через RFC.

## 7. Проверка соответствия

- [ ] Раздел 3 — один список, сгруппированный по Capability, без деления по продуктам.
- [ ] Каркас раздела 5 один; доменные стандарты — только в подпунктах 5.2.x.
- [ ] Каждое стыковое ФТ имеет описание сторон, контракт, UC через оба продукта и зависимость 8.2.
- [ ] TM Forum ODA применён только при ODA-1…ODA-3 и только к L2; выбор записан в 8.5.
- [ ] Профили переданы промпту как данные; новых промптов по продуктам нет.
