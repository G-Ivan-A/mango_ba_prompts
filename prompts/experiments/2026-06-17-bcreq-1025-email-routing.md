## Что сработало (успешные паттерны)

- **Цепочка 3 промптов работает.** Последовательный запуск трёх промптов дал
  цельное ТЗ без потери контекста между сессиями (контекст переносился явно через
  данные пользователя, а не автоматически).
- **`stepwise` для раздела 6 — лучше, чем `oneshot`.** Пошаговый анализ
  ограничений через Шаг 2 (майнинг) позволил выявить неочевидные граничные
  условия вокруг архитектурных связок ЛК/КЦ/Редактор.
- **Глоссарий как якорь.** Раздел 1 с чёткими определениями «Точка входа»,
  «Почтовый ящик», «Маршрут» предотвратил смешивание понятий в разделе 4.
- **Матрица приоритетов в ФТ** — ценная находка; помогает Заказчику расставить
  priority при сжатых сроках разработки.
- **Защита скоупа через ограничения.** Архитектурные связки между ЛК ВАТС, КЦ и
  Редактором были зафиксированы именно в разделе 6, а не «размазаны» по ФТ.

## Выявленные проблемы промптов

> Детальный анализ паттернов ошибок — в
> [`governance/analysis-bcreq-1025-2026-06-17.md`](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/governance/analysis-bcreq-1025-2026-06-17.md).

**Паттерн Б1 — Путаница настроек ЛК/КЦ:**
LLM несколько раз смешивал настройки, относящиеся к Личному кабинету (ЛК ВАТС),
с настройками Контакт-центра (КЦ). Промпт `fr-documentation-stepwise` не имеет
явного правила «зафиксируй архитектурные связки на Шаге 1 суммаризации контекста».

**Паттерн Б2 — Нарушение уровня иерархии ФТ:**
Вместо структуры `4.x` → `4.x.1` → `4.x.1.1` LLM периодически генерировал
требования как `4.x.x.x` (четыре уровня), нарушая правило атомарности верхнего
уровня. Особенно для сложных правил маршрутизации с несколькими условиями.

**Паттерн Б3 — Канцелярит на нижних уровнях иерархии:**
Уровни `4.x.1` — `4.x.1.1` (включая уровень `4.x.x.x`) генерировались тяжёлыми
канцелярскими оборотами (та же проблема, что в эксперименте 1027, Г2). Правка P2
из эксперимента 1027 ещё не применена к промпту. Дополнительно: при доработке
существующей системы на уровне ФТ `4.x.x` необходимо явно использовать ключевое
слово «ВОЗМОЖНОСТЬ» — промпт этого не предписывает явно.

**Паттерн Б4 — Путаница ролей (уточнение):**
Замены ролей инициированы пользователем; модель действовала в границах допустимого,
предлагая роли. Паттерн Б4 исключён из перечня ошибок LLM — ответственность
на стороне пользователя, а не промпта.

**Паттерн Б5 — Не учитывались архитектурные связки:**
LLM генерировал ФТ, не учитывая, что маршрутизация в КЦ зависит от настроек
в ЛК ВАТС и поведения Редактора. Архитектурные зависимости «всплывали» только
после явных корректировок БА.

## Инсайты для онтологии

> Связь с ADR #003–#010. Детальный разбор — в
> [`governance/analysis-bcreq-1025-2026-06-17.md`](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/governance/analysis-bcreq-1025-2026-06-17.md)
> §5.

**ADR-003 (Онтология БА):**
Эксперимент подтверждает трёхуровневую модель «Операция → Процесс → Артефакт».
Цепочка 3 промптов — это три процесса с явными артефактами-выходами
(Глоссарий+Контекст → ФТ → Ограничения). Связь через передачу контекста —
ключевое условие корректности.

**ADR-009 (Процесс BCREQ):**
Эксперимент соответствует конвейеру П1 (приём/нормализация) → П3 (моделирование
сценариев) → П4 (документирование). Human gate G2 (валидация) реализовывался
через ~30 итераций — высокая нагрузка на БА, что подтверждает необходимость
оптимизации промптов.

**ADR-006 (Нейминг):**
Все три промпта соответствуют стандарту нейминга `[домен]-[операция]-[режим].md`.
Выявлено: нет промпта для передачи контекста между сессиями цепочки — возможная
точка роста.

**ADR-007 (БЗ):**
Руководство пользователя КЦ v1.26.04 (PDF) было обработано как БЗ через механизм
«извлечение фактов As-Is → выжимка → генерация». Механизм работает, но потребовал
нескольких итераций на проверку выжимки.
