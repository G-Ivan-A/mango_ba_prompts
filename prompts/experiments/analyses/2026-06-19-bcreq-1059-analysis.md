# Анализ боевого эксперимента BCREQ-1059 (Email-маршрутизация по Точке входа)

Версия: 0.1

Дата: 2026-06-19

## 1. Назначение

Этот документ содержит детальный анализ результатов боевого эксперимента BCREQ-1059 —
прогона цепочки промптов `mango_ba_prompts` на задаче маршрутизации email-ответов
по «Точке входа» в Контакт-центре MANGO OFFICE. Анализ выполнен в режиме `Creative`
по требованию [issue #113](https://github.com/G-Ivan-A/mango_ba_prompts/issues/113).

**Цели анализа:**
1. Выявить 5 паттернов ошибок LLM (Э1–Э5) в ходе ~30 итераций согласования.
2. Зафиксировать 6 успешных паттернов (У1–У6).
3. Проанализировать взаимодействие БА + LLM: инсайты о точках согласования.
4. Сформировать 6 методологических инсайтов (M1–M6) для будущих стандартов БА.
5. Выявить связь с онтологией (ADR #003–#010) и сформировать RFC-1059.

**Контекст задачи:**
BCREQ-1059 — маршрутизация email-ответов по «Точке входа» в КЦ: когда оператор
отвечает на входящее письмо, система автоматически использует почтовый ящик,
на который это письмо пришло. Три продуктовых компонента:
ЛК ВАТС (Личный кабинет) ↔ КЦ (Контакт-центр) ↔ Редактор писем — образуют
архитектурные зависимости, усложнившие формулировку ФТ.

**Сравнительный контекст:**
Эта задача содержательно близка к BCREQ-1025 (тот же домен, те же три компонента).
BCREQ-1059 — независимый прогон, позволяющий проверить воспроизводимость паттернов
ошибок из BCREQ-1025.

## 2. Паттерны ошибок LLM (классификация Э1–Э5)

Паттерны сгруппированы в три класса: **структурные** (проблемы формата),
**семантические** (проблемы содержания) и **контекстные** (потеря/путаница контекста).

### 2.1 Контекстные паттерны

#### Э1 — Путаница архитектурных связок ЛК ВАТС ↔ КЦ ↔ Редактор (критический)

**Симптом:** LLM несколько раз выдумывал несуществующие механизмы — «выбор ящика
в КЦ-Исходящие», смешивал настройки ЛК ВАТС и КЦ, приписывал операторские функции
административным интерфейсам.

**Пример из сессии:**
- LLM генерировал ФТ вида «Оператор выбирает ящик в разделе "Исходящие КЦ"» —
  такого раздела в MANGO не существует; ящики настраиваются только в ЛК ВАТС.
- LLM путал настройку «по умолчанию» ящика (администраторская задача в ЛК ВАТС)
  и отображение ящика оператору (задача КЦ).

**Причина-гипотеза:** Промпт `glossary-context-understanding-stepwise` на Шаге 0
запрашивает термины и As-Is, но не запрашивает явно **архитектурные компоненты** и
**их зоны ответственности**. В результате LLM опирается на общую лексику
(«настройки», «интерфейс», «выбор») без привязки к конкретным компонентам.

**Повторяемость (ключевой сигнал):**
- Б5 в BCREQ-1025 (тот же продукт, тот же домен)
- Б1 в эксперименте 1027 (другой домен, та же архитектурная путаница)
- **Э1 в BCREQ-1059 — третий раз подряд**

Это **устойчивый системный паттерн**, а не случайная ошибка одного прогона.

**Влияние:** Наибольшее количество правок (~8 из ~12 ба_правок), самый
длительный цикл согласования.

**Связь с RFC:** RFC-1059-P1 (усиление RFC-1025-P1).

---

### 2.2 Структурные паттерны

#### Э2 — Нарушение иерархии ФТ (глубина и состав уровней)

**Симптом:** LLM генерировал 4-й уровень нумерации (`4.x.x.x`) вместо допустимых
трёх уровней; функции, сценарии, настройки и исключения смешивались в одной структуре.

**Пример из сессии:**
```
4.2.1.1 Если ящик активен — использовать его
4.2.1.2 Если ящик неактивен — использовать запасной
4.2.1.3 Если запасной не задан — вернуть ошибку
```
Три условия — это одна матрица, не три отдельных ФТ на разных уровнях.

**Причина-гипотеза:** Промпт `fr-documentation-stepwise` задаёт три уровня
иерархии, но не содержит явного **шаблона декомпозиции** («Функция → Сценарий → Исключения»).
При сложных правилах маршрутизации с несколькими условиями LLM инстинктивно добавляет
уровень вложенности для каждого условия.

**Повторяемость:** Совпадает с Б2 из BCREQ-1025.

**Связь с RFC:** RFC-1059-P2.

#### Э3 — Канцелярит на нижних уровнях иерархии

**Симптом:** На уровнях 4.x.x и ниже LLM использовал громоздкие канцелярские
обороты вместо лаконичных технических формулировок.

**Примеры из сессии:**
- ❌ «Инициализировать значение атрибута "адрес-отправителя" значением, соответствующим ящику Точки входа»
- ✅ «Система подставляет адрес ящика из Точки входа»
- ❌ «В случае отсутствия возможности определения технического идентификатора...»
- ✅ «Если Точка входа не определена...»

**Причина-гипотеза:** Промпт не разделяет требования к стилистике по уровням
иерархии. На верхних уровнях (4.x) LLM выдаёт бизнес-формулировки, а на нижних —
технические, при этом копируя избыточные конструкции.

**Повторяемость:** Совпадает с Б3 из BCREQ-1025.

**Связь с RFC:** RFC-1059-P3.

---

### 2.3 Семантические паттерны

#### Э4 — Путаница ролей (Оператор vs Администратор vs Пользователь)

**Симптом:** LLM приписывал административные действия (настройка ящиков, изменение
правил маршрутизации) роли «Оператора» — актора, у которого в As-Is нет доступа
к ЛК ВАТС.

**Пример из сессии:**
- ❌ «Оператор настраивает ящик-отправитель через меню "Настройки"»
- ✅ «Администратор настраивает связку Канал → Ящик в ЛК ВАТС»

**Причина-гипотеза:** Промпт `fr-documentation-stepwise` не запрашивает явную
ролевую модель **перед** генерацией ФТ. В итоге LLM опирается на общий смысл
слова «пользователь» вместо заранее определённой ролевой матрицы.

**Примечание:** В BCREQ-1025 паттерн Б4 (путаница ролей) был исключён из RFC
по итогам ревью. В BCREQ-1059 аналогичный паттерн выявлен снова, однако
инициатива ошибочной ролевой атрибуции здесь принадлежала LLM, а не пользователю.
Это подтверждает, что явная ролевая модель нужна как входной контекст промпта.

**Связь с RFC:** RFC-1059-P4.

#### Э5 — Ложные обещания в формулировке Цели

**Симптом:** Формулировка Цели (Раздел 2.2) обещала «возможность выбора ящика
в контексте обращения» — то, что ФТ (Раздел 4) реализует не напрямую, а через
настройки КЦ. Противоречие обнаружилось при ревью финального ТЗ.

**Причина-гипотеза:** Промпт `glossary-context-understanding-stepwise` генерирует
Цель до разработки ФТ. При финальном согласовании ФТ промпт `fr-documentation-stepwise`
не предлагает верифицировать, что формулировки ФТ согласуются с ранее заявленной Целью.

**Уникальность:** Паттерн Э5 не наблюдался в BCREQ-1025 и является новым для
этой экосистемы промптов. Он возникает только при несовпадении уровней абстракции
(Цель описывает желаемый результат; ФТ описывают механизм реализации).

**Связь с RFC:** RFC-1059-P6.

## 3. Успешные паттерны (У1–У6)

### У1 — Эффективность пошаговой цепочки (stepwise mode)

Разбиение процесса на 3 промпта с «человеческими воротами» (human-gate) позволило
обнаружить ошибки после каждого шага, не продолжая с неверным основанием.

**Доказательство:** Основные архитектурные ошибки Э1 были обнаружены **после Шага 1**
и исправлены до начала Шага 2. Без human-gate они унаследовались бы в Разделе 4.

### У2 — Глоссарий как «якорь» контекста

Явный глоссарий (Раздел 1) с 11 терминами использовался как общий язык в
последующих шагах. Когда LLM начинал «съезжать» с архитектуры, БА апеллировал
к глоссарию как точке отсчёта.

**Доказательство:** Из ~12 ба_правок ~4 принимали вид «термин X в глоссарии означает Y,
используй именно это определение».

### У3 — Матрица приоритетов как инструмент структурирования условий

Предложенная в ходе итераций матрица приоритетов (4.2.1.1: 3 условия → 3 строки)
избавила ФТ от нагромождения вложенных уровней.

**Инсайт:** Матрица — это «коллапс» нескольких уровней нумерации в одну таблицу,
что в итоге делает ТЗ читаемее.

### У4 — Чёткость разделения сценариев «система делает» vs «пользователь делает»

Явное разграничение системных триггеров («Система подставляет...») и пользовательских
действий («Система обеспечивает возможность оператору видеть...») вышло из итераций
Э4. После введения правила M3 иерархия ФТ стала однозначной.

### У5 — Раздел «Ограничения» как место для UI-ограничений As-Is

Перенос UI-ограничений (отсутствие ручного выбора ящика в Редакторе) в Раздел 6
очистил Раздел 4 от негативных формулировок («недоступен», «не предусмотрен»),
улучшив его читаемость.

**Контраст:** В BCREQ-1025 UI-ограничения оставались внутри ФТ, что приводило
к смешению «что система делает» и «чего система не делает».

### У6 — Воспроизводимость результатов через эксперимент-лог

Фиксация 6-метрической структуры эксперимента в формате `experiment-log.md`
позволила не только сохранить результаты, но и создать доказательную базу для
RFC. Будущие итерации промптов могут верифицироваться по тем же метрикам.

## 4. Инсайты взаимодействия БА + LLM

### 4.1 Где тратилось больше всего времени

| Шаг | Количество итераций | Основная причина |
| --- | --- | --- |
| Шаг 1 (глоссарий + контекст) | ~4 | Уточнение архитектурных связок |
| Шаг 2 (ФТ) | ~18 | Э1 (архитектурная путаница) + Э2 (иерархия) |
| Шаг 3 (ограничения) | ~8 | Э4 (ролевая модель) + перенос UI-ограничений |
| Финальное ревью | ~2 | Обнаружение Э5 (несоответствие Цели и ФТ) |

### 4.2 Характер правок БА

- **~40% правок** — исправление архитектурных ошибок (Э1)
- **~25% правок** — реструктурирование иерархии ФТ (Э2)
- **~20% правок** — стилистика (Э3: замена канцелярита)
- **~10% правок** — ролевая модель (Э4)
- **~5% правок** — синхронизация Цели и ФТ (Э5)

### 4.3 Инсайт о «точке невозврата»

Если архитектурные ошибки (Э1) не исправить на Шаге 1 — они мультиплицируются
на Шаге 2. При наличии human-gate этот риск управляем. При автономном режиме
(без human-gate) ошибки Э1 + Э2 создают экспоненциальный рост правок.

**Практическое следствие:** Stepwise-режим не просто «красивее» — он структурно
необходим для задач с многокомпонентной архитектурой.

## 5. Методологические инсайты (M1–M6)

### M1 — «Дерево решений» для ФТ (кандидат в стандарт)

**Формулировка:**
```
Функция (4.x)
  └─ Сценарий (4.x.1, 4.x.2, ...)
       └─ Исключения (4.x.1.1, 4.x.1.2, ...)
            └─ Если много условий → матрица приоритетов вместо углубления
```

**Обоснование:** Этот шаблон одновременно предотвращает Э2 (иерархию) и
позволяет корректно размещать сложные условия без нарушения структуры ТЗ.

**Статус:** Кандидат в стандарт `standards/fr-hierarchy-rules.md`.

### M2 — Стилистика ФТ по уровням (кандидат в стандарт)

**Формулировка:**

| Уровень | Шаблон | Пример |
| --- | --- | --- |
| 4.x | «Система должна [глагол] [объект] [при условии]» | «Система должна определять ящик-отправитель...» |
| 4.x.x | Строгий бизнес-формат | «При создании ответа система подставляет...» |
| 4.x.x.x | Краткий, без «при условии, что...» | «Если ящик неактивен — [действие]» |

**Обоснование:** Предотвращает Э3 (канцелярит) и обеспечивает единообразие
стилистики на всех уровнях иерархии.

### M3 — Системные vs пользовательские действия (правило «возможности»)

**Формулировка:**
- **Системные действия** (по триггеру/событию): «Система [глагол] [объект]» — без «возможности».
- **Пользовательские действия** (инициируемые вручную): «Система обеспечивает
  возможность [актор] [действие]».

**Обоснование:** Предотвращает Э4 и делает явным, кто является субъектом действия
в ФТ — система или человек. Это также помогает генерировать тест-кейсы:
«системные» ФТ тестируются через триггеры; «пользовательские» — через UI.

### M4 — Правило переноса UI-ограничений As-Is в Раздел 6

**Формулировка:**
- UI-ограничения As-Is (то, чего система «не делает» в текущей версии) → Раздел 6.
- Ролевая модель As-Is (если не меняется в рамках задачи) → Раздел 6.
- Раздел 4 содержит только **позитивные** формулировки («что система делает»).

**Обоснование:** Улучшает читаемость Раздела 4 и снижает когнитивную нагрузку
при ревью. Реализованный в BCREQ-1059 вариант уже лучше, чем в BCREQ-1025.

### M5 — Матрица приоритетов для сложных условий

**Формулировка:**
Если ФТ содержит более двух взаимоисключающих условий с разными исходами → 
формировать таблицу-матрицу приоритетов вместо нескольких вложенных под-ФТ.

**Обоснование:** Матрица одновременно:
- Предотвращает углубление иерархии (Э2)
- Является готовой инструкцией для QA (тест-кейс = строка в матрице)
- Предотвращает пропуск edge-case (матрица явно перечисляет все состояния)

### M6 — Синхронизация Цели и ФТ (правило финального ревью)

**Формулировка:**
После завершения Шага 2 (ФТ) — явная верификация: «Выполняют ли ФТ в точности то,
что обещает Цель в Разделе 2.2?»

**Граничные случаи:**
- Цель обещает то, что ФТ не реализуют → исправить Цель или добавить ФТ.
- ФТ реализуют через ненаблюдаемые настройки → Цель должна явно это отражать
  («реализуется через настройки КЦ», а не «оператор сможет выбрать ящик»).

**Обоснование:** Предотвращает Э5. Этот шаг наиболее важен при разрыве в
уровне абстракции между постановкой задачи и её технической реализацией.

## 6. Связь с онтологией (ADR #003–#010)

### ADR #003 — Онтология БА

**Подтверждает:** Трёхуровневую модель (Операция → Процесс → Артефакт) — в BCREQ-1059
каждый промпт цепочки = отдельная операция над единым артефактом (ТЗ).

**Новый инсайт:** Артефакт (ТЗ) не завершён до момента синхронизации Цели и ФТ (M6).
Онтология должна включать явный переход «ТЗ в работе» → «ТЗ верифицировано» как
отдельное состояние.

### ADR #004 — Таксономия операций

**Подтверждает:** Использованные операции: `glossary-context-understanding`,
`fr-documentation`, `constraints-documentation` корректно покрывают задачу.

**Новый инсайт:** Нужна новая операция `fr-structuring` (структурирование ФТ как
дерева решений + формирование матрицы приоритетов). Без неё `fr-documentation`
перегружен двумя разными задачами — написанием содержания и его структурированием.

### ADR #005 — Продуктовая принадлежность

**Подтверждает:** Критическую важность архитектурных компонентов (ЛК ВАТС ↔ КЦ ↔ Редактор)
как основы для корректной генерации ФТ.

**Новый инсайт:** Промпты с `scope: mango-only` должны по умолчанию запрашивать
«архитектурную карту» компонентов и их зон ответственности на Шаге 0. Это —
специфика MANGO OFFICE, а не общее правило.

### ADR #006 — Работа с базой знаний (БЗ)

**Подтверждает:** Механизм «выжимки из БЗ → генерация ФТ» работает.

**Новый инсайт:** Выжимка должна явно включать **архитектурные связки**
(«в ЛК ВАТС делается X; в КЦ доступно Y; в Редакторе видно Z»), а не только
фактические данные. Текущий формат выжимки не структурирован по компонентам.

### ADR #007 — Нейминг

**Статус:** Все промпты соответствуют стандарту нейминга. Изменений не требует.

### ADR #008 — Отраслевые стандарты

**Статус:** ODA-Check корректен. Маппинг: email-routing → CEM → Omnichannel.

## 7. Выводы

### 7.1 Системные наблюдения

1. **Архитектурная путаница (Э1) — устойчивый системный паттерн** (3 прогона подряд).
   Требует изменения промпта, а не «воспитания» пользователя.

2. **Иерархия ФТ (Э2) и канцелярит (Э3) — повторяющиеся паттерны**, ранее
   зафиксированные в BCREQ-1025. Подтверждают необходимость RFC-1059-P2 и P3.

3. **Паттерн Э5 (ложные обещания Цели) — новый** для этой экосистемы. Возникает
   на стыке уровней абстракции (Цель vs ФТ) и требует явного шага верификации (M6).

| --- | --- | --- | --- |
| RFC-1059-P1 | Э1 (архитектура) | 3 прогона | 🔴 Критический |

### 7.3 Рекомендации

- **Немедленно (до следующего прогона):** RFC-1059-P1 — архитектурные связки в
  Шаге 0 промпта `glossary-context-understanding-stepwise`.
- **В следующей итерации промптов:** RFC-1059-P2 (дерево решений для ФТ) и P3
  (стилистика по уровням).
- **Как кандидат в стандарт:** M1–M3 — задокументировать в `standards/`.
