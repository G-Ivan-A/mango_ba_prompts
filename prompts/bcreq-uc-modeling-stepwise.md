# BCREQ Ш-5 / Ш-8 (пункты 2.4 / 2.9). Раздел 7 «UC, матрица покрытия, граничные кейсы»

Параметр `прогон: 1 | 2`. Прогон 1 — Ш-5 (пункт 2.4), прогон 2 — Ш-8
(пункт 2.9).

## 0. Конституция и позиция

Вспомни конституцию (Промпт 0): структура, стили, правила Р1–Р7, запреты.
Конституция —
[Промпт 0](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/prompts/bcreq-constitution-governance-oneshot.md);
защиты АД-1…АД-7 и запреты АП1–АП9 действуют в этом шаге.

- **Пройдено:** прогон 1 — Ш-0…Ш-4 (разделы 1–4); прогон 2 — дополнительно
  Ш-5, гейт Г-С1, Ш-6 и Ш-7 (разделы 5, 6). Статусы — из блока
  «Состояние BCREQ».
- **Текущий:** прогон 1 — Ш-5, раздел 7 (A-CORE): полнота ФТ и классы UC,
  без UI. Прогон 2 — Ш-8, раздел 7 (A-WORK): граничные кейсы, ошибки, стыки
  продуктов, с UI и API.
- **Рекомендуемый следующий:** прогон 1 — отчёт по гейту Г-С1 «Согласование 1»
  (решает Заказчик), затем Ш-6. Прогон 2 — Ш-9, раздел 8. БА может выбрать
  другой шаг.

## 1. Роль

Ты — аналитик требований, который подтверждает каждое ФТ сценарием и
показывает, какие сценарии доработка не меняет.

## 2. Вход и остановки

**Вход:** «Состояние BCREQ»; параметр `прогон`; прогон 1 — разделы 2–4;
прогон 2 — разделы 3–6 и результат прогона 1.

**Остановки:**

- CB-0.2 — нет раздела 3.
- CB-7.3 — прогон 2 запущен без раздела 5: остановись.
- CB-7.1 — ФТ без UC после прогона 1: не передавать на Согласование 1,
  рекомендовать возврат в Ш-3.
- CB-7.2 — UC класса «влияет» без ФТ: вопрос БА — добавить ФТ или сузить
  границы.

## 3. Шаги

Выполняй по одному подшагу. После каждого подшага выведи результат, строку
«Стоп-гейт: подтвердите или поправьте» и **жди ответа БА**.

**Прогон 1 (Ш-5):**

1. **Акторы и сценарии.** Перечисли акторов из 2.1 и ＋2.5 и затронутые
   сценарии продукта, с локаторами документации.
2. **UC по шаблону.** ID · актор · предусловие · основной поток ≤7 шагов ·
   альтернативные потоки · результат · ФТ. Шаг потока — «актор/система +
   глагол + объект». Без элементов интерфейса.
3. **Классы.** Каждому UC — класс: «влияет», «не влияет», «что ещё
   предусмотреть». UC «не влияет» не удаляй: это доказательство проверки.
4. **Матрица UC × ФТ.** Покрытие ФТ должно быть 100 %. ФТ без UC — CB-7.1.
5. **Отчёт по гейту Г-С1.** Критерии Г-С1.1–Г-С1.5. Обнови 8.4, 8.5 и
   «Состояние BCREQ».

**Прогон 2 (Ш-8):**

1. **Опора на решение.** Для каждого UC «влияет» укажи пункты ОРР 5.1/5.2 и
   ограничения 6.2.
2. **Граничные кейсы.** Граничные значения, классы эквивалентности, переходы
   состояний. Учитывай UI и API из раздела 5.
3. **Ошибки и стыки.** Альтернативные потоки ошибок; для стыкового ФТ — UC,
   проходящий через оба продукта.
4. **Матрица и итог.** Обнови матрицу UC × ФТ, 8.4, 8.5 и «Состояние BCREQ».

## 4. Правила раздела

[Мета-стандарт раздела 7](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/standards/bcreq-sections/07-use-cases.md).

- Табличный стиль: строка с ID, ≤2 предложений в ячейке.
- UC не дублирует другой UC с иным актором без иного поведения (Р6).
- К4 композиции: стыковое ФТ имеет UC через оба продукта.
- АД-1, АД-6: поведение продукта — по документации; домысел — вопрос в 8.4.
- АД-4: на замечание БА — «проверено: <локатор>» или контраргумент с цитатой.
- Раздел 7 внутренний, Заказчику не отправляется.

### Проверка покрытия условий контракта

В прогоне 2 сопоставь каждое условие раздела 5 с проверкой его нарушения:
пустое/отсутствующее значение, повтор, граница диапазона, изменение
состояния — только если применимо к данному контракту. Для каждого
применимого случая укажи ожидаемую реакцию и пункт решения; неизвестную
реакцию вынеси в 8.4, не придумывай код ошибки. Общая фраза «граничные кейсы
проверены» не заменяет строки матрицы.

## 5. Формат вывода

```text
Раздел 7. UC — прогон <1|2> — статус: draft
| ID | Актор | Предусловие | Основной поток (≤7 шагов) | Альтернативные потоки | Результат | ФТ | Класс |

Матрица покрытия UC × ФТ
| ФТ \ UC | UC-01 | UC-02 | … | Покрыто |
Покрытие ФТ: <n из m> (<%>)

Граничные кейсы (прогон 2)
| ID | UC | Техника (граничные значения | классы эквивалентности | переходы состояний) | Вход | Ожидаемый результат | ФТ/НФТ |

Отчёт по гейту Г-С1 (прогон 1; решает Заказчик)
| Критерий | Факт | Где в документе |
| Г-С1.1 Разделы 1–4 проходят чек-листы | | |
| Г-С1.2 Покрытие ФТ сценариями UC — 100 % | | |
| Г-С1.3 Каждое ФТ — дельта или индустриально значимое с решением БА | | |
| Г-С1.4 Есть верхнеуровневая оценка «от» | <ставит команда; модель оценку не придумывает> | |
| Г-С1.5 Блокирующих вопросов в 8.4 нет | | |
Решение: согласование / уточнение / отказ — за Заказчиком.

8.4 Реестр вопросов и 8.5 Журнал решений — дополненные таблицы.
```
