# `scripts/kb/` — конвейер извлечения БЗ (issues #111, #117)

Скрипты превращают исходный документ (PDF) в структурированную, machine-readable
базу знаний под `kb/processed/<doc>/`: разделы-чанки + индекс + метаданные. Это
**git-нативный, детерминированный** конвейер (без GPU, без обращений в сеть),
который воспроизводимо гоняется и локально, и в GitHub Actions.

> Полное обоснование выбора инструментов, оценку качества и сравнение с
> ML-альтернативами (marker / nougat / MinerU) см. в
> [`docs/kb-experiment-report.md`](../../docs/kb-experiment-report.md).
> Архитектура каталогов БЗ и инструкция по пополнению —
> [`kb/sources/README.md`](../../kb/sources/README.md). Примеры обращения
> промптов — [`kb/USAGE.md`](../../kb/USAGE.md).

## Файлы

| Скрипт | Назначение |
| --- | --- |
| [`extract.py`](extract.py) | Главный конвейер: PDF → `sections/*.md` + `index.md` + `meta.json` (+ `images/`). |
| [`tokens.py`](tokens.py) | Подсчёт токенов (tiktoken `cl100k_base`, иначе эвристика). Числа в отчёте/`meta.json` — реальные. |
| [`make_sample_pdf.py`](make_sample_pdf.py) | Генератор синтетической фикстуры КЦ (реальный PDF из issue не загрузился). |
| [`requirements.txt`](requirements.txt) | Зависимости (только для извлечения/генерации; валидатору не нужны). |

## Быстрый старт

```bash
python3 -m pip install -r scripts/kb/requirements.txt

# 1) (опционально) собрать тестовую фикстуру, если нет реального PDF
python3 scripts/kb/make_sample_pdf.py

# 2) извлечь PDF в структуру БЗ
python3 scripts/kb/extract.py \
    kb/sources/contact-center-manual-sample/CC_manual_sample.fixture.pdf \
    --out kb/processed/contact-center-manual-sample \
    --doc-code CC --doc-title "Контакт-центр MANGO OFFICE" --doc-version 1.26.23-sample

# 3) проверить результат (только stdlib, как в CI)
make kb-validate
```

Через Makefile то же самое: `make kb-sample`, `make kb-extract`, `make kb-validate`.
Для split-руководства КЦ из issue #119: `make kb-mango`. Для split-руководства
ЛК из issue #117: `make kb-lk`.

## `extract.py` — что делает (ФТ-1/ФТ-2/ФТ-3)

1. **Текст со структурой.** `pdfplumber` даёт строки с координатами и кеглем.
   Если у PDF есть встроенное оглавление/bookmarks, границы чанков берутся из него
   (это защищает от ложных разделов из жирных нумерованных списков). Outline
   понимает как `N` / `N.M`, так и верхнеуровневые заголовки вида `Раздел N. ...`.
   Если outline отсутствует, включается прежняя эвристика: заголовок = строка с
   кеглем больше основного текста ИЛИ короткая жирная строка с нумерацией
   `N` / `N.M` / `N.M.K`; уровень — из глубины нумерации.
2. **Деление на разделы скриптом, без LLM (ФТ-3).** Каждый outline-раздел или
   эвристически найденный верхнеуровневый раздел → отдельный файл-чанк
   `sections/NN-slug.md`. LLM нужен только для документов БЕЗ структуры заголовков
   и без пригодного outline — гибрид описан в отчёте.
3. **Таблицы → Markdown.** `page.find_tables()`; текст внутри таблицы исключается
   из потока строк, чтобы не дублироваться.
4. **Изображения.** Позиция — из `pdfplumber` (та же система координат, что текст),
   байты — из `PyMuPDF`. Файлы кладутся в `images/`, ссылка вставляется на своём
   месте в разделе. Без `PyMuPDF` остаётся HTML-комментарий-плейсхолдер.
5. **Индекс `index.md`.** Карта разделов (раздел → файл → страницы → токены →
   «когда обращаться»). Это замена retrieval-шага до RAG (ADR-007, правило R2).
6. **Трассировка.** Каждый раздел получает `pdf_section`, `pdf_heading`,
   глобальные страницы, `source_refs` с точным PDF-файлом, номером части и
   локальными страницами. В Markdown-разделе есть строка `Трассировка` для
   ручной проверки.
7. **Multi-part PDF.** Несколько PDF-частей передаются одним запуском в порядке
   документа. Скрипт ведёт сквозную пагинацию и присоединяет продолжение текста в
   начале новой части к предыдущему разделу, а не создаёт ложную титульную часть.
8. **`meta.json`.** Инструмент и версия, `sha256` источников, число частей/
   страниц/разделов/таблиц/изображений, токены по разделам и итог, метод
   подсчёта токенов.

### Параметры

```
extract.py <source.pdf> [<source-part-2.pdf> ...] --out <dir>
    [--doc-code CC] [--doc-title "…"] [--doc-version 1.26.23] [--note "…"]
```

Для Makefile multi-part запуск передаётся через `SRCS`:

```bash
make kb-extract \
    SRCS="kb/sources/<slug>/part-1.pdf kb/sources/<slug>/part-2.pdf" \
    OUT=kb/processed/<slug> CODE=LK TITLE="..." VERSION=1.21
```

`--out` каждый раз **полностью пересоздаётся** (старые `sections/*` и `images/*`
удаляются) — вывод детерминирован при том же входе.

## Детерминированность

`pdfplumber` + `tiktoken` + фиксированный порядок обхода и сортировка ключей в
`meta.json` дают **байт-в-байт одинаковый** результат на одном входе. Поэтому
извлечённую БЗ можно держать в git и ревьюить как обычный diff. Поле
`token_method` в `meta.json` всегда честно фиксирует, как считались токены
(`tiktoken:cl100k_base` или `heuristic:chars/3.3`).
