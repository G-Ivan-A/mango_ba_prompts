# Процесс отладки промптов (Draft)

> **Статус: Draft.** Документ закрывает процессный зазор, выявленный в
> [`governance/audit-contracts-2026-06-17.md`](audit-contracts-2026-06-17.md):
> контракты описывают **создание** промптов и границу «требует human review», но
> не описывают, **как отлаживать и изменять** уже существующие. Сам документ —
> предложение; он валидируется на 2–3 ближайших отладках и правится по факту, а
> не подгоняет практику под форму.

## Зачем

Чтобы наблюдение из реального прогона БА превращалось в правку промпта
**предсказуемо и с согласия пользователя**, а не напрямую. Контракт порядка:

> **эксперимент → RFC → согласование с пользователем → изменение**

Прямое изменение промпта в обход этого порядка — нарушение контракта отладки
(прецедент — попытка поднять 6 промптов `0.1 → 0.2` в PR #102 без RFC).

Ключевой принцип: **диагноз ≠ право на правку**. Зафиксированный эксперимент даёт
*основание предложить* правку (RFC), но не *право внести* её. Право на изменение
даёт только согласование с пользователем.

## Обзор потока

```
[1] Сбор обратной связи        → накапливаем сигналы о недотягах промптов
        │
        ▼
[2] RFC-реестр (живой документ) → сигнал оформляется в RFC: proposed → in-review
        │                                                    → accepted/rejected
        ▼                                                    → implemented
[3] Пользователь инициирует     → выбирает RFC, решает что и когда менять
        │
        ▼
[4] Изменение промпта           → только после согласования; bump версии + CHANGELOG
```

## Часть 1. Сбор обратной связи

Сигналы о том, что промпт «недотягивает», собираются из трёх источников и не
требуют немедленной правки — они лишь накапливают доказательную базу.

| Источник | Что это | Как попадает |
| --- | --- | --- |
| `runs/YYYY/RUN-XXXX/outputs/*.md` | Зафиксированные прогоны по [стандарту фиксации](../standards/experiment-log-standard.md) (Уровень 1): метрики, цитаты, секция «Предложения по промптам» | Создаётся БА при прогоне; секция «Предложения» = вход для RFC |
| `governance/prompt-feedback.json` | Статический срез обратной связи (поле `prompt` = id промпта) | Заполняется вручную или скриптом по issues с лейблом `prompt:feedback` |
| Issues с лейблом `prompt:feedback` | Точечные жалобы/наблюдения по конкретному промпту | Заводятся БА/контрибьютором; агрегируются в JSON и в дашборд «Проверки» |

**Правило сбора.** Сигнал фиксируется *как наблюдение с цитатой* (что именно
недотянуло, в каком прогоне). Без цитаты/прогона сигнал не является основанием
для RFC — тот же принцип доказуемости, что в стандарте фиксации.

## Часть 2. RFC-реестр как живой документ

RFC (Request for Comments) — предложение изменить промпт. Все RFC живут в одном
реестре [`governance/rfc-register.md`](rfc-register.md) и проходят статусы:

```
proposed → in-review → accepted  → implemented
                     ↘ rejected
```

| Статус | Значение | Кто переводит |
| --- | --- | --- |
| `proposed` | RFC оформлен из сигналов (часть 1), ждёт рассмотрения | Автор RFC (БА/агент) |
| `in-review` | Пользователь/ревьюер рассматривает | Пользователь |
| `accepted` | Принят к реализации | **Только пользователь** |
| `rejected` | Отклонён (с причиной) | **Только пользователь** |
| `implemented` | Правка внесена в промпт (часть 4), связана с PR | Исполнитель после merge |

**Минимальная запись RFC** (строка реестра): `ID`, `промпт(ы)`, `суть`,
`источник-сигнал` (ссылка на эксперимент/issue), `статус`, `тип версии`
(Minor/Major/Breaking), `ссылка на PR реализации`.

RFC-реестр — **living doc**: статусы обновляются по мере движения, история не
переписывается (rejected остаётся в реестре с причиной).

## Часть 3. Пользователь инициирует отладку

Отладку промпта инициирует **пользователь**, не агент и не эксперимент.

1. Пользователь смотрит RFC-реестр и сигналы (часть 1).
2. **Выбирает**, какой RFC брать в работу, **что** и **когда** менять.
3. Переводит RFC `proposed → in-review`, рассматривает, и **только он** ставит
   `accepted`/`rejected`.
4. Согласование может быть в комментарии к PR/issue или через перевод RFC в
   `accepted` — в любом случае это явное действие пользователя.

Агент/исполнитель **не переводит RFC в `accepted` сам** и не вносит правку «по
факту убедительного эксперимента». Молчание ≠ согласие на правку промпта (в
отличие от приёмки PR, где молчание+merge = согласие на уже сделанное).

## Часть 4. Изменение промпта — только после согласования

Правка вносится **после** `accepted` (часть 3) и связывается со своим RFC.

**Классификация версии** (от типа правки):

| Тип | Что меняется | Bump версии (draft) |
| --- | --- | --- |
| **Minor** | Уточнение формулировки, пример, читаемость; поведение в целом то же | `0.1 → 0.2` (patch/minor в пределах draft) |
| **Major** | Меняется логика/структура промпта, новые шаги | `0.x → 0.(x+1)` со заметкой в RFC; для canonical — `+1.0` |
| **Breaking** | Меняется контракт ввода/вывода или id; ломает совместимость с прежними прогонами | требует отдельного RFC-обсуждения и пометки `breaking` |

**Связка артефактов при реализации** (обязательна):

```
RFC (accepted) → правка prompts/<файл>.md (frontmatter version + updated)
              → prompts/README.md (колонка «Версия»)
              → CHANGELOG.md (## Unreleased, ссылка на RFC и issue)
              → site/data/*.json (регенерация: node scripts/generate-pages-data.mjs)
              → RFC статус → implemented (ссылка на PR)
```

Правка идёт **малым reviewable PR** (правило 6 `AI_GOVERNANCE.md`), отдельным от
исследования/RFC. Это держит «предложение» и «применение» в разных PR — как и
требует контракт отладки.
