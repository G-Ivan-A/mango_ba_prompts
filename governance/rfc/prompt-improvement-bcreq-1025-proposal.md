# RFC: Улучшение промптов на основе эксперимента BCREQ-1025

## Статус: proposed

> **КРИТИЧНО:** Этот RFC — **предложение**, не изменение. Промпты **не тронуты**.
> Изменения вносятся только после явного решения пользователя (принцип
> [rfc-process.md](../rfc-process.md): молчание = согласие только с текущим
> состоянием, не с повышением статуса).

## Контекст

В ходе эксперимента BCREQ-1025 (маршрутизация email-ответов в КЦ по Точке входа)
на задаче с трёхкомпонентной архитектурой (ЛК ВАТС ↔ КЦ ↔ Редактор) выявлено
**5 паттернов ошибок LLM**, потребовавших ~30 итераций корректировок БА. Часть
паттернов совпадает с ранее выявленными в эксперименте 1027 (и уже есть RFC-1027-P2),
часть — новые для данной экосистемы промптов.

В ходе эксперимента BCREQ-1025 выявлены следующие паттерны ошибок:

| ID | Паттерн | Класс | Промпт |
| --- | --- | --- | --- |
| Б1 | Путаница настроек ЛК ВАТС vs. КЦ (повторяющееся «забывание») | Контекстный | `fr-documentation-stepwise` |

## Предлагаемые изменения

### RFC-1025-P1: Явная фиксация архитектурных связок в промпте glossary

**Промпт:** `prompts/glossary-context-understanding-stepwise.md`

**Что изменить:**
Добавить в Шаг 0 (Сбор контекста и As-Is) явный запрос архитектурных компонентов:

```
ШАГ 0. Сбор контекста и As-Is (Подготовительный)
Запроси у пользователя:
1. Базовые термины и определения (если есть).
2. Источники информации о текущем состоянии (As-Is): описание, PDF, ссылки.
3. Перечень продуктовых компонентов/систем, затронутых задачей (например: ЛК,
   КЦ, Редактор, CRM и др.) и их роль в сценарии. Если задача затрагивает
   несколько компонентов — явно зафиксируй границы каждого и их взаимосвязи.
   Это предотвратит смешение функций разных компонентов при генерации ФТ.
```

**Обоснование:**
Паттерн Б5 из BCREQ-1025 — LLM генерировал ФТ для КЦ без учёта того, что
настройки почтовых ящиков находятся в ЛК ВАТС. Промпт не запрашивает
архитектурный контекст явно. Добавление пункта 3 в Шаг 0 создаёт «якорь»
для последующих промптов цепочки.

**Риски:**
- Шаг 0 становится длиннее → возможное увеличение времени подготовительной фазы.
- При задачах в рамках одного компонента пункт 3 избыточен (пользователь должен
  указать «один компонент, связи нет»).
- Не устраняет проблему «забывания» контекста в длинных сессиях (паттерн Б1)
  полностью — только при старте.

**Тип изменения:** Minor (добавление запроса, не изменение структуры шагов)

### RFC-1025-P2: Явная фиксация ролей и архитектурных границ в промпте FR (Шаг 1)

**Промпт:** `prompts/fr-documentation-stepwise.md`

**Что изменить:**
Дополнить Шаг 1 (Синхронизация контекста) явным требованием извлечь и зафиксировать:
(а) матрицу ролей из контекста; (б) архитектурные компоненты и их границы.

```
ШАГ 1. Синхронизация контекста и памяти диалога
Проанализируй историю текущего диалога.
- Если в ней уже есть согласованные Разделы 1, 2, User Story (US) или Use Case
  (UC), извлеки их.
- Если диалог новый или контекста нет — запроси у пользователя ввод данных.
Сформируй и выведи КРАТКУЮ СУММАРИЗАЦИЮ извлечённого контекста, включая
ОБЯЗАТЕЛЬНО:
  - Глоссарий, Проблема, Цель, Задачи, ключевые сценарии из US/UC;
  - Матрица ролей: [Роль] → [Что может делать в данной задаче];
  - Архитектурные компоненты: [Компонент] → [Что настраивается / где живёт].
Эта суммаризация является «якорём» для всей сессии генерации ФТ. При
возникновении противоречий обращайся к ней, а не к свободной памяти диалога.
```

**Обоснование:**
Паттерны Б1 и Б4 — LLM «забывал» разграничение ЛК ВАТС / КЦ и смешивал роли
при переходе к новым ФТ. «Якорная суммаризация» с явной матрицей ролей и
компонентов служит постоянной точкой референса в сессии.

**Риски:**
- Суммаризация становится длиннее → больший «токенный» контекст для шагов 2–4.
- Если пользователь не предоставил данные о ролях, LLM может генерировать их
  из эвристик (риск галлюцинаций) — нужен явный запрос при отсутствии данных.

**Тип изменения:** Minor (расширение суммаризации, добавление явных секций)

### RFC-1025-P3: Пример-эталон стиля для уровня 4.x.1 (усиление RFC-1027-P2)

**Промпт:** `prompts/fr-documentation-stepwise.md`

**Что изменить:**
В Правиле 1 (Иерархия ФТ) добавить конкретный пример-эталон для уровня `4.x.1`
(уровень детализации), явно показывающий разницу между канцеляритом и
читаемым стилем:

```
Правило 1. Иерархия ФТ:
- Уровень 4.x (Родительский): Строгий классический формат «Система должна [глагол]
  [объект] [при условии]».
- Уровень 4.x.1 (Детализация): Описание сценария, бизнес-правила или логического
  уточнения. Деловой стиль, без жёсткого шаблона. ЭТАЛОН СТИЛЯ:
  ✅ ПРАВИЛЬНО: «Оператору доступна возможность выбора источника ответа.»
  ✅ ПРАВИЛЬНО: «Система применяет маршрут, соответствующий Точке входа письма.»
  ❌ НЕПРАВИЛЬНО: «Инициация действия осуществляется Сотрудником посредством
  выбора специального элемента управления…»
- Уровень 4.x.1.1 (Атомарный): Конкретные значения, параметры, состояния, триггеры.
```

**Обоснование:**
Паттерн Б3 воспроизвёл Г2 из эксперимента 1027 — тот же промпт, та же ошибка.
RFC-1027-P2 предлагает правку, но без конкретного примера абстрактное правило
«деловой стиль» не предотвращает возврат к канцеляриту. Пример-эталон даёт LLM
однозначный образец без интерпретации.

**Риски:**
- Примеры устаревают при смене предметной области → привязка примера к домену КЦ
  может вводить в заблуждение для других доменов.
- Риск «копирования» эталона вместо понимания принципа (зависит от модели).

**Тип изменения:** Minor (добавление эталонных примеров в правило)

**Связь с RFC-1027-P2:** Является **уточнением и усилением** RFC-1027-P2.
При реализации рекомендуется выполнять оба RFC совместно.

### RFC-1025-P4: Явный запрет на 4-й уровень иерархии и правило раскладки условий

**Промпт:** `prompts/fr-documentation-stepwise.md`

**Что изменить:**
Добавить в Правило 1 (Иерархия ФТ) явный запрет на 4-й уровень и правило
декомпозиции многоусловных требований:

```
Правило 1. Иерархия ФТ:
[существующие уровни 4.x / 4.x.1 / 4.x.1.1]
ЖЁСТКОЕ ОГРАНИЧЕНИЕ: Иерархия НЕ должна превышать трёх уровней (4.x / 4.x.1
/ 4.x.1.1). Уровень 4.x.y.z (4 уровня) — ЗАПРЕЩЁН.
Если правило содержит несколько условий (A ∧ B → результат):
  - Для 2–3 условий: каждое условие → отдельный пункт 4.x.1.1.
  - Для 4+ условий: декомпозировать на 2 родительских 4.x с собственными 4.x.1.
```

**Обоснование:**
Паттерн Б2 — при сложных правилах маршрутизации (тип письма → ящик → маршрут →
приоритет) LLM добавлял 4-й уровень. Промпт задаёт 3 уровня, но не содержит
явного запрета. Правило раскладки условий даёт алгоритм вместо запрета без
инструкции.

**Риски:**
- Принудительная декомпозиция при 4+ условиях может создать «плоские» ФТ без
  логической группировки.
- Правило «для 2–3 условий» может быть интерпретировано буквально при более
  сложных сценариях.

**Тип изменения:** Minor (добавление явного ограничителя и алгоритма раскладки)

### RFC-1025-P5: Явный запрос архитектурных связок на Шаге 1 промпта constraints

**Промпт:** `prompts/constraints-documentation-stepwise.md`

**Что изменить:**
Добавить в Шаг 1 (Инициализация и анализ контекста) явный запрос и фиксацию
архитектурных связок при анализе «триггеров ограничений»:

```
ШАГ 1. Инициализация и анализ контекста
Запроси (или возьми из чата): Раздел 4 (ФТ), User Story / Use Case, или сырое
описание задачи.
Проанализируй текст на наличие «триггеров ограничений»: внешние системы (CRM, FTP),
работа с историческими данными, UI-ограничения, API-эндпоинты, устаревший
функционал.
ДОПОЛНИТЕЛЬНО: Если задача затрагивает несколько продуктов/компонентов (например,
ЛК + КЦ + Редактор), явно зафиксируй:
  - Какой компонент является «владельцем» каждого ФТ?
  - Где проходит граница ответственности между компонентами?
  Это обязательно нужно отразить в ограничениях раздела 6.
Сделай краткую суммаризацию выявленных областей.
```

**Обоснование:**
Паттерн Б5 — Шаг 1 промпта constraints не запрашивает явно архитектурные границы
между компонентами, хотя именно раздел 6 является правильным местом для их
фиксации. Без этого запроса ограничения формулируются без учёта межкомпонентных
зависимостей.

**Риски:**
- Шаг 1 удлиняется → незначительное увеличение времени фазы инициализации.
- При однокомпонентных задачах раздел становится избыточным (пользователь должен
  явно сказать «один компонент»).

**Тип изменения:** Minor (добавление секции в существующий Шаг 1)

## Альтернативы

### А1 — «Промпт-связка» для передачи контекста между сессиями

Вместо усиления каждого промпта по отдельности — создать новый артефакт
«context-handover template»: формальный шаблон для явной передачи контекста
от одного промпта к следующему.

**Плюсы:** Решает корневую проблему «забывания» архитектурных связок между
сессиями; промпты остаются минимальными.
**Минусы:** Новый артефакт требует отдельного RFC и усложняет рабочий процесс БА.
**Оценка:** Целесообразно рассмотреть после реализации P1–P5 как следующий шаг.

### А2 — Один «мастер-промпт» вместо цепочки трёх

Объединить все три промпта в один с переключением режимов.

**Плюсы:** Нет проблемы передачи контекста.
**Минусы:** Нарушает принцип атомарности промптов (ADR-001); ухудшает
переиспользование; промпт превращается в инструкцию на >5000 слов.
**Оценка:** Не рекомендуется — противоречит архитектурным решениям репозитория.
