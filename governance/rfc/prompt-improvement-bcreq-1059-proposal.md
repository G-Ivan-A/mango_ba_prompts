# RFC: Улучшение промптов на основе боевого эксперимента BCREQ-1059

## Статус: proposed

> **КРИТИЧНО:** Этот RFC — **предложение**, не изменение. Промпты **не тронуты**.
> Изменения вносятся только после явного решения пользователя (принцип
> [rfc-process.md](../rfc-process.md): молчание = согласие только с текущим
> состоянием, не с повышением статуса).

## Контекст

В ходе боевого эксперимента BCREQ-1059 (маршрутизация email-ответов по Точке входа
в КЦ MANGO OFFICE) выявлено **5 паттернов ошибок LLM** (Э1–Э5), потребовавших
~30 итераций согласования и ~12 ручных правок БА.

Особая значимость этого эксперимента: паттерны Э1, Э2 и Э3 полностью воспроизводят
аналогичные паттерны из BCREQ-1025 (Б5, Б2, Б3). Это **третий или второй прогон**,
подтверждающий системность этих паттернов. Паттерны Э4 и Э5 требуют отдельного
рассмотрения.

## Предлагаемые изменения

### RFC-1059-P1: Явный запрос архитектурной карты компонентов на Шаге 0

**Промпт:** `prompts/glossary-context-understanding-stepwise.md`

**Связь с предыдущим RFC:** Усиление RFC-1025-P1. Отличие: RFC-1025-P1 предлагал
запрашивать «перечень компонентов». RFC-1059-P1 дополняет это требованием явной
«карты зон ответственности» для каждого компонента.

**Что изменить:**
Добавить в Шаг 0 раздел «Архитектурная карта компонентов»:

```
ШАГ 0. Сбор контекста и As-Is
...
3. ОБЯЗАТЕЛЬНО для задач, затрагивающих несколько продуктовых компонентов:
   Запроси или уточни архитектурную карту:
   - Какие компоненты/системы/интерфейсы затронуты задачей?
   - Для каждого компонента: кто его пользователь? Какие действия он выполняет?
     Что НЕЛЬЗЯ сделать в этом компоненте (ограничения As-Is)?
   - Как компоненты взаимодействуют в сценарии задачи?
   Зафиксируй эту карту до начала генерации терминов.
```

**Ожидаемый эффект:** Снижение итераций по Э1 с ~8 до ~2. Архитектурные ошибки
LLM будут отсечены на Шаге 0, а не обнаружены на Шаге 2.

**Приоритет:** 🔴 Критический (3 прогона подряд).

### RFC-1059-P2: Шаблон «дерева решений» для структурирования ФТ

**Промпт:** `prompts/fr-documentation-stepwise.md`

**Что изменить:**
Добавить в раздел «Правила структурирования ФТ» явный шаблон декомпозиции:

```
ПРАВИЛО СТРУКТУРИРОВАНИЯ ФТ:
Используй шаблон «дерево решений»:

  4.x. [Функция] — что система делает
    4.x.1. [Сценарий 1] — при каких условиях
    4.x.2. [Сценарий 2] — при каких условиях
      4.x.2.1. [Исключение] — крайний случай

НЕ ДОПУСКАЕТСЯ:
- 4-й уровень нумерации (4.x.x.x)
- Смешение Функций, Сценариев, Настроек и Исключений на одном уровне
- Несколько взаимоисключающих условий как отдельные ФТ одного уровня

ВМЕСТО углубления иерархии — МАТРИЦА ПРИОРИТЕТОВ:
Если сценарий имеет N взаимоисключающих условий → свести в таблицу:
| Приоритет | Условие | Результат |
| --- | --- | --- |
| 1 | [условие] | [действие] |
| 2 | [условие] | [действие] |
```

**Ожидаемый эффект:** Снижение итераций по Э2 с ~5 до ~1. Устраняет необходимость
«перестройки иерархии» как отдельного цикла согласования.

**Приоритет:** 🟠 Высокий (2 прогона).

### RFC-1059-P3: Стилистические правила по уровням иерархии ФТ

**Промпт:** `prompts/fr-documentation-stepwise.md`

**Что изменить:**
Добавить таблицу стилистических правил рядом с правилами иерархии:

```
СТИЛИСТИКА ФТ ПО УРОВНЯМ:

4.x (Функция):
  Шаблон: «Система должна [глагол инфинитив] [объект] [условие через „на основе" / „при"]»
  ✅ «Система должна определять ящик-отправителя на основе Точки входа»
  ❌ «Осуществление определения отправителя на основании...»

4.x.x (Сценарий/подфункция):
  Шаблон: «[При условии] система [глагол] [объект]»
  ✅ «При создании ответа система подставляет адрес ящика из Точки входа»
  ❌ «Инициализировать значение атрибута "адрес-отправителя"...»

4.x.x.x (Исключение/уточнение):
  Шаблон: короткий, без «при условии, что» и канцелярских оборотов
  ✅ «Если ящик неактивен — использовать ящик по умолчанию»
  ❌ «В случае отсутствия возможности определения...»
```

**Ожидаемый эффект:** Снижение итераций по Э3 с ~3 до ~1. Устраняет необходимость
«деканцеляризации» как отдельного цикла согласования.

**Приоритет:** 🟠 Высокий (2 прогона).

### RFC-1059-P4: Правило «системные vs пользовательские действия» в ФТ

**Промпт:** `prompts/fr-documentation-stepwise.md`

**Что изменить:**
Добавить раздел «Правило субъекта ФТ»:

```
ПРАВИЛО СУБЪЕКТА В ФТ:

СИСТЕМНОЕ ДЕЙСТВИЕ (по триггеру/событию, без участия пользователя):
  Шаблон: «Система [глагол] [объект]» — без слова «возможность»
  ✅ «Система подставляет адрес ящика из Точки входа»
  ✅ «Система уведомляет оператора об использовании ящика по умолчанию»

ПОЛЬЗОВАТЕЛЬСКОЕ ДЕЙСТВИЕ (инициируемое пользователем, интерактивное):
  Шаблон: «Система обеспечивает возможность [актор в дат. падеже] [действие]»
  ✅ «Система обеспечивает возможность оператору видеть ящик-отправитель»
  ❌ «Система должна предоставить оператору выбор...» (если выбора нет)

ПРАВИЛО РОЛЕЙ: Перед началом генерации ФТ явно уточни ролевую модель:
  - Кто [Оператор / Администратор / Руководитель] и что им доступно As-Is?
  - Какие действия в задаче выполняет система автоматически (без участия людей)?
```

**Ожидаемый эффект:** Снижение итераций по Э4. Предотвращает приписывание
LLM административных действий операторским ролям.

**Примечание:** В BCREQ-1025 аналогичный паттерн (Б4) был исключён из RFC
по итогам ревью, т.к. ошибка была инициирована пользователем. В BCREQ-1059
ошибка была инициирована LLM, что подтверждает необходимость явного правила.

**Приоритет:** 🟡 Средний (1 прогон с атрибуцией на LLM).

### RFC-1059-P5: Правило переноса UI-ограничений As-Is в Раздел 6

**Промпты:**
- `prompts/fr-documentation-stepwise.md`
- `prompts/constraints-documentation-stepwise.md`

**Что изменить (в `fr-documentation-stepwise.md`):**
```
ПРАВИЛО UI-ОГРАНИЧЕНИЙ:
Если задача предполагает, что определённые действия недоступны пользователю
(As-Is UI-ограничения), НЕ включай их в Раздел 4 в виде:
  ❌ «[Действие] недоступно»
  ❌ «Выбор X не предусмотрен»

Вместо этого — зафикусируй их как PLACEHOLDER для Раздела 6:
  ✅ [Раздел 6: UI-ограничение — отсутствие ручного выбора X] 

Раздел 4 содержит ТОЛЬКО позитивные формулировки «что система делает».
```

**Что изменить (в `constraints-documentation-stepwise.md`):**
```
ШАГ 0. Источники ограничений
Дополнительно к ФТ и источникам БЗ — запроси у пользователя:
  - Какие действия НЕДОСТУПНЫ пользователю в текущей версии (As-Is)?
    (Отсутствующие UI-элементы, нет кнопок, readonly-поля, etc.)
  - Есть ли ограничения ролевой модели, которые НЕ меняются в рамках задачи?
Эти ограничения помещаются в 6.1 (Технические) или 6.2 (Ролевые).
```

**Ожидаемый эффект:** Раздел 4 становится чище и содержит только позитивные ФТ.
Раздел 6 становится единственным источником информации об ограничениях As-Is.

**Приоритет:** 🟡 Средний (новая практика, улучшает читаемость ТЗ).

### RFC-1059-P6: Шаг верификации синхронизации Цели и ФТ

**Промпт:** `prompts/fr-documentation-stepwise.md`

**Что изменить:**
Добавить в финальный шаг промпта явную инструкцию верификации:

```
ШАГ ФИНАЛЬНОЙ ВЕРИФИКАЦИИ (обязательный):
После завершения генерации Раздела 4 — выполни проверку:

1. Прочитай Цель из Раздела 2.2.
2. Перечисли ФТ из Раздела 4.
3. Ответь на вопросы:
   a) Каждое утверждение из Цели покрывается минимум одним ФТ?
   b) Цель не обещает действий, которых нет в ФТ?
   c) Если реализация идёт через настройки/конфигурацию — Цель это явно отражает?

Если ответ на любой вопрос «нет» → сообщи пользователю о несоответствии
и предложи варианты: (a) скорректировать Цель или (b) добавить ФТ.
```

**Ожидаемый эффект:** Паттерн Э5 обнаруживается **до** финального ревью, а не
после. Экономия ~2 итераций согласования при финальном ревью.

**Приоритет:** 🟡 Средний (новый паттерн, предотвращает потенциально серьёзные
несоответствия в переданных в разработку ТЗ).
