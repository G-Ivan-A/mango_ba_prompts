# Контрольная проверка «Запись разговоров»

[Решение владельца](https://github.com/G-Ivan-A/mango_ba_prompts/pull/475#issuecomment-6723485929):
модель сама находит evidence и снимает закрытый технический вопрос. Проверка
выполнена текущей моделью Codex с реальным `gh api`, без передачи готовой
цитаты пользователем. Это одна наблюдаемая проверка под-контракта нормализации
AIN-09, не изолированный запуск другой модели и не весь маршрут 01…24.
Ни один результат не принят за БА, раздел 2 и гейт 21 не формировались.

## Вход и наблюдение

Синтетический тезис: существующая запись разговора появляется в карточке
контакта amoCRM с задержкой, прослушивание учитывает права сотрудника.
Преждевременный вопрос TECH-1 к интеграциям: поддерживается ли эта возможность?
Клиентских данных нет. Полный текущий common и конкретное действие AIN-09
прочитаны перед фиксацией ответа; хеш полного промпта — в
[recording-observation.json](recording-observation.json).

Физический доступ этой сессии: GitHub CLI/API. Прочитаны README, MAP,
оглавление `integration-amocrm.toc.tsv` (поиск заголовка «Запись разговоров»),
затем весь `sections/60-zapis-razgovorov.md`, строки 1…34. Проверялись
буквальная запись и системный эквивалент: появление в карточке, задержка,
права/настройки и ограничения. Один небольшой раздел вместо клона всей БЗ.

Найден E-1: INTAMO, версия 25.08.2025, §10, страницы 112–113,
[закреплённый источник, L34](https://github.com/G-Ivan-A/mango-ba-ai-runtime/blob/68ad8fcffd47439fc3051852d9a2fbbe23815855/docs/kb/integration-amocrm/sections/60-zapis-razgovorov.md#L34).
Точная короткая цитата и SHA-256 прочитанного файла сохранены в JSON.
Это извлечённый текст runtime; первичный PDF заново не проверялся, OCR
иллюстрации не использовался как доказательство.

Вывод модели: указанный факт подтверждён для ВАТС + amoCRM, если услуга
записи включена и запись существует. В разделе есть проверка прав ВАТС и
ограничение коротких разговоров. TECH-1 снят с E-1; повторять технический
вопрос интеграциям/БА не требуется. Список вопросов Заказчику пуст именно для
этого узкого входа. Это не оценка любого реального клиентского ТЗ.

Остаток: API-привязка по ID, численное SLA и работа HDE/другой CRM данным
разделом не установлены. Аналогия не превращается в «Да» по этим требованиям.
Без инструмента либо при непокрывающем context — точный ACCESS_GAP, без
вердикта «Нет» и без технического вопроса БА. Эти отрицательные случаи в JSON
— примеры ожидаемого поведения, не дополнительные модельные запуски.

## Воспроизведение и пределы

```bash
python3 experiments/issue_474/retrieval_smoke.py --fetch
python3 scripts/validate_issue_474_execution.py
```

Первая команда реально перечитывает закреплённый источник через `gh api`,
проверяет весь SHA-256 и цитату, не генерирует ответ за модель. Без `--fetch`
работает офлайн-проверка целостности сохранённого наблюдения. CI проверяет
пакет офлайн; доступ к внешней частной БЗ для CI не требуется.

Новый regression требует полного общего алгоритма во всех 24 текстах и
совместимых входах. У прежнего `a55ab964` отсутствовал строгий маркер доступа
и полный алгоритм; эти проверки на его текстах падают. Остаются проверки
16 старых gate cases, отсутствия подписи модели, раздельного вызова 22,
потери версии, паузы и гипотезы. Статические проверки не подтверждают
следование произвольной LLM; наблюдаемый smoke даёт один положительный
пример. Массовые сравнения на двух моделях и тесты БА — последующий порядок
ADR-018, эффективность новых draft пока не измерена.
