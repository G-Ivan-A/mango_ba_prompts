# Инструкция по ведению бэклога

Правила для всех, кто меняет бэклог: Пользователь (владелец репозитория),
исполнитель PR, агент. Основа — инструкция бэклога Хаба
([`ops/backlog-instruction.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/32b5fa524e542af23c1a8e67c919bd66d5f4e399/ops/backlog-instruction.md)).
Ниже — она же, применённая к этому репозиторию, и все отличия от неё.

## Роли файлов

| Файл | Роль | Кто меняет |
| --- | --- | --- |
| [`BACKLOG.md`](BACKLOG.md) | Входной документ: порядок, решения владельца, спринты, статусы, открытые вопросы, долг, архив. | Исполнитель PR; решения — владелец. |
| [`backlog-ba-model.md`](backlog-ba-model.md) | Карточки трека Б (`BL-1xx`): процессы, промпты, уроки, golden set, этапы 1–5. | Исполнитель PR. |
| [`backlog-repository.md`](backlog-repository.md) | Карточки трека А (`BL-2xx`): документы и устройство репозитория. | Исполнитель PR. |
| `backlog-instruction.md` | Этот файл: правила ведения. | Только по решению владельца. |
| GitHub issue и PR | Обсуждение, ревью, доказательство выполнения. | Все. |
| `CHANGELOG.md` | Запись об изменении бэклога после слияния. | Исполнитель PR. |
| [`artifact-map.md`](artifact-map.md) | Навигация: все четыре файла бэклога зарегистрированы. | Исполнитель PR. |

Статус и порядок задачи живут только во входном документе. Карточка не
повторяет статус: так статус не расходится между файлами.

## Принципы

- **Одна задача — один проверяемый результат.** Задача заканчивается
  изменённым артефактом или одним проверяемым действием («Готово, когда.»).
- **Трассируемость.** У каждой карточки есть источники: ссылка, раздел,
  цитата до 100 символов. Задача без источника в бэклог не попадает.
- **Факты вместо догадок.** Нет источника для значения — ставится «—».
- **Порядок — по причинам, а не по приоритету.** Спринт собирает причинно
  связанную работу; порядок спринтов — в разделе 1 входного документа.
- **Anti-Inflation.** Новые файлы бэклога, статусы и поля появляются только
  по решению владельца. Четыре файла — предел.
- **Stop-factor.** Бэклог фиксирует *что* делать. Исполнение — отдельными
  PR после решений владельца, от которых задача зависит.
- **Качество важнее экономии токенов.** Текст бэклога короткий, но полный:
  карточка не опускает причину, источник или критерий готовности ради
  краткости (issue #418).

## Идентификаторы

| Код | Что это | Правило |
| --- | --- | --- |
| `BL-1xx` | Задача трека Б | Номер не переиспользуется. Десяток — спринт: 10x — Спринт 1, 11x — Спринт 3, 12x — Спринт 6, 13x — Спринт 7, 14x — Спринт 8. |
| `BL-2xx` | Задача трека А | 20x — Спринт 2, 21x — Спринт 4, 22x — Спринт 5. |
| `Р-NN` | Решение владельца | Каждое решение открывает хотя бы одну задачу; каждая ссылка на `Р` есть в реестре. |
| `КФ-NN` | Противоречие между документами | Снимается решением `Р` или задачей `BL`. |
| `S-NNN` | Технический долг | Нумерация раздела 6, не меняется. |
| `M-NNN` | Задача прежнего плана миграции | Только в архиве. |

Префикс `BL` выбран, чтобы не путать задачи с задачами Хаба `B-NNN`. Задача
Хаба в тексте называется «B-NNN Хаба».

## Формат спринта

Спринты — подразделы `### Спринт N: Название` раздела «4. Спринты» входного
документа. Каркас — как в Хабе:

```markdown
### Спринт N: <Название>

**Story.** Почему задачи связаны и какую боль закрывает спринт.

**Цель.** 1–2 предложения с измеримым результатом.

**Критерий закрытия.** Когда спринт считается выполненным.

| ID | Название | Приоритет | Зависимости | Статус | Issue | Источник | Краткое содержание | Режим запуска |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
```

Поля строки:

| Поле | Правило |
| --- | --- |
| ID | `BL-NNN`. |
| Название | Ссылка на карточку задачи. |
| Приоритет | `P0`…`P3` или «—». `P0` — блокирует ворота этапа; `P1` — нужно до ворот; `P2` — улучшает, не блокирует; `P3` — условная или отложенная. |
| Зависимости | `BL-NNN` и `S-NNN`, затем через «;» решения `Р-NN`. Задача стартует, когда зависимости `DONE` и решения приняты. |
| Статус | Из списка в разделе «Статусы». |
| Issue | Ссылка на issue или PR; иначе «— (planned)» или «— (deferred)». |
| Источник | Короткое указание на документ; полные источники с цитатами — в карточке. |
| Краткое содержание | 1–2 предложения: что делаем и зачем. Для `deferred (triggered)` — триггер. |
| Режим запуска | `Structured`, `Hybrid`, `Creative` или «—». |

## Формат карточки

```markdown
### BL-NNN. Название

**Почему.** Проблема, которую закрывает задача.

**Что меняется.** Однозначный список изменений.

**Источники.**
- [ссылка](путь#якорь),
  раздел «Название раздела»: “цитата до 100 символов”

**Зависит от.** BL-NNN, S-NNN или «—».

**Решение владельца.** Р-NN.

**Готово, когда.** Проверяемый критерий.
```

Правила источника:

- Одна строка — одна ссылка, один раздел «…», одна цитата “…” до 100
  символов.
- Цитата дословная. Для файлов репозитория проверка ищет её в разделе, на
  который ведёт якорь; без якоря — во всём файле.
- Внешние документы (Хаб, PR, issue) — по ссылке на закреплённый коммит или
  на issue, чтобы цитата не уехала.
- Пока PR #419 не слит, RFC стратегии цитируется по коммиту PR. После
  слияния (BL-201) ссылки переводятся на файл в `docs/rfc/`.

## Статусы

| Статус | Когда ставится |
| --- | --- |
| `TODO` | Задача в спринте, работа не начата. |
| `in-progress` | Есть исполнитель или открытый PR. |
| `review` | PR готов и ждёт ревью или слияния. |
| `DONE` | Результат слит или принят; есть ссылка на доказательство. |
| `ЧАСТИЧНО` | Часть результата принята, остаток описан в «Кратком содержании». |
| `CANCELLED` | Основание задачи отпало; нужно явное решение владельца и причина в «Кратком содержании». |
| `deferred (triggered)` | Задача ждёт названного события; триггер — в «Кратком содержании». |
| `deferred (regular)` | Регулярная задача по расписанию. |
| `deferred (icebox)` | Блок работ отложен до эмпирических данных; строка остаётся в бэклоге. |

Жизненный цикл: идея → строка в спринте (`TODO`) → `in-progress` → `review`
→ `DONE` → спринт архивируется.

## Решения владельца

1. Владелец отвечает одной строкой на решение в комментарии к PR бэклога
   (сейчас — PR #421): «Р-01 да», «Р-04 В», «Р-03 порог 0.95, N = 5».
   «Р-01…Р-12 да» принимает все рекомендации сразу.
2. Исполнитель меняет статус решения в реестре раздела 2 на «принято» и
   добавляет ссылку на комментарий.
3. Если владелец выбирает не рекомендацию, исполнитель правит карточки,
   которые открывает это решение, в том же PR.
4. Новое решение получает следующий номер `Р-NN`; номера не переиспользуются.

## Архивация

Как в Хабе: спринт удаляется из входного документа, когда все его задачи
`DONE` или `CANCELLED` и итог согласован в issue, PR или ADR. Карточки задач
удаляются вместе со спринтом. История остаётся в issue, PR, `CHANGELOG.md` и
в git.

Отдельный архивный файл не создаётся. Раздел «7. Архив» входного документа —
только указатель на прежние планы, чтобы ссылки на `M-NNN` оставались
понятны.

## Отличия от бэклога Хаба

| Хаб | Здесь | Почему |
| --- | --- | --- |
| Один файл `ops/backlog.md` | Входной документ и два файла карточек | Issue #418 разрешает два документа (репозиторий и модель БА) и требует у каждой задачи обоснование и источники с цитатой; в одной таблице это не помещается. |
| `## Спринт N:` | `### Спринт N:` внутри «## 4. Спринты» | Входной документ держит ещё разделы о решениях, мета-модели, вопросах и долге. |
| `null` | «—» | Так принято в таблицах этого репозитория; значение то же. |
| «Зависимости» — только ID задач | ID задач и долга, затем решения `Р-NN` | Большинство задач ждёт решения владельца; это видно в строке. |
| ID `B-NNN` | ID `BL-NNN` | Чтобы не путать с задачами Хаба. |

## Проверки

Перед PR, меняющим бэклог:

```bash
python3 scripts/validate_issue_418_backlog.py
make validate-fast
make validate-full
```

Проверка `validate_issue_418_backlog.py` контролирует: порядок разделов
входного документа; ответ про мета-модель; порядок «Этап 1 → мета-модель →
OpenCode»; реестр решений и их использование; формат строк спринтов; одну
карточку на строку; поля карточек; формат и дословность цитат; ссылки и
якоря; регистрацию файлов в `artifact-map.md`; запись в `CHANGELOG.md`;
неизменность защищённых путей в коммитах issue #418.
