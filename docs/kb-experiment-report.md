# Отчёт по эксперименту: машиночитаемая база знаний из PDF (issue #111)

> **Режим:** Creative (исполнитель сам выбирает методологию/инструменты/структуру
> и применяет сразу, без RFC). Регулируется существующим
> [ADR-007 / kb-standard](../standards/kb-standard.md) — данная работа
> **расширяет** его pre-RAG-механизм с «ручных KB-записей» на **извлечённые из
> документов разделы**, не меняя формат цитат и адресации.

## TL;DR

Построен сквозной конвейер **«источник (PDF/веб) → machine-readable БЗ»**:
извлечение текста и структуры, картинок и таблиц, нарезка на разделы-чанки,
индекс для поиска, подсчёт токенов и проверка целостности в CI. Цель —
**не грузить большой документ целиком** (это дорого по токенам, а часто и
невозможно), а дать агенту прочитать индекс → выбрать раздел по саммари →
загрузить **только** нужный фрагмент → процитировать стабильным адресом. Это
**эволюционный шаг к векторной БЗ и RAG**: те же файлы-чанки и адреса
`path#anchor` станут chunk-id ретривера без переписывания артефактов.

Главное ограничение issue соблюдено буквально: **качество извлечения важнее
экономии токенов**. Конвейер детерминированный (regex + pdfplumber, без LLM по
умолчанию), кириллица извлекается чисто, таблицы и картинки сохраняются.

## 1. Контекст и задача

Промпты и агенты должны опираться на продуктовую документацию (руководства КЦ,
справку ЛК ВАТС и т.п.). Положить такой PDF целиком в промпт нельзя: это десятки
тысяч токенов на каждый запрос, а большие документы просто **не влезают** в
контекст. Issue #111 требует машиночитаемую БЗ, из которой агент берёт **только
релевантный фрагмент**, и которая спроектирована как ступень к будущему RAG.

Issue прямо предупреждает: **не закладывать текущие ADR (#003–#010) и промпты как
канонические** — они будут меняться (драйф). Поэтому БЗ привязывается к
**содержанию документов-источников**, а не к формулировкам ADR (см. §10).

### Ловушка кириллицы в PDF (важно для реальных файлов)

Частый дефект: если в PDF нет корректной карты `ToUnicode`, текст извлекается как
«мусор» (например, `nnnn` вместо букв) — это известная проблема pdfplumber/
pdfminer на плохо сформированных PDF. На этапе генерации фикстуры мы это
**воспроизвели и устранили**: PIL по умолчанию рисует диаграмму битмап-шрифтом
без кириллических глифов (получаются «тофу»-квадраты), поэтому в
`make_sample_pdf.py` подключён TTF-шрифт с кириллицей. **Рекомендация для
реальных PDF:** если извлечённый текст — мусор, документ нужно прогнать через OCR
(см. §5, ветка pytesseract/OCR), а не «чинить» постобработкой.

## 4. Структура PDF (определённая иерархия)

`extract.py` определяет заголовки гибридно: **кегль больше базового** ИЛИ
(**нумерация `N`/`N.M`/`N.M.K`** И короткая строка И **bold**); уровень — из
глубины нумерации. Ненумерованные крупные строки (титул) разделом **не**
считаются. Для фикстуры получилось:

```
00 Титульная часть                 (стр. 1)   ← front-matter до первого заголовка
01 Введение                        (стр. 2)   — 1.1 Назначение; 1.2 Системные требования
02 Рабочее место оператора         (стр. 3)   — 2.1 Статусы; 2.2 Очередь
03 Каналы коммуникации             (стр. 4)   — 3.1 Голос; 3.2 Текст; 3.3 E-mail
04 Обработка обращений             (стр. 5)   — 4.1 Контроль; 4.2 Правила распределения; 4.3 Каналы  [+ диаграмма]
05 Роли и права доступа            (стр. 6)   — таблица ролей
06 Отчёты и аналитика              (стр. 7)
```

Каждый раздел верхнего уровня → отдельный файл-чанк. Подразделы (`4.2`) остаются
внутри файла как Markdown-заголовки `##`, давая стабильные **якоря** для цитат
(`…#42-правила-распределения`).

## 5. Инструменты извлечения: сравнение и выбор (ФТ-2)

Сравнивались актуальные подходы. Жёсткие критерии issue: **GitHub-native**
(работает в Actions), **качество важнее токенов**, **воспроизводимость** (CI без
GPU и без сети для модели).

| Инструмент | Сильные стороны | Почему **не** основной здесь |
| --- | --- | --- |
| **pdfplumber** (выбран) | Детерминирован, чистый текст + bbox + таблицы, ставится pip-ом, без GPU, идеален для CI | Слаб на сканах (нужен OCR) и на сложной вёрстке формул |
| **PyMuPDF / fitz** (выбран как опц.) | Быстрый, отдаёт **байты картинок**, рендер страниц | Текст-слой проще, чем у pdfplumber; берём только для изображений |
| pdfminer.six | База для многих инструментов, тонкий контроль | Низкоуровневый; pdfplumber удобнее как обёртка |
| **marker** (marker-pdf) | Отличный Markdown, хорошо с формулами/таблицами | Тяжёлые ML-модели, фактически нужен **GPU**, недетерминирован — не для лёгкого CI |
| **nougat** (Meta) | SOTA на научных PDF/формулах | Модель ~1.3 ГБ, GPU, галлюцинации на нестандартных макетах — риск для **качества** |
| **MinerU** | Сильный лэйаут-анализ, таблицы, формулы | GPU/тяжёлые модели и зависимости — избыточно для структурированного руководства |
| OCR (pytesseract/ocrmypdf) | Единственный путь для **сканов** и «мусорной» кириллицы | Не нужен для текстового PDF; держим как явную ветку для сканов |

**Решение:** основной путь — **pdfplumber** (текст/структура/таблицы) +
**PyMuPDF** (картинки) + **tiktoken** (токены). ML-инструменты (marker/nougat/
MinerU) **сознательно отклонены как путь по умолчанию**: они требуют GPU и
недетерминированы, что ломает воспроизводимость в Actions и противоречит
приоритету качества (риск галлюцинаций модели на нестандартной вёрстке). Они
остаются **задокументированным запасным вариантом** для сложных PDF (формулы,
многоколоночная вёрстка) и подключаются точечно, не становясь обязательной
зависимостью CI. Для **сканов** явная ветка — OCR.

Зависимости разделены в [`scripts/kb/requirements.txt`](../scripts/kb/requirements.txt):
извлечение (pdfplumber/PyMuPDF/tiktoken) и только-фикстура (reportlab/Pillow);
**валидатору не нужно ничего** (stdlib) — поэтому он гоняется в CI без `pip`.

## 6. Разбиение артефакта на разделы: скрипты vs LLM (ФТ-3)

| Подход | Когда | Плюсы / минусы |
| --- | --- | --- |
| **Детерминированный (regex + кегли)** — выбран | Документы с явной нумерацией/заголовками (руководства, ADR, ТЗ) | + Воспроизводимо, бесплатно, проверяемо в CI. − Требует распознаваемой структуры |
| **LLM-нарезка** — запасной | Неструктурированные тексты (стенограммы, сплошной текст без заголовков) | + Понимает смысл, разрежет «по темам». − Недетерминирована, стоит денег/токенов, нужен контроль галлюцинаций |

**Решение:** по умолчанию — **скрипт** (`build_sections()` в `extract.py`):
заголовок = «кегль больше базового» ИЛИ «нумерация + короткая + bold». LLM — **не
в конвейере по умолчанию**, а задокументированный fallback для документов без
структуры (тогда LLM только предлагает границы разделов, а текст всё равно
берётся детерминированно из PDF — чтобы не терять качество и не выдумывать).
Это устойчиво к будущему драйфу: если структура документов изменится, правится
**один** распознаватель, а не разметка вручную.

## 7. Структура каталогов БЗ (ФТ-4)

Имя **нейтральное** — `kb/` (исходно требовалось не использовать `mango-kc`).
Обязательный **каталог ручного ввода** — `kb/mango-product-docs/sources/` (туда человек кладёт файлы).

```
kb/
├── README.md                      ← общий индекс БЗ (практики issue #97 + указатель на ingestion)
├── USAGE.md                       ← 5 конкретных примеров для промптов (ФТ-6)
├── sources/                       ← РУЧНОЙ ВВОД (обязательно, ФТ-4): человек кладёт файлы сюда
│   ├── README.md                  ← человекочитаемая инструкция пополнения (ФТ-7)
│   ├── <doc-slug>/                ← один документ = один каталог (+ source.md манифест)
│   └── web-links/                 ← источники-ссылки (веб) — манифестом, без краулинга
├── processed/                     ← СГЕНЕРИРОВАННОЕ (машиночитаемое, не править руками)
│   └── <doc-slug>/
│       ├── index.md               ← карта разделов (retrieval-шаг до RAG)
│       ├── meta.json              ← инструмент, sha256, счётчики, токены
│       ├── sections/NN-*.md       ← раздел = файл = чанк (frontmatter: id, pages, tokens, source)
│       └── images/                ← извлечённые картинки
└── fragments/                     ← ЗАДЕЛ ПОД RAG (пуст намеренно): атомарные фрагменты + эмбеддинги
```

Разделение **`sources/` (вход человека) ↔ `processed/` (выход скрипта)** —
ключевое: правят **источник** и перезапускают извлечение, а не
сгенерированные файлы. Подробности слоёв — в
[`kb/mango-product-docs/sources/README.md`](../kb/mango-product-docs/sources/README.md),
[`kb/mango-product-docs/processed/README.md`](../kb/mango-product-docs/processed/README.md),
[`kb/fragments/README.md`](../kb/fragments/README.md).

## 9. Как промпт использует БЗ и расход токенов (ФТ-6)

Пять конкретных примеров с **реальными сниппетами** (индекс → выбор раздела →
загрузка раздела → цитата → сравнение токенов) — в
[`kb/mango-product-docs/USAGE.md`](../kb/mango-product-docs/USAGE.md). Ключевая таблица расхода токенов
(метод `tiktoken:cl100k_base`):

| Что грузит агент | Токены | Комментарий |
| --- | ---: | --- |
| **Весь документ** (текст всех разделов) | **1587** | как если «вшить PDF в промпт» |
| Только §4 «Обработка обращений» | **378** | полезная нагрузка ответа — на 76 % меньше |
| Только §5 «Роли и права» | **253** | на 84 % меньше |
| Индекс `index.md` | 912 | разовая навигация, переиспользуется на все вопросы |

**Честная рамка.** На игрушечной фикстуре из 7 разделов индекс (912) сопоставим
с целым документом (1587) — экономия на одном вопросе невелика. Но:
(1) **полезная нагрузка ответа** — это один раздел (~250–380 токенов), а не весь
документ; (2) индекс читается **один раз** и переиспользуется; (3) на реальном
объёме (руководство КЦ — десятки страниц, **десятки тысяч** токенов) целый
документ **не влезает** в промпт вообще, а индекс растёт лишь на строку-на-раздел.
То есть БЗ не столько «экономит проценты», сколько **делает работу с большим
документом возможной** — без потери качества (раздел читается полностью).

## 10. Устойчивость к драйфу ADR/промптов (обязательно)

Issue требует спроектировать БЗ с учётом будущего изменения ADR (#003–#010) и
промптов. Механизмы устойчивости:

1. **Привязка к содержанию документа, а не к ADR.** Чанки и их адреса
   (`kb/mango-product-docs/processed/<doc>/sections/NN#anchor`) зависят от текста источника, а не от
   формулировок ADR. Переписали ADR — БЗ валидна, переизвлечение источника не
   меняет схему путей.
2. **Стабильный контракт обращения.** Промпты ссылаются на БЗ через **формат
   цитаты** `[CC, §N, с.P]` и **адрес чанка**, а не на конкретные правила. Это тот
   же контракт, что уже зафиксирован в [ADR-007/kb-standard](../standards/kb-standard.md)
   (правила R1–R4), поэтому новый слой не вводит конкурирующего стандарта.
3. **Один распознаватель структуры.** Изменится разметка документов — правится
   `build_sections()`, а не разметка вручную (см. §6).
4. **Драйф уже наблюдаем — и это нормально.** Сама issue ссылается на
   `006-kb-integration.md`, тогда как в репозитории — `006-prompt-naming.md` +
   `007-kb-standard.md`. Это **конкретный пример драйфа нумерации ADR**: именно
   поэтому БЗ намеренно **не** хардкодит номера ADR как канонические, а опирается
   на устойчивые адреса и формат цитат.

### Почему методология зафиксирована в отчёте, а не в новом каноническом ADR

[CONTRIBUTING](../CONTRIBUTING.md) рекомендует фиксировать архитектурные/
governance-решения как ADR в `docs/adr/`. Здесь решение **сознательно иное**, и
это обоснованное отклонение в режиме Creative (CONTRIBUTING разрешает обойти
правило, явно объяснив это в PR):

- Issue прямо запрещает **закладывать текущие ADR как канонические** (они будут
  драйфовать) и **ждать согласования инфраструктуры** — то есть на этом этапе
  заводить новый «канонический» ADR преждевременно.
- Этот слой **не вводит новый стандарт**, а **применяет существующий**
  [ADR-007/kb-standard](../standards/kb-standard.md) (pre-RAG, R1–R4) к
  извлечённым из документов разделам. Источник истины по правилам остаётся
  ADR-007; дублировать его в новом ADR — значит плодить расхождения.
- Методология, выбор инструментов и структура — это **результаты эксперимента**,
  и их каноничное место по issue — именно **этот отчёт** (ФТ-8), а не ADR.
- Если методология стабилизируется и перестанет драйфовать, **будущая** issue
  сможет «повысить» её до ADR (например, обновив ADR-007). Делать это сейчас —
  противоречит явному требованию не энтренчить.

## 11. Эволюционный шаг к векторной БЗ и RAG (обязательно, явно)

**Эта БЗ — осознанный промежуточный (pre-RAG) этап на пути к векторной базе
знаний и полноценному RAG, а не конечная архитектура.** Сегодня «retrieval» — это
чтение `index.md` и выбор раздела по колонке «когда обращаться»; завтра это
сделает векторный поиск по эмбеддингам. Переход — **бесшовный**, потому что:

- **раздел = файл = чанк** уже сейчас (правило R1) → станет единицей индексации;
- `index.md` — это retrieval-шаг (R2) → заменяется векторным индексом;
- стабильные адреса `path#anchor` и `id` (R3) → становятся `chunk_id` ретривера
  **без переписывания** артефактов (R4, RAG-готовность);
- каталог [`kb/fragments/`](../kb/fragments/README.md) — заранее заложенная точка,
  куда лягут атомарные фрагменты и эмбеддинги, когда появится векторный слой.

Идея согласуется с исходной работой по RAG (Lewis et al., 2020): ответ всегда
сопровождается ссылкой на извлечённый источник — что у нас уже обеспечивает
формат цитаты.

## 12. Выводы и следующие шаги

**Выводы.**

- Детерминированного извлечения (pdfplumber + PyMuPDF + regex) **достаточно** по
  качеству для структурированных руководств; ML-инструменты не нужны по умолчанию
  и вредят воспроизводимости в CI.
- Механика «индекс → раздел → цитата» решает задачу больших документов и
  соблюдает приоритет **качество > токены**.
- Инфраструктура применена сразу (режим Creative), проверяется в CI и
  спроектирована под будущий драйф ADR/промптов и переход к RAG.

**Следующие шаги (для будущих issue, не входят в этот PR).**

1. Прогнать конвейер на **реальном** `CC_manual_1.26.23.pdf`, когда он будет
   доступен (команда — §2), и на справке ЛК ВАТС.
2. Ветка **OCR** (ocrmypdf/pytesseract) для сканов и PDF с «мусорной» кириллицей.
3. Точечное подключение **marker/MinerU** для PDF со сложной вёрсткой/формулами
   (как опциональный extractor, без обязательной зависимости CI).
4. **Векторный слой:** наполнить `kb/fragments/` атомарными фрагментами +
   эмбеддингами и поднять RAG поверх существующих чанков/адресов.
5. (Опц.) Автоматический сбор веб-источников вместо ручных манифестов.
