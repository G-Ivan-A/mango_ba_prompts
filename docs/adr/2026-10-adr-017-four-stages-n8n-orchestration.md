# ADR-017: четыре этапа развития, n8n — оркестратор этапа 3

## Статус

`accepted` — решение владельца в [issue #413](https://github.com/G-Ivan-A/mango_ba_prompts/issues/413)
(«n8n может быть оркестратором… runner требует навыков программирования, я
как БА их не имею… n8n был выбран как промежуточный вариант запуска
автоматизации БА процессов»). ADR записывает решение и его инженерные
следствия. Варианты DEC-05 «А/Б» RFC v0.3 им заменены
([RFC v0.4](../rfc/2026-10-repository-modernization.md#dec-05-роль-n8n-на-этапе-3-f-07)).

## Контекст

1. Владелец задал четыре этапа развития в [#409](https://github.com/G-Ivan-A/mango_ba_prompts/issues/409):
   (1) промпты в чате LLM по инструкции сайта; (2) агентный клиент типа
   OpenCode; (3) автоматизация оркестрацией процессов через n8n;
   (4) промышленная эксплуатация на выделенном сервере.
2. RFC v0.3 предложил на этапе 3 «runner ведёт маршрут, n8n — слой
   интеграций», опираясь на отказ Хаба от n8n как ядра (вариант В-6, риски
   Г-44…Г-49). Владелец это отклонил: runner — программный код, а владелец
   реализует автоматизацию визуальной сборкой и вайб-кодингом. Исполнитель,
   которого владелец не может сопровождать сам, не годится как промежуточный
   этап.
3. Границы [#263](https://github.com/G-Ivan-A/mango_ba_prompts/issues/263) в
   `README.md`, `ai-governance/ai-governance.md` и `docs/ba-ecosystem.md` §7
   говорили: «GitHub — единственная платформа», «серверной инфраструктуры…
   нет», «уровни 3–4 не являются планом работ». Это противоречит этапам 3–4.
   Валидатор `scripts/validate_issue_263_vision_alignment.py` требовал
   первую фразу дословно.

## Решение

1. **Четыре этапа — план этого репозитория.** Порядок задан владельцем.
   Критерии входа и выхода — в [`docs/roadmap.md`](../roadmap.md).
2. **n8n — оркестратор этапа 3.** n8n ведёт маршрут процесса: запускает
   шаги, хранит состояние исполнения, ждёт решения человека на гейтах и
   вызывает модели. Runner на этапе 3 не требуется. Отказ Хаба (В-6,
   Г-44…Г-49) для этого репозитория не является запретом; его риски
   превращены в обязательные инженерные требования (таблица ниже).
3. **Границы #263 заменены.**
   - Этапы 1–2 работают на GitHub и у БА (чат LLM, агентный клиент).
   - Этап 3 добавляет n8n, этап 4 — выделенный сервер в контуре Манго.
   - Слова «серверной инфраструктуры нет» и «уровни 3–4 не являются
     планом» больше не действуют.
4. **Без изменений остаются:**
   - видимость и роль `ai-ba-playbooks` — до отдельного решения владельца
     (DEC-03 и DEC-04 RFC);
   - запрет на изменение статистики `runs/`;
   - правило «изменения — только по RFC или ADR».

### Требования к n8n-оркестрации (вместо рисков В-6)

| Риск Хаба | Требование этапа 3 | Как проверить |
| --- | --- | --- |
| Вторая копия графа маршрута | Источник истины маршрута — описание процесса и контракт состояния в Git. n8n-поток собирается по ним, а каждый узел-шаг ссылается на шаг процесса | Валидатор сверяет экспорт потока со списком шагов |
| Недетерминированный узел AI Agent | Узел AI Agent не принимает решений на гейтах и переходах. Модель вызывается обычным LLM- или HTTP-узлом и возвращает артефакт. Переход определяет детерминированный узел IF/Switch по проверенным полям | Ревью экспорта: в потоке нет AI Agent с правом перехода |
| Нет `$ref` в структурном выводе | Схемы ответа подставляются развёрнутыми, без `$ref`. Ответ проверяется отдельным узлом валидации, а при ошибке поток возвращает шаг | Тест на заведомо невалидном ответе |
| Платная Git-синхронизация | Потоки выгружаются в JSON (`n8n export:workflow`) и коммитятся по правилу «PR на изменение потока». Платная функция не нужна | Экспорт в Git совпадает с работающим потоком |
| Поток уязвимостей | Self-hosted n8n с закреплённой версией и регламентом обновления, без публичного доступа к редактору; учётные данные — в хранилище n8n, а не в потоках | Чек-лист перед этапом 4 |
| Человек в цикле | Гейт — узел ожидания решения человека (форма или Wait). Решение записывается в журнал решений с автором и временем | Повторный запуск не дублирует решение |

Лицензия n8n — Sustainable Use License: внутреннее использование в компании
допускается. Юридическая проверка нужна до этапа 4.

## Рассмотренные варианты

| Вариант | Почему не выбран |
| --- | --- |
| Runner ведёт маршрут, n8n — слой интеграций (RFC v0.3, DEC-05 «Б») | Требует программирования и сопровождения кода. Владелец, исполнитель этапа, так работать не может |
| Пропустить этап 3 и сразу перейти на сервер | Нет промежуточной проверки автоматизации силами БА |
| Сохранить границы #263 | Противоречит четырём этапам владельца |

## Следствия

- Обязательства перед Хабом (обращения H-01…H-07 RFC v0.3) отозваны:
  проверка Хаба нужна была, чтобы взять стандарты экосистемы, а не чтобы
  менять Хаб (#413).
- `README.md`, `ai-governance/ai-governance.md`, `docs/ba-ecosystem.md` §7 и
  валидатор #263 обновлены в том же PR.
- Где хранить экспорт потоков n8n (этот репозиторий или
  `mango-ba-ai-runtime`), решает владелец (DEC-04). До решения здесь лежат
  только требования и критерии этапа.
- Сам поток n8n в этом ADR не создаётся: вход в этап 3 — выход этапа 2.
