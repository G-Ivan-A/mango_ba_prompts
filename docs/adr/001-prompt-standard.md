# ADR-001: Стандарт промптов `mango_ba_prompts`

> **Статус:** Accepted · **Дата:** 2026-06-11 · **Issue:**
> <https://github.com/G-Ivan-A/mango_ba_prompts/issues/63> · **Стандарт-контракт:**
> <https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/standards/prompt-standard.md>

> **Поправка (2026-06-16, [issue #92](https://github.com/G-Ivan-A/mango_ba_prompts/issues/92)):**
> в обязательный frontmatter добавлены поля `id` (уникальный токен) и `title`
> (человекочитаемое название на русском). Маркер
> `<!-- EXPERIMENTAL: DO NOT USE IN PRODUCTION -->` удалён из всех промптов:
> экспериментальность достаточно отражает `status: draft`.

## Контекст

В репозитории `mango_ba_prompts` после PR #57, PR #59 и PR #60 одновременно
существуют две линии промптов:

1. **Промпты, мигрированные из Хаба** (`hybrid-Intelligence-lab`). Они имеют
   компактную структуру role-prompting: `РОЛЬ` -> `КАК РАБОТАЕМ` -> `ПРАВИЛА`
   -> `ФОРМАТ ВЫВОДА` -> `НАЧНЕМ?`. После hotfix PR #59 эти промпты считаются
   устаревшими для активной библиотеки и лежат в `prompts/archive/`.
2. **Промпты из PDF/разделов 1-4 ФТ**, разрезанные PR #57 на отдельные файлы.
   Они чаще описывают не один ответ, а управляемый workflow БА: жесткие правила,
   режим работы, шаги с подтверждением, формат результата и ограничения.

На дату ADR в активной библиотеке `prompts/` находится 23 prompt-файла, в
`prompts/archive/` - 6 архивных prompt-файлов. Этот ADR не меняет их размещение.

Обе линии полезны, но до этого ADR были зафиксированы только фрагменты стандарта:

- `standards/prompt-standard.md` задает короткий контракт: 4 обязательных поля
  frontmatter, схему именования, RAG-формат ссылок и жизненный цикл.
- PR #57 обосновывает токены `stepwise`, `oneshot`, `legacy` вместо
  `expert`/`express`, но это обоснование было только в PR-описании.
- PR #60 фиксирует таксономию 13 когнитивных операций и связь имен файлов с
  `docs/taxonomy.md`.
- `docs/ba-processes/00-index.md` ведет центральный маппинг
  процесс -> операция -> рекомендуемые промпты, чтобы не перегружать
  frontmatter промптов.

**Ядро проблемы.** Для нового промпта было неочевидно:

- какую из двух структур выбрать;
- чем `stepwise`, `oneshot` и `legacy` отличаются как режимы;
- какие значения допустимы в frontmatter;
- как применять схему `[домен]-[операция]-[режим].md`;
- как переводить промпт из `draft` в `canonical` и как архивировать.

Этот ADR фиксирует стандарт как архитектурное решение. Короткий нормативный
контракт остается в `standards/prompt-standard.md`; ADR объясняет контекст,
правила применения и последствия.

## Решение

1. Поддержать **две допустимые структуры промптов**:
   - **Структура A: Hub-style prompt.**
   - **Структура B: Mango BA workflow prompt.**
2. Зафиксировать режимы в имени файла как технические токены:
   `stepwise`, `oneshot`, `legacy`.
3. Считать `expert` и `express` устаревшими токенами. Они могут встречаться в
   исторических обсуждениях и legacy-промптах, но не используются для новых
   файлов.
4. Оставить frontmatter минимальным: `id`, `title`, `status`, `version`,
   `updated`, `temperature`. Поля `id` и `title` добавлены поправкой по
   [issue #92](https://github.com/G-Ivan-A/mango_ba_prompts/issues/92) для
   стабильной идентификации промпта в аналитике и человекочитаемого названия в
   интерфейсе GitHub Pages. Для мигрированных артефактов допустимы
   provenance-поля.
5. Использовать схему именования `[домен]-[операция]-[режим].md` с операцией из
   таксономии `docs/taxonomy.md`.
6. Не менять существующие промпты в рамках этого ADR. Он стандартизирует
   дальнейшее создание, ревью и архивирование.

## Структура A: Hub-style prompt

### Скелет

```markdown
# РОЛЬ
Кто отвечает и какую задачу решает.

# КАК РАБОТАЕМ
Как пользователь передает вход, как агент проверяет достаточность данных, где
останавливается на уточнения.

# ПРАВИЛА
Ограничения, запреты на домыслы, требования к терминологии и качеству.

# ФОРМАТ ВЫВОДА
Структура результата.

# НАЧНЕМ?
Краткая инструкция, что пользователь должен отправить первым сообщением.
```

### Когда использовать

Структура A подходит для зрелых, компактных промптов, где:

- задача укладывается в один понятный сценарий role -> task -> rules -> output;
- шаги не требуют длинного интерактивного согласования;
- промпт переносится из Хаба или готовится как обобщаемая практика для Хаба;
- важна читаемость и быстрый старт, а не подробная процессная рамка.

### Преимущества

- Быстро читается и копируется.
- Совместима с распространенной role-prompting практикой.
- Хорошо подходит для переносимых, hub-ready промптов.

### Ограничения

- Слабо выражает stop-gates и многошаговое согласование.
- Может быть недостаточна для формирования сложных разделов ФТ/ТЗ, где важно
  явно разделить сбор контекста, генерацию, валидацию и уточнения.
- Для новых активных Mango BA workflow-промптов чаще предпочтительна структура B.

### Примеры в репозитории

| Пример | Назначение |
| --- | --- |
| <https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/prompts/archive/user-story-generator-legacy.md> | Генерация User Story из сырого запроса; Hub-style структура `РОЛЬ` -> `КАК РАБОТАЕМ` -> `ПРАВИЛА` -> `ФОРМАТ ВЫВОДА` -> `НАЧНЕМ?`. |
| <https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/prompts/archive/usecase-stepwise-generator-legacy.md> | Пошаговая генерация Use Case из требования и User Story; исторический пример структуры из Хаба. |

## Структура B: Mango BA workflow prompt

### Скелет

```markdown
# РОЛЬ
Кто отвечает, какой доменный профиль у агента, какой артефакт он формирует.

# ЖЕСТКИЕ ПРАВИЛА
Нерушимые ограничения: запрет домыслов, границы уровня требований, правила
терминологии, форматирования и безопасности работы с источниками.

# РЕЖИМ РАБОТЫ
`stepwise`: строго пошаговый диалог с остановками на подтверждение.
`oneshot`: весь результат за один ответ без промежуточных согласований.

# ШАГ 1
Сбор, проверка или суммаризация входного контекста.

# ШАГ 2
Основная аналитическая операция: декомпозиция, генерация, моделирование,
валидация или нормализация.

# ФОРМАТ ВЫВОДА
Точная структура результата, таблицы, статусы, чек-листы, поля и порядок блоков.

# ОГРАНИЧЕНИЯ
Что агент не делает: не добавляет реализацию, не меняет смысл источника, не
выходит за глоссарий, не подменяет согласование.
```

В существующих PDF-derived промптах встречаются совместимые варианты заголовков:
`СТИЛИСТИКА`, `АЛГОРИТМ РАБОТЫ`, `АЛГОРИТМ ВЫПОЛНЕНИЯ`, `ВХОДНЫЕ ДАННЫЕ`.
Они допустимы для уже созданных файлов. Для новых промптов следует сходиться к
скелету выше, если нет причины оставить более точный локальный заголовок.

### Когда использовать

Структура B подходит для рабочих промптов бизнес-аналитика Mango, где:

- результат формируется через несколько согласуемых шагов;
- есть риск смешать бизнес-требования, технические детали и реализацию;
- нужно явно зафиксировать правила ФТ/ТЗ, глоссарий, сценарии, проверки и
  ограничения;
- агент должен действовать как workflow, а не просто как генератор одного ответа.

Для `oneshot`-варианта та же структура сохраняет правила и формат, но блок шагов
заменяется на `АЛГОРИТМ ВЫПОЛНЕНИЯ (весь вывод в одном ответе)`.

### Преимущества

- Явно задает контрольные точки и снижает риск галлюцинаций.
- Подходит для сложных документов БА: ФТ/ТЗ, UC/US, валидации, резюме встреч.
- Хорошо связывается с таксономией операций и процессами БА.

### Ограничения

- Тяжелее для чтения и сопровождения, чем структура A.
- Не нужна для коротких, mature prompt-assets без интерактивного workflow.
- Требует аккуратного выбора режима `stepwise` или `oneshot`, иначе пользователь
  получает либо слишком много остановок, либо слишком мало контроля.

### Примеры в репозитории

| Пример | Назначение |
| --- | --- |
| <https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/prompts/glossary-context-understanding-stepwise.md> | Пошаговое формирование терминологии и бизнес-контекста для разделов 1-2 ТЗ. |
| <https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/prompts/fr-documentation-stepwise.md> | Пошаговое формирование раздела 4 ФТ на основе контекста, US и UC. |
| <https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/prompts/fr-validation-oneshot.md> | One-shot валидация и перегенерация ФТ в одном ответе. |

## Режимы

Режим - это последний токен имени файла. Он отвечает на вопрос **как агент
взаимодействует с пользователем**, а не какую роль агент играет.

| Токен | Значение | Когда использовать | Обоснование |
| --- | --- | --- | --- |
| `stepwise` | Многошаговый режим с stop-gates: агент делает шаг, показывает промежуточный результат и ждет подтверждения. | Сбор контекста, формирование ФТ/ТЗ, UC/US, валидация с уточнениями, сценарная декомпозиция. | Ближе к ReAct-подходу `thought -> act -> observe` и к workflow, где действие зависит от обратной связи пользователя. |
| `oneshot` | Одноразовый режим: агент выдает полный результат за один ответ. | Экспресс-аудит, нормализация, постобработка ASR, ситуации с достаточным входом и низкой ценой уточнений. | Соответствует международной терминологии one-shot learning / one-shot prompting: задача решается без промежуточного диалога. |
| `legacy` | Исторический или унаследованный режим/вариант, который сохраняется для совместимости или сравнения. | Промпт пришел из старого источника, сохраняет прежний стиль, нужен как активный черновик до замены или как архивный эталон. | `legacy` - стандартный технический термин для унаследованных систем и артефактов. |

### Почему не `expert` и `express`

`expert` отвергнут как режим, потому что в prompt engineering он читается как
роль (`act as an expert`), а не как способ взаимодействия. Это создает коллизию
между ролью агента и режимом файла.

`express` отвергнут как режим, потому что это маркетинговое слово. Технический
эквивалент для одношагового исполнения - `oneshot`.

### Важное различие: `legacy` и `archived`

`legacy` - это **режим в имени файла**. `archived` - это **значение поля
`status` во frontmatter**.

Поэтому файл `*-legacy.md` не обязан лежать в `prompts/archive/` и не обязан иметь
`status: archived`. PR #59 сознательно оставил часть PDF-derived legacy-промптов
активными в `prompts/` со `status: draft`, например:

- <https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/prompts/fr-validation-legacy.md>
- <https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/prompts/technical-details-solution-design-legacy.md>

Архивный файл, наоборот, должен иметь `status: archived` и жить в
`prompts/archive/`.

## Frontmatter

Каждый prompt-файл должен начинаться с YAML-frontmatter.

### Обязательные поля

| Поле | Тип | Допустимые значения | Пример | Правило |
| --- | --- | --- | --- | --- |
| `id` | string | `mango-[операция]-[режим]`, по схеме имени файла с префиксом `mango-` | `id: mango-fr-documentation-stepwise` | Уникальный токен промпта для аналитики использования. Совпадает с именем файла (без `.md`) и не дублируется между активными и архивными промптами. |
| `title` | string | человекочитаемое название на русском, 2-5 слов | `title: "ФТ: Генерация требований"` | Понятное БА название без технических аббревиатур (кроме общепринятых: ФТ, ТЗ, ASR, UC, US, LLM). Отображается жирным заголовком в интерфейсе GitHub Pages. |
| `status` | enum | `draft`, `canonical`, `archived` | `status: draft` | Отражает жизненный цикл промпта, а не режим имени файла. |
| `version` | semver-like string/number | `0.1`, `1.0`, `1.1`, `2.0` | `version: 0.1` | Версия содержимого; `0.x` для черновиков, `1.0+` для утвержденных или исторически зафиксированных вариантов. |
| `updated` | date | `YYYY-MM-DD` | `updated: 2026-06-11` | Дата последнего содержательного изменения. |
| `temperature` | number | обычно `0.1`; допустимый диапазон по умолчанию `0.0`-`1.0` | `temperature: 0.1` | Рекомендуемая температура запуска. Для требований БА предпочтительна низкая температура. |

### Пример корректного frontmatter

```yaml
---
id: mango-fr-documentation-stepwise
title: "ФТ: Генерация требований"
status: draft
version: 0.1
updated: 2026-06-11
temperature: 0.1
---
```

### Опциональные поля

Для новых промптов frontmatter не расширяется. Маппинг на процессы, паттерны и
research-зависимости ведется централизованно:

- <https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/docs/ba-processes/00-index.md>
- <https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/docs/hub-research-dependencies.md>

Для мигрированных артефактов допустимо сохранять provenance-поля, если они уже
есть и помогают аудиту:

- `source_hub`
- `source_sha`
- `based_on`
- `migration_status`
- `selftest_ref`
- `selftest_result`

Новые поля вроде `output_format`, `glossary_ref`, `research_dep` не добавляются в
новые prompt-файлы без отдельного решения: PR #60 уже вынес эти связи в
центральные реестры.

## Именование файлов

### Базовая схема

```text
[домен]-[операция]-[режим].md
```

Все компоненты пишутся в kebab-case и нижнем регистре.

| Компонент | Что означает | Источник значения | Примеры |
| --- | --- | --- | --- |
| `домен` | Предмет или артефакт, с которым работает промпт. | Практика Mango BA и процессная область. | `fr`, `glossary-context`, `technical-details`, `meeting-customer`, `asr`, `uc`, `us`. |
| `операция` | Когнитивная операция БА. | `docs/taxonomy.md`, где `_` в ID заменяется на `-` для имени файла. | `ingestion`, `understanding`, `validation`, `modeling`, `documentation`, `solution-design`, `risk-analysis`. |
| `режим` | Способ взаимодействия агента с пользователем. | Этот ADR. | `stepwise`, `oneshot`, `legacy`. |

### Корректные имена

- `glossary-context-understanding-stepwise.md`
- `fr-documentation-oneshot.md`
- `fr-validation-legacy.md`
- `technical-details-solution-design-stepwise.md`
- `asr-ingestion-oneshot.md`
- `uc-modeling-stepwise.md`

### Правила суффиксов

| Суффикс | Правило |
| --- | --- |
| `-legacy` | Это не дополнительный суффикс, а штатный режим. Он всегда последний токен перед `.md`: `fr-validation-legacy.md`. |
| `-v2` | По умолчанию не используется: версию хранит `version`. Допустим только по human review, если две несовместимые версии должны временно сосуществовать. Тогда режим остается последним: `fr-documentation-v2-stepwise.md`. |
| `-alt` | Временный альтернативный вариант для сравнения в PR/эксперименте. Требует явного контекста в issue и последующего решения: promote, archive или remove. Режим остается последним: `uc-modeling-alt-oneshot.md`. |

Если возникает желание добавить `-v2` или `-alt`, сначала проверить, нельзя ли
решить задачу через `version`, `status`, `runs/` и PR-описание.

## Правила применения

### Как выбрать структуру

| Ситуация | Выбор |
| --- | --- |
| Новый рабочий промпт для БА с согласованием, шагами, quality gates или риском домыслов | Структура B |
| One-shot вариант уже существующего workflow-промпта | Структура B с `АЛГОРИТМ ВЫПОЛНЕНИЯ (весь вывод в одном ответе)` |
| Компактный mature prompt без сложного workflow | Структура A |
| Миграция или адаптация prompt-практики из Хаба | Структура A, если исходник уже в ней; структура B, если Mango-специфика требует stepwise workflow |
| Архивный или сравнительный исторический вариант | Сохранить исходную структуру, режим `legacy`, статус по фактическому жизненному циклу |

### Как выбрать режим

| Ситуация | Режим |
| --- | --- |
| Нужно подтверждение пользователя между шагами | `stepwise` |
| Вход достаточен и нужен полный результат сразу | `oneshot` |
| Промпт сохраняется как унаследованный вариант, старый стиль или архивная база сравнения | `legacy` |

### Процесс `draft` -> `canonical`

1. Создать или изменить prompt-файл только в рамках issue -> PR.
2. Добавить обязательный frontmatter и имя по схеме
   `[домен]-[операция]-[режим].md`.
3. Указать в PR, какую структуру и режим выбрали и почему.
4. Добавить или обновить запись в
   <https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/docs/ba-processes/00-index.md>,
   если промпт становится рекомендуемым для процесса БА.
5. Зафиксировать минимум один прогон в `runs/`, если промпт
   претендует на `canonical`.
6. После human review обновить:
   - `status: canonical`;
   - `version: 1.0` или следующую согласованную версию;
   - `updated: YYYY-MM-DD`.

До human review новый prompt-asset остается `status: draft`.

### Процесс архивации

1. Если промпт выводится из активного использования, перенести его в
   `prompts/archive/`, если он еще не там.
2. Поставить `status: archived`.
3. Сохранить `version`, тело и provenance, если они важны для аудита.
4. Добавить или сохранить `-legacy` в имени, если файл является унаследованным
   вариантом.
5. Обновить `docs/ba-processes/00-index.md`, если промпт был рекомендованным.

Архивация - низкорисковое изменение: отдельный issue не обязателен, но изменение
все равно проходит через PR.

## Критерии соответствия

Новый или измененный prompt-файл соответствует стандарту, если:

- имя файла следует `[домен]-[операция]-[режим].md`;
- режим - один из `stepwise`, `oneshot`, `legacy`;
- операция есть в `docs/taxonomy.md` и записана в имени как kebab-case;
- frontmatter содержит 6 обязательных полей (`id`, `title`, `status`,
  `version`, `updated`, `temperature`);
- `id` уникален и совпадает с именем файла с префиксом `mango-`;
- `title` человекочитаем, на русском, без лишних аббревиатур;
- `status` не смешивается с режимом `legacy`;
- выбранная структура A или B явно соответствует сценарию применения;
- `canonical`-промпт содержит явный блок `ФОРМАТ ВЫВОДА`;
- маппинг процесса обновлен в `docs/ba-processes/00-index.md`, если промпт
  становится рекомендуемым;
- ссылки на стандарты внутри тела промпта оформлены Markdown-ссылками от корня
  репозитория, как требует `standards/prompt-standard.md`.

## Последствия

Положительные:

- Новый БА или AI-агент может создать промпт без восстановления контекста из PR #57.
- Токены режимов становятся стабильной частью стандарта, а не только решением в
  PR-описании.
- Сохраняется совместимость с существующими prompt-файлами: ADR не требует
  миграции текущего корпуса.
- Стандарт можно передать в Хаб как рекомендацию, потому что он отделяет
  переносимую структуру A от Mango-specific workflow структуры B.

Отрицательные / технический долг:

- В репозитории временно остается неоднородность заголовков в структуре B
  (`ЖЕСТКИЕ ПРАВИЛА`, `СТИЛИСТИКА`, `АЛГОРИТМ РАБОТЫ`). Это осознанно: issue #63
  запрещает менять существующие промпты.
- `CONTRIBUTING.md` и `AI_GOVERNANCE.md` еще упоминают `prompts/drafts/`, хотя
  текущий каталог был удален после PR #57. Этот ADR не меняет workflow-файлы;
  синхронизация терминологии и путей должна быть отдельной задачей.
- `-v2` и `-alt` разрешены только как исключение, поэтому при появлении таких
  файлов потребуется внимательное review.

## Альтернативы (отклонены)

1. **Оставить только структуру A.** Отклонено: Mango BA prompts часто являются
   workflow definitions с многошаговым согласованием; компактная структура не
   выражает эти gates достаточно явно.
2. **Оставить только структуру B.** Отклонено: мигрированные Hub-style промпты и
   переносимые практики полезнее сохранять в компактном виде.
3. **Вернуть режимы `expert` и `express`.** Отклонено: `expert` конфликтует с
   role-prompting, `express` не является техническим термином; PR #57 уже
   обосновал замену.
4. **Расширить frontmatter маппингами и ссылками (`output_format`,
   `glossary_ref`, `research_dep`).** Отклонено: PR #60 сознательно вынес эти
   связи в централизованные реестры. Поправка по issue #92 добавила только
   идентификационные поля `id` и `title` (без маппингов): они нужны для
   аналитики и UI и не дублируют центральные реестры.
5. **Немедленно привести все существующие промпты к одному шаблону.** Отклонено:
   issue #63 явно запрещает менять существующие промпты; этот ADR фиксирует
   стандарт для дальнейшей работы.
