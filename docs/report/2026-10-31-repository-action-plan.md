# Отчёт #413: что изменить дальше, чтобы вести репозиторий как проект

Один документ вместо пакета #409. Здесь только три вещи: что решил
владелец, что уже сделано в PR #414 и что предлагается сделать на
следующем шаге. Остальные документы #409 читать не обязательно (раздел 6).

## 1. Итог в пяти строках

1. **Этап 1 описан, сайт не менялся.** Порядок запуска этапа 1 и четыре
   этапа записаны в [roadmap](../roadmap.md). Сайт меняется только после
   принятия RFC/ADR отдельными задачами (указание владельца в PR #414);
   целевая структура сайта — DEC-11 RFC модернизации.
2. **n8n — оркестратор этапа 3.** Решение владельца записано в
   [ADR-017](../adr/2026-10-adr-017-four-stages-n8n-orchestration.md).
   Риски, из-за которых Хаб отказался от n8n как ядра, стали требованиями
   к потокам, а не запретом.
3. **RFC проекта не рассматривает процессы BCREQ.** Их содержание ведёт
   трек промптов [#411](https://github.com/G-Ivan-A/mango_ba_prompts/issues/411).
4. **Промпт содержит только паттерны, классы и принципы.** Вопросы и фразы
   конкретных задач уходят в golden set. Правило записано в
   [стандарте промптов](../../standards/prompt-standard.md#обобщение-содержимого-промпта-issue-413)
   и проверяется валидатором.
5. **Следующий шаг — серия реальных прогонов этапа 1** и семь решений
   владельца по RFC модернизации (раздел 5).

## 4. Разборы

### 4.1. n8n на этапе 3

Владелец прав: оркестрация в n8n совместима с целью проекта. Отказ Хаба
от n8n как ядра (вариант В-6) обоснован рисками для программной среды
исполнения: маршрут вне Git, решения модели вместо гейтов, нет проверки
ответа, зависимость от облака. Эти риски не запрещают n8n. Они задают
требования к тому, как собирать потоки. ADR-017 превращает каждый риск в
проверяемое требование: экспорт потока в Git, гейты только
детерминированными узлами и узлом ожидания решения человека, проверка
ответа модели по контракту, self-hosted n8n с закреплённой версией.
Шаги процесса и гейты при этом не меняются.

Лицензия n8n (Sustainable Use License) разрешает внутреннее использование.
Для этапа 4 её нужно подтвердить у юристов Манго (раздел 5, П-8).

### 4.2. Промпт — уровень паттернов, задача — уровень исполнения

| Уровень | Что содержит | Где живёт |
| --- | --- | --- |
| Принцип | «Вопрос Заказчику — только о бизнес-смысле, не о внутреннем устройстве» | Промпт, конституция процесса |
| Класс | C05 «таксономия»: атом требования привязан к Domain → Capability | Промпт, `standards/bcreq-manual-classes/` |
| Паттерн | «Для метрики времени уточни источник: план или факт» | Промпт (обобщённо) |
| Пример фразы | «Q-2.7: что считать началом смены для API — WFM или сессия в КЦ?» | Golden set процесса, журнал вопросов задачи |
| Решение задачи | «Q-2.1 удалён: схема JSON — задача архитектора» | Журнал решений документа BCREQ, не репозиторий промптов |

Правило проверяется в CI. Валидатор
`scripts/validate_issue_413_prompt_generalization.py` ищет в активных
промптах `prompts/bcreq-*.md` номера вопросов задач (`Q-N.N`), номера
BCREQ, прогонов и issue. Текущие вхождения (только промпт конституции)
зафиксированы как долг #411: новые не пропускаются, существующие
снимаются в треке промптов.

### 4.3. «ВАТС vs КЦ»

Пара пришла из двух прогонов: RFC-MCH-P1 (#109, М1) и RFC-1025-P1 (#107,
Б1/Б5). В обоих случаях задача затрагивала настройку в личном кабинете
ВАТС и исполнение в КЦ, и модель путала слои. Предложения переносят эту
пару в ШАГ 0 промпта как правило.

| Факт | Значение | Источник |
| --- | --- | --- |
| Домены продуктов Манго | 7 | `docs/taxonomy/products.json`, каталог 2026-10-28.1 |
| Capability | 43; по основному домену: ВАТС 16, КЦ 11, аналитика 6, цифровые каналы 4, AI и автоматизация 4, оборудование 1, безопасность 1 | там же |
| Capability, не относящиеся ни к ВАТС, ни к КЦ | 16 из 43 | там же |
| Сквозные Capability (несколько доменов) | 6 | там же |
| Профили продуктов стандарта композиции | 6: ЛК, ВАТС, КЦ, РА, API, оператор; доменов без профиля — 4 (цифровые каналы, AI и автоматизация, оборудование, безопасность) | [`bcreq-composition-standard.md` §4](../../standards/bcreq-composition-standard.md#4-профили-продуктов) |

Вывод: правило на одну пару — частный случай. Оно не поможет задачам по
цифровым каналам, AI или безопасности и подтолкнёт модель видеть ВАТС и
КЦ там, где их нет. Действующие промпты эту пару не закрепили: промпт
конституции перечисляет шесть профилей, промпт продуктов классифицирует
по Domain → Capability.

Предложение для #411: обобщить RFC-MCH-P1 и RFC-1025-P1 до паттерна
«для каждой затронутой Capability зафиксируй слой настройки и слой
исполнения» (класс C05) и закрыть пробел профилей для четырёх доменов
(П-3). В реестре RFC обе записи получили пометку #413, статусы не
менялись.

### 4.4. Хаб

Хаб проверялся только для того, чтобы найти стандарты экосистемы, которые
стоит взять. Взяты или предложены к взятию: формат ADR и RFC, четыре
стратегических документа в `docs/`, корневой `AGENTS.md` (DEC-07). Мета-модель БА Хаба
остаётся нормой, решения #413 ей не противоречат. Передача опыта в Хаб
(H-01…H-07) снята с повестки.

### 4.5. Заблокировано: экспорт чатов

В #413 сказано: «прикрепляю чаты, в которых я общаюсь с ИИ ассистентом» и
«ПРИОРИТЕТНЫМИ безусловно — мои решения в чатах». К issue не приложено ни
одного файла, комментариев нет. Поэтому сверка решений из чатов с
issues репозитория **не выполнена**. Отчёт опирается только на текст
#409 и #413. Как только экспорт будет приложен, нужно сверить решения
владельца с issues и этим отчётом и исправить расхождения (П-9).
