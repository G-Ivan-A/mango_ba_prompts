## 0. Поток BCREQ: процессы, шаги, гейты

**Поток BCREQ** — процесс верхнего уровня, который проводит документ BCREQ
от сырого запроса Заказчика в Jira до утверждённого и зафиксированного
документа. Результат получается циклом девяти процессов ПБ-0…ПБ-7 и ПБ-С.
Цепочка элементов: **Поток → Процесс (подпроцессы) → Операция → Артефакт**.
Шаг и гейт — элементы описания процесса, стадия A-IN…A-RELEASE —
состояние артефакта ([словарь потока](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/standards/bcreq-flow-glossary.md#1-цепочка-элементов)).
Новых процессов нет: каждый процесс собран из шагов v0.1, операций
каталога и процессов L2 мета-модели runtime (RFC #427, раздел 5.1).

### 0.2. Гейты и стадии артефакта

Гейт — точка решения в процессе: доказательства (К-20) → решение
исполнителем по типу гейта → запись (К-34) → выбор ребра по исходу.
Типы гейта: `человек`, `гибрид` (модель рекомендует с обоснованием,
решает человек), `llm` (промпт или агент), `код`. Ключевые гейты —
человеческие ([словарь потока, раздел 3](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/standards/bcreq-flow-glossary.md#3-гейт-определение-типы-ключевые-гейты)).

| --- | --- | --- | --- | --- | --- | --- |
| Г-IN | ПБ-1 | A-IN → A-CORE | БА | `гибрид`: модель выводит отчёт по критериям и рекомендацию (П-5, П-7) | да сейчас: G1 правила B3; первый кандидат в неключевые (BL-159) | Г-IN.1…Г-IN.5; дальше / доработать A-IN |
| Г-С1 «Согласование 1» | ПБ-3 | A-CORE → A-WORK | Заказчик | `человек`; предпроверка критериев для БА — `гибрид` | да | Г-С1.1…Г-С1.5; согласование / уточнение / отказ |
| Г-W | ПБ-5 | A-WORK → A-RELEASE | ПО продукта, архитектор продукта, руководитель КК | `человек`; предпроверка критериев — `гибрид` | да | Г-W.1…Г-W.5; согласование / уточнение / отказ |
| Выпуск | ПБ-7 | A-RELEASE → утверждённый BCREQ | по процессу A-RELEASE | `человек` | да | baseline (G3) |

Критерии гейтов — в
[контракте стадий и гейтов](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/docs/contracts/bcreq-stage-gates.md#2-гейты).
Тип гейта меняет только того, кто решает; критерии, исходы и рёбра
остаются. Перевод гейта в другой тип — решение владельца на
доказательствах (BL-159).

## 1. Ручной процесс БА

### 1.1. Общие правила ручного прогона

| № | Правило |
| --- | --- |
| П-1 | Один промпт — один класс операции. Шаг 1.2 — первое появление класса; в следующих стадиях класс повторяется по порядку 1.3 с тем же контрактом. |
| П-2 | Промпт копируется целиком кнопкой ⧉ на сайте; первая строка копии — комментарий с ID промпта, его не удалять. Вместе с промптом вставить контракт состояния, применимые мета-стандарты и конституцию: К-36 проверяет их версии. |
| П-3 | Вход заполняется в JSON-блоке стандарта класса: task, phase, class, input_mode (START или CONTINUE), revision, rule_bundle. `null` — неизвестно, `[]` — проверено и пусто. |
| П-4 | Каждый ответ модели — один блок `BCREQ_OUTPUT`. БА проверяет receipt и recommendation и передаёт блок в следующий вызов; новый чат — через К-12 FULL и проверку переноса К-13. |
| П-5 | Модель только рекомендует следующий класс и гейт. Шаг, повтор, пропуск, возврат и гейт выбирает БА или согласующий; молчание не согласие. |
| П-6 | Вопросы К-04 БА отправляет пакетом по адресатам, модель ответы не придумывает. Пробел источника блокирует только зависящие утверждения (WAITING). |
| П-7 | Цикл стадии: К-12 собирает фазу, К-20 предлагает гейт, человек решает, К-34 фиксирует решение, К-12 обновляет полный результат. |
