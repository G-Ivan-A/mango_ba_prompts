## Как выполнен аудит

Старт: https://www.mango-office.ru/support/1_nachat-zdes/

Дата наблюдений — 2026-10-28 UTC; индивидуальные времена и хэши указаны
в каждой записи. Обход следует всем обнаруженным HTML-ссылкам `/support/`
на том же HTTPS-хосте, включая меню и перекрёстные ссылки. Это шире буквального
URL-префикса стартовой страницы и охватывает обязательные соседние разделы.
Завершение означает пустую очередь достижимых ссылок. Страницы без входящей
ссылки, URL за поисковой формой, личный кабинет и закрытый JS-контент этим
методом не обнаруживаются; утверждения о полном интернете не делаются.

Исключены downloads/«Скачать», раздел тикетов/«Поддержка», файлы, query-endpoints
и внешние сайты. HTML-архив интеграций включён, поскольку это документация;
архив скачиваемых материалов исключён. Список исключений сохранён с причинами.
Перед redirect проверяется граница, до чтения тела проверяется Content-Type.
PDF, изображения, архивы, установщики и другие вложения портала не скачивались.
Медиа учитываются только по HTML-метаданным. Отдельно прочитаны явно заданные
источники таксономии и forensic JSON из issue; это входы исследования.

Аудитор использует четыре параллельных запроса, не более 4 MiB на ответ и
10 000 страниц. Достижение лимита завершает запуск ошибкой, не «полным» отчётом.
Кэш позволяет продолжить прерванный обход. HTTP 502 и пустые ответы проверяются
повторно с сохранением первой попытки. HTTP 200 без тела статьи остаётся
нечитаемым/неопознанным шаблоном. Доступность оценивается по фактическому коду,
а не по наличию URL в меню. Снимок не гарантирует будущую доступность портала.

## Читаемость: что установлено

В снимке **3918 URL: 3913 HTTP 200 и пять HTTP 301**, заблокированных на границе
обхода. После повторной проверки 502 не осталось. У 36 ответов 200 не найдено
тело статьи (включая landing и неизвестные шаблоны); это не считается успешным
чтением. 1557 страниц проходят консервативный gate (1401 текстовая, 156 с простыми
таблицами); 2320 требуют visual review, ещё 41 запись недоступна для извлечения
статьи. На 552 страницах обнаружено 813 таблиц, на 2079 — 8998 изображений.
SVG/canvas/mermaid учитываются как потенциальный визуальный контекст и могут
включать декоративные элементы: это объясняет консервативность gate.

Текст статьи, заголовки, строки и ячейки таблиц присутствуют в исходном HTML
у обычных страниц портала: запуск JS для их извлечения не требуется. Это
проверено парсером отдельно от меню и логотипов. Страницы с неизвестным
шаблоном не считаются динамическими автоматически: причина остаётся неизвестной.

Для простых таблиц сохраняются границы строк/ячеек, заголовки, merged-cell
флаг и число строк. Проверка речевой аналитики читает конкретное пересечение
строки и колонки, а не только факт наличия `<table>`. При merged cells или
отсутствии `<th>` устанавливается `table-review-required`: линейный текст
может потерять соответствие параметра значению. Даже простой HTML не доказывает
правильность любого последующего ответа LLM.

Скриншоты и схемы — реальная граница наблюдения. URL/alt/title, подпись и текст
вокруг изображения не восстанавливают все стрелки, варианты dropdown и поля
интерфейса. Наличие изображения/canvas/SVG приводит к `visual-review-required`
даже при заполненном alt. Проверка не скачивает изображение, не делает OCR и
не приписывает ему неувиденное содержание. Поэтому ответ о семантике схемы
без дополнительного источника считается недоказанным. Это консервативная
проверка извлекаемости, **не LLM-eval** и не измеренная доля верных ответов.

Обязательные области проверяются отдельно: «Продукты и приложения» — формы
Конструктора/ЛК, «Интеграции» — различие amoCRM/BPMSoft и таблицы server-client,
«API и разработка» — поля/типы/обязательность и статусы/сессии, «Администрирование»
— права/роли/SSO, «Контакт-центр» — WFM и статус сотрудника, «Речевая аналитика»
— матрица интеграции и настройки. Точные URL, результаты и ограничения находятся
в `readability-checks.json`; сводные числа — в `coverage.json`.

## Изменения Product Layer

Сохранены все семь Domain, 42 исторические Capability, 132 Feature, 98 Atomic
Function, параметры, номера строк, исторические Mango status и commercial
overlays. Нормализованы связи прежде плоских списков Feature и Atomic Function:
одна функция может обслуживать несколько Feature. Эти связи имеют явный
`binding_basis: editorial-association-of-inherited-lists`; исходник не задавал
каждое ребро. Они не являются новыми утверждениями доступности продукта.

Добавлена Capability `report-builder` в существующих доменах voice-ucaas,
contact-center и analytics, с Feature авторства отчёта и моделирования данных:
https://www.mango-office.ru/support/3_produkty-i-prilozheniya/12_konstruktor-otchetov/

Добавлены атомарные операции WFM/пунктуальности, смены статуса, web-КЦ,
мобильного ЛК, Wallboard, Talker, SIP Trunk, контроля качества, МангоДиалогов,
роботов/NLU, речевой аналитики, Коллтрекинга, коннекторов и API. Каждая запись
добавления содержит конкретный URL и локатор заголовка. `verification` описывает
проверяемый эффект для последующего продуктового теста; такие тесты в чужой
системе не выполнялись. Полный список и количество добавлений вычисляются
в `catalog-diff.json` и `coverage.json`, а не ограничены несколькими примерами.

Портальные ветви mobile-account, cc-web, wallboard, report-builder и отдельные
интерфейсы текстовых коммуникаций явно представлены в карте. Их нет как
отдельных строк исторического Product Layer; они распределены по существующим
Capability либо по новой report-builder. Это выявленные различия представлений,
а не утверждение, что продукты выпущены именно после мая.

**Deprecated:** подтверждённых оснований удалить исторический ID не найдено.
В API МангоДиалогов явно выделены восемь HTML-страниц устаревших методов:
https://www.mango-office.ru/support/5_api-i-razrabotka/3_api-mango-dialogi/8_ustarevshie_metody_api/

Они получают `documentation_lifecycle: deprecated-method`; для нового чтения
используется актуальная ветвь управления сессиями:
https://www.mango-office.ru/support/5_api-i-razrabotka/3_api-mango-dialogi/3_rukovodstvo_po_api/3_api_upravleniya_sessiyami/

HTML-ветка «Архив интеграций» помечается архивным расположением; оно не доказывает
снятие продукта с поддержки. Исторические «Не выявлено»/«Частично» не превращаются
в «нет продукта». Для каждого класса карта показывает число кандидатов и
curated additions. Ноль совпадений означает пробел обнаружения документации;
положительное число кандидатов ещё не закрывает пробел доказательств функции.
Все узлы сохраняют `availability: not-established-by-taxonomy`.

## Механизм маппинга и метрики

`products.json` содержит `nodes`: уникальный `id`, `level`, `parent_ids`,
`source_urls`, `origin`, `lifecycle`, необязательные `legacy_id`, `params` и
локатор. Родитель всегда на один уровень выше. Cross-domain — несколько
родителей Domain у Capability, коммерческие атрибуты — поля. Различающие
сегменты `/feature/` и `/function/` в ID не добавляют уровень.

В `portal-map.jsonl` одна статья связана с несколькими узлами:

- `taxonomy_matches.status=candidate`: регулярное правило по заголовку/URL,
  дающее только локатор Capability. `candidate_domains` вычисляется по родителям.
- `status=curated`: явно выбранный заголовок связывает Feature/Atomic Function.
  Одна страница может описывать несколько атомарных операций; один узел может
  иметь несколько источников. Находка статьи API не присваивает ей автоматически
  уровень Atomic Function. «Интеграции» — навигация к нескольким capabilities.
- `unmapped_reason`: явная причина отсутствия сопоставления; неизвестное
  не принуждается к ближайшему классу. Название приложения и `connector_id`
  сохраняются независимо от классификации.

| Поле | Смысл и использование |
| --- | --- |
| relevance_for_BA | FT/NFT/integrations, редакционная шкала 0–3; приоритет поиска, не измеренная точность и не доказательство ФТ |
| has_visual_context | Есть таблица, изображение или inline-диаграмма внутри статьи; меню исключено |
| is_llm_readable | Консервативный gate: извлечён текст, нет изображений/диаграмм и неоднозначных таблиц; false требует проверки/fallback |
| readability | text, text-and-tables, table-review-required, visual-review-required либо unreadable-or-unrecognized-template |
| update_frequency | unknown: одно наблюдение не позволяет измерить частоту; Last-Modified хранится отдельно; 30 дней — рекомендация повторного аудита |
| cross_product_links | Только фактически найденные ссылки тела статьи на другой продукт; отсутствие ссылки не доказывает отсутствие зависимости |
| observed_at/source_sha256 | Время и хэш HTML для проверки свежести и воспроизводимости |
| question_owner | Недоказанный As-Is → продуктовая команда/владелец документации; целевая потребность → заказчик |

Для изменения частоты нужны минимум две датированные версии и сравнение хэшей,
а для устойчивой оценки — ряд наблюдений. Приоритеты и алиасы настраиваются
редакционно; по ним нельзя вычислять продуктовые ограничения.
В снимке наблюдается 312 перекрёстных ссылок на 209 страницах. По умолчанию
планировщик не выбирает архивные/устаревшие страницы; такой поиск включается
явным словом «архив»/«устаревший»/legacy/deprecated в запросе.

## Как промптам искать знания

1. Сохранить исходное требование и все затронутые продукты. Выбрать ветвь
   Domain → Capability → Feature → Atomic Function; неизвестные связи оставить
   вопросом. Полнота каталога проверяется отдельно от выбора runtime-класса.
2. Использовать карту как индекс: фильтр продукта/коннектора, совпадения узлов,
   ФТ/НФТ/интеграции, HTTP и свежесть. Читать сначала несколько точных статей,
   затем смежные локаторы по зависимости. Путь URL и счётчик страниц не заменяют
   чтение источника.
   Сначала открыть малый `portal-index.json`, выбрать продукт и диапазоны строк
   `portal-map.jsonl` (нумерация с 1). Весь многомегабайтный снимок не помещается
   в рабочий prompt: планировщик возвращает до 12 статей, увеличивая предел
   только если число явно запрошенных продуктов больше. Диапазоны привязаны
   к SHA-256 карты; при обновлении индекса их нужно пересчитать.
3. Для `text`/простых `text-and-tables` использовать прямой HTML с цитатой URL,
   заголовка и строки/колонки. Сверить тип, обязательность, значения, примечания
   и версию; не обрезать исключения. При сомнении снизить confidence.
4. Для visual/table-review или HTTP gap сначала проверить адресный runtime
   fallback: README → MAP → выбранный класс → sections_map/index → несколько
   разделов. Соседний runtime-класс выбирает БА согласно действующим правилам.
   Публичное API, внутренние сессии, UI статусы и статусы Talker проверяются
   отдельно; CRM-коннектор должен совпадать с предметом вопроса.
5. Сверить web/runtime версии и записать конфликт. Если семантика изображения
   не описана текстом, нужен проверенный caption/OCR/ручное описание со ссылкой
   на исходный локатор. При недоступности сохранить gap и вопрос владельцу
   As-Is, не изобретать ограничение или архитектурное решение.
6. Завершить receipt: исходный scope, реально прочитанные URL/разделы/версии,
   доказанные факты, гипотезы, пробелы и владельцы. Это вход будущих BCREQ-шагов.

Runtime README действительно описывает извлечение изображений в `images/` и
ссылки из Markdown, но не обещает, что каждое изображение преобразовано
в эквивалентное текстовое описание:
https://github.com/G-Ivan-A/mango-ba-ai-runtime/blob/b67410f627801345309281faa15e7219722bfb1a/docs/kb/README.md

Карта документов с версиями и адресным порядком чтения:
https://github.com/G-Ivan-A/mango-ba-ai-runtime/blob/b67410f627801345309281faa15e7219722bfb1a/docs/kb/MAP.json

Поэтому обоснован гибрид: доступный статический web для свежих текстовых фактов,
runtime для адресной альтернативы и документных локаторов, дополнительная
проверенная предобработка для визуальных зависимостей. Нельзя объявить весь web
непригодным или runtime полностью устраняющим визуальную слепую зону.

`prepare_sources.py` ожидает локальные `classification.source.txt` из закреплённого
Hub URL и `chat-export-1131.source.json` из приложения issue. Получать приватные
источники следует через authenticated `gh api`/`curl`; файлы игнорируются git.
Публичные артефакты достаточны для offline rebuild/test без исходного чата и сети.
`audit.py --retry-errors` повторяет только недоступные/пустые ответы; для нового
временного снимка нужно отдельно сохранить старый кэш и очистить рабочий.

Регрессии сначала воспроизвели отсутствие реализации, затем проверили границы
обхода, отказ читать binary body, redirect, таблицы, четыре уровня, сохранение
всех исторических ключей/параметров, источники добавлений, полную карту снимка,
WFM/API охват, независимость коннекторов и явные gaps. Автоматические проверки
не симулируют продукт Mango и не оценивают следование реальной LLM.
