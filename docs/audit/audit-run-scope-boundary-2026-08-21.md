# Аудит границ задачи «фиксация прогона» (2026-08-21)

## Факты

### Ф-1. `site/data/` — производный артефакт, собираемый в CI

`.github/workflows/github-pages.yml:32` выполняет `node scripts/generate-pages-data.mjs`
на каждом деплое Pages. То есть содержимое `site/data/*.json` полностью
восстанавливается из `runs/`, `prompts/`, `kb/` и в коммите не нуждается:
закоммиченная версия — это кэш, который устаревает при любом изменении
источников и порождает конфликты слияния в параллельных ветках.

**Подтверждение:** при мерже `upstream/main` в ветку issue #270 из 15 конфликтов
8 (более половины) пришлись ровно на `site/data/*.json` — при том, что
содержательного вклада эти файлы в PR не вносили.

### Ф-2. Ни один контракт прямо не запрещал регенерацию `site/data/`

- `standards/runs-contract-standard.md` описывает **что должно быть внутри**
  `runs/YYYY/RUN-XXXX/`, но не описывает, чего задача на прогон **не должна
  касаться**. Раздела о границах в стандарте нет.
- Более того, DoD того же стандарта содержит пункт
  «`scripts/generate-pages-data.mjs` читает evidence из `runs/`» — формулировка,
  которую исполнитель прочитал как «новый прогон должен быть виден в данных
  сайта», то есть как **основание** для регенерации.
- `AI_GOVERNANCE.md` относит к «требует human review» изменение промптов,
  но `site/data/` в перечнях границ не упомянут вовсе.

### Ф-3. Правило нумерации не рассчитано на параллельные ветки

Стандарт определяет `RUN-XXXX` как «монотонный локальный идентификатор» и
требует совпадения `run_id` с именем каталога. Процедуры **резервирования**
номера при работе нескольких исполнителей одновременно нет. Способ, которым
исполнитель выбирает номер («следующий после максимального в `main`»),
детерминированно приводит к коллизии, когда параллельно открыто несколько задач
на прогон: PR #286, #287, #288, #289, #290 независимо выбрали `RUN-0013`.

### Ф-4. Валидатор фиксирует коллизию только постфактум

`scripts/validate_issue_123_runs_contract.py` требует **точного** совпадения
множества каталогов `runs/2026/RUN-*` со списком `EXPECTED_RUNS`. Это ловит
дубли на этапе мержа (что и произошло), но не помогает исполнителю выбрать
свободный номер в момент создания прогона — список в ветке отражает только
состояние `main` плюс собственный вклад.

## Пошаговый разбор: почему исполнитель решил, что регенерация входит в границы

1. **Онбординг дал команду сборки как часть рутины.** В репозитории
   регенерация `site/data` через `node scripts/generate-pages-data.mjs`
   присутствует как штатный шаг и повторяется в истории коммитов, поэтому была
   воспринята как «шаг завершения работы», а не как отдельный вид изменения.
2. **DoD контракта Run прочитан как требование (Ф-2).** Пункт про
   `generate-pages-data.mjs` в разделе «Критерии соответствия» стандарта Run
   создаёт прямую ассоциацию «новый Run ⇒ данные сайта должны его содержать».
3. **Отсутствие явного запрета (Ф-2).** Исполнитель искал ограничение, не нашёл
   его и применил дефолт «сделать состояние репозитория согласованным».
4. **Ложный сигнал «согласованности».** Так как файл закоммичен в репозиторий,
   несовпадение его содержимого с источниками выглядит как незавершённая
   работа — противоположная норма («это кэш, его не трогают») нигде не записана.
5. **Проверки не возражали.** Все 20 валидаторов проходят и с регенерацией, и
   без неё, поэтому обратной связи, что граница нарушена, исполнитель не получил.

Корневая причина — **не** ошибка суждения в конкретной задаче, а пробел в
контрактах: производный артефакт хранится в репозитории и при этом нигде не
помечен как производный, а стандарт Run описывает только содержимое прогона, но
не его границы.
