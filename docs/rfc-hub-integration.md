# RFC: перенос лучших практик из `mango_ba_prompts` в Хаб

> **Статус: Draft.** RFC выносится на решение фаундера
> ([AI_GOVERNANCE.md](../AI_GOVERNANCE.md)). До утверждения — предложение,
> не обязательное правило. Формат сознательно выбран **RFC, а не ADR**:
> перенос практик в Хаб — стратегическое governance-направление
> (по практике Хаба такие решения живут в `governance/rfc/`), а ADR в
> `docs/adr/` фиксируют локальные архитектурные решения спока.

## 1. Контекст

`mango_ba_prompts` — **тактическая база** автоматизации бизнес-анализа в
Mango: библиотека паттернов и промптов, организованная
[таксономией](taxonomy.md). Хаб
(`hybrid-Intelligence-lab`) — **стратегический дом** общих практик,
стандартов и исследований.

Сегодня существует только поток **Хаб → спок**: research-зависимости через
[docs/hub-research-dependencies.md](hub-research-dependencies.md) и
осознанная синхронизация стандартов (см.
[README.md](../README.md), раздел «Связь с Хабом»). Этот RFC фиксирует
обратный поток — **спок → Хаб**: как наработка, доказавшая ценность в
Mango, становится общей практикой Хаба.

## 2. Что считается практикой-кандидатом

- **Паттерны** из `patterns/` — воспроизводимые способы решения класса
  задач БА (см. [standards/pattern-standard.md](../standards/pattern-standard.md)).
- **Обобщённые промпты** — промпты `prompts/`, очищенные от
  Mango-специфики.
- **Стандарты и контракты** из `standards/`, полезные за пределами Mango
  (например, стандарт frontmatter промптов).
- **Workflow и шаблоны** — процессы фидбека, шаблоны issue, форматы
  фиксации тестов.

**Не переносится:** артефакты с корпоративной спецификой Mango
(внутренние термины без обобщения, закрытые данные), сырые эксперименты
из `prompts/experiments/`, архивные промпты.

## 3. Критерии переноса

Практика-кандидат должна удовлетворять всем критериям:

| ID | Критерий | Как проверяется |
| --- | --- | --- |
| C1 | **Повторная ценность.** Применена в ≥ 2 реальных задачах БА с зафиксированным результатом. | Записи в `prompts/experiments/` и/или issues `prompt:feedback` |
| C2 | **Обобщаемость.** Не содержит Mango-специфики, либо специфика отделена в параметры/контекст. | Review обобщённой версии |
| C3 | **Зрелость.** Прошла human review; для промптов — `status: canonical`. | Frontmatter, история PR |
| C4 | **Чистота данных.** Не содержит закрытых корпоративных данных и ссылок на закрытые документы. | Review перед публикацией |
| C5 | **Документированность.** Есть назначение, примеры и quality gates (для паттернов — все 8 полей). | Соответствие стандартам `standards/` |

## 4. Процесс переноса

1. **Номинация.** Любой участник создаёт в споке issue с label
   `hub-candidate`: что переносим, какие критерии C1–C5 уже выполнены.
2. **Подготовка.** AI-агент или contributor готовит обобщённую версию
   артефакта (без Mango-специфики) в PR спока; review подтверждает C1–C5.
3. **RFC в Хабе.** В Хабе создаётся RFC в `governance/rfc/`
   (для governance-практик) или issue по `issue-workflow` Хаба
   (для прикладных артефактов) со ссылкой на исходник в споке.
4. **Решение фаундера.** Принять / отклонить / доработать — финальное
   решение за человеком (правило 4 AI_GOVERNANCE Хаба).
5. **Перенос с provenance.** Артефакт размещается в Хабе с полями
   `source_spoke` + `source_sha` (permalink на коммит спока) — зеркально
   практике `source_hub`/`source_sha` при миграции из Хаба.
6. **Фиксация.** Перенос отражается в `CHANGELOG.md` обоих репозиториев;
   спок продолжает использовать свою локальную версию (источник истины
   для общей практики переходит к Хабу, синхронизация — осознанное
   действие, как для `standards/GLOSSARY.md`).

## 5. Роли

| Роль | Ответственность |
| --- | --- |
| Founder & PO | Финальное решение о переносе (шаг 4); приоритеты. |
| Human reviewer | Проверка критериев C1–C5 и чистоты данных (C4). |
| Contributor / AI agent | Номинация, подготовка обобщённой версии, черновики RFC. |
