# Итоговый артефакт раннего разбора — Многоканальная нагрузка агента

> **Что это.** Консолидация результатов цепочки промптов по сырому требованию из
> [issue #109](https://github.com/G-Ivan-A/mango_ba_prompts/issues/109). Это
> **ранний разбор**, а НЕ финальное ТЗ: нормализация + вопросы + US/UC + варианты
> (Раздел 3). Полная навигация — в [README кейса](./README.md).

## 1. Резюме для заказчика (одна страница)

- **Что просили:** единый механизм, позволяющий агенту вести одновременно максимум 3
  активных контакта из разных каналов (голос/чат/e-mail) с учётом приоритета
  голос > чат > e-mail.
- **Что есть в продукте сегодня:** лимит одновременных обращений настраивается, но
  **только для текста** (Ф3); очереди голоса и текста независимы (Ф2); кросс-канальная
  связь — это **один чекбокс** «не давать текст во время звонка» (Ф5); межканального
  приоритета каналов **нет** (Ф8). Источники — [`inputs/kb-files.md`](./inputs/kb-files.md).
- **Корневой разрыв (gap):** нет **единой межканальной модели загрузки агента** —
  общего счётчика активных контактов и сквозного приоритета каналов.
- **Куда двигаться:** 3 варианта (минимальный A / целевой B / компромисс C),
  предварительно — A как MVP с эволюцией в B; окончательно после ответов на ключевые
  вопросы В1/В3/В4/В5.

## 2. Нормализованная потребность

> Дать агенту вести одновременно ограниченное число активных обращений из разных
> каналов так, чтобы каналы реального времени (голос, затем чат) обслуживались раньше
> асинхронного e-mail, и чтобы суммарная нагрузка не превышала заданный порог (в
> требовании — 3).

Полная декомпозиция, 5 Whys и разведение «боль vs решение» —
[`steps/step-2-normalization.md`](./steps/step-2-normalization.md).

## 3. Ключевые вопросы заказчику (блокирующие)

| № | Вопрос (кратко) |
| --- | --- |
| В1 | Что считается «активным контактом» (удержанный звонок, спящий чат, неоткрытый e-mail)? |
| В3 | «Максимум 3» — жёсткий потолок или настраиваемый параметр; входит ли голос в счёт? |
| В4 | Приоритет — это порядок распределения, право прерывания или порядок в UI? |
| В5 | Что делать с входящим голосом при заполненном лимите? |

Полный список (В1–В12) с обоснованиями — [`steps/step-3-questions.md`](./steps/step-3-questions.md).

## 4. Модель потребности

- **User Story:** US-1 (единый лимит), US-2 (приоритет каналов), US-3 (поведение при
  полном лимите) — с INVEST и BDD-критериями.
- **Use Case UC-1:** актеры, предусловия, happy path, альтернативы, исключения (в т.ч.
  E1 «звонок при полном лимите» — в БЗ не описано).

Детали — [`steps/step-4-story.md`](./steps/step-4-story.md).

## 5. Варианты доработки (Раздел 3)

| Вариант | Суть | Сложность | Закрытие боли |
| --- | --- | --- | --- |
| **A** | Расширить текстовый лимит до единого счётчика + чекбокс-приоритет | низкая | частично |
| **B** | Единый диспетчер нагрузки с межканальным приоритетом | высокая | полно |
| **C** | Единый лимит + резерв слота под реальное время | средняя | в основном |

Плюсы/минусы/риски и матрица — [`steps/step-5-options.md`](./steps/step-5-options.md).

## 6. Рекомендация БА

1. Согласовать В1/В3/В4/В5 с заказчиком.
2. Принять **A как MVP** (опора на Ф3/Ф5, быстрая ценность) с дорожной картой к **B**.
3. После согласования — отдельный прогон на финальное ТЗ (Раздел 4/7): ФТ,
   ограничения, тех-дизайн (вне объёма issue #109).

## 7. Ограничения достоверности

- То, чего нет в документации, явно помечено «не найдено в документации» и вынесено в
