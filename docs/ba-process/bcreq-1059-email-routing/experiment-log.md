## Выявленные проблемы промптов

### Паттерн Э1: Путаница в архитектурных связках ЛК ↔ КЦ ↔ Редактор (критический)

LLM несколько раз путался в структуре компонентов: выдумывал несуществующий
механизм «выбор ящика в КЦ-Исходящие», смешивал настройки ЛК ВАТС и КЦ.

- **Корневая причина:** Промпт `glossary-context-understanding-stepwise` не запрашивает
  явно архитектурные компоненты системы на Шаге 0.
- **Повторяемость:** Тот же паттерн, что Б5/M1 в BCREQ-1025 и Б1/Б5 в
  эксперименте #1027 — **усиленный сигнал** (3 эксперимента подряд).
- **RFC:** RFC-1059-P1 (усиление RFC-1025-P1).

### Паттерн Э2: Нарушение иерархии ФТ

LLM генерировал 4-й уровень нумерации (`4.x.x.x`) вместо допустимых трёх
уровней; смешивал функции/режимы/настройки/исключения в структуре ФТ.

- **Корневая причина:** Промпт `fr-documentation-stepwise` не содержит явного
  правила «дерева решений» (Функция → Сценарий → Исключения).
- **Повторяемость:** Б2 из BCREQ-1025, Г3 из 1027.
- **RFC:** RFC-1059-P2.

### Паттерн Э3: Канцелярит на нижних уровнях иерархии

«Инициализировать значение атрибута» вместо «подставлять адрес»; громоздкие
обороты на уровнях 4.x.1 и 4.x.x.x.

- **Корневая причина:** Промпт не разделяет стилистику по уровням иерархии.
- **Повторяемость:** Б3 из BCREQ-1025, Г2 из 1027.
- **RFC:** RFC-1059-P3.

### Паттерн Э4: Путаница ролей

«Оператор» vs «Администратор» vs «Пользователь» — ошибки в приписывании
действий конкретным акторам.

- **Корневая причина:** Промпт `fr-documentation-stepwise` не запрашивает явную
  ролевую модель перед генерацией ФТ.
- **RFC:** RFC-1059-P4 (часть RFC-1025-P2).

### Паттерн Э5: Ложные обещания в Цели

Цель (2.2) обещала «выбор ящика в контексте обращения», но ФТ реализовали
через настройки КЦ, а не прямой выбор. Несоответствие обнаружено при ревью.

- **Корневая причина:** Промпт не верифицирует синхронизацию Цели и ФТ.
- **RFC:** RFC-1059-P6.

## Методологические инсайты

### M1 — Правило «дерева решений» для ФТ

```
Функция
↓
Сценарий
↓
Исключения
```

Вместо смешения функций/режимов/настроек/исключений в одной структуре ФТ.

### M2 — Правило разделения стилистики по уровням

- **4.x:** «Система должна [глагол] [объект] [при условии]» — строгий бизнес-формат
- **4.x.x:** Строгий бизнес-формат без канцелярита
- **4.x.x.x и ниже:** Короткий, без «при условии, что...», без канцелярских оборотов

### M3 — Правило системных vs пользовательских действий

- **Системные действия** (по триггеру/событию): без слова «возможность»
  (пример: «Система подставляет адрес...»)
- **Пользовательские действия** (инициируемые вручную): через
  «Обеспечение возможности...» (пример: «Система обеспечивает возможность оператору
  видеть...»)

### M4 — Правило переноса UI-ограничений

- UI-ограничения As-Is → в Раздел 6 «Ограничения», а не в ФТ
- Ролевая модель (если не меняется) → в Раздел 6 «Ограничения»

### M5 — Правило матрицы приоритетов

- Для сложных ФТ с несколькими условиями — формировать единую матрицу приоритетов
- Матрица является готовой инструкцией для QA и разработчиков

### M6 — Правило синхронизации Цели и ФТ

- Проверять, что Цель (Раздел 2.2) не обещает больше, чем реализуют ФТ (Раздел 4)
- Если ФТ реализуют через настройки — Цель должна это явно отражать
