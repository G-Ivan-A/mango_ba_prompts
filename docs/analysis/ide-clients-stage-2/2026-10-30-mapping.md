# Итерация 2: перенос контракта в клиента

Вход — принятое [сравнение](2026-10-30-comparison.md). Ниже **проект**
применения документированных функций. Он сохраняет
[состояние](../../contracts/bcreq-manual-state.md),
[гейты](../../contracts/bcreq-stage-gates.md),
[процесс](../../../standards/bcreq-process-standard.md) и все 39 стандартов.
Активные промпты, стандарты и полномочия этим исследованием не меняются.

## Слои доставки

1. **Постоянное ядро**: идентичность задачи, разделение правил и данных,
   статусы, запрет самосогласования, З1–З5, правила изменения состояния и
   остановки. Малое ядро всегда в правилах клиента. Оно требует прочитать
   полную конституцию и контракт перед работой; краткое ядро их не заменяет.
2. **Пакет класса**: purpose, inputs, outputs, algorithm, stops, context,
   checks из соответствующего стандарта. Загружается как native skill по
   имени `bcreq-cNN` (в файловом имени — нижний регистр). Skill не запускает
   другой skill сам и не даёт дополнительных прав инструментам.
3. **Рабочие данные**: сырьё, проверенные источники, baseline, slices,
   решения и вопросы в отдельном каталоге задачи. Текст документа/сайта,
   даже содержащий «ignore rules», остаётся данными. Его нельзя включать
   через механизм правил или помещать в глобальную memory.
4. **Receipt доставки**: список фактически прочитанных файлов, revision/SHA,
   версии конституции/shared/local/класса/стандартов, область и конфликт.
   Имя файла в списке доступных skills ещё не означает чтения его тела.

| Слой | Goose | OpenCode V1 | Cline |
| --- | --- | --- | --- |
| Ядро | Один проектный `.goosehints`; `@file` включает локальное тело. `AGENTS.md` тоже читается: проверить отсутствие противоречий (G02). | `AGENTS.md` + локальный `instructions` в `opencode.json`; произвольные `@` внутри правил не разворачиваются автоматически (O01, O05). | Один выбранный `.clinerules/` **или** `.cline/rules/`; проверить включённые global/AGENTS/legacy правила в UI (L01). |
| Пакет класса | `.agents/skills/bcreq-cNN/SKILL.md`, явный `/skills bcreq-cNN` (G03). | `.opencode/skills/bcreq-cNN/SKILL.md`, явное поручение загрузить через `skill` (O02). | `.cline/skills/bcreq-cNN/SKILL.md`, явный выбор доступного skill/slash (L02). |
| Чтение/запись | Developer editor Ask Before; shell Never Allow. Пооперационная граница read/write требует проверки фактического tool call (G04, G05). | `read`/`edit` по путям, `bash`/`task` deny, `external_directory` deny; reviewer с edit deny (O03, O04). | Plan для чтения, Act для согласованной записи; auto-approve выключен, команды отклоняются; запрет ОС нужен для жёсткой изоляции (L03, L04). |
| Проверяющий | Отдельная сессия, только замороженный кандидат, исходный manifest и источники; инструменты записи запрещены/отключены. | Отдельная сессия с reviewer-профилем, edit/bash deny. | Отдельная задача в Plan; без разрешений записи и исполнения. |

Ни один из вариантов не обеспечивает транзакционный state machine. При
ошибке модели запрос tool approval может отсутствовать для текстового ответа.
Значение `approved` поэтому проверяет человек по реальному журналу, а не
доверяет наличию JSON-поля. Формат native skill — транспорт инструкции,
а не гарантия соответствия бизнес-контракту.

## Файловое состояние и SLICE/FULL

Проектная структура внутри выделенной рабочей папки:

```text
rules/                       # проверенные полные правила, только чтение
tasks/<task>/
  request.md                 # сырой запрос, роли, исходный manifest
  sources/                   # разрешённые материалы + source_register
  baseline/r000/             # полный неизменяемый принятый снимок
  slices/r001.json            # полный текст изменённых сущностей
  candidates/r002/            # новый FULL + receipt, ещё draft
  decisions/                 # сообщения людей, роль/полномочия/локатор
  reviews/                   # замечания к конкретному frozen revision
  handoff.md                 # указатель на актуальный полный пакет
```

`handoff.md` — индекс, не замена полному пакету. Baseline нельзя переписывать;
новый кандидат создаётся отдельно, указатель меняется после проверки записи.
Один активный писатель на задачу: два чата не редактируют один candidate.
Git/diff помогает найти изменение, но SHA файла не удостоверяет роль человека.
Секреты и персональные данные в такой Git не помещаются.

| Переход | Действие агента | Проверка/стоп |
| --- | --- | --- |
| START | C36 читает тела правил; C01 получает raw; неизвестное `null`, проверенное отсутствие `[]`. | Нет raw — WAITING; нет обязательного совместимого rule bundle — C36 WAITING. Встроенный fallback старых промптов допускает лишь явно ограниченную независимую работу, не приёмку C36. |
| CONTINUE | Прочитать полный baseline и **всю** упорядоченную цепь slices одной задачи/фазы. | Разрыв parent_revision, чужая задача, неполное тело — WAITING с точным missing input; последняя реплика не baseline. |
| SLICE | `BCREQ_OUTPUT`, task/phase/class/revision/parent_revision/mode/status; upserts с полным текстом, conditions/source_ids/dependencies, tombstones с основанием и разрешением. | Не переиспользовать ID; не удалять молча; preserved_ids и stale_ids явны. Унаследованные вопросы не исчезают. |
| C12 FULL | Восстановить все живые сущности, разделы фазы, source_register, decisions, unresolved, exceptions и receipt.live_ids. | Каждое live ID имеет полное тело; ссылки, «без изменений» и summary не считаются FULL. Проверить отсутствие dangling dependencies. |
| Большой FULL | Разбить на именованные части с порядком, revision и общим перечнем частей. | INCOMPLETE, пока все части не сохранены и перечитаны. При малом контекстном окне сузить задачу/сменить модель; не выпускать усечённое как FULL. |
| Новая сессия/compaction | C13 перечитывает handoff, C36 — правила, C12 — актуальный пакет с диска. | Сверить revision и receipt; cached summary/Memory Bank не удостоверяют полноту. |
| Изменение | C29 строит impact по транзитивным зависимостям; C30 правит только authorized delta. | Все затронутые проверки/гейты stale. Повторное согласование или явное человеческое подтверждение применимости к новой ревизии; без молчаливого наследования. |

Это файловые действия штатного редактора клиента. В процессе БА нет Python,
shell-скрипта, фонового router, cron или внешнего бота. CI исследовательского
репозитория проверяет примеры отдельно и не участвует в выполнении BCREQ.

## Все 39 классов

Профиль **A** — автор: выбранный native skill + editor с согласованием;
**E** — источник: A + разрешённое чтение/approved read-only MCP;
**V** — проверяющий: отдельный read-only контекст;
**H** — отчёт и человеческое решение;
**K** — доставка/восстановление контекста;
**B** — пакетирование и baseline с человеческим выпуском.
Во всех трёх клиентах ID класса и его I/O неизменны. Различается транспорт
из таблицы слоёв, не смысл стандарта. Полная машиночитаемая таблица
[class-mapping.json](../../../experiments/issue_405/class-mapping.json)
сохраняет inputs, outputs, phases, behavior, stop, checks исходного каталога
и 117 клиентских отображений. Следующая таблица объясняет конкретное применение.

## Гейты и circuit breakers

| Граница | Как переносится | Что нельзя подменять |
| --- | --- | --- |
| CB-0.1 | Нет читаемого запроса Заказчика — C01 запрашивает raw и останавливается. | Анкета или догадка агента не заменяет raw. |
| CB-0.2 | Нет входа предыдущего шага — назвать недостающий артефакт; C13 восстанавливает контекст. | Не генерировать предшествующий результат задним числом. |
| CB-0.3 | Обязательный факт без источника, UNKNOWN лишает раздел смысла — остановить зависимый раздел, дать вопросы. | Заполнение типовым отраслевым значением не устраняет пробел. |
| CB-0.4 | Противоречие — C10 сохраняет обе цитаты и запрашивает решение владельца. | Более новая дата сама не выбирает правильный источник. |
| CB-0.5 | Требуется гейт/выбор человека — равноправные варианты и ожидание решения. | Техническое разрешение инструмента не бизнес-решение. |
| Г-IN | C20 показывает чек-лист разделов 1/2, scope, продукты/команды, вопросы; БА решает переход A-IN→A-CORE. | Кнопка Allow разрешает editor, а не бизнес-переход. |
| Г-С1 | C19 доказывает 100% покрытия ФТ UC; C20 собирает разделы 1–4, delta/новизну, оценку «от», отсутствие blockers; Заказчик решает A-CORE→A-WORK. | Фраза модели «согласовано» без реального сообщения Заказчика недействительна. |
| Г-W | Разделы 5–8, ФТ↔ОРР, Ш-В, риски с владельцами, итоговая оценка; ПО, архитектор продукта и руководитель КК по контракту. | Одно одобрение БА не заменяет требуемые роли. |
| G1/G2/G3 | Отдельные ID: структура уровней / owner-review рисков / утверждение и baselining. Сохраняются вместе со stage-gates. | Нельзя переименовать их в Г-IN/Г-С1/Г-W и потерять критерии. |
| A-RELEASE | C32→C33→реальный уполномоченный человек→C34→C35, по draft RFC. Пока орг-роль неизвестна, выпуск WAITING. | eligible_for_review и ready_for_human_release — рекомендации, не released. |
| Недостаток знаний, CB-0.6 | Нет подтверждённого факта/источника — UNKNOWN, запрос владельцу, блокируется зависимое утверждение. | Повтор генерации не создаёт evidence. |
| Чужой контекст, CB-0.7 | Исключить вход другой задачи без явного разрешения БА из доказательств, уточнить принадлежность до зависимого вывода. | Глобальная memory и поиск по всему диску не дают разрешения смешать задачи. |
| Сохранение, З2/C39 | До выдачи сверить полный новый результат с manifest и authorized delta, условия/отрицания/вопросы/единицы. | Валидный JSON или наличие всех заголовков не доказывают сохранение смысла. |
| Отсутствие прогресса | Receipt фиксирует новый evidence/decision/закрытый gap. При неизменном gap — назвать blocker и адресата; прекратить только зависимую ветку. | Не вводить общее «три попытки» и не путать с native OpenCode doom_loop. |
| Запрещённый инструмент | Права клиента отказывают; агент предлагает неисполняющий путь — ручной импорт/ответ без ФС. | Нельзя просить Python/shell как обязательную зависимость класса. |

Каждый class-specific stop остаётся в skill и таблице. Native permissions
останавливают инструмент; смысловой breaker задаётся инструкцией и проверяется
по receipt/человеком. Не заявляется hard enforcement для смыслового breaker.
Возврат в другую бизнес-фазу предлагает агент, выбирает БА; предыдущие разделы
не меняются без решения, последующие зависимые отмечаются stale, журнал 8.5
сохраняет причину, человека и точку входа.

## Автоприёмка и ручная проверка применения

`python3 scripts/validate_issue_405_ide_research.py --stage 2` проверяет
39/39 идентичностей, сохранность исходных I/O/stop/checks, адаптеры трёх клиентов,
инертность примеров, ссылки и конечные положительные/отрицательные fixtures
цепочки ревизий, stale и факторов. Применяется существующий офлайн reference
checker контракта; он не устанавливается БА и не становится оркестратором.

Для deployment обязательны наблюдаемые пробы в конкретной версии клиента:
отказ shell и внешнего пути, запрос на edit, загрузка тела skill, восстановление
после compaction, недействительное старое согласование и prompt injection
из источника. Здесь они заданы как критерии внедрения; выполнение моделей
и сертификация корпоративного контура не заявляются результатом исследования.
