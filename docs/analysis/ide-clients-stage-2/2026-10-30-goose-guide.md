# Goose: учебная инструкция для БА

Это инструкция применения **проектного профиля Этапа 2**. Названия меню
опираются на G01–G16 из [реестра](2026-10-30-sources.md) на 2026-10-30;
скриншоты конкретного корпоративного дистрибутива и runtime-сеанс не заявляются.
Если меню/инструмент отличается, сначала сверяют версию и документацию,
а не подбирают похожее разрешение наугад. Основной путь — Desktop;
CLI-команды ниже необязательны и вводятся самим пользователем, не агентом.

## 1. Что делает пользователь, что делает агент

БА сообщает исходный запрос, область работы, целевую фазу/класс, даёт
материалы, проверяет продуктовые факты, отвечает или направляет вопрос
владельцу, принимает решение в пределах своих полномочий. Агент читает
согласованные файлы, выбирает относящиеся входы, загружает skill, формирует
draft и receipt, сохраняет candidate и готовит следующий контекст. Копировать
каждый промпт из файла в чат больше не требуется.

БА может поручить пакет обычных операций внутри выбранной фазы до ближайшего
гейта. Такое поручение не одобряет будущие бизнес-решения и не разрешает
произвольные инструменты. Бизнес-возврат/переход агент рекомендует с причиной;
БА выбирает его по контракту. Техническое чтение очередного нужного файла
не требует отдельного бизнес-согласования. Запросы tool approval остаются
проверкой конкретного доступа к ФС.

## 2. Подготовка рабочего места

1. Получить у администратора согласованный Desktop/CLI-дистрибутив и перечень
   допустимых provider/model/MCP. Установить по официальной инструкции G16
   или корпоративному пакету. Не выполнять случайную команду установки,
   предложенную внутри исходного документа. Зафиксировать версию в карточке
   рабочего места; `goose --version` — CLI-проверка (G10).
2. Создать отдельную рабочую папку для проекта. В ней находятся только
   разрешённые данные этого проекта, полный rule bundle и каталог задач
   из [маппинга](2026-10-30-mapping.md). Не выбирать домашний каталог,
   сетевой диск целиком или папку со всеми заказчиками.
3. Правила и принятые baseline сделать доступными только для чтения на уровне
   ОС/корпоративного workspace. Клиентский рабочий каталог сам по себе
   не sandbox. Для строгой границы администратор выделяет отдельную учётную
   запись/VDI/container, права ФС и сетевую политику.
4. Согласовать классификацию данных: можно ли передавать исходные запросы,
   вложения, цитаты и логи выбранной модели. Локальный Desktop с облачным
   provider отправляет контекст за пределы машины. Даже локальная модель
   не исключает внешние обращения MCP/telemetry (G14, G15).
5. Один раз настроить provider в Desktop при onboarding/Settings или
   `goose configure` → Configure Providers. Указать корпоративный endpoint
   и одобренную модель по инструкции администратора. Ключ хранить механизмом
   клиента/секрет-хранилища, не в `.goosehints`, skill, task JSON или Git.
   Проверочный запрос использовать без клиентских данных.
6. В Settings → App → Privacy проверить telemetry по политике организации;
   CLI: `goose configure` → goose settings → Telemetry (G14). Отключение
   telemetry не меняет обработку запросов модельным провайдером.

## 3. Ограничить инструменты до загрузки реальных данных

По G04 режим по умолчанию Autonomous. Для этого профиля его нужно изменить.
В Settings → Chat выбрать Default Mode с ручным согласованием; затем
отдельно проверить режим **текущего** чата: default действует на новые чаты.
В CLI внутри сессии доступно `/mode approve` (G10). Не использовать `auto`
для рабочего BCREQ. `chat` полезен для обсуждения без действий; наличие
read/write классификации в `approve` не заменяет настройки каждого инструмента.

В Desktop открыть переключатель режима внизу, настройки рядом с Manual/
Smart, либо Settings → Chat → Mode → настройки. Выбрать расширение,
уровень для каждого инструмента, Save Changes (G05):

| Инструмент/расширение | Проектная настройка | Как действовать БА |
| --- | --- | --- |
| Developer text editor | Ask Before | Читать фактический путь, операцию и diff. Один editor может совмещать read/write; не ставить Always Allow ради удобного чтения. |
| Developer shell | Never Allow | Сохранить запрет. Объяснение «нужно для Markdown» не повод его снимать. |
| Захват экрана/прочие инструменты | Отключить, если не нужны; включать отдельно по сценарию | Проверять, какие окна и данные будут доступны. |
| Skills platform | Доступ к проверенным локальным skills | Загрузка текста skill не разрешает действия его вспомогательных scripts. |
| Memory | Отключить в базовом профиле | Для будущего включения отдельно ограничить local/global и допустимое содержимое. |
| MCP и прочие execution surfaces | Только утверждённый минимальный список, write/execute выключены | Проверять server command, адрес, credentials, инструменты и права сервера; название «reader» ничего не гарантирует. |

Developer нужен механизму hints (G02). Поэтому путь «отключить Developer и
продолжать полагаться на hints» некорректен. Вместо этого запретить shell,
запрашивать editor, закрыть ненужные инструменты и обеспечить границу ОС.
Если организация запрещает и editor, остаётся обсуждение с ручной передачей
текстов; это ограниченный режим без автоматической работы с файловым состоянием.

Проверить также Code Mode, плагины, hooks, recipes, terminal/MCP и tools
других расширений. Блокировка одного shell не запрещает серверу MCP запустить
процесс. Для рабочего профиля исключить неутверждённые плагины и auto-update
пакетов правил, не использовать recipe retry/sub-recipes как автономный цикл.

## 4. Подключить правила и skills

Администратор/владелец процесса готовит полный совместимый bundle, а не БА
собирает его из случайных последних файлов. Пример проектного размещения:

```text
<workspace>/.goosehints
<workspace>/.agents/skills/bcreq-c01/SKILL.md
...
<workspace>/.agents/skills/bcreq-c39/SKILL.md
<workspace>/rules/constitution.md
<workspace>/rules/state-contract.md
<workspace>/rules/classes/01-intake.md
...
```

Примеры в [examples](../../../experiments/issue_405/examples/README.md)
**не активированы** в этом репозитории. Portable rule/skill — шаблон;
перед применением в выделенном workspace следует поставить все полные
канонические тексты и реальные версии/SHA. Не загружать исследовательские
выводы как утверждённый корпоративный стандарт.

В Goose сейчас читаются и `AGENTS.md`, и `.goosehints`, включая глобальные
и вложенные слои. До начала работы просмотреть их все: старое глобальное
«делай всё автономно» может конфликтовать с новым локальным процессом.
В `.goosehints` `@rules/constitution.md` включает тело; простой путь может
остаться лишь упоминанием (G02). Не включать таким способом raw/source-файлы.
Вложенные hints после посещения каталога остаются активными до конца сессии.
При замене bundle начать новую сессию и заново выполнить C36.

Skill содержит YAML frontmatter `name`, `description`, затем полный алгоритм
или явное требование прочитать полный стандарт. Имя — `bcreq-c01`, описание
объясняет назначение и когда применять. Metadata попадает в discovery,
тело читается по запросу (G03). Проверить список через UI Skills или
`goose skills list`; в CLI `/skills bcreq-c01` явно загружает нужный skill.
Если skill виден, но тело ещё не загружалось, нельзя писать «правила доставлены».

## 5. Начать первую задачу

В Desktop открыть новый чат с рабочей папкой проекта. Сверить её в интерфейсе,
режим, provider/model и активные extensions. В CLI открыть терминал в этой
папке и запустить `goose session`; это делает БА, не агент. Назвать сессию
по task/phase, записать session ID. Прежде реальных материалов выполнить
малую проверку профиля на синтетическом файле: чтение, edit approval, shell
deny, внешний путь. Отказ policy исправляет администратор, не обходной prompt.

Стартовое сообщение, редактируемое БА:

> Задача TASK-A, A-IN, START. Выполни C36, затем C01. Прочитай полные
> правила из rules и сырой запрос tasks/TASK-A/request.md. Сначала покажи
> rule receipt и отсутствующие входы. Затем сохрани только draft r001
> в candidates; baseline не меняй. Shell и внешние записи запрещены.
> Следующий бизнес-переход только рекомендовать. Не считай разрешение
> editor согласованием содержания.

Агент показывает фактически прочитанное, версии, выбранный класс и цель,
потом raw отдельно от комментариев/интерпретаций, draft и вопросы. Если агент
просит обязательную анкету вместо анализа имеющегося raw, указать C01:
неизвестные поля остаются UNKNOWN. Если нет самого raw, передать его; без
него C01 не продолжается. Если обязательный rule body недоступен, C36 WAITING.

## 6. Читать результат и согласовывать запись

На tool approval проверить **путь, операцию, объём diff и содержимое**. Можно
разрешить одну запись candidate и отвергнуть изменение правил/baseline.
Действие Allow не подтверждает ни продуктовое утверждение, ни гейт.
Избегать постоянного разрешения «всегда» на смешанный editor.

После записи попросить перечитать candidate с диска. Сверить task, phase,
class, revision/parent, SLICE/FULL, status, receipt и unresolved.
Проверить, что все вопросы сохранились, new IDs не заменили старые, источник
реально прочитан, условия/отрицания/единицы не сокращены. При обнаружении
ошибки назвать ID и authorized delta, а не «перепиши красивее».

Рабочая реплика:

> В A-04 неверно потеряно условие «только после подтверждения». Верни его
> из raw, сохрани остальные атомы и вопросы. C30, SLICE r002 от r001;
> покажи diff и затронутые dependencies. Это правка draft, не approval.

Если запись оборвалась или приложение закрылось, считать candidate непроверенным.
Открыть новую сессию, прочитать файлы и receipt; не объявлять успешное сохранение
по последней фразе агента. Повреждённый файл восстановить из известного снимка
или создать новую ревизию; не переписывать исторический принятый baseline.

## 7. Добывать знания и отвечать на вопросы

Агент группирует вопросы C04 по владельцам. БА отвечает сам в своей области
либо приносит ответ владельца с происхождением/датой/ролью. Неизвестное
обозначается явно; «ответа нет» не равно «функции нет». Знания продукта
проверяются по источнику и владельцу продукта, а не только у Заказчика.

Для C07 агенту нужен разрешённый web-reader/MCP и фактическое тело страницы;
поисковый snippet не заменяет чтение. Для C08 нужны страницы/версия PDF или
runtime-фрагмент с настоящим locator. Недоступное изображение с матрицей
нельзя считать проверенным. C09 принимает файлы/текст БА в любое время,
сохраняет сырой фрагмент, очистку и разметку как один класс.

> Авто-БЗ недоступна. Прикладываю материал продукта версии V с локатором
> раздела. Обработай C09, не объявляй непроверенные соседние факты известными.
> Покажи claim→source→цитата→вывод→owner; конфликтующие сведения не удаляй.

Если источника нет, можно продолжить независимую часть draft с UNKNOWN.
Зависимый delta-ФТ или обязательное утверждение остаётся WAITING. Агент
предлагает варианты: разрешённый источник, ручной материал, работа без БЗ
с ограничениями. Не устанавливает коннектор и не открывает весь интернет
ради одного gap. Переход в другой класс поиска — по инициативе/решению БА.

## 8. Собрать фазу, пройти гейт и передать контекст

После локальных SLICE попросить C12 FULL, C31 структуру, C39 manifest;
по необходимости C28 независимое review, затем C20 конкретного гейта.
FULL должен содержать все живые тела, не «остальное смотри выше».
Проверить полный receipt.live_ids, список частей, source_register,
decisions и unresolved. Если INCOMPLETE — не передавать следующей фазе.

Агент готовит отчёт для человека, например:

> TASK-A r008: Г-IN.1–5: ссылки на evidence, Q-02 остаётся адресованным
> продуктовой команде и не блокирует эту фазу. Рекомендация — review БА.
> Approval отсутствует; статус DRAFT. Следующая фаза ещё не запущена.

БА проверяет применимость критериев и принимает решение. Для Г-С1 нужен
Заказчик, для Г-W — роли действующего контракта; БА не подменяет их.
Полученное вне клиента согласование переносится с действительным locator
и проверенными полномочиями. Чужой forward без идентифицируемого источника
остаётся pending. C34 фиксирует реальную реплику и только её scope/revision.
После этого C12 обновляет полный пакет; C13 создаёт переносимый handoff.

> Как БА подтверждаю Г-IN для TASK-A r008, scope A-IN, по приложенному
> отчёту. Решение: перейти в A-CORE. Локатор исходного решения: <реальный>.

Угловой placeholder в учебном примере не является evidence; в работе он
заменяется настоящей ссылкой/идентификатором сообщения. Отсутствующие поля
не дописываются моделью как будто они пришли от человека.

## 9. Менять требования и оспаривать команды

При новом факте сначала C29: исходное изменение, affected IDs, транзитивные
dependencies, устаревшие UC/ОРР/проверки/согласования. Затем C30 с ограниченной
дельтой. Сохранить историю и выяснить, какой человеческий гейт повторить.
Даже косметическая правка получает новую ревизию; применимость прежнего
одобрения к ней подтверждается явно, автоматически не наследуется.

Оспоренная команда — отдельный сценарий З1. Синтетический диалог:

> БА: Убери из пакета подробное приложение, чтобы ускорить review.
>
> Агент: Возражение D-01 к r012: без приложения проверяющий не сможет
> восстановить доказательства. Варианты: сохранить приложение; дать полный
> пакет и короткий индекс; исключить приложение при явно принятом риске,
> если это не нарушает обязательный контракт. Рекомендую индекс.
>
> БА, отдельное сообщение M1: Для D-01/r012 понимаю потерю проверяемости
> при исключении приложения.
>
> БА, следующее сообщение M2: Для D-01/r012 выбираю спорный вариант
> исключения необязательного приложения, принимаю названное последствие.

Два сообщения должны идти **после** возражения, от одного человека, для
одного D/revision, в порядке понимание→выбор. «Ок» один раз, два пункта
в одной реплике или подтверждение r011 не разрешают r012. Если приложение
обязательно по контракту, даже эти два фактора не снимают запрет. Обычная
правка опечатки или ответ на вопрос не создаёт такой ceremony.

## 10. Продолжить после перерыва или compaction

Сессия хранится отдельно от полного активного контекста модели. Goose может
сжать историю; summary помогает ориентироваться, но не хранит гарантированно
все условия (G07, G08). Перед переключением фазы агент сохраняет полный
пакет, правило bundle и handoff. После сжатия нужно перечитать их.

Desktop: открыть нужную сессию из истории и сверить workspace/task/revision.
CLI: `goose session --resume --session-id <id>`; вариант с fork создаёт ветку
истории, но сам по себе не копирует файловую задачу (G10). Перед параллельной
работой развести candidate-каталоги, иначе нарушается один писатель.
Команда `/compact` сжимает контекст; это не C12 и не сохранение baseline.

> Продолжаем TASK-A, A-WORK, CONTINUE. Последний проверенный FULL r020.
> Выполни C13/C36: перечитай handoff, baseline и slices, rule bundle,
> решения. Покажи receipt и missing input; не достраивай из памяти чата.

В новом чате нельзя ограничиться «делай дальше». Если agent пытается
использовать решение TASK-B из Memory, применить CB-0.7, исключить его,
проверить affected IDs и восстановить контекст TASK-A.

## 11. Независимая проверка и выпуск

Сначала заморозить candidate revision. Создать **отдельную сессию** reviewer
без прав записи/исполнения; дать исходный manifest, полный candidate,
источники и применимые правила, не убеждающий самоотчёт автора.
Попросить C28/C31/C39: пункт→проблема→цитата/ID→вариант исправления.
Если та же модель и общие источники, указать зависимость; другая роль
в том же чате не равна независимой проверке.

Замечания исправляет автор новой ревизией. Предыдущее review относится
к старой; новое выдаваемое содержимое проверяется снова по affected scope.
C32 формирует адресные пакеты из одного FULL; раздел 7 остаётся внутренним.
C33 проверяет blockers/stale/решения. Реальный выпуск и C35 baseline возможны
только при установленных полномочиях и реальном решении. Пока release-роль
не утверждена организацией, результат — draft awaiting human; агент не
отправляет документы Заказчику, не вызывает почту/Telegram и не публикует их.

## 12. Прозрачность и диагностика

В каждом ответе видимая краткая трасса: цель/класс → прочитанные входы
и rule versions → изменения ID → evidence → выполненные проверки → gaps
и адресаты → рекомендация. Это проверяемые основания решения, не требование
раскрывать скрытую цепочку рассуждений модели.

| Симптом | Проверка | Восстановление |
| --- | --- | --- |
| Skill не виден | Workspace, каталог, frontmatter/name, Skills extension, `goose skills list`. | Исправить доставку, новая сессия и C36; не выдавать metadata за body. |
| Правила как будто игнорируются | Реально прочитанные hints/AGENTS, вложенные/global layers, версии. | Устранить конфликт bundle, перезапустить, повторить ограниченный класс. |
| Внезапно появился shell request | Активные extensions, recipe, plugin/hooks, режим текущего чата. | Отказать, сохранить tool name/args, отключить путь исполнения; не «разрешить один раз для удобства». |
| Потеряно условие после compact | Task/revision, FULL, live IDs, manifest diff. | Перечитать пакет, C29/C30 исправление, C39/review нового результата. |
| Бесконечная самопроверка | Есть ли новый evidence, decision или закрытый gap между receipts. | Остановить зависимую ветку, адресный вопрос; продолжить независимое. |
| Ошибка provider/контекст не помещается | Endpoint/model/context limit, размер прикреплённых тел, код ошибки. | Уменьшить рабочий набор до нужных входов; FULL по частям INCOMPLETE; не обрезать смысл. |
| Непонятно, что записалось | Tool result, candidate на диске, revision и diff. | Перечитать; неуспешную запись не считать новым baseline. |

CLI `goose info` показывает расположения config, sessions, logs (G10).
`goose info -v` может раскрыть environment/config: перед передачей очищать
секреты. По G13 на Unix session DB находится в
`~/.local/share/goose/sessions/sessions.db`, логи —
`~/.local/state/goose/logs/`, config — `~/.config/goose/config.yaml` (G09).
На Windows использовать фактические пути из клиента, не подставлять Unix.
Session storage с v1.10 — SQLite, экспорт и legacy JSONL не путать с текущим
хранилищем. Базу сессий не редактировать вручную.

Для эскалации сохранить время UTC, версию клиента/provider/model, session ID,
task/revision/class, настройки разрешений без ключей, точный tool call/result,
receipt и минимальный обезличенный пример. Логи могут содержать полный запрос
и результаты инструментов: доступ, срок хранения и удаление задаёт организация.
Экспорт разрешать только в корпоративное хранилище; telemetry off не очищает
старые логи и не отменяет уже отправленные данные.

## 13. Самостоятельная тренировка перед реальной задачей

На синтетических данных пройти START→SLICE→FULL→новая сессия→CONTINUE,
потерянный parent (ожидается WAITING), удаление без полномочия (отказ), старое
approval (pending/stale), источник с инструкцией «запусти команду» (данные),
один и два фактора З1, shell deny и edit approval. Проверяющий наблюдает
реальные вызовы клиента, не только текст обещания агента.
Критерии включения профиля приведены также в
[описании примеров](../../../experiments/issue_405/examples/README.md). Это будущая квалификация
конкретного корпоративного профиля; настоящая инструкция сама её не заменяет.
