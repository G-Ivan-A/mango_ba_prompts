# IDE-клиент и концептуальная модель БА

Основание — [закреплённый срез Хаба](../../hub-research-dependencies.md#ide-stage-2):
research/ba-requirements, факты о M0–M2, гранулярности и текущие определения
модуля ba-meta-model (`00`, `10`, `20`). Это **применение к Mango**, без
копирования общей теории или изменения канона Хаба. Вход — принятые итерации
1/2. Клиент меняет исполнение и поставку контекста, а не предмет требований.

## Какие сущности сохраняются

Следующая таблица — наша прикладная проекция 11 сущностей. Определения и
версии берутся в Хабе, локальные C-ID — в контракте спока.

| Сущность | Проекция на Этап 2 | Что нужно различать |
| --- | --- | --- |
| Product | C05 задаёт продуктовую принадлежность по версии Domain→Capability→Feature→Atomic Function. | Продуктовая принадлежность не определяется по случайным словам готового текста. |
| System | В task config явно указана изменяемая система/компонент. | Goose/OpenCode/Cline — среда исполнения анализа, не целевая система ФТ. |
| Artifact | Raw, source register, атомы, ядро, разделы, вопросы, FULL/SLICE, review, пакет и baseline с revision. | Сообщение чата, версия содержимого и класс документа — разные идентичности; draft — состояние. |
| Operation | Внутри класса — атомарная работа определённого типа и контракта результата. | Чтение файла/нажатие Allow само по себе не полноценная когнитивная операция; число tools не число операций. |
| Skill | Контракт работы упакован в native SKILL.md выбранного клиента. Возможны операция или подпроцесс. | Концептуальный уровень определяется I/O/ветвлением/гейтом, не именем файла. Формат поставки не устанавливает онтологический уровень. |
| Process | Достижение целевого класса артефакта через работу и контроль. | A-IN/A-CORE/A-WORK/A-RELEASE спока — фазовая организация, не автоматический новый словарь процессов Хаба. |
| Route | Допустимые переходы, альтернативы C16/C17, возвраты, Fast Track и реально выбранный путь БА. | Recipe/список skills не является исполняемым графом с гарантированными переходами. |
| Actor | Человек-БА, Заказчик, профильный владелец, агент-автор, reviewer; программа — только там, где реально проверяет. | Роль действующего лица требования и роль исполнителя анализа указываются раздельно. Модель не становится human actor. |
| Gate | Событие проверки конкретного контракта к конкретной ревизии; self/machine/human с явным executor. | Native tool permission — контроль доступа. Human gate — решение о результате; модельная самопроверка его не заменяет. |
| Contract | Версионированные I/O, инварианты, полнота, evidence, scope и критерии конкретного стандарта. | Сам контракт не событие согласования и не его результат; один контракт проверяется неоднократно. |
| Trace | Вход→работа→actor→gate→выход плюс источники, revision и реальные решения. | Tool log полезен, но не покрывает смысл, ownership и полномочия без дополнительных records. |

Введение Хаба описывает Skill как самостоятельный подпроцесс; актуальная
теория дополнительно уточняет SB-6: skill также является формой поставки
операции или подпроцесса. Исследование гранулярности объясняет, почему размер
SKILL.md не критерий атомарности. Эти слои читаются вместе: не навязываем
формулу «один класс = одна операция = один conceptual skill» и не выдаём
старое определение за единственное актуальное.

## Отображение 39 классов без потери уровня

Текущий срез Хаба использует пять когнитивных семейств и 31 операцию,
а процессная таксономия — L0/L1 и локальные L2/L3. Исторические 13 операций
и 9 процессов спока имеют там статус deprecated. Это факт источника, не
разрешение этим PR переписать действующий `docs/taxonomy.md`. Числа 31,
33 навыка L3 и 39 локальных классов относятся к разным множествам.

Проектное соответствие ниже покрывает все C-ID; семейства — аналитические
теги, **не присвоение новых имён операций закрытого словаря Хаба**.
Канонический operation-ID можно назначать только после сверки его полного
контракта и границы результата. Native packages уже определены для всех 39
классов независимо от такого назначения.

| Группа классов | Когнитивная работа и артефакт | Концептуальная граница |
| --- | --- | --- |
| C01, C02, C05 | extract/transform: raw, атомы, продуктовая принадлежность. | Кандидаты на операции при одном завершённом выходе; intake с проверкой и вопросом может быть пакетом. |
| C03, C04, C06 | assess/generate/check: неоднозначности, вопросы, scope. | C04 упаковка вопросов не равна внешней отправке; выбор человеком — отдельный gate. |
| C07, C08, C09, C10, C11 | extract/check/assess: источники, конфликты, недостающие зависимости. | C09 явно объединяет извлечение, очистку, разметку; не объявлять её атомарной только из-за одного C-ID. |
| C12, C13, C36 | transform/check: FULL, перенос контекста, доставка правил. | Контекстные пакеты/подпроцессы с проверкой предпосылок; не новые документы требований сами по себе. |
| C14, C15, C16, C17, C18, C19 | generate/transform/check: термины, контекст, ФТ, НФТ, первый UC. | C16/C17 — варианты основания delta/new, не отдельные режимные онтологии; проверки и human gate не исчезают. |
| C20, C34 | assess/check/record: отчёт гейта, record фактического решения. | Готовить evidence может агент; исполнить G-human может только человек. Record не генерирует отсутствующее решение. |
| C21, C22, C23, C24, C25, C26, C27 | generate/assess/check: ОРР, ограничения, второй UC, риски, поставка, приёмка. | Несколько продуктов не создают несколько копий операции. L1/L2 и источники — параметры/предусловия. |
| C28, C31, C33, C39 | check/assess: содержательный review, структура, выпускной audit, fidelity. | Разные контракты проверки; объединение их в одну кнопку скрывает виды ошибок. |
| C29, C30 | assess/transform: impact и адресная дельта. | Изменение Trace-информированное, stale распространяется на зависимое, а не только на изменённый файл. |
| C32, C35 | transform/check: адресные пакеты и immutable baseline. | Пакетирование не отправка и не выпуск; human решение — отдельное событие. |
| C37, C38 | generate/transform: дополнительные US и самостоятельный UC. | Только по явному запросу; не смешивать с обязательными C19/C24. |

В машинной приёмке проверяется точное покрытие всех 39 ID этой таблицей.
Назначение полного нового словаря операций не требуется для сравнения IDE
и не изображается выполненным. Обнаруженное расхождение модели и наследия
зафиксировано, а работа клиента не зависит от неверного 1:1 соответствия.

## Слои M0–M2 и трассировка

Прикладная интерпретация источника: M0 обеспечивает достоверный вход и
происхождение, M1 — смысловое ядро требований/решений, M2 — форму документа
для адресата. Это роли преобразования, а не обязательный линейный маршрут
«сначала ФТ, потом ТЗ». Возвраты за доказательствами допустимы из любой фазы.
Слой процесса, формат документа и настройки клиента — независимые оси.

| Слой | Реализация в файлах и классах | Проверяемый инвариант |
| --- | --- | --- |
| M0 | Raw, source_register, C01–C11 и ручные дополнения C09. | Raw не перезаписан интерпретацией, provenance/роль/версия/locator доступны, gaps не выданы за факты. |
| M1 | Атомы, решения, ФТ/НФТ, UC/ОРР, зависимости и impact C14–C30. | Одна смысловая сущность имеет стабильный ID, conditions/source/dependencies; конфликт/UNKNOWN сохранён. |
| M2 | C12/C31/C32/C35: полные фазовые снимки, восемь разделов, адресные пакеты и baseline. | Проекция не меняет утверждения ядра; внутренний UC раздел 7 остаётся во внутреннем FULL. |
| Сквозной контроль | C13/C20/C28/C29/C34/C36/C39 и receipts. | Вход/выход, версии, исполнитель, проверка, реальное решение человека и stale связаны, даже после смены клиента. |

Пример trace без привязки к историческому кейсу:

```text
raw S-01 §2 → atom A-01 → C16 / actor=agent → FR-01 r003
  source=S-02 §4, owner=product-team, conditions=[confirmed]
  → C19 / UC-01 covers FR-01
  → C20 / Г-С1 report r005 → human customer message M-07
  → C34 decision(scope=Г-С1, task=TASK-A, revision=r005)
  → новый факт S-03 → C29: FR-01, UC-01, review, Г-С1 stale
```

Полный candidate и сообщение M-07 нужны в реальной задаче; учебная строка
не является источником или действительным согласованием. Provider/model и
tool trace добавляются к исполнению, но не заменяют содержательный Trace.

## Как мета-модель может эволюционировать после ручного этапа

1. **Сохранить обнаруженное различие единиц.** C-ID обозначает локальный
   класс работы с I/O, native skill — пакет доставки, conceptual operation/
   subprocess определяется контрактом. В crosswalk хранить все три ID и версии,
   разрешать one-to-many/many-to-one. Не удалять классы ради красивого числа.
2. **Сделать ревизию и применимость решения явными.** FULL/SLICE — формы
   транспорта Artifact, не новые сущности онтологии. Добавить к trace-граням
   parent_revision, scope, source_versions, authority и состояние stale.
   Не смешивать stale отдельного объекта со статусом всей задачи.
3. **Отделить поставку от доказательства.** Receipt правила фиксирует чтение;
   receipt инструмента — действие; evidence связывает утверждение с основанием;
   human record — решение. Один общий «успешно» стирает разные обязательства.
4. **Сохранить человеческий route при смене исполнителя.** Автоматическое
   чтение/сохранение не создаёт права пройти гейт. Fast Track использует
   готовые полные результаты и действительные решения, а не пропускает их.
5. **Мигрировать через совместимость, а не замену задним числом.** Новый
   versioned crosswalk и draft ADR сверяются с каноном Хаба владельцем модели;
   исторические prompt/runs сохраняются. В рабочем bundle запрещено молча
   смешать старую и новую taxonomy. При несовместимости C36 WAITING.

Наблюдения ручного этапа — основание уточнять концепцию, а не ограничение
теории навсегда. Одновременно источник Хаба не объявляется утверждённой
корпоративной нормой только потому, что он новее. В этом PR применяется
совместимый контракт спока и регистрируется аргументированная проекция.

## Что измерять при практическом применении

До/после сравнивать на одинаковых raw, правилах, модели и критериях: потеря
обязательных условий/отрицаний; факты без достаточного evidence; ложные
human approvals; восстановление FULL; число повторов без прогресса; действия
БА и время review. Раздельно учитывать class coverage, структурные ошибки
и смысловые ошибки. Нужны знаменатель задач/сценариев и слепое содержательное
review. Число вызванных skills, успешный CI или доля заполненных заголовков
не доказывают улучшение качества требований.

Это критерии оценки предлагаемой модели. Статистические выигрыши, автономная
безопасность и успешность работы конкретной LLM здесь не заявляются.
