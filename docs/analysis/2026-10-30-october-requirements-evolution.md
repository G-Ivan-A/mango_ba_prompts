Это анализ текста переходов, не диагноз внутренней работы модели и не статистика частоты ошибок.

Исходные сообщения читаются по последовательности с разделением реплик Фаундера и ассистента. В TXT нет надёжных UTC-меток и машиночитаемой атрибуции каждого сообщения; локальная последовательность доказуема, точное время каждой реплики — нет. Маркеры «Завершено размышление» не являются доступом к внутреннему рассуждению. Авторство коротких реплик определяется по контексту диалога, подтверждается последующей первичной постановкой; неоднозначность нельзя разрешить статистической догадкой.

Для каждого утверждения отделены: исходное намерение → извлечённое требование → предложение ассистента → ответ/коррекция → опубликованный артефакт → проверка. APPROVED относится к явно поставленному требованию в его области; не ко всему последующему проектному решению. Более поздний текст не отменяет старый автоматически. Полная цепь source IDs для отсутствующего JSON остаётся открытой.

## Что означает смена «ФТ/ТЗ» на фазовую модель

Уточнение EV-09 задаёт актуальное направление, но не означает удаления функции проверки требований. Старые формирование/валидация ФТ/ТЗ в активной навигации больше не должны представляться общей архитектурой проекта. Валидация становится обязанностью операций и gates над артефактами, с возвратами и проверками по мере изменения состояния. Исторические названия в статистике остаются прежними.

| Понятие | Локальная эволюция / сравнение с EV-10–EV-12 | Вывод для будущей актуализации |
| --- | --- | --- |
| A-IN | Сырой вход и контекст, а не готовое требование. Уже есть в локальном stage-gates и в четырёхфазном проекте. | Сохранять source/roles/unknowns до нормализации; не требовать от сырого текста качества A-CORE. |

Контроль выявил существенное несовпадение версий: старый https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/c105323322d7e3a0450199db28071ea21fa9404d/docs/ba-meta-model-overview.md называет Skill реализацией Operation, а EV-10 выделяет Skill отдельно. Использовать только overview было бы недостаточно. Выбор опорного модуля обусловлен его объявленной canonical-ролью и явным определением, а не просто более поздней датой. Область draft/accepted и адаптация к библиотеке сохраняются в compliance matrix; автоматического обновления локальных контрактов нет.

## Универсальные рекомендации и проверяемый цикл обратной связи

В начале каждого задания фиксировать тип результата и абсолютные границы отдельно от архитектурных идей. При передаче намерения сохранять атомарные обязанности, происхождение, оговорки и негативные ограничения; явное «услышал» не считается исполнением.

Каждый цикл: источник/версия → атомарная норма → место в методологии → архитектурная обязанность → рабочий prompt/rule/template → доступный execution trace → проверка с oracle → замечание владельца → адресная правка и повторная проверка затронутых связей. Если звена нет, отмечать gap, а не достраивать по памяти. Для результата LLM нужен семантический тест, для неизменности данных — сравнение blobs, для полномочия — решение человека.

После получения приоритетного JSON требуется отдельно проверить структуру экспорта, даты/часовой пояс, роли, вложения и связи ветвей; присвоить message IDs и source hashes; выделить все октябрьские реплики Фаундера; сравнить каждую с исходной постановкой и последующим артефактом; расширить AR/FM, включая случаи **сохранённых** требований как контрольную группу. До этого нельзя обобщать частоту и полноту потерь на весь месяц. Обновляются только аналитические результаты и RFC; исторические данные остаются прежними.
