# Эволюция требований к mango_ba_prompts: май — октябрь 2026

Ответ на задачу [issue #409](https://github.com/G-Ivan-A/mango_ba_prompts/issues/409)
«проанализировать эволюцию требований пользователя к проекту». Первоисточник,
указанный в issue, — **история задач**: 197 issues (#1–#409) этого репозитория
плюс решения Хаба и соседнего runtime, которые меняли рамку проекта. Документ
расширяет [октябрьский анализ #407](2026-10-30-october-requirements-evolution.md)
на всю историю и не заменяет его: там разобраны механизмы потери намерения
внутри октябрьского диалога, здесь — траектория требований целиком.

## Результат

1. **Требования сменили предмет пять раз**: библиотека промптов → набор
   стандартов и онтологии → корпус прогонов → «приватная операционка без
   серверов» (#263) → **фазовый конвейер BCREQ с сайтом как каналом
   этапа 1 и четырёхэтапной автоматизацией** (#384–#409). Каждый поворот
   оставлял артефакты прежнего предмета активными, потому что механизма
   депрекации не было (см. [реестр диспозиции](2026-10-31-file-disposition-register.md)).
2. **Текущая постановка противоречит трём ранее зафиксированным решениям**,
   и все три — действующие тексты: границы #263 (заперты валидатором),
   статус `legacy/archived` Хаба (#583 Хаба) и модель двух репозиториев
   ADR-009 Хаба. Противоречия не снимаются молча: они вынесены в реестр
   ниже с вариантами апелляции.
3. **Вектор «по мета-модели» совместим** с четырьмя этапами: этапы 2–4 —
   это смена исполнителя маршрута (человек в чате → агентный клиент →
   runner с оболочкой n8n → сервер), а не смена маршрута. Маршрут и
   контракты задаёт мета-модель Хаба (`M0`–`M4`), исполнение — runtime.
   Корпус `runs/` этого репозитория уже является эмпирической базой
   мета-модели (замер Хаба на 57 прогонах), поэтому «корректировка
   мета-модели по практике» имеет законный канал — свидетельство в форме
   LG-5 ADR-014 Хаба.
4. **Октябрьская смена «ФТ/ТЗ-валидации» на фазы `A-IN` → `A-CORE` →
   `A-WORK` → `A-RELEASE`** — не косметика: она переводит проект с
   документ-ориентированной модели (генераторы разделов ТЗ/ФТ) на
   ядро требований и рендер (`M1`/`M2` мета-модели). Документы, описывающие
   прежнюю модель, устарели по содержанию, даже если формально корректны.

Ключевой вывод: **маршрут и контракты не меняются между этапами** — меняется
исполнитель. Поэтому SSOT маршрута должен быть один (мета-модель Хаба →
runtime), а спица хранит практику этапа 1 и его статистику.

## Выводы для стратегических документов

- **Видение** формулируется вокруг результата БА (проверяемое требование
  BCREQ быстрее и полнее), а не вокруг формы (промпты, агенты, сервер):
  форма меняется по этапам, результат — нет.
- **Концепция** фиксирует роли трёх репозиториев (Хаб — нормы и
  мета-модель; runtime — исполнение; спица — практика этапа 1, сайт,
  статистика) и правило ADR-014 для обратной связи.
- **Архитектура** описывает один маршрут `A-IN` → `A-CORE` → `A-WORK` →
  `A-RELEASE` и смену исполнителя по этапам (C4: контекст и контейнеры).
- **Roadmap** — четыре этапа с критериями входа и выхода, привязанными к
  статистике `runs/` и средам Хаба.

Черновики и обоснование — в [предложении по стратегическим документам](2026-10-31-strategic-documents-proposal.md);
решения — в [RFC v0.3](../rfc/2026-10-repository-modernization.md).

## Остаточные ограничения

- JSON-экспорт чата из комментария к PR #408 не загружен; анализ опирается
  на историю задач, как указывает #409. Если владелец загрузит файл,
  проверка сводится к сверке реестра К-01…К-10 с его содержимым.
- Дата переименования `ai-ba-playbooks` → `mango-ba-ai-runtime` не
  установлена (GitHub API её не отдаёт); факт переименования подтверждён
  совпадением ID репозитория.
- Тела ранних issues частично сформулированы ИИ-ассистентом; намерение
  владельца восстанавливается по комментариям и последующим постановкам.
