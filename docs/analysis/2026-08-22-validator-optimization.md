# Анализ: оптимизация валидаторов для локального выполнения

## Summary / BLUF

Гипотеза issue [#299](https://github.com/G-Ivan-A/mango_ba_prompts/issues/299)
**подтверждена частично, но не там, где ожидалось**.

- **Медленно — не «много валидаторов», а два из них.** Полный последовательный
  прогон 23 валидаторов занимал 6.7 с, из которых 2.7 с — один
  `validate_issue_265_hub_sync` (7287 ссылок по 1486 файлам). Остальные 21
  укладываются в 0.1–0.7 с каждый. Массовая оптимизация «всех» дала бы почти
  ноль; выигрыш даёт (а) не запускать неизменившееся, (б) ускорить один хвост.
- **Конфликты слияния — не следствие скорости, а следствие хардкодных
  реестров.** Два файла содержали перечни прогонов (`EXPECTED_RUNS` —
  ~450 строк, `EXPECTED_CLASSIFICATION`) и правились в **каждом** PR с новым
  прогоном: 37 и 26 коммитов против 1–4 у всех остальных валидаторов. Это
  единственная реальная точка конфликта.
- **Решение:** раннер [`scripts/validate_all.py`](../../scripts/validate_all.py)
  с *наблюдаемыми* зависимостями (трассировка I/O валидатора), кэшем по
  содержимому и двумя уровнями (`fast`/`full`) + замена реестров на обнаружение
  на диске. Полная проверка при 997 прогонах — **10.4 с** (цель ≤15 с),
  инкрементальная — **0.4 с** без правок и **0.6–1.7 с** после правки файла
  (цель ≤1 с достигается для всего, кроме правки Markdown, см. §Ограничения).

## Context / Scope

- **Дата:** 2026-08-22. **Автор:** Konard (AI) по постановке issue #299.
- **Охват:** 21 `scripts/validate_issue_*.py`, 2 `scripts/test_*.py`,
  2 `tools/validate-*.sh`, цели `Makefile`, workflow `.github/workflows/*.yml`.
- **Метод:** замер времени каждого валидатора (`--full`, холодный кэш);
  подсчёт коммитов на файл (`git log --oneline -- <файл> | wc -l`);
  инвентаризация фактически прочитанных файлов через трассировку I/O;
  стенд на 997 синтетических прогонов
  ([`experiments/bench_validators.py`](../../experiments/bench_validators.py)).
- **Ограничение:** всё измерено локально, на одной машине; абсолютные числа
  зависят от диска, но соотношения устойчивы.

## Ф-2. Узкое место конфликтов: хардкодные реестры

`scripts/validate_issue_123_runs_contract.py` содержал словарь `EXPECTED_RUNS`
(~450 строк: для каждого прогона — год, тип, перечень артефактов), а
`scripts/test_runs_contract_run_type.py` — `EXPECTED_CLASSIFICATION`. Каждый PR,
фиксирующий прогон, дописывал строку в **тот же конец того же словаря** — это
классический конфликт «две ветки добавили строку в одно место».

Подтверждение — распределение правок: 37 и 26 коммитов на эти два файла против
1–4 на любой другой валидатор. Прямой след в истории репозитория —
`738457a4 runs: перенумеровать прогон RUN-0022 → RUN-0025 (RUN-0022..0024
заняты в main)`: коллизия идентификаторов между параллельными ветками.

**Устранено:** реестр заменён на обнаружение на диске (`discover_runs()` —
`runs/<YYYY>/RUN-*`), источником истины по типу прогона стал сам
`metadata.yaml` прогона, а перекрёстной сверкой — таблица `runs/README.md`.
Новый прогон теперь добавляет **только свой каталог и свою строку реестра**;
файлы валидаторов не трогаются вовсе. Замороженный список из 22 путей,
перемещённых до миграции, вынесен в
[`scripts/data/runs-legacy-moved-paths.txt`](../../scripts/data/runs-legacy-moved-paths.txt):
список закрыт (пополняться не может), поэтому конфликтов не создаёт.

Побочный эффект: файл валидатора сократился с 656 до 357 строк.

## Ф-3. Дублирование проверок

Трассировка даёт фактические множества читаемых файлов, поэтому дублирование
измеримо, а не додумано:

| Пара | Общих файлов | Природа |
|---|---|---|
| `111_kb_pipeline` ↔ `117_kb_traceability` | 1125 из 1140/1126 | оба обходят весь `kb/processed/`, но проверяют разное (структура vs traceability) |
| `265_hub_sync` ↔ `111`/`117` | 1116–1128 | 265 читает все `*.md`, включая `kb/` |
| `123_runs_contract` ↔ `test_runs_contract_run_type` | 23 из 32/24 | первый проверяет реальные прогоны, второй — правила на синтетике |
| `267_onboarding` ↔ `validate-frontmatter`, `validate-file-naming` | 17 и 31 | **267 запускает оба shell-валидатора как подпроцессы** |

Совпадение *входов* — не то же, что совпадение *проверок*: во всех парах, кроме
последней, проверяются разные свойства одних и тех же файлов, слияние потеряло
бы адресность («какая issue сломалась»). Единственное настоящее дублирование —
`267`, который заново прогоняет `validate-frontmatter` и `validate-file-naming`
(они и так входят в набор). Это оставлено намеренно: проверка D в 267 — не
«прогнать валидаторы», а «allowlist именования не маскирует новые нарушения»,
то есть мета-проверка самих валидаторов. Стоимость — 0.3 с, и раннер
пропускает 267 целиком, пока его входы не изменились.

## Ф-4. Хвост времени: `265_hub_sync`

Профилирование показало, что 60 % времени уходило не на чтение файлов, а на
`pathlib`: `Path.resolve()` и `relative_to()` на каждую из 7287 ссылок
(`realpath` — системные вызовы на каждый сегмент). Замена на строковую
нормализацию `os.path.normpath` + мемоизация существования цели +
предкомпиляция регулярных выражений: **2.73 с → 1.45 с** без изменения
поведения (битая ссылка и выход за корень репозитория ловятся по-прежнему —
проверено пробой обоих дефектов).

## Options: чем ускорять

Рассмотрены не только очевидные варианты; каждый оценён по критериям issue
(локально, без внешних сервисов, без потери проверок, устойчиво к параллельной
работе двух веток).

| Вариант | Что даёт | Почему не он (или почему он) |
|---|---|---|
| О-1. Параллельный запуск | ×N по числу ядер, ничего не меняет в проверках | Дёшево и совместимо с любым другим вариантом — **взят**, но сам по себе даёт 6.7 → ~3 с и не решает конфликтов |
| О-2. Уровни `fast`/`full` вручную (список «быстрых» валидаторов) | быстрый цикл разработки | Список «быстрых» — снова **хардкод**, который придётся править в каждом PR: воспроизводит корень проблемы Ф-2 |
| О-3. Инкрементальность по `git diff` | «изменил `prompts/` → гоняем только промпт-валидаторы» | Требует **таблицы соответствия** «путь → валидатор»: третий хардкодный реестр, к тому же врущий (валидатор читает не то, что заявлено). Не берём |
| О-4. Инкрементальность по *объявленным* зависимостям (`DEPENDS_ON` в каждом валидаторе) | точнее О-3 | Объявление расходится с кодом молча: валидатор читает файл, не указанный в списке, → **ложное попадание кэша**, то есть пропущенная поломка. Худший из отказов. Не берём |
| О-5. Инкрементальность по *наблюдаемым* зависимостям (трассировка I/O) | точность без деклараций; новый валидатор работает без единой строчки конфигурации | **Взят.** Цена — обёртка вокруг `open`/`stat`/`scandir` и ~10 % накладных на прогон |
| О-6. Кэш по `mtime` | простейший | Ломается на `git checkout` (переключение веток меняет mtime без изменения содержимого) → полная инвалидация на каждом переключении. Не берём как единственный ключ |
| О-7. Кэш по содержимому (sha256) + stat-кэш | устойчив к `checkout` и `touch` | **Взят.** `mtime`/размер — только как ускоритель поиска, ключ — хэш содержимого |
| О-8. Демон/файловый монитор (`inotify`) | мгновенный отклик | Фоновый процесс, состояние вне репозитория, «залипание» при пропущенных событиях. Избыточно для проекта, где проверка и так укладывается в секунды |
| О-9. Общий процесс-раннер (импортировать валидаторы как модули вместо `subprocess`) | экономия ~25 × 30 мс запуска Python | Валидаторы завершаются через `sys.exit()` и мутируют глобальное состояние; изоляция важнее 0.7 с |
| О-10. Удалить/слить валидаторы | меньше кода | Прямо противоречит требованию «полная обратная совместимость: ни одна проверка не удалена». Не берём |

**Выбранная комбинация: О-5 + О-7 + О-1 + динамическое обнаружение.**
Обоснование именно для этого проекта: репозиторий — документный, правки почти
всегда затрагивают 1–2 файла, а валидаторов много и они мелкие; при этом их
пишут разные агенты и добавляют пачками. Значит, оптимум — механизм, который
(а) не требует от автора валидатора **ничего** (иначе он это забудет или
соврёт), (б) не имеет ни одного места, куда все PR пишут одновременно.
Трассировка + хэш содержимого + обнаружение по маске — единственная из
рассмотренных комбинаций, где оба условия выполнены одновременно.

## Отчёт по граничным гипотезам

Обязательный раздел issue #299. Каждая гипотеза проверена экспериментом, а не
рассуждением; воспроизводящие тесты — в
[`scripts/test_validate_all.py`](../../scripts/test_validate_all.py) (15 тестов).

| # | Гипотеза | Поведение | Где закреплено |
|---|---|---|---|
| Г-1 | Внешний/отсутствующий ресурс | Зависимость «файла нет» хранится явно (`e:<путь>` = `absent`): появление файла инвалидирует кэш. Сеть валидаторами не используется вовсе (stdlib-only) | `test_appearing_optional_file_invalidates` |
| Г-2 | Кэш испорчен | Нечитаемый JSON записи и обрезанный `stat-cache.json` трактуются как **промах**, а не как ошибка: проверка выполняется заново | `test_garbage_entry_is_treated_as_miss`, `test_truncated_stat_cache_is_treated_as_miss` |
| Г-3 | Кэш устарел / подделан | Подмена сохранённого состояния на «правдоподобное» не скрывает реальную поломку: сверяется хэш содержимого, а не запись о нём | `test_stale_state_with_stale_hash_is_rechecked` |
| Г-4 | Файл изменён, но хэш не пересчитан (гонка «racily clean») | Правка внутри той же секунды, что и запись stat-кэша, не переиспользует `(размер, mtime)`: запись с `mtime_ns >= saved_at_ns` считается «грязной» и хэшируется заново (приём git) | `Hasher._file_hash`, `test_changed_dependency_invalidates` |
| Г-5 | Валидатор проверяет сгенерированные файлы (`site/data/*.json`) | Сгенерированные файлы закоммичены и являются обычными зависимостями. **Найден реальный дефект процесса:** `node scripts/generate-pages-data.mjs` меняет `generatedAt` при каждом запуске, поэтому «regenerate → validate» в CI всегда даёт грязное дерево. Валидаторы намеренно проверяют **закоммиченную** версию — ровно то, что уедет на Pages | §Не выполнено, п.1 |
| Г-6 | Два экземпляра раннера параллельно | Каждая запись кэша — отдельный файл, пишется атомарно (`tmp` + `os.replace`), блокировок нет. Два одновременных `--full` оставляют пригодный кэш, без `*.tmp`-мусора | `test_two_runners_at_once_leave_usable_cache` |
| Г-7 | *(сверх списка)* Валидатор **пишет** в рабочее дерево во время параллельного прогона | **Найден реальный дефект:** `validate_issue_267` создавал `docs/adr/validator-self-check.md` в репозитории — и параллельно работавший `validate-file-naming` законно падал на этом файле. Результат прогона был недетерминированным. Проба перенесена в изолированную песочницу `tempfile.mkdtemp()` | `validate_issue_267_onboarding_v15.py:143` |
| Г-8 | *(сверх списка)* Валидатор читает служебные каталоги раннера | **Найден реальный дефект:** валидаторы, обходящие репозиторий целиком, видели `.validate-cache/`, созданный самим прогоном → вечный промах кэша. Служебные имена (`.git`, `.validate-cache`, `__pycache__`, `node_modules`) исключены из зависимостей на любом уровне пути | `_validator_trace.py:IGNORED_NAMES`, `validate_all.py:IGNORED_NAMES` |
| Г-9 | *(сверх списка)* Изменился сам валидатор, а не его входы | Файл валидатора — всегда его собственная зависимость: правка кода проверки инвалидирует запись | `test_changed_validator_source_invalidates` |
| Г-10 | *(сверх списка)* Валидатор непрозрачен для трассировки (shell-скрипт, `find`) | Трассировщик не видит I/O дочернего процесса. Для shell-валидаторов объявлен **корень области** (`docs/adr`, `docs/rfc`, …), который разворачивается динамически; неизвестный дочерний процесс помечает прогон «непрозрачным», и его зависимостью становится отпечаток всего дерева (`git ls-files`) — то есть безопасный отказ в сторону лишнего перезапуска | `validate_all.py:SH_SCOPES`, `worktree_fingerprint()` |
| Г-11 | *(сверх списка)* Файл появился в каталоге, который валидатор обходит | Зависимостью является **перечень каталога** (`d:<путь>`), а не только прочитанные файлы: новый файл в `docs/adr/` инвалидирует именно тех, кто обходит каталог | `test_new_file_in_scanned_directory_invalidates` |
| Г-12 | *(сверх списка)* Валидатор упал — кэшируется ли провал? | Кэшируются **только успехи**. Провал воспроизводится при каждом запуске, пока причина не устранена: «зелёный» кэш не может замаскировать красный результат | `test_failure_is_reported_and_not_cached` |
| Г-13 | *(сверх списка)* Добавлен новый валидатор | Обнаружение по маске (`validate_issue_*.py`, `test_*.py`, `validate-*.sh`): новый файл попадает и в локальный набор, и в CI без правки реестра, `Makefile` или workflow | `test_new_validator_is_discovered_without_registry_edit` |
| Г-14 | *(сверх списка)* `git checkout` другой ветки | `mtime` меняется у всех файлов, содержимое — нет. Ключ кэша — хэш содержимого, поэтому переключение ветки туда-обратно не вызывает полного перепрогона | `test_touch_without_content_change_stays_cached` |

## Измерения

¹ Полный прогон вырос за счёт **нового** валидатора `test_validate_all` (7.6 с:
он сам порождает подпроцессы-раннеры). Без него полная проверка — 2.4 с против
6.69 с исходно.

**Ограничение (честно):** цель «≤ 1 с» не достигается для правки любого
`*.md` — такая правка законно инвалидирует `265_hub_sync`, который обязан
перепроверить ссылки всего корпуса (1.45 с после оптимизации Ф-4). Дальнейшее
ускорение требует пофайлового кэша внутри самого 265 (кандидат в BACKLOG),
что дублировало бы механику раннера. Для правок вне Markdown цель выполнена.

## Не выполнено и вопросы

1. **`site/data/*.json` расходятся с генератором.** Повторный запуск
   `node scripts/generate-pages-data.mjs` на чистом дереве даёт непустой diff
   (не только `generatedAt`: например, `checks.json` меняет `tests.total`).
   Значит, закоммиченные данные Pages отстают от источников. Это **вне охвата
   issue #299** (не касается скорости валидаторов), но требует отдельной issue:
   либо генерация детерминирована и запускается в CI, либо данные объявлены
   артефактом сборки. Валидаторы намеренно оставлены на закоммиченной версии.
2. **Дублирование `267` ↔ shell-валидаторы** оставлено намеренно (Ф-3). Если
   владелец сочтёт мета-проверку allowlist избыточной, её можно вынести в
   отдельный маленький валидатор — вопрос вынесен на ревью.
3. **Пофайловый кэш внутри `265_hub_sync`** — единственный путь к «≤ 1 с» на
   правках Markdown. Предложение: отдельная issue, чтобы не смешивать
   инфраструктуру раннера и логику конкретной проверки.
