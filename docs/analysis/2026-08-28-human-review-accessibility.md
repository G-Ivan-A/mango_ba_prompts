# Читаемость ссылок в отчётах для Human Review

> **Дата:** 2026-08-28 · **Issue:**
> <https://github.com/G-Ivan-A/mango_ba_prompts/issues/335> · **Объект анализа:**
> 53 сноски в `runs/2026/RUN-0060/outputs/L4-combined-gap-report.md`

## 1. Проблема

Сноска `^1` в разделе 6.3 отчёта L4 описывает поля `role` и `message_type`
структуры `WebhookPayloadChatMessageCreated`, а ссылка ведёт на
<https://api.hh.ru/openapi/redoc#tag/Webhook-API/operation/post-webhook-subscription>.
Человек, открывший эту страницу, не видит ни имени `WebhookPayloadChatMessageCreated`,
ни перечисленных полей: страница показывает операцию создания подписки, а
структура payload раскрывается внутри свёрнутого блока Callbacks под другим
заголовком.

Формально ссылка ведёт в правильный раздел документации. Практически она не
проходит проверочный вопрос Human Review:

> увидит ли человек, перешедший по ссылке без дополнительных знаний об API,
> именно тот объект, который описан в сноске?

Ссылка, требующая догадки о том, где искать, обесценивает трассируемость: ревьюер
не может подтвердить факт, не изучив API самостоятельно, то есть не может
выполнить Human Gate.

## 2. Методика проверки

Проверка выполнена машинно, чтобы её можно было повторить и включить в quality
gate.

1. Скачивается спецификация <https://api.hh.ru/openapi/specification/public> и
   вычисляется SHA-256. Проверка засчитывается только при совпадении с SHA-256,
   закреплённым в отчёте L4
   (`8ea1380bf87d7351cf2f977f9918bbdd03a26a6b9c9e95eb50f3d4ae080a7576`), — иначе
   факты отчёта относятся к другой версии источника.
2. Из спецификации строятся индексы: 728 схем (`components.schemas` с их `title`,
   свойствами любой вложенности, `enum` и номерами строк), 131 операция
   (`operationId`, метод, путь, теги, параметры), `components.examples`,
   `components.parameters`, все значения `enum` документа.
3. Из отчёта разбираются все таблицы `### N.M. Источники`: маркер сноски, раздел
   документации, описание, URL. Найдено ровно 53 сноски — совпадает с
   `metrics.footnote_sources: 53` в `runs/2026/RUN-0060/metadata.yaml`.
4. Каждый токен описания (`` `...` ``) классифицируется: операция, эндпоинт,
   схема, пример, значение `enum`, служебная нотация OpenAPI (`callbacks`,
   `onData`, `oneOf`, коды ответов), поле, неопознанный идентификатор.
5. Каждая сноска сопоставляется со своим якорем: существует ли операция из якоря,
   объявлены ли названные схемы, совпадает ли имя схемы с её отображаемым
   заголовком, объявлены ли названные поля в названных схемах.

Инструменты: `experiments/issue_335_footnote_audit.py` (аудит) и
`experiments/issue_335_human_review_checklist.py` (генерация чек-листа), оба
только на стандартной библиотеке — как `experiments/issue_333_hh_api_source_index.py`.
Результат: [`runs/2026/RUN-0060/outputs/human-review-checklist.md`](../../runs/2026/RUN-0060/outputs/human-review-checklist.md).

## 3. Классификация проблем

| Тип | Определение | Найдено |
| --- | --- | --- |
| A | Ссылка ведёт на неверный объект | 1 |
| B | Ссылка верна, но объект требует дополнительной навигации | 16 |
| C | Ссылка верна, объект существует, но описан недостаточно точно | 14 |
| D | Объект не найден в документации (GAP SSOT) | 0 |
| — | Без замечаний | 22 |
| | **Всего** | **53** |

**Тип A (1 сноска).** Сноска 9.3 `^7` ведёт на
`#tag/Prosmotr-rezyume/Prosmotr-rezyume-s-kontaktami` — это подраздел тега, а не
операция. Якорь такого вида не подчиняется схеме
`#tag/<tag>/operation/<operationId>` и не проверяем машинно.

**Тип B (16 сносок).** Причина одна и она механическая: **Redoc печатает в
заголовке блока значение `title` схемы, а не её имя в `components.schemas`.**
Примеры из отчёта:

| Имя в сноске | Что человек видит в Redoc |
| --- | --- |
| `WebhookPayloadChatMessageCreated` | «CHAT_MESSAGE_CREATED» |
| `WebhookActionChatCreated` | «Подписка на CHAT_CREATED» |
| `ChatsCommonMessage` | «Информация о сообщении» |
| `ChatsCommonChatBasic` | «Базовая информация о чате» |
| `NegotiationsObjectsTopicItemCommon` | «Общая информация об отклике/приглашении» |

Поиск по имени схемы на странице ничего не даёт: этой строки на странице нет.

**Тип C (14 сносок).** Сноска называет операцию и поле, но не называет
схему-владельца поля. Человек видит правильную страницу, но должен сам найти
поле среди раскрывающихся блоков ответа. Частный случай: сноска 12.5 `^6`
ссылается на заголовок `X-Manager-Account-Id`, который в спецификации встречается
только в текстовых описаниях (строки 9639 и 20043) и нигде не объявлен как
параметр, — это факт уровня «упомянуто в описании», а не «объявлено в контракте».

**Тип D (0 сносок).** Ни один описанный объект не отсутствует в источнике
целиком: все операции из якорей существуют, все названные схемы объявлены.

## 4. Ключевое ограничение Redoc: якорей на схемы не существует

Спецификация hh.ru объявляет `x-tagGroups`. При наличии `x-tagGroups` Redoc не
рендерит раздел Schemas, поэтому якорей вида `#schema/<Имя>` или
`#/components/schemas/<Имя>` в этом рендере **нет вообще**. Схема отображается
только внутри страницы операции, которая на неё ссылается, в свёрнутом блоке.

Следствие: правило «ставить якорь на дочерний элемент» для схем этого источника
технически недостижимо. Значит, требование к сноске о схеме должно быть другим —
явный путь навигации плюс цитата из спецификации, закреплённой по SHA-256.

## 5. Правила оформления ссылок

Правила согласованы с непубличным черновиком контракта ссылок из RUN-0061
(`runs/2026/RUN-0061/outputs/link-reference-contract-draft.md`): якорь обязателен,
если страница публикует заголовки; заголовок раздела цитируется дословно; один
токен — одна страница; ссылка ведёт на страницу, а не на индекс; требование
обязано быть проверяемым машинно.

**Правило 1 — сноска ведёт напрямую на описанный объект.**
Если у объекта есть собственный якорь (операция), сноска обязана вести на него:
`#tag/<tag>/operation/<operationId>`. Проверка: `operationId` присутствует в
спецификации с закреплённым SHA-256.

```text
| `^3` | Чаты | `GET /common/chats` (`get-common-chat-list`) | <https://api.hh.ru/openapi/redoc#tag/Chaty/operation/get-common-chat-list> |
```

**Правило 2 — якорь на дочерний элемент, если он существует.**
Если у дочернего элемента есть собственный якорь, ссылка ведёт на него, а не на
родителя. Для рендера hh.ru это применимо только к операциям внутри тега; для
схем правило неприменимо (раздел 4) и заменяется правилом 3.

**Правило 3 — явный путь навигации, когда прямой ссылки не существует.**
Сноска обязана назвать: (а) ближайший достижимый якорь, (б) путь до объекта на
этой странице, (в) отображаемый заголовок объекта, (г) цитату из спецификации в
виде `components.schemas.<Имя>` с номером строки под закреплённым SHA-256.

```text
| `^1` | Webhook API | Payload `CHAT_MESSAGE_CREATED` (поля `role`, `message_type`) | <https://api.hh.ru/openapi/redoc#tag/Webhook-API/operation/post-webhook-subscription> | Раздел «Webhook API» → операция `post-webhook-subscription` → блок **Callbacks** → `onData` → тело «CHAT_MESSAGE_CREATED» | `components.schemas.WebhookPayloadChatMessageCreated` |
```

**Правило 4 — отображаемый заголовок вместо имени схемы.**
В колонке «Метод / схема» приводится строка, которую человек увидит в интерфейсе
(`title`), а машинное имя схемы уходит в колонку цитаты. Проверка:
`spec.components.schemas[<Имя>].title == <заголовок в сноске>`.

**Правило 5 — разделять «объявлено в контракте» и «упомянуто в описании».**
Факт, найденный только в тексте `description`, помечается явно и не выдаётся за
объявленный элемент контракта.

## 6. Выводы для стандарта (ADR)

1. В обязательную структуру раздела «Источники» добавляются колонки «Где
   смотреть» (путь навигации) и «Цитата из спецификации» (путь в спецификации +
   строка под закреплённым SHA-256).
2. Отчёт обязан закреплять версию источника по SHA-256 — без этого ни номер
   строки, ни номер страницы не имеют смысла.
3. Требование читаемости ссылки формулируется как проверочный вопрос Human Review
   и сопровождается чек-листом на 100 % сносок, а не выборкой.
4. Проверка ссылок обязана быть машинной: существование `operationId`, совпадение
   `title`, объявленность схемы. Ручная проверка не масштабируется на 53+ сноски.
5. Классы A и D блокируют выпуск отчёта; классы B и C допускаются только с
   заполненными колонками «Где смотреть» и «Цитата из спецификации».
