# Анализ: итоговые промпты генерации разделов BCREQ-ФТ по прогонам RUN-0073…RUN-0076

## Summary / BLUF

По четырём прогонам (594 реплики, 843 вхождения ошибок ИИ, 137 критериев успеха,
1423 сверенные цитаты, 0 расхождений) сформулированы три самодостаточных промпта
генерации разделов BCREQ-ФТ — а) 1, 2; б) 3, 5; в) 4, 6 (§5) — с общей частью из 14
правил, 36 правилами разделов и 7 правилами конструкции промпта; каждое правило
опирается на критерии успеха, правила прошлых промптов или дефекты шаблонов с
проверяемыми ссылками, и каждая категория ошибок, встреченная в группе разделов,
покрыта правилом промпта этой группы (§2.7, §2.8). Главные выводы: 31,8 % вхождений
— вне текста разделов, в ходе диалога (из них 132 из 268 — угодничество и
самосертификация), поэтому проверка вынесена
во вторую роль отдельным вызовом; самая частая ошибка — непроверенное утверждение
(19,0 %), поэтому каждое утверждение о продукте требует локатора. Промпт GitHub
issue на сбор golden set запретов и необходимых и достаточных критериев приёмки —
в §6. Промпты ещё не проверены прогоном модели (§7).

## 3. Findings: выводы для промптов

1. **Треть вхождений — вне текста разделов.** Группа `dialog` — 268 из 843
   (31,8 %), из них U10 (угодничество, самосертификация) — 132. Поэтому общая часть
   промптов запрещает оценки собственного ответа (О13) и заменяет их проверяемым
   блоком «Проверка решений» (О14), а приёмку выносит во вторую роль (§5.4).
2. **Главная ошибка содержания — непроверенное утверждение (U09, 160, 19,0 %).** Она
   есть во всех четырёх прогонах и во всех группах, кроме `prompt`. Правило О1
   (локатор на каждое утверждение) — первое в общей части; в а) оно усилено шагом 0
   (А0.1–А0.4), в в) — правилом о параметрах и методах API (В4.5).
3. **Промпт а) (`a` + `asis`, 169).** Для `asis` U09 даёт 36 из 69; для `a` — U09
   20, расширение границ U04 12, регресс U06 10, нерелевантные факты U23 10.
   Правила: шаг 0 только по документации, границы — атомарными пунктами только из
   согласованного, риски — только от Заказчика.
4. **Промпт б) (`b`, 133).** Первые категории: формулировка U12 27, регресс U06 16,
   не-требование U24 15, U09 13, U01 11, U11 11. Правила: ФТ — только изменение и
   только по запросу (Б3.1, Б3.2), единая формула с обязательной «возможностью»
   (Б3.4), без дробления (Б3.5).
5. **Промпт в) (`c`, 191).** Первые категории: U09 40, архитектура в дизайне U01 36,
   U12 18, U06 16, пропуск содержания U13 14, доменное представление U15 13.
   Правила: бизнес-логика вместо архитектуры (В4.1), параметры только из
   документации (В4.5), порядок «настройки → проверки → логика → хранение» (В4.3).
6. **Дефекты самих промптов (`prompt`, 59; U19 — 53 по всем группам).** Роль с
   методологией, «стандартные» требования, фиксированные имена групп, запрет
   формулы «Система должна», готовые фразы самосертификации порождали ошибки модели.
   Правила П1–П7 (§5.5) убирают эти конструкции из итоговых промптов.
7. **Регресс (U06, 49) и угодничество (U10, 142) — во всех четырёх прогонах**, хотя в
   стандарте BCREQ есть правило только на часть таких случаев (RUN-0076,
   `prompt-improvements.md` §1–§2). Поэтому правила общей части повторяются в каждом
   из трёх промптов дословно (валидатор это проверяет), а сверка с журналом решений БА
   (О3) — обязательный шаг перед ответом.

- Изменение штатной логики — явной последовательностью (В4.6); размещение и права — по журналу решений или вариантами (В4.7).
- Раздел 6 не повторяет раздел 4; 6.2 пуст без заданных технологий (В6.1–В6.3).

### 5.4. Проверка второй ролью

По предложению БА в RUN-0074 (р. 204; `section-prompts.md` §2.4, SC-27) ответ
промптов 2 и 3 (разделы 3–6) проверяет вторая роль — архитектор — тем же перечнем
«Проверка решений». Здесь проверка применяется ко всем трём промптам а)–в)
(расширение на а) — допущение автора анализа). В RUN-0076 модель сама
написала «Отчет валидации (Эксперт-Архитектор)» внутри ответа (I-150, U10), поэтому
проверка — **отдельный вызов** с отдельным промптом, а не раздел ответа генератора:

```text
# РОЛЬ
Ты — архитектор, проверяешь раздел BCREQ-ФТ, подготовленный бизнес-аналитиком. Текст раздела не переписываешь.

# ВХОДНЫЕ ДАННЫЕ
- ПРОМПТ ГЕНЕРАЦИИ: <промпт а), б) или в) целиком>
- ВХОДНЫЕ ДАННЫЕ ГЕНЕРАЦИИ: <те же, что получил генератор>
- ОТВЕТ: <ответ генератора>

# ПРАВИЛА
1. По каждому правилу ПРОМПТА ГЕНЕРАЦИИ (О1–О14 и правила раздела) — «выполнено» или «нарушено» с цитатой из ОТВЕТА и источником (локатор входных данных или реплика БА).
2. Утверждение ОТВЕТА без локатора во ВХОДНЫХ ДАННЫХ ГЕНЕРАЦИИ — нарушение О1.
3. Оценка качества, похвала и итоговое «готово» не пишутся: итог — только перечень нарушений.

# ФОРМАТ
Таблица «Правило | Выполнено / нарушено | Цитата из ОТВЕТА | Источник | Что исправить».
```

Если найдено нарушение, раздел перегенерируется с перечнем замечаний. Порог
совпадения ролей (БА в RUN-0074, р. 204, предложил «90 %») и предел числа
перегенераций не зафиксированы — открытый вопрос Q3 RUN-0074.

## 6. Промпт для GitHub issue: сбор статистики и цитат для golden set

Текст ниже вставляется в issue целиком; `<…>` заполняет автор issue.

<!-- section-prompts:issue -->
```markdown
## Задача: сбор статистики и цитат для golden set промптов разделов BCREQ-ФТ

**Цель.** По выгрузкам чатов задач <номера задач> собрать статистику и дословные
цитаты для двух golden set приёмки итоговых промптов а) разделы 1, 2; б) разделы 3, 5;
в) разделы 4, 6 (docs/analysis/2026-10-20-bcreq-fr-section-prompts.md, §5):

1. **Запреты — «как не надо делать»**: правило + отрицательная цитата модели +
   цитата замечания БА + частота.
2. **Необходимые и достаточные критерии успеха (шаблоны)** приёмки результата
   каждого промпта.

**Входные данные.** Выгрузки чатов задач (передаёт БА). Режим гибридный:
mango-ba-ai-runtime не используется; сырая выгрузка, расшифровки и подписанные
ссылки CDN в репозиторий не коммитятся (правило #309) — только выписки цитат.

**Запись.** `runs/YYYY/RUN-NNNN` по контракту `runs/README.md`; номер —
`python3 scripts/resolve_registry_conflicts.py --next-run-id` (учитывает открытые PR).

### Словарь и разметка

- Категории — единый словарь U01–U26 (§1, §2.2 аналитического файла). Новая
  категория U27+ — только с обоснованием: ни одна из U01–U26 не подходит, и есть
  ≥ 2 вхождения.
- Группа раздела — `a` / `asis` / `b` / `c` / `open` / `dialog` / `prompt` (§1).
- Одна строка реестра вхождений:
  `ID | реплика | раздел | группа | категория U | цитата модели | цитата БА (замечание) |
  повтор после замечания (да/нет) | нарушенное правило промпта (О*/А*/Б*/В*/П* или «нет правила»)`.
- Одна строка критерия успеха:
  `ID | реплика | группа | критерий (да/нет-проверка) | цитата БА | принятая редакция (цитата)`.
- Каждая цитата проверяется скриптом сверки с выгрузкой; расхождений — 0.

### Статистика (числа, не пересказ)

1. Вхождения: категория U × группа × задача; повторы после замечания БА.
2. Для каждого правила промптов а)–в): сколько вхождений оно предотвратило бы
   (вхождения его категорий в его группе) и сколько раз нарушено, несмотря на
   правило в промпте.
3. Вхождения с «нет правила» — кандидаты в новые правила; список с цитатами.
4. Критерии успеха: группа × задача; какие критерии повторяются в ≥ 2 задачах.

### Golden set «запреты»

Запрет включается, если его нарушение вызвало замечание БА в ≥ 2 задачах или в 1
задаче с пометкой БА «критично». Поля: `ID | группа | правило | отрицательная
цитата модели | цитата замечания БА | вхождений | задач | повторов после замечания`.

### Golden set «критерии успеха» (шаблоны)

Поля шаблона: `ID | группа | проверка (да/нет) | как проверить (источник) |
пример «принято» (цитата принятой редакции) | пример «отклонено» (цитата
отклонённой редакции) | категории U | частота`.

- **Необходимость:** нарушение критерия вызвало замечание БА (≥ 2 задачи или 1 с
  пометкой «критично»).
- **Достаточность:** каждая принятая БА редакция раздела проходит все критерии
  группы, каждая отклонённая — нарушает хотя бы один. Если отклонённая редакция
  проходит все критерии — критериев не хватает: добавить критерий и указать, какое
  замечание БА он закрывает.

### Результат и проверки

- [ ] Файлы записи: реестр вхождений, статистика, оба golden set (`.md` и `.json`),
      сверка цитат; `metadata.yaml` с числами из скриптов.
- [ ] Предложения по правкам промптов а)–в): правило → вхождения → цитаты.
- [ ] Валидатор записи в `scripts/validate_issue_<N>_*.py`; `CHANGELOG.md`,
      `runs/README.md`; `make validate-full` проходит.
```

## 7. Ограничения и допущения

1. Сопоставление словаря RUN-0075 с U01–U26 и отнесение его «4. Функциональные
   требования (доработка)» к группе `b` — интерпретация автора анализа. Если
   отнести этот раздел к `c`, группа `b` уменьшится на 23 вхождения, а `c`
   увеличится на 23 (§2.3, строки RUN-0075 с меткой «4»).
2. По разделу 5 данных почти нет: в §2.3 раздел 5 встречается в RUN-0073 (2
   вхождения) и RUN-0076 (1); правило Б5.1 опирается на решение БА RUN-0076 SC-02,
   правило RUN-0073 R5.3 и дефект шаблона RUN-0073 I-011, а не на статистику
   вхождений.
3. Промпты не проверены прогоном модели: это следующий шаг (issue по §6) — golden
   set приёмки нужен, чтобы такую проверку провести.
4. Открытые вопросы к БА: (Q1) нужна ли в роли явная ссылка на методологию (П1 /
   О10 убирают её полностью, RUN-0074 RX.2 — структура по ODA); (Q3 RUN-0074) порог
   совпадения второй роли и предел числа перегенераций.
