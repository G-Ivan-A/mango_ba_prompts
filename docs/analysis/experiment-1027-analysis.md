### Гипотеза 1 — «ИИ воспринимает документацию как контекст задачи; нужен явный шаг запроса/подтверждения фактов из БЗ»

**Цитата БА (раздел 1.4):**
> «(гипотеза) добавить явный шаг запроса документации по продукту (ссылок,
> доков, др.); цель — для минимизация риска галлюцинации в результате передачи
> документации с контекстом, иначе ИИ воспринимает содержание документации как
> контекст задачи».

**Вердикт: ПОДТВЕРДИТЬ ЧАСТИЧНО** (подтвердить ценность явного шага и явного
правила-разграничения; оспорить тезис, что механизма сейчас нет).

**Что показывает стенограмма.** Механизм безопасной работы с документацией в
`glossary-context-understanding-stepwise.md` **уже есть** и в сессии 1027
**сработал штатно**. Когда пользователь предложил загрузить PDF-руководство,
агент не стал генерировать ТЗ по всему документу, а выделил только факты As-Is:

> «Я обработаю его в соответствии с правилом безопасной работы с документацией:
> Извлеку только те факты, которые относятся к текущему состоянию процессов
> обработки обращений (As-Is). … Покажу вам эту выжимку для сверки» (раздел 1.1).

И далее, после загрузки 13.7 МБ PDF, агент извлёк именно факты As-Is с явными
ссылками на пункты руководства (п. 4.3.5, 7.4.2, 4.3.2) и снова попросил
подтверждение. То есть тезис «ИИ воспринимает содержание документации как
контекст задачи» в данной сессии **не материализовался** — галлюцинаций «по
шуму» не было. В этом смысле гипотезу в её жёсткой формулировке можно оспорить.

**Но рациональное зерно есть, и оно важно.** Триггером безопасной обработки
послужил **сам пользователь**, который проактивно предложил PDF:

> «Могу предоставить руководство по КЦ для извлечения информации как из БЗ,
> исключитено для проверки состояния AsIs. Загрузить pdf файл руководства?»
> (раздел 1.1).

Текущий Шаг 0 промпта запрашивает «Источники информации о текущем состоянии
(As-Is): описание, PDF, ссылки», но:

- не называет явно **документацию по продукту / базу знаний (руководства,
  регламенты)** как отдельный, ожидаемый класс источника;
- не фиксирует жёстко роль такого документа: он — **источник верификации
  фактов As-Is**, а не источник нового скоупа/требований.

Если бы пользователь не догадался предложить PDF, агент бы его и не запросил.
Поэтому ценность гипотезы — в **робастности**: сделать запрос документации
явным, не полагаясь на инициативу пользователя, и кодифицировать различение
«документация = верификация As-Is, не источник требований».

**Изменение в промпт:** да (Шаг 0 + Правило 5 в stepwise; аналогично в oneshot).
См. [правку P1](#p1--glossary-context-явный-запрос-документации-и-её-роль).

### Гипотеза 2 — «Читаемость 4.x.x: сложные логические построения на уровне детализации плохо читаются бизнесом»

**Цитата БА (раздел 1.4):**
> «проверить правило для уровня 4.х.х — сложное логическое построение даёт —
> плохо читается».

**Вердикт: ПОДТВЕРДИТЬ.**

**Что показывает стенограмма.** На первом проходе генерации раздела 4 агент
выдал детализацию (уровень 4.x.1) тяжёлым канцеляритом:

> «4.1.1. Инициация действия осуществляется Сотрудником посредством выбора
> специального элемента управления (условно: „Завершить без ответа“) в
> интерфейсе карточки Обращения» (раздел 1.2).

Пользователь прямо потребовал улучшить читаемость и дал эталон формулировки:

> «стилистика требований на уровне 4.х.х — можно улучшить читаемость для
> бизнеса, например: „Сотруднику доступна возможность выбора «Завершить без
> ответа» вместо «Завершить» при обработке обращения“ … вместо „4.1.1.
> Инициация действия осуществляется Сотрудником посредством выбора специального
> элемента управления…“» (раздел 1.2).

Агент исправил и сам признал проблему:

> «Читаемость для бизнеса: Убран канцелярит („Инициация действия
> осуществляется...“). Формулировки переписаны в формате „Сотруднику доступна
> возможность...“» (раздел 1.2).

Текущее Правило 1 для уровня 4.x.1 звучит так: «Описание сценария, бизнес-правила
или логического уточнения. Деловой стиль, без жёсткого шаблона, чтобы не
перегружать текст». Формулировка **пассивна**: она запрещает жёсткий шаблон, но
не направляет к читабельности и не предостерегает от канцелярита/отглагольных
конструкций. Результат — модель по умолчанию ушла в бюрократический стиль, и
читабельность пришлось «чинить» вручную через одну итерацию.

Сопутствующее наблюдение из той же реплики БА — требование явного субъекта на
уровне 4.x:

> «стилистика требований на уровне 4.х — принято, явно добавить субъект —
> „...возможность Сотруднику“».

**Изменение в промпт:** да (Правило 1, уровни 4.x и 4.x.1 — в stepwise и
oneshot). См. [правку P2](#p2--fr-documentation-читаемость-4x1-и-явный-субъект-4x).

доказанный диффом дефект.

**Изменение в промпт:** да (Правило 1 в `constraints-documentation-oneshot.md` —

### Дополнительная находка (вне списка БА) — поздняя сверка ФТ с фактами As-Is

делегированное пользователем право «оспаривать правки, противоречащие
документации».

**Изменение в промпт:** да, лёгкое (добавить пункт сверки с фактами As-Is в
Шаг 4 валидации `fr-documentation-stepwise.md`). См.
[правку P5](#p5--fr-documentation-stepwise-сверка-фт-с-фактами-as-is-в-шаге-4).

## ФТ-2. Стандарт фиксации экспериментов (Draft v0.1)

Полный стандарт вынесен в отдельный файл:
[`standards/experiment-log-standard.md`](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/standards/experiment-log-standard.md).
Здесь — резюме и аргументация выбора формата.

**Проблема, которую решаем.** Сейчас прогоны фиксируются богатыми Markdown-файлами
в `runs/` (YAML-frontmatter + структурированные секции). Это
отлично для канонизации промпта, но **тяжело** для повседневной фиксации каждого
реального кейса БА. Issue прямо запрещает стандарт «на 20 полей перед началом
работы» и даёт право на отказ от бюрократии.

**Решение — два уровня, выбор за БА:**

- **Уровень 0 (по умолчанию, 30 секунд): GitHub Issue с лейблом `experiment`.**
  Создать issue, вставить туда чат и заполнить **5 минимальных метрик** (см.
  ниже). Подходит для большинства кейсов и для быстрого старта feedback loop.
- **Уровень 1 (по запросу): лёгкий Markdown-шаблон** в `runs/YYYY/RUN-XXXX/outputs/`
  (~10 строк метрик + цитаты). Нужен, только когда прогон станет доказательной
  базой для перевода промпта `draft → canonical` или для правки промпта.

**Минимальный набор метрик (ядро, обязательно на обоих уровнях):**

| Метрика | Тип | Зачем |
| --- | --- | --- |
| `iterations` | число | Кол-во итераций «генерация → правка» до приёмки. Прокси трудозатрат. |
| `ba_edits` | число | Кол-во правок БА (ручных вмешательств). Прокси «недотянутости» промпта. |
| `quality` | 1–5 | Субъективная оценка качества результата БА. |
| `prompts_used` | список | Какие промпты запускались (id/файлы). Связь с библиотекой. |
| `verdict` | enum | `works` / `works-with-edits` / `fails`. |
| `outcome` | 1–2 строки | Что зафиксировано/что чинить. Вход для следующей правки. |

Шесть полей, заполняются за минуты. Метрики `iterations`, `ba_edits`, `quality`
прямо названы в issue как пример. На примере 1027: `iterations ≈ 8`,
`ba_edits ≈ 12`, `quality = 4`, `verdict = works-with-edits`.

**Почему так.** Уровень 0 = «право на отказ от бюрократии» в действии (Issue +
чат, как и предлагал issue). Уровень 1 сохраняет совместимость с принятой в
репозитории практикой `runs/` и требованием README «минимум один
зафиксированный прогон перед `canonical`». Ядро из 6 метрик даёт сопоставимость
между экспериментами без тяжёлых форм.

**Статус — Draft v0.1.** Стандарт **подлежит валидации на 2–3 следующих
экспериментах** (как требует issue). Открытые вопросы вынесены в стандарт и в
`pr-ops/BACKLOG.md`. Чтобы стандарт не остался теорией, к этому PR приложен
**первый прогон по нему — «dogfood» на самой сессии 1027**:
[`runs/2026/RUN-0007/outputs/fr-generation-1027-live_2026-06-16.md`](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/runs/2026/RUN-0007/outputs/fr-generation-1027-live_2026-06-16.md).

### Рекомендация O1 — `documentation`: генерация с нуля против итеративного редактирования

Сессия 1027 — это на 80% **итеративное редактирование** черновика под фидбек, а
не одноразовая генерация: почти каждый ход — «версия принята, вношу
корректировки». Операция `documentation` в [`docs/taxonomy.md`](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/docs/taxonomy.md)
описана как единое «оформление результатов», без различения режимов
*«генерация с нуля»* и *«доработка/ревизия черновика под обратную связь»*.

**Рекомендация:** в онтологическом треке рассмотреть либо разделение
`documentation` на под-режимы (genesis vs revision), либо отдельную ось
«состояние артефакта» (см. O3). Формулировка-кандидат для ADR: *«Операция
documentation требует разделения на „генерацию с нуля“ и „редактирование
черновика“»* (это ровно тот пример, что приведён в issue).

### Рекомендация O2 — недопредставлена «валидация против источника»

Дополнительная находка (поздняя сверка п. 4.1.3 с руководством) показывает, что
сверка артефакта с авторитетным источником (БЗ/руководство) — отдельный тип
работы. Сейчас это «прячется» внутри шагов промптов (Шаг 4) и формально
относится к `validation`, но без явной семантики «проверка на соответствие
зафиксированным фактам/документации».

**Рекомендация:** при ревизии онтологии явно отразить связь артефакта с
источником-фактом (например, отношение «ФТ ← проверено против → факты As-Is/БЗ»)
или уточнить определение `validation`, чтобы включить consistency-check против
источника.

### Рекомендация O3 — промежуточные типы артефактов не типизированы

Сессия 1027 произвела артефакты, которых нет в примерах таксономии, но которые
**повторяемы и переиспользуемы**:

- «выжимка As-Is» (верифицированный экстракт фактов из БЗ);
- «матрица сценариев» (реконструированные US/UC: Happy Path / альтернативы /
  исключения);
- «отчёт валидации» (Шаг 3/4);
- «список вопросов заказчику».

**Рекомендация:** рассмотреть добавление промежуточных/рабочих типов артефактов
(As-Is-выжимка, сценарная матрица, отчёт валидации, перечень вопросов) либо ось
«состояние артефакта» (draft → reviewed → canonical), которая заодно закрывает
O1. Это рекомендация для ADR-трека, не изменение здесь.
