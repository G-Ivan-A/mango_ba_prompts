# Проверка конвейера промптов BCREQ по опыту прогонов

Отчёт отвечает на постановку задачи #411:

- почему замечания БА к ошибкам модели не превращались в правила промптов;
- почему качество промптов падало при каждой смене структуры;
- как это исправить и запустить этап 1 (ручной чат с промптами сайта).

Все числа получены из файлов репозитория. Скрипты и построчные данные лежат
в `experiments/issue_411/research/`. Номера задач, прогонов и кейсов
приведены только в таблицах свидетельств (разделы 1–7 и 9). В BLUF и
в выводах их нет — по правилу «розовых слонов».

## BLUF

1. **Опыт прогонов был, а канала в промпты не было.** Прогоны фиксировали
   сотни ошибок модели и замечаний БА. Но в контракте прогона нет версии
   промпта, адресата урока и статуса его закрытия, а сам прогон не вправе
   менять промпты. Перенос уроков в правила делали вручную и только один
   раз.
2. **Каждая смена структуры теряла уроки.** При переходе от 14 промптов
   этапа 1 к 39 классам ручного конвейера 17 из 55 уроков стали общими
   формулировками или исчезли. Ни один класс не ссылается на уроки
   прогонов. Проверки классов только структурные и не ловят потерю смысла.
3. **Правил в тексте недостаточно.** В последних размеченных прогонах
   62% ошибок модели случились уже после первого замечания БА в том же
   диалоге, причём для части ошибок правило в промпте уже было. Значит,
   нужны не только правила, но и вопрос-проверка ответа, пара «Не так /
   Так» и правило сессии у БА.
4. **Выбранный SSOT — реестр уроков.** Один машиночитаемый реестр:
   правило, вопрос «Проверка», пара «Не так / Так», адресаты, эталонный
   кейс. Каждый код ошибки из статистики прогонов сопоставлен ровно одному
   уроку. Блоки уроков в промптах и классах генерируются из реестра, ручная
   правка обнаруживается в CI.
5. **Регрессия теперь измерима.** Golden set (62 синтетических кейса) и
   бинарная рубрика из шести критериев. Слепой A/B на этом наборе: промпт
   проверки без уроков прошёл 49 из 62 кейсов, с уроками — 61 из 62; ложных
   срабатываний на корректном тексте нет ни у одной версии. Это сигнал, а
   не приёмка: проверен один промпт из 14, судья — модель.
6. **Изменения промптов и процесса — после согласования.** По решению
   владельца (комментарий к PR #412) сайт, процесс БА и тексты промптов в
   этом PR не меняются. Блоки уроков, правила П-8…П-10 и версия промптов
   0.2 предложены в RFC и вносятся отдельными задачами после принятия.
7. **Цена — размер промптов.** Промпты этапа 1 выросли примерно втрое:
   с 277 КБ до 792 КБ на все 14 (каждый — до 46–78 КБ). Владелец поставил
   качество выше экономии токенов; способ сжатия без потери связи с
   реестром предложен в RFC.

| Уровень | Что есть в прогоне | Прогонов |
| --- | --- | ---: |

Существенный отзыв человека-БА есть в 15 из 78 прогонов, все в раннем
периоде. Уровень L3 приходится на два периода: 15 прогонов в начале

AI-разметчик.

### 2.2. Достаточно ли информации для переиспользования

**Неуспешные применения — да, частично.** В RUN-0064 и RUN-0073…0076
размечен 851 инцидент по 87 кодам. Этого хватает, чтобы вывести уроки, и
реестр их вывел. Но:

| # | Пробел | Последствие |
| --- | --- | --- |
| G-1 | Нет версии использованного промпта: 20 прогонов ссылаются на `prompts/`, ни один — с версией или SHA | Нельзя связать ошибку с текстом правила и проверить, исправила ли её следующая версия |
| G-2 | Урок не адресован промпту: секция уроков у 7 прогонов, путь и версия промпта — у 3 | Урок остаётся в прогоне и никуда не попадает |
| G-3 | Нет обратной ссылки «промпт → прогон»: урок закрыт ссылкой только для двух прогонов | Нельзя проверить, какие уроки уже перенесены |
| G-4 | Контракт запрещает прогону менять `prompts/`, механизма «урок → бэклог» нет | Перенос зависит от отдельной задачи, которая не появляется |
| G-5 | Диалог сохранён в 17 из 78 прогонов | Критика результата БА в 25 прогонах потеряна |
| G-6 | Отзыв человека-БА — в 15 из 78 прогонов | Остальное — самооценка модели или пусто |
| G-7 | Разметка инцидентов не перепроверена вторым разметчиком | Счётчики — оценка, а не факт |
| G-8 | Четыре несовместимых словаря кодов ошибок | Одинаковые коды в разных прогонах означают разное; свести можно только внешним сопоставлением |
| G-9 | 200 кандидатов golden set и 137 сценариев — все `draft` | Эталонов нет |
| G-10…G-13 | Модель не записана (11 прогонов), промпты из чата БА не связаны с `prompts/`, шкала успеха пуста (`success` — 2 из 78), размещение вне контракта | См. исследование, раздел 6 |

Кроме того, `success_rate` определяется как минимум пятью несовместимыми
способами, поэтому метрики прогонов несравнимы.

**Успешные применения — почти нет.** Положительных эталонов 42, все в
статусе `draft`; что именно сработало и на какой версии промпта, по
прогонам восстановить нельзя.

### 2.3. Ключевое наблюдение: правило есть, повтор есть

В последнем размеченном периоде 524 из 843 инцидентов (62%) случились
**после** первого замечания БА в том же диалоге; в RUN-0076 — 265 из 333.
Для части кодов правило в промпте уже было: C09 — 45 повторов из 48,
C12 — 37 из 41, C01 — 16 из 18. Вывод: одного правила в тексте мало. Нужны
вопрос, которым модель (и БА) проверяет ответ; пара «Не так / Так»;
удержание замечаний БА как правил сессии. Все три элемента вошли в урок.

### 2.4. Предложенные поля контракта прогона

Только для новых прогонов, существующие не меняются (DEC-411-02):
`prompt_ref` (путь и версия промпта), `lessons[]` (затронутые уроки),
`golden_promotion` (какие кейсы предложены в набор), `ba_reviewed`
(просмотрел ли результат БА). RUN-0079 заполнен по этой схеме как пример.

### 4.2. Учтён ли опыт прогонов

Только декларативно. В RFC модернизации есть цикл «свидетельство в
`runs/` → обращение в Хаб → решение → правка → регрессия», но у него нет
решения, задачи и артефакта-носителя. Критерий «Golden и оценка» дан
только для будущей приёмки; утверждение эталонов владельцем задачей не
оформлено. `standards/runs-contract-standard.md` и
`standards/evals-contract-standard.md` в аудите, RFC и задачах не
упоминаются ни разу. Анализ деградации промптов из предыдущих итераций
помечен как исторический, а не принят как вход.

Чего нет совсем: реестра уроков; версии промпта и уроков в прогоне; связи
«урок → правило → кейс → перезапуск»; метрики повторов после первого
замечания БА.

### 4.3. Противоречия с запуском этапа 1

1. **`runs/` заморожен и одновременно пополняется.** Реестр диспозиций
   требует, чтобы `runs/` «не изменялся», а DoD задачи T-07 — пустого diff.
   При этом аудит пишет «новые RUN дописываются», а предложение — «с полем
   этапа и версии маршрута». `runs/README.md`, то есть контракт формата
   прогона, получил диспозицию «статистика». Поправка: DoD «существующие
   RUN не изменены», а не «diff пуст».
2. **Любое изменение — только через RFC/ADR.** Если каждую правку промпта по
   уроку вести через отдельный RFC, цикл обратной связи остановится. Нужен
   один ADR с лёгким классом изменения «правка по уроку с регрессионным
   доказательством» — это ADR-017.
3. **Уроки идут через Хаб.** Локальные дефекты промптов надо исправлять в
   репозитории, а в Хаб передавать только обобщённые наблюдения в форме
   LG-5 и асинхронно.
4. **В прогоне нет версии промпта.** Без неё невозможны ни трасса этапа 1 до
   эталона, ни сравнение этапов 1 и 2.

## 5. Оценка конвейера 39 классов

Классы ручного конвейера — правильная цель для этапов 2–3: в них описаны
вход и выход в JSON, состояние, гейты и стопы. Для этапа 1 они непригодны
как источник уроков:

- класс не исполняется без ручной сборки контекста;
- 95% текста общие, специфика — несколько строк;
- уроки прогонов в классах отсутствовали;
- регрессионного прогона классов нет, проверка только структурная.

Решение (DEC-411-07): этап 1 работает на 14 промптах сайта; классы
получают те же уроки из того же реестра (блок «Уроки прогонов» в 39
файлах, +2001 строка), а переработка классов в самостоятельные промпты
остаётся задачей этапов 2–3.

## 6. Выбор SSOT

| Вариант | Почему не подходит или подходит |
| --- | --- |
| Тексты 14 промптов и 39 классов, правка вручную | Так было: уроки терялись при каждой смене структуры, полноту переноса проверить нельзя |
| Классы ручного конвейера | Не исполняются самостоятельно; этап 1 работает на промптах сайта |
| Реестры инцидентов в `runs/` | Прогоны неизменяемы, словари несовместимы |
| Отдельный файл уроков, на который ссылается промпт | В ручном чате БА вставляет один промпт; ссылка не доставляет правило модели |
| Истории ошибок с номерами в промпте | Нарушает правило «розовых слонов», создаёт прайминг-риск |
| **Реестр уроков + генерация блоков** | **Выбран** (ADR-017): одна точка правки, генерация в промпты и классы, проверка в CI, связь с прогонами — только в реестре свидетельств |

Нормы остаются в конституции BCREQ и мета-стандартах разделов. Урок

## 8. Структура конвейера и режимы прогона

```text
замечание БА в чате ──► правило сессии (П-9) ──► следующий запрос
        │
        └─ нет в реестре (П-10) ──► урок в lessons.json ──► кейс golden set
                                         │
                       build_bcreq_lessons.py
                                         │
                ┌────────────────────────┴───────────────────┐
         14 промптов этапа 1 (сайт)                   39 классов (этапы 2–3)
                │
     прогон по рубрике K1–K6 ──► RUN с prompt_ref, lessons[], ba_reviewed
                │
     сравнение версий ──► порог DEC-411-04 ──► решение владельца
```

Режимы (раздел «Режимы прогона» RFC):

1. **Проверка на golden set.** Промпт проверки разбирает 62 кейса, судья
   оценивает по рубрике вслепую. Дёшево и воспроизводимо; измеряет
   удержание правил.
2. **Генерация на реальном входе БА.** Полный проход этапа 1 с
   отзывом БА и разметкой по урокам. Измеряет качество документа; нужен
   для приёмки.

## 12. Ограничения

- Golden set синтетический: он измеряет, удерживает ли промпт правило, а
  не качество реального документа.
- Проверен один промпт из 14 и один режим прогона. Режим 2 требует участия
  БА.
- Судья — модель, рубрика бинарная; спорные оценки разобраны в отчёте
  прогона.
- Уровни полноты прогонов и деградация уроков размечены эвристикой со
  сверкой граничных случаев вручную.
- Пороги приёмки, урок L-42 и бюджет токенов ждут решения владельца.

## Выводы и рекомендации

1. **Принять реестр уроков как единый источник** правил «как делать и как
   не делать» и запретить ручную правку блоков уроков в промптах. Иначе
   следующая смена структуры снова потеряет уроки.
2. **Дополнить контракт прогона четырьмя полями** только для новых
   прогонов: версия промпта, затронутые уроки, предложенные эталоны,
   признак просмотра БА. Без версии промпта ни один урок нельзя закрыть.
3. **Сделать golden set контрактом регрессии.** Любое изменение промпта
   или урока — с повторным прогоном по рубрике и записью результата.
   Утвердить порог приёмки; предложенный порог новая версия промпта
   проверки проходит, старая — нет.
4. **Ввести правило сессии у БА.** Большинство ошибок повторялось после
   замечания БА, поэтому БА проверяет каждый ответ по всем замечаниям
   сессии и по вопросам «Проверка», а не только по последнему замечанию.
5. **Новое замечание БА — сначала кейс, потом правило.** Путь замечания:
   правило сессии → урок в реестре → кейс golden set → генерация блоков →
   повторный прогон.
6. **Расширить проверку на остальные промпты и режим реальной работы БА**
   до приёмки этапа 1; затем решить вопрос сжатия блоков уроков.
7. **Классы ручного конвейера** получают те же уроки из реестра; их
   превращение в самостоятельные промпты — задача этапов 2–3 с прохождением
   того же golden set.
8. **Поправить RFC модернизации репозитория** по разделу 4: цикл опыта
   прогонов должен получить решение, задачу и владельца, а критерий
   неизменности прогонов — формулировку «существующие прогоны не
   изменены».
