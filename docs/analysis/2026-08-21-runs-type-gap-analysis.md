# Анализ: пробел контракта прогонов — типы прогонов не разделены

## Summary / BLUF

Гипотеза issue [#293](https://github.com/G-Ivan-A/mango_ba_prompts/issues/293)
**подтверждена**. Действующий контракт
[`standards/runs-contract-standard.md`](../../standards/runs-contract-standard.md)
(v0.1) не содержит ни поля типа прогона, ни различия метрик успеха, ни правил
границ по отношению к рабочим артефактам: слова `run_type`, «тип прогона»,
«статистика» и запрет на изменение `prompts/`, `kb/`, `site/data/`, `patterns/`
в тексте стандарта отсутствуют. Фактические записи `RUN-0001…RUN-0014` уже
содержат два разных класса задач под одной схемой, а метрики этих классов
смешаны в одном поле `status`/`success_rate`. Следствие для issue #293:
расширение контракта нужно выполнить.

## Context / Scope

- **Дата:** 2026-08-21. **Автор:** Konard (AI) по постановке владельца репозитория.
- **Охват (`scope`):** `standards/runs-contract-standard.md` v0.1,
  `runs/README.md` v0.1, все 14 записей `runs/2026/RUN-XXXX/metadata.yaml`,
  валидатор `scripts/validate_issue_123_runs_contract.py`.
- **Что интерпретируется:** достаточность контракта Run для фиксации серии из
  30+ предстоящих прогонов, среди которых есть прогоны ради артефакта и прогоны
  ради накопления статистики о применении промптов.
- **Метод:** чтение текста контракта, инвентаризация `metadata.yaml` всех
  прогонов, сверка заявленной цели каждого прогона (его `outputs/`) с полями,
  которыми зафиксирован его результат.

## Findings / Options

### Ф-1. В контракте нет понятия типа прогона

Обязательные поля v0.1 — `run_id`, `process`, `version`, `date`, `author`,
`model`, `status`. Поле `process` называет процесс («что выполнялось»), но не
цель фиксации («зачем зафиксировано»). Проверка текста:

```bash
$ grep -nEi 'run_type|тип прогона|статистик' standards/runs-contract-standard.md
$ # пусто
```

Из-за этого прогон ради артефакта и прогон ради данных неотличимы машинно и
попадают в одну выборку.

### Ф-2. Метрики успеха смешаны

`status` описан в `runs/README.md` как «состояние результата: `draft`,
`experimental`, `success`, `partial-success`, `works-with-edits`» — это шкала
качества **артефакта**. Для прогона, который фиксируется ради статистики,
осмысленной шкалы в контракте нет, и метрики статистики попадают в те же поля:

- `RUN-0013` (`metadata.yaml`): `status: works-with-edits` (шкала артефакта) и
  одновременно `success_rate: "0.62 (75 из 121 ответов приняты БА…)"` — доля
  принятых реплик, то есть статистика коммуникации «пользователь ↔ ИИ»,
  записанная в карточку прогона-исполнения.
- `RUN-0014`: заявлен в
  [`CHANGELOG.md`](../../CHANGELOG.md) как «запись сделана для статистики и
  анализа результативности промптов и галлюцинаций», при этом его собственный
  результат оценён по шкале артефакта (`success_rate` 0.25 — «завершён 1 шаг из
  4»). Один и тот же прогон читается и как исполнение, и как статистика.

Однородную выборку по такой разметке собрать нельзя: `success_rate` в RUN-0013 и
в RUN-0014 измеряет разные вещи.

### Ф-3. Границы прогона не зафиксированы

Контракт описывает, что Run **содержит**, но не описывает, чего Run **не
делает**. Ни в стандарте, ни в `runs/README.md` нет запрета на то, чтобы прогон
менял `prompts/`, `kb/`, `site/data/`, `patterns/`. Фактически все 14 записей
этому правилу следуют — все пути в полях `inputs`/`outputs`/`logs`/`feedback`/
`source_paths` указывают внутрь каталога самого прогона, — но это соблюдается
по традиции, а не по норме, и не проверяется валидатором.

### Ф-4. Два класса уже существуют де-факто

Инвентаризация по фактической цели (из `outputs/` каждого прогона):

| Класс де-факто | Прогоны | Цель |
| --- | --- | --- |
| Исполнение | RUN-0001, 0002, 0003, 0006, 0007, 0010, 0011, 0012, 0013, 0014 | Получить артефакт: ТЗ, US, UC-матрицу, ФТ, суммаризацию сессии. |
| Фиксация статистики | RUN-0004 (аудит корпуса промптов), RUN-0005 (self-test 6 промптов), RUN-0008 (A/B проверки цитирования БЗ), RUN-0009 (A/B применения отраслевых стандартов) | Накопить данные о применении промптов и сравнить варианты. |

Оба класса лежат в одной схеме без признака различения — это и есть пробел.

### Опции

- **O-1 (отклонена).** Оставить как есть, различать типы в свободном тексте
  `process`. Не даёт машинной выборки, не решает Ф-2 и Ф-3.
- **O-2 (отклонена).** Завести отдельный корневой каталог `stats/`. Ломает
  сквозную нумерацию `RUN-XXXX`, генератор Pages (`RUNS_DIR`) и валидатор; для
  30+ прогонов это дороже, чем одно поле.
- **O-3 (выбрана).** Ввести обязательное поле `run_type` с фиксированным
  словарём (`execution` | `statistics`), описать метрики успеха каждого типа,
  зафиксировать правило границ и проверять и то и другое валидатором. Для
  записей без поля — дефолт `execution` (обратная совместимость).

## Recommendations

1. Расширить `standards/runs-contract-standard.md`: раздел «Типы прогонов»
   (цель, целевые артефакты, метрики успеха для `execution` и `statistics`),
   поле `run_type` в обязательных полях `metadata.yaml`, раздел «Границы
   прогона» с запретом изменять `prompts/`, `kb/`, `site/data/`, `patterns/`.
2. Обратная совместимость: `run_type` отсутствует → читается как `execution`;
   при явной пометке допускается `legacy` для записей, тип которых не
   восстанавливается.
3. Отразить типы в `runs/README.md` и в колонке реестра.
4. Обновить `scripts/validate_issue_123_runs_contract.py`: словарь значений
   `run_type` и проверка, что пути артефактов прогона не выходят за каталог
   `runs/YYYY/RUN-XXXX/`.
5. Техдолг: расширение сделано без цепочки анализ → RFC → стандарт в полном
   объёме (этот анализ есть, RFC — нет). Завести задачу на восстановление
   цепочки в [`pr-ops/BACKLOG.md`](../../pr-ops/BACKLOG.md).
