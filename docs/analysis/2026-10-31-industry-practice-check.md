# Контрольная проверка стратегии автоматизации БА на соответствие индустриальным практикам

Отчёт отвечает на вторую задачу постановки
[#417](https://github.com/G-Ivan-A/mango_ba_prompts/issues/417). Нужно
проверить, что решения по структуре проекта и архитектуре из
[RFC стратегии](../rfc/2026-10-ba-automation-strategy.md) совпадают с
индустриальными практиками agentic coding и инженерии LLM-систем, то есть
что проект «не изобретает велосипед». Порядок действий по итогам
проверки задан владельцем:

- **критичные отклонения есть** — согласование RFC откладывается,
  корректировки от видения до дорожной карты предлагаются, но не вносятся;
- **критичных отклонений нет** и выбранный путь целесообразен — статус
  согласования подтверждается.

## Summary / BLUF

1. **Критичных отклонений нет. Статус согласования RFC подтверждён
   (`accepted`, версия 0.2).** Проверено 12 решений с исправлениями
   владельца из #417. Девять совпадают с практикой полностью, три —
   частично. Ни одно частичное совпадение не меняет видение, концепцию
   или порядок этапов. Каждое закрывается мерой внутри своего этапа до
   его ворот.
2. **Каркас стратегии совпадает с практикой.**
   - Процессы — детерминированные потоки (workflows) с вызовами модели
     внутри шагов, а не автономный агент.
   - Решения на гейтах принимает человек.
   - Контракт процесса отделён от исполнителя.
   - Качество проверяется регрессионной оценкой на golden set.
   - Промпты, решения и архитектура ведутся в Git как код (RFC и ADR).
   - Сложность растёт по этапам только при доказанной пользе.
3. **Путь «n8n как стенд → код в промышленной эксплуатации» оправдан,
   но в нём есть место для велосипеда.** Это исполнитель этапа 4. Если
   писать с нуля хранение состояния, повторы, возобновление и ожидание
   человека, проект повторит то, что уже умеют готовые движки
   устойчивого исполнения (durable execution). Решение принимается в
   начале этапа 4. Сейчас это не блокирует согласование, но должно стать
   критерием входа этапа 4 (REC-417-01).
4. **Шесть некритичных рекомендаций REC-417-01…REC-417-06 предложены
   владельцу на согласование и в RFC не внесены.**

## Context / Scope

**Что проверялось.** Решения RFC стратегии v0.2 с исправлениями владельца:
- этап 2 — OpenCode;
- этап 3 — потоки n8n на выделенном сервере как испытательный стенд
  машинной оркестрации;
- этап 4 — промышленное решение без n8n: процессы в коде на Python под
  управлением собственного исполнителя процессов (runner);
- витрина — сайт GitHub Pages на этапах 1–3, решение о портале на этапе 3;
- структура проекта: документы, решения, промпты, статистика прогонов.

**Что не проверялось.**
- Качество отдельных промптов: это делает трек промптов #411.
- Выбор поставщика LLM.
- Оценки трудоёмкости: это гипотезы, их калибрует этап 1.

**Метод.**
1. Выписаны решения RFC, которые задают направление: этапы, исполнители,
   гейты, качество, безопасность, документирование.
2. Для каждого решения найдена практика в первичном источнике
   (документация, стандарт, публикация разработчика) — раздел
   [«Источники»](#источники).
3. Вердикт по шкале «совпадает / частично / отклоняется».
4. Отклонение считается **критичным**, если выполнены все три условия:
   - решение противоречит общепринятой практике;
   - продолжение по выбранному пути создаёт необратимые затраты или риск;
   - исправление требует пересмотра видения, концепции или порядка этапов,
     а не меры внутри этапа.

## Recommendations

Все рекомендации — **PROPOSED**. В RFC стратегии они не внесены и
зарегистрированы в [реестре RFC](../rfc/rfc-register.md) для решения
владельца.

| ID | Рекомендация | Что меняется при принятии | Когда | Основание |
| --- | --- | --- | --- | --- |
| <a id="rec-417-01"></a>REC-417-01 | Исполнитель этапа 4 строить на зрелом движке устойчивого исполнения (например, Temporal) или библиотеке оркестрации, а не писать хранение состояния, повторы и возобновление с нуля. Сравнение «строить или взять» по требованиям ИБ и сопровождения — критерий входа этапа 4 | Карточка этапа 4 («Вход», «Как»); ADR об исполнителе этапа 4 | Вход этапа 4 | Матрица, п. 9 |
| <a id="rec-417-02"></a>REC-417-02 | Контракты процессов (шаги, состояние, гейты) вести в машиночитаемом формате вне n8n, а прогон golden set — отдельным инструментом, который вызывает любой исполнитель. Тогда на этап 4 переносятся контракты и кейсы, а не потоки | Карточка этапа 3 («Как», «Выход»); архитектура, таблица «ядро — исполнитель» | Этап 3 | Матрица, п. 8 |

| <a id="rec-417-04"></a>REC-417-04 | На этапах 3–4 трассировать вызовы модели и шаги процесса по соглашениям OpenTelemetry GenAI и связывать трассы с записями `runs/` | Архитектура, цель «Наблюдаемость» | Этап 3 | Матрица, п. 11 |

## Решение по согласованию

Критичных отклонений нет; двигаться по выбранному пути целесообразно.
По правилу постановки #417 статус согласования подтверждён:
[RFC стратегии](../rfc/2026-10-ba-automation-strategy.md) переведён в
`accepted` (версия 0.2) с исправлениями владельца. Корректировки «от
видения до дорожной карты» не требуются. Рекомендации REC-417-01…06
уточняют этапы 2–4 и могут войти в следующую версию RFC или в задачи
этапов по решению владельца.

## Ограничения проверки

- Веб-источники прочитаны 31.10.2026. Соглашения OpenTelemetry GenAI имеют
  статус Development и могут измениться.
- Статья Anthropic об evals прочитана по выдержкам. Использован только
  общий тезис о типах оценщиков и регрессионных evals.
- Проверка сравнивает решения с практиками, а не измеряет результат.
  Доказательство качества дают ворота этапов и golden set.
- Юридическое заключение по лицензии n8n не делалось. Оно остаётся
  критерием входа этапа 3.
