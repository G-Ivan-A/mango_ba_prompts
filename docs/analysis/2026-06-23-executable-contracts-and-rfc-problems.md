# Систематизация проблем исполнимых контрактов и RFC

> Аналитический отчёт (research, Creative mode). **Только анализ и предложения.**
> Контракты, промпты и RFC этим документом **не изменяются** и **не создаются**
> (жёсткое ограничение задачи [#198](https://github.com/G-Ivan-A/mango_ba_prompts/issues/198)).
> Сам отчёт следует структуре, которую предлагает для RFC в §7.3:
> введение → короткие ссылки на проблемы → подробный план.

## 1. Введение

**Что.** Сквозная инвентаризация дефектов всех *исполнимых* артефактов (контракты,
промпты, run-инструкции) и всех RFC проекта с привязкой каждой проблемы к
конкретному файлу/секции и планом исправления.

**Зачем.** Артефакты, которые AI-агент исполняет дословно, и артефакты, которыми
*управляют* этим исполнением, перемешаны: агент при выполнении конкретной задачи
вынужден тянуть цепочку «контракт → RFC → стандарт → ADR», правила записаны прозой,
а формат (текст / YAML / JSON) выбирается стихийно. Это снижает повторяемость и
машиночитаемость и удорожает поддержку.

**Охват.** Весь проект, а не только BCREQ-FR / RFC-184: 9 стандартов с
`type: contract`, governance-контракты, ~21 активный промпт, 37 валидаторов,
11 RFC-семейных файлов в трёх «домах». Инвентарь — §8.

**Метод.** Четыре параллельных прохода (промпты; стандарты-как-контракты +
валидаторы; каскад `.executable.md` + governance; RFC) с последующей ручной
верификацией ключевых ссылок по `file:line`.

### 1.1 Аналитическая линза: три уровня и каскад

| Уровень | Что | Роль агента в задаче |
| --- | --- | --- |
| **L1 — Боевой** (исполнимый) | контракты, промпты, run-инструкции | работает **только** с ними |
| **L2 — Данные (KB)** | таксономии, реестры, глоссарии, product docs | **может** ссылаться для контекста |
| **L3 — Управление** | `standards/`, `docs/adr/`, RFC, process-доки | служат для **улучшения L1/L2**; агент **не** обходит цепочку L3 в рамках задачи |

**Каскадный принцип.** Сбой исполнимого документа → правят сам документ (L1);
сбой системный → правят через уровень управления (L3). **Критическое правило:**
вход задачи на генерацию артефакта **не должен** предписывать ссылаться на ADR/
стандарты (L3); **может** — на исполнимые контракты (L1) и данные KB (L2).

## 3. Проблемы исполнимых контрактов (детально)

### K-P1 Смешение уровней

**K-P1.1 — самый сильный образец.** `governance/bcreq-fr-generation-contract.md`,
§2 «Входные данные» делает обязательными (`Да`) входами:
- стр. 64 `rfc_184` → `governance/rfc/bcreq-ft-scope-formation-rules-proposal.md` (L3, RFC);
- стр. 65 `taxonomy_sources` → `standards/industry-taxonomy-standard.md`,
  `standards/mango-taxonomy-standard.md` (L3, стандарты) + `kb/*/registry.json` (L2).

Исполнимый контракт предписывает агенту читать RFC и стандарты **как вход задачи** —
прямое нарушение критического правила. L2-реестры (`kb/*/registry.json`) допустимы;
L3 (RFC-184, taxonomy-standards) — нет.

**K-P1.2.** Тот же файл, frontmatter `integrates:` (стр. 16) перечисляет RFC-184 и
taxonomy-стандарты на уровне метаданных — закрепляет L3-зависимость контракта.

**K-P1.3.** `standards/ba-ontology.executable.md`, TRIGGER-4 (стр. 28): условие
эскалации в «полный» слой сформулировано как «краткая онтология конфликтует с
**ADR-003**». Исполнимый слой именует L3-ADR в триггере — агент должен «знать» про
ADR, чтобы исполнять.

**K-P1.4.** `governance/approval-contract.md`, `applies_to:` (стр. 11-16) =
RFC/ADR/Standards/Research/Analysis. Контракт *исполняется над* L3-документами —
это легитимно (его работа — согласование), но он помечен `executable: true` и при
этом не отделяет «правила, которые агент исполняет» от «документов уровня L3, над
которыми он работает». Риск: при использовании как L1-вход тянет L3-контекст.

**K-P1.5.** `standards/prompt-standard.md`, правило 6 (стр. 76-80): тело промпта
**ДОЛЖНО** содержать Markdown-ссылки на стандарты и глоссарий. То есть сам норматив
требует встраивать L3/L2-ссылки в L1-промпты. Дополнительно frontmatter стандарта
`related_artifacts` (стр. 8-12) указывает на `docs/adr/006-prompt-naming.md`,
`docs/ba-processes/00-index.md` — управленческая трассировка зашита в контракт.

**K-P1.6.** `prompts/README.md` (раздел «Связанные документы» → `standards/` +
ADR-001), `prompts/README.executable.md` (frontmatter `related_standard`, тело →
`docs/ba-processes/`), `prompts/session-debug-documentation-oneshot.md` (упоминает
ADR-001). Активные task-промпты (21 шт.) от L3 чисты — утечка локализована в
README/служебных промптах.

### K-P2 Неясные ссылки на источники

**K-P2.1.** `governance/bcreq-fr-generation-contract.md`, `source_attachments:`
(стр. 12) — ссылка на `github.com/user-attachments/files/…` (внешнее вложение, не
permalink в репозитории; нестабильно, не версионируется).

**K-P2.2.** `governance/approval-contract.md`, `source_attachment:` (стр. 10) =
`"Правила согласования документа.txt"` — голое имя файла. Источника нет в
репозитории, нет permalink, нет SHA. Воспроизвести генезис контракта невозможно.

> Контраст-эталон: `standards/cascading-context-loading-standard.md`,
> `AI_GOVERNANCE.md`, `governance/rfc-process.md` дают `source_hub` + `source_sha`
> (пиннинг на коммит Хаба). Это норма, которую остальным контрактам не хватает.

### K-P3 Нет машиночитаемости

**K-P3.1.** Нормативные правила записаны прозой почти везде. **Единственный**
контракт с машиночитаемым индексом правил — `governance/bcreq-fr-generation-contract.md`
§3 «Machine-readable index» (стр. 81): стабильные ID (`BCREQ-FR-GEN-SCOPE-01/02`,
`RFC-184-S1`). Остальные 8 контрактов-стандартов (`standards/*` с `type: contract`)
и все промпты правил в YAML/JSON не выносят — валидатор/агент вынужден парсить прозу.

**K-P3.2.** Нет систематического разделения **ПРАВИЛО** (нормативное, исполняемое)
и **ПОЯСНЕНИЕ** (обоснование, контекст). Положительное исключение —
`standards/prompt-standard.md` `## Обоснование` (стр. 147) и `## Критерии (DoD)`:
обязательства сверху, rationale в конце. Этот паттерн нигде не закреплён как норма.

### K-P4 Нет разделения классов правил

**K-P4.1.** `AI_QUICK_RULES.md` смешивает **управленческие** правила (fail-closed
семантика, «выключенные гены», эскалация — это про *то, как принимаются решения*) и
**боевые** правила (что агент делает по шагам). Один файл одновременно и L3
(governance), и L1 (операционные инструкции) — агент не может отличить «исполнить»
от «учесть при управлении».

**K-P4.2.** `runs/CONTRACT.md` дублирует `standards/runs-contract-standard.md` —
один и тот же норматив существует и как боевой контракт (рядом с данными `runs/`),
и как стандарт (L3). Дрейф неизбежен; неясно, какой источник истинный.

### K-P5 Нет правила выбора формата

**K-P5.1.** В проекте нет правила, **когда** норматив пишется прозой, а когда —
YAML/JSON. Следствие: §3 BCREQ-FR — YAML-индекс; те же по природе правила в других
контрактах — проза; формат выбирается по контракту, а не по типу содержимого.

**K-P5.2.** Температура промпта задаётся минимум тремя несогласованными способами
(frontmatter `temperature:` по `standards/prompt-standard.md`; прозой в теле
отдельных промптов; в README). Один параметр — три представления (P5 + P3).

**K-P5.3.** `prompts/archive/fr-validation-*-legacy.md` предписывают вывод «без
разметки Markdown», тогда как остальные промпты требуют Markdown. Правила формата
вывода противоречат друг другу между артефактами и нигде не сведены.

## 4. Проблемы RFC (P6)

**R-1 — несколько «домов», нет реестра-источника истины.** RFC-семейство
разбросано: `governance/rfc/` (3 файла), `governance/rfc-to-hub-*` (2),
`docs/analysis/` (6: `2026-06-22-rfc-industry-taxonomy-improvement.md`,
`2026-06-22-rfc-mango-taxonomy-improvement.md`, `2026-06-22-rfc-rules-registry-system.md`,
`2026-06-22-rfc-taxonomy-extension-mechanism.md`, `2026-06-02-migration-strategy-rfc.md`,
`2026-06-23-approval-contract-test-industry-rfc.md`), плюс реестр `governance/rfc-register.md`
и процесс `governance/rfc-process.md`. Где «настоящий» RFC, а где анализ — по
расположению не определить.

**R-2 — два расходящихся шаблона.** «Тяжёлый» с блоком `## Статус: proposed` +
предупреждением «это предложение, не изменение»
(`governance/rfc/bcreq-ft-scope-formation-rules-proposal.md`) против «лёгкого» с
тонким frontmatter. `docs/analysis/2026-06-22-rfc-rules-registry-system.md` вовсе без поля
`type:` и с `issue: 186` (голое число), тогда как
`docs/analysis/2026-06-22-rfc-industry-taxonomy-improvement.md` имеет `type: rfc` и
`issue: "<url>"`. Единого нормативного шаблона нет.

**R-3 — анализ перемешан с предложениями.** В
`governance/rfc/bcreq-ft-scope-formation-rules-proposal.md` каждое правило несёт
inline-блоки `**Обоснование:**` и `**Риски:**` (стр. 101-116 для S1, 151-167 для
S2). Нормативная инструкция и аналитическое обоснование склеены в одном месте —
исполнителю/валидатору приходится отделять «что делать» от «почему» вручную.

**R-4 — примеры вместо инструкций.** Там же блок `Пример:` (стр. 142-144) и
иллюстративные псевдо-кодовые врезки несут смысловую нагрузку правила. Пример
показывает частный случай, но не задаёт алгоритм — агент вынужден обобщать сам.

**R-5 — структурная вода.** Разделы `## Альтернативы`, `## Приоритизация`,
`## Риски` присутствуют как обязательные даже там, где не несут решения (RFC-184:
А1/А2 завершаются «рассмотреть, если…», «не рекомендуется» — без влияния на план).
Объём растёт, плотность падает.

**R-6 — список проблем неполный/фрагментирован.** RFC-184 фиксирует ровно 2
паттерна (S1/S2), хотя по названию покрывает «правила формирования скоупа ФТ»
целиком. `governance/rfc-register.md` дробит проблемы по нескольким таблицам (по
классам RFC), есть устаревшая связка. Единого исчерпывающего списка проблем на RFC
нет.

**R-7 — гигиена решений/статусов неровная.** Сосуществуют ≥3 конвенции фиксации
решения: чекбоксы + ручная строка «Подпись: ___ Дата: ___»
(`…/bcreq-ft-scope-formation-rules-proposal.md` стр. 205-209), статус во
frontmatter, статусная модель реестра (`proposed→in-review→accepted→implemented`,
`governance/rfc-process.md` §4). Машинно отследить статус RFC нельзя.

**R-8 — разброс размера.** От ≈6.6 КБ до ≈53 КБ (6×) при отсутствии нормы объёма —
прямое следствие R-3/R-4/R-5.

## 5. Сквозные проблемы

**X-1 — sprawl валидаторов «один на issue».** 37 файлов `scripts/validate_issue_*.py`,
именованных по номеру issue, а не по проверяемому правилу; общий помощник
`require_text` копипастится; большинство проверок — наличие подстроки. Проверки
привязаны к разовым задачам, а не к стабильным ID правил (контраст с §3 BCREQ-FR,
где ID правил уже есть). Масштабирование линейно по issue, а не по правилам.

**X-2 — дрейф каскада `.executable.md` без single-source.** Модель
`standards/cascading-context-loading-standard.md` (лёгкий исполнимый слой
`*.executable.md` + полный `*.md`, закрытые TRIGGER-списки, DoD по токен-доле) —
жизнеспособна и рекомендуема. Но bootstrap-промпт хендовера растиражирован по
`AI_SESSION_HANDOVER_PROMPT.md`, `AI_SESSION_HANDOVER_PROMPT.executable.md`,
`governance/agent-onboarding-protocol.md` (+ копии в README/ADR) и уже разошёлся.
Нет single-source и CI-проверки паритета копий → контент дрейфует (P1/P3 на уровне
архитектуры).

**X-3 — L2-данные подшиты под `standards/`.** `standards/GLOSSARY.md` и
`standards/team-directory.md` — это данные KB (L2), а лежат в каталоге уровня
управления (L3). Обратное смешение уровней: каталог говорит «стандарт», содержимое —
«данные».

| L3 как обязательный вход L1 (K-P1.1/.2/.3/.5) | агент обходит цепочку управления в рамках задачи |
| L1, работающий над L3 без разделения (K-P1.4) | боевой ⇄ управленческий контур слиты |
| L2-данные в каталоге L3 (X-3) | каталог ≠ уровень содержимого |
| Управленческие + боевые правила в одном файле (K-P4.1) | нет разделения классов правил |
| Один норматив в двух местах (K-P4.2, X-2) | нет single-source, дрейф |

## 7. Детальный план исправления

Принципы плана: **минимум воды, минимум примеров, полный список действий.** Каждое
действие помечено закрываемыми проблемами. Действия — нормативные предложения для
будущих RFC/PR; этим отчётом они **не внедряются**.

### 7.1 Разделение классов правил: управление vs боевой

Ввести явную классификацию правил и закрепить её машинно.

1. **Метка класса во frontmatter.** Каждый артефакт с правилами несёт
   `layer: L1|L2|L3` и (для L1) `rule_class: combat`. Управленческие документы —
   `rule_class: management`. *(K-P4.1, K-P1.4, X-3)*
2. **Боевые правила (L1)** — императивы (ДОЛЖЕН/НЕ ДОЛЖЕН/СЛЕДУЕТ/МОЖНО, BCP-14),
   со стабильными ID, машинно-проверяемые, **без** L3 во входах. Живут в
   `prompts/`, `governance/*-contract.md`, `runs/`. *(K-P1.1, K-P1.5)*
3. **Управленческие правила (L3)** — объясняют «почему» и регулируют **эволюцию
   L1/L2**. Живут в `standards/`, `docs/adr/`, RFC. Агент их **не загружает** во
   время задачи. *(K-P1.3, K-P4.1)*
4. **Жёсткий инвариант входов.** Вход L1-контракта **НЕ ДОЛЖЕН** перечислять L3 как
   обязательный (`Да`) вход; **МОЖЕТ** — L1-контракты и L2-данные. Закрыть
   CI-проверкой по `executable: true`. *(K-P1.1, K-P1.2)*
5. **Развести дубль** `runs/CONTRACT.md` ↔ `standards/runs-contract-standard.md`:
   один источник истины (норматив — L3-стандарт; боевой — тонкая ссылка-обёртка).
   *(K-P4.2)*
6. **Перенести L2-данные** `GLOSSARY.md`, `team-directory.md` из `standards/` в
   каталог данных KB (напр. `kb/` или `docs/`); обновить ссылки. *(X-3)*
7. **Расщепить `AI_QUICK_RULES.md`** на управленческий слой (решения/эскалация) и
   боевой чек-лист, либо явно разметить блоки по `rule_class`. *(K-P4.1)*

### 7.2 Правило выбора формата: текст vs YAML/JSON

Закрепить детерминированный выбор формата по типу содержимого.

| Содержимое | Формат | Почему |
| --- | --- | --- |
| Нормативные правила, входы/выходы, перечислимые наборы, критерии валидации | **YAML/JSON** со стабильными ID | парсится агентом и CI без эвристик |
| Обоснование, контекст, нарратив, обучающие пояснения | **проза (Markdown)** | для человека; не исполняется |
| Смешанное (контракт) | YAML-индекс правил **+** соседний прозовый блок ПОЯСНЕНИЕ, явно разделённые | разделение ПРАВИЛО/ПОЯСНЕНИЕ |

Действия:

8. **Обязать машиночитаемый индекс правил** в каждом исполнимом контракте по
   образцу `governance/bcreq-fr-generation-contract.md` §3 (стабильные ID правил).
   Проза допускается только как смежное ПОЯСНЕНИЕ. *(K-P3.1, K-P3.2, X-1)*
9. **Единый источник для параметров** (температура и пр.): только frontmatter-поле;
   запретить дублирование прозой/в README. *(K-P5.2)*
10. **Свести правила формата вывода** (Markdown vs «без разметки») в один норматив;
    устранить противоречие legacy-промптов. *(K-P5.3, K-P5.1)*
11. **Критерий формата как правило стандарта:** добавить в норматив явный тест
    «правило перечислимо/проверяемо → YAML; иначе → проза». *(K-P5.1)*

### 7.3 Рекомендуемая структура RFC

Единый нормативный шаблон (введение → короткие ссылки на проблемы → подробный
план), один «дом», анализ отделён от предложений.

```
Frontmatter: type: rfc · id: RFC-NNN · status · единственная ссылка на реестр · трассировка (source/based_on)
1. Статус        — одна строка: proposed|in-review|accepted|...; «это предложение, не изменение»
2. Контекст      — ≤1 абзац: почему сейчас, ссылка на сигнал/прогон (L2/run)
3. Список проблем — ТАБЛИЦА: ID | паттерн | где (file:section) | класс. ПОЛНЫЙ, не фрагментированный
4. Предлагаемые изменения — по каждому ID проблемы: нормативная ИНСТРУКЦИЯ (императив), без примеров
5. План реализации — упорядоченные действия; каждое → закрываемый ID проблемы
6. Решение       — машиночитаемые статус-чекбоксы (без ручных «Подпись:»)
7. Приложение (опц., ОТДЕЛЕНО) — Обоснование / Альтернативы / Риски: весь анализ ТОЛЬКО здесь
```

Действия:

12. **Один дом для RFC.** Принять `governance/rfc/` как каталог RFC; `docs/analysis/`
    оставить под анализ. Файлы `docs/analysis/rfc-*` либо перевести в RFC по шаблону,
    либо переименовать в анализ. Реестр `governance/rfc-register.md` — единственный
    источник статуса. *(R-1)*
13. **Один нормативный шаблон** (выше) + обязательный frontmatter `type: rfc` и
    `id: RFC-NNN`. Устранить тонкие frontmatter без `type:`. *(R-2)*
14. **Анализ — в приложение.** Перенести `Обоснование`/`Риски` из тела правил в §7
    шаблона; в §4 оставить только инструкции. *(R-3)*
15. **Инструкции вместо примеров.** Правило формулируется как алгоритм; `Пример:`
    допускается только в приложении как иллюстрация, не как носитель правила. *(R-4)*
16. **Полный список проблем.** Один исчерпывающий перечень с ID; запрет дробить по
    нескольким таблицам. *(R-6)*
17. **Машиночитаемое решение.** Статус-чекбоксы вместо ручной подписи; статус
    синхронизируется с реестром. *(R-7)*
18. **Убрать обязательность «водяных» блоков.** `Альтернативы`/`Приоритизация` —
    опциональны и только при влиянии на план; норма объёма ориентирует на плотность.
    *(R-5, R-8)*

### 7.4 Прочие действия (контракты)
