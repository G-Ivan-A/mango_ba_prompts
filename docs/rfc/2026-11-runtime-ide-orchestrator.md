# RFC-RT-003: IDE-слой runtime для этапа 2 — оркестратор, гейты, MCP

## Summary / BLUF

Задача — [#506](https://github.com/G-Ivan-A/mango_ba_prompts/issues/506).
Это анализ и RFC `proposed`. Runtime, тексты промптов и SHA реестра не
меняются. Ничего не деплоится, модельных прогонов не было. Задача runtime
только описана (раздел 11), не создана. Вход:
[аудит готовности](../audit/2026-11-26-runtime-stage2-ide-readiness.md).

**Вывод аудита.** Runtime готов как источник контекста, но не как
IDE-среда. Не хватает пяти вещей:

- оркестратора и команд `/a-*`;
- маршрута этапа 1 в runtime: исполняется RG-BCREQ-v1, а не Ш-* и AIN-01…24;
- карты автономных шагов и гейтов;
- MCP и разрешений;
- песочницы для состояния прогона.

В прогоне 1143 критические сбои шли на гейтах. Допуск AIN-21 был выведен
из ответа на другой вопрос и затем ушёл в Г-IN. Корень — решение БА
определяет модель по тексту чата.

**Что предлагается** (решения Р-RT-10…Р-RT-21, раздел 9):

1. **Оркестратор — агент OpenCode**, а не скрипт. Это продолжает ADR-016:
   «Python/скриптовый оркестратор в работе БА не нужен». Состав:
   - первичный агент `bcreq-orchestrator`;
   - субагент `bcreq-step` исполняет один шаг в отдельном контексте;
   - субагент `bcreq-reviewer` проверяет только на чтение.

   Команды `/a-in`, `/a-core`, `/a-work`, `/a-release` запускают
   оркестратор на своём процессе.
2. **Граница автономии — норма этапа 1, без ослабления.** Без остановки
   идут только 14 технических шагов из
   [исполнения A-IN](../ba-processes/bcreq-a-in-execution.md#формат-шагов-и-итог-шага-issue-490).
   Каждый шаг с проверкой БА (Р-09) — остановка с конкретным вопросом.
   Каждый гейт — остановка с вопросом решения, исходами и ролью, которая
   решает.
3. **Контракт подтверждения.**
   - Решение засчитывается только как явный ответ на последний заданный
     вопрос, с кодом гейта и редакцией (Р-09, LE-04).
   - Вставка промпта, «дальше» или ответ на другой вопрос допуском не
     считаются.
   - Решения пишутся в журнал вне контекста модели. Закрытый гейт не
     повторяется.
   - Возврат предлагает агент — по таблице возвратов, с основанием.
     Подтверждает БА.
4. **MCP — единственный канал к Jira, Confluence и вебу.** По умолчанию
   всё запрещено, серверы только на чтение, секреты в окружении. БЗ
   читается из файловой системы. Недоступный сервер даёт `ACCESS_GAP`, а
   затем `BLOCKED` (Р-19).
5. **Песочница и экспорт.** Состояние прогона живёт вне отслеживаемых
   путей. Правка контрактов, маршрутов, навыков, `AGENTS.md` и конфигурации
   IDE агенту запрещена. Изменения идут только через PR.
6. **Миграция M0…M7** с откатом на каждом этапе. IDE-слой аддитивен поверх
   BL-192 (PR runtime #29) и приёма SSOT (BL-185…BL-188). Откат — удалить
   `.opencode/` и `opencode.json`. Веб-канал этапа 1 работает параллельно,
   пока владелец не переключит.

[ADR-020](../adr/2026-11-adr-020-ide-orchestrator-runtime.md) фиксирует
решение на согласование владельцу.

## 3. Индустриальные источники

Документация прочитана 2026-11-26. Цитаты дословные.

| Источник | Что взято |

| [OpenCode: Agents](https://opencode.ai/docs/agents/) | `primary` — «Runs as the main agent for a session»; `subagent` — «Runs only in a child session through the `subagent` tool»; «The parent agent's `subagent` permissions control which agents it may launch»; «The Markdown body becomes the agent's `system` prompt»; `hidden` «controls visibility, not security» |

| [OpenCode: Tools](https://opencode.ai/docs/tools/) | «`question` pauses execution and presents one or more questions to the user»; свободный ответ разрешён всегда; отказ отменяет вопрос |

| [MCP 2025-06-18: Elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation) | ответы `accept`, `decline`, `cancel`; «Servers MUST NOT use elicitation to request sensitive information» |
| [RFC-RT-002, раздел 3](2026-11-runtime-universal-agent-context.md#3-индустриальные-источники-и-матрица-совместимости-клиентов) | матрица клиентов, Agent Skills, `AGENTS.md` (на 2026-11-19) |

Выводы для дизайна:

- **Нативные примитивы OpenCode покрывают модель #506 без внешнего
  оркестратора.**
  - Команда выбирает агента.
  - Первичный агент вызывает субагентов, а список разрешённых задаёт
    `subagent` в разрешениях.
  - Остановку обеспечивает `question` или обычный ответ в чате.
  - Песочницу задают `edit` и `external_directory`.
- **`hidden` — не защита.** Безопасность держится на разрешениях, а не на
  видимости агента.
- **`ask` — не гейт.** Это подтверждение вызова инструмента. Гейт процесса
  — бизнес-решение роли с журналом. Поэтому контракт гейта задаётся в
  `AGENTS.md` и агенте, а не только разрешениями (раздел 6).
- **Диалект V1 или V2 решает BL-132.** Раздел 4 даёт структуру, которая
  верна для обоих. Имена полей конфигурации выбираются на закреплённой
  версии.

## 4. Целевая структура runtime (ФТ-4)

### 4.1. Дерево

Дельта поверх PR runtime #29 (BL-192, Э1, Э2, Э4) и приёма SSOT
(BL-185…BL-188, каталог `ssot/mango_ba_prompts/` по Р-RT-6):

```text
mango-ba-ai-runtime/
├── AGENTS.md                      # +раздел «Оркестрация и гейты» (канал компиляции, Р-RT-2)
├── opencode.json                  # новое: разрешения, MCP (выключены по умолчанию), инструкции
├── .opencode/
│   ├── agents/
│   │   ├── bcreq-orchestrator.md  # primary: ведёт процесс, держит гейты и журнал
│   │   ├── bcreq-step.md          # subagent: один шаг в отдельном контексте
│   │   └── bcreq-reviewer.md      # subagent: только чтение, проверка до гейта (ADR-016)
│   └── commands/
│       ├── a-in.md                # agent: bcreq-orchestrator; процесс A-IN
│       ├── a-core.md              # A-CORE
│       ├── a-work.md              # A-WORK
│       └── a-release.md           # A-RELEASE
├── .agents/skills/<имя>/SKILL.md  # зеркало BL-192 (без изменений)
├── skills/<имя>.md                # SSOT навыков (без изменений)
├── ssot/mango_ba_prompts/         # приём SSOT этапа 1: маршрут, итог шага, гейты (BL-185…BL-188)
│   └── ... /bcreq-ide-gates.json  # новое: карта шагов и гейтов раздела 5, генерируется в спице
├── docs/kb/                       # БЗ, чтение через ФС (без изменений)
├── routes/rg-bcreq-v1.yaml        # без изменений; не маршрут этапа 1
└── work/  (в .gitignore)          # песочница прогона: состояние, журнал решений, черновики
```

### 4.2. Роли файлов

| Файл | Кто владеет текстом | Что в нём | Что не в нём |
| --- | --- | --- | --- |
| `AGENTS.md`, раздел «Оркестрация и гейты» | `ba-ai-metamodel` → компиляция (Р-RT-2) | правила раздела 6 кратко; ссылки на карту гейтов и агентов | тексты шагов |
| `.opencode/agents/bcreq-orchestrator.md` | runtime; норма — из спицы | цикл раздела 6.1, формат вопроса гейта, журнал | тексты промптов шагов: они читаются из `ssot/` |
| `.opencode/agents/bcreq-step.md` | runtime | «исполни один шаг по промпту из `ssot/`, верни итог шага» | права на запись вне `work/` |
| `.opencode/agents/bcreq-reviewer.md` | runtime | проверка итога шага против критериев, только чтение | права на правку и решение гейта |
| `.opencode/commands/a-*.md` | runtime | `agent: bcreq-orchestrator`, процесс, `$ARGUMENTS` — ключ задачи | логика процесса |
| `ssot/.../bcreq-ide-gates.json` | спица (генерируется из процесса v0.3 и маршрута A-IN) | раздел 5 в машинном виде | правки в runtime |
| `opencode.json` | runtime | раздел 7 | секреты |

### 4.3. Почему не расширять RG-BCREQ-v1

`routes/rg-bcreq-v1.yaml` — исполняемый маршрут runtime: узлы n1…n12,
операционные гейты `G-self` и `G-mach` (тип `llm` или `код`) и гейт
`G-human` (тип `человек`). Он не совпадает с шагами этапа 1:
- в нём нет AIN-01…24;
- нет гейтов Г-IN, Г-С1, Г-W, AIN-21;
- нет 14 технических шагов.

Если перенести туда этап 1, появится второй мастер маршрута, а это
противоречит ролям репозиториев и манифесту #492. Поэтому маршрут этапа 1
приходит в runtime только передачей SSOT (BL-186, BL-188), а RG-BCREQ-v1
остаётся как есть (Р-RT-14).

### 4.4. Пересмотр Р-RT-5 RFC-RT-002

Р-RT-5 («агентов не вводить») опиралась на два факта:

- в RG-BCREQ-v1 одна роль;
- рецензент ADR-016 появится после BL-132.

С моделью #506 триггер наступил. Ролей с разными правами теперь три:

| Роль | Права | Почему отдельный агент |
| --- | --- | --- |
| Оркестратор | ведёт диалог; пишет только в `work/`; вызывает `bcreq-step` и `bcreq-reviewer` | держит журнал и гейты |
| Исполнитель шага | отдельный контекст; читает `ssot/` и БЗ | LE-01 (сжатие) и LE-02 (один шаг) — проблемы 16, 40, 49 прогона 1143. AIN-22 по норме — «отдельный вызов» |
| Рецензент | только чтение | ADR-016 «отдельный reviewer»; П-1143-43: самопроверка в том же контексте пропустила выдуманное |

Р-RT-11 заменяет Р-RT-5 для IDE-слоя. Решение Р-RT-9 (адаптеры) не
меняется.

### 4.5. Уточнение RFC-BCREQ-STEP-FORMAT-001, раздел 6

[Раздел 6](2026-11-bcreq-step-format.md#6-перенос-практики-на-этап-2-opencode)
уже переносил практику этапа 1 в OpenCode. RFC-RT-003 использует его без
изменений в четырёх местах:

- структурированный выход шага: `done`, `check_kind`, `check`,
  `approvals[]`, `next`;
- гейт — инструмент, который ждёт ответа человека; решение пишется в файл;
- формат шагов хранится в файле состояния;
- правила грузятся на каждом вызове шага.

Уточнение одно. Там предлагалось: «Шаг = команда или skill пакета
(`/bcreq-ain-07`, `/bcreq-sh-3`)». По модели #506 БА набирает только 4
команды процесса. Шаг — внутренний вызов субагента `bcreq-step` с промптом
шага из `ssot/`. Пошаговые команды остаются запасным ручным входом, если
владелец его захочет (Р-RT-11). Это не новый пакет: пакет этапа 2 по-прежнему
BL-131 (Р-RT-8).

## 5. Карта автономных шагов и гейтов (ФТ-4)

Источники:

- [ручной процесс v0.3](../ba-processes/bcreq-manual-process.md#действия-после-шага):
  Р-09, таблица «Действия после шага»,
  [решения гейтов](../ba-processes/bcreq-manual-process.md#решения-гейтов);
- [исполнение A-IN](../ba-processes/bcreq-a-in-execution.md#формат-шагов-и-итог-шага-issue-490):
  «Технических шагов 14»;
- маршрут [`bcreq-a-in-route.json`](../ba-processes/bcreq-a-in-route.json):
  24 шага, `advance_while_paused=false`, `resume_requires_ba_instruction=true`;
- BL-230 — форма процесса по шагам.

Карта **не меняет норму**, она её исполняет.

### 5.1. Типы остановок

| Тип | Что делает оркестратор | Кто решает | Чем закрывается |
| --- | --- | --- | --- |
| **T — технический шаг** | исполняет автономно и выводит «Итог шага» в журнал; БА видит итог на ближайшей остановке | — | итог шага без `BLOCKED` |
| **P — проверка БА (Р-09)** | стоп; вопрос «Принять результат <шаг>, редакция <N>?» с исходами «принять / доработать: что / вернуться: куда» | БА | явный ответ на этот вопрос |
| **G — гейт** | стоп; вопрос решения гейта: исходы, роль, для гибрида рекомендация модели с основанием | роль из таблицы гейтов | явный ответ с кодом гейта; запись в журнал с `model_recommendation` и `divergence` для гибрида |
| **B — блокировка (Р-19)** | стоп всего процесса; источник `ACCESS_GAP` или конфликт норм | БА | новые данные или доступ; повтор шага |

### 5.2. A-IN (24 шага)

| Шаг | Тип | Вопрос остановки, если есть |
| --- | --- | --- |
| Ш-0 → AIN-01 | T | — |

### 5.3. Системный формат A-IN, A-CORE, A-WORK, A-RELEASE

Шаги и гейты — по таблицам «Шаги этапа 1» и «Решения гейтов»
[ручного процесса](../ba-processes/bcreq-manual-process.md#шаги-этапа-1).

| Процесс (команда) | Шаги | Остановки |
| --- | --- | --- |
| A-IN, формат `system` (`/a-in`) | Ш-А → Ш-1 → Ш-2 | Ш-А, Ш-1 — P; после Ш-2 — **Г-IN** (G, гибрид, БА; модель рекомендует) |
| A-CORE (`/a-core`) | Ш-3 → Ш-4 → Ш-5 | Ш-3, Ш-4 — P; после Ш-5 — **Г-С1** (G, человек, Заказчик). Оркестратор не ставит критериям «выполнено» за роль (П-1143-54) |
| A-WORK (`/a-work`) | Ш-6 → Ш-7 → Ш-8 → Ш-9 → Ш-В | Ш-6…Ш-9 — P; Ш-В — отдельный контекст без истории (субагент); после Ш-В — **Г-W** (G, человек: PO, архитектор продукта, руководитель КК) и согласованная итоговая оценка |
| A-RELEASE (`/a-release`) | Ш-Р | после Ш-Р — **Выпуск** (G, человек, БА по A-RELEASE); без согласованной оценки Ш-Р не запускается |
| по запросу | Ш-С | P; после — возврат в исходный шаг и его состояние |

Ш-0 — технический шаг старта любого процесса. `/a-in` выбирает формат по
«Состоянию BCREQ», записанному на Ш-0.

### 5.4. Автономные отрезки

Между остановками оркестратор идёт без вопросов БА:

- Ш-0 → AIN-01;
- AIN-03 → AIN-10 (8 шагов);
- AIN-12;
- AIN-15;
- AIN-19;
- AIN-22 — только после допуска AIN-21.

Это 14 технических шагов, ни одного больше. В 1143 на этих шагах шло около
16 ходов БА чистого транспорта (аудит, раздел 4.3) — их снимает оркестратор.

Факт для владельца. AIN-06 и AIN-22 по норме технические, но в 1143 вели
себя как точки решения: вопросы и три хода доработки. Оркестратор исполняет
норму. Если владелец захочет поменять их тип, это правка процесса в спице
через #505, не правка runtime (Р-RT-12).

### 5.5. Совместимость с правилом «запуск — отдельная команда БА»

[Исполнение A-IN](../ba-processes/bcreq-a-in-execution.md#старт-и-один-вызов),
п. 5: «Принятие разрешает предложить следующий шаг, но запуск — отдельная
команда БА и отдельный промпт… на техническом шаге ввод следующего промпта
и есть принятие». В IDE это правило сохраняется так:

| Где | Что считается отдельной командой БА |
| --- | --- |
| Начало автономного отрезка | команда `/a-<процесс>` или явный исход «принять и запустить <следующий шаг>» на вопросе P или G |
| Внутри автономного отрезка (только шаги T) | ввод следующего промпта делает оркестратор; по Р-09 на техническом шаге это и есть принятие |
| После шага P или гейта | исходы вопроса разделены: «принять и запустить <шаг>», «принять и остановиться», «доработать», «вернуться». Принятие без запуска не продвигает маршрут |
| Пауза (`advance_while_paused=false`) | оркестратор ничего не исполняет и не задаёт вопросов, пока БА явно не возобновит (`resume_requires_ba_instruction=true`) |

Это **изменение формы**, а не нормы. Принятие и запуск по-прежнему —
явные решения БА, только в одном адресном ответе с названными исходами.
Неявного вывода нет: П-1143-05 возник, когда одно «продолжаем» засчитали
за два решения. Владелец подтверждает это в Р-RT-13. Если владелец
откажет, исход «принять и запустить» убирается, и запуск остаётся
отдельной командой.

## 6. Контракт оркестратора и подтверждений (ФТ-4)

### 6.1. Цикл

1. Команда `/a-<процесс> <ключ задачи>` выбирает `bcreq-orchestrator`.
   Оркестратор создаёт или открывает `work/<ключ>/state.json` и журнал
   решений `work/<ключ>/decisions.jsonl`.
2. Перед каждым шагом он **перечитывает состояние и журнал из файла** (LE-01).
   Контекст чата источником решений не является.
3. Следующий шаг он берёт из карты раздела 5: из
   `ssot/.../bcreq-ide-gates.json` и маршрута A-IN, а не из памяти.
4. **Тип T.** Вызывает `bcreq-step` с промптом шага из `ssot/` и входами
   из `work/`, один шаг на вызов (LE-02). Итог шага пишет в `work/`. Если
   нет `BLOCKED`, сразу переходит к следующему шагу.
5. **Тип P или G.**
   - Вызывает `bcreq-reviewer` (только чтение) на критерии шага или гейта.
   - Показывает итог шага и ровно один вопрос решения: исходы, роль, для
     гибрида — рекомендацию с основанием.
   - Ждёт ответа. В клиенте с инструментом `question` использует его, в
     остальных — текстовый вопрос.
6. Ответ пишется в журнал (раздел 6.3). Дальше — по исходу: следующий шаг,
   доработка или возврат (раздел 6.4).
7. **Тип B.** Процесс останавливается с указанием источника или конфликта.
   Автономных шагов после `BLOCKED` нет (Р-19).

### 6.2. Что считается подтверждением

| Ввод БА | Засчитывается? | Почему |
| --- | --- | --- |
| Явный ответ с исходом на текущий вопрос: «AIN-21: допуск», «принять редакцию 2» | да | Р-09, LE-04 |
| Выбор варианта в `question` | да | вопрос адресный по построению |
| «ок», «да», «дальше» сразу после вопроса | да, если открыт ровно один вопрос с двумя исходами; иначе — один уточняющий вопрос | LE-04: «подтверждает только последний прямо заданный вопрос» |
| Ответ на другой вопрос: «снимок полон» на гейте AIN-21 | **нет** | П-1143-38 |
| Вставка текста следующего промпта или команды | **нет**, команда только запускает процесс | П-1143-05, 53 |
| Одна строка на несколько решений: «все согласовать» | **нет** для решений с разными ролями или исходами; уточнение по каждому | П-1143-29 |
| Молчание, отказ от `question` | **нет**: вопрос отменён, процесс стоит | Tools: «dismissing it cancels the question» |

Неявного распознавания намерения нет. Общий вопрос «Продолжаем?»
запрещён: вопрос всегда называет шаг или гейт, редакцию и исходы.

### 6.3. Журнал решений

Одна строка JSON на решение. Поля — по таблице «Решения гейтов» ручного
процесса:

```json
{"code": "AIN-21", "type": "hybrid", "outcome": "allow", "who": "BA",
 "when": "<ISO-8601>", "locator": "work/<ключ>/ain-20.md#снимок",
 "version": "r2", "question_id": "<id вопроса>",
 "model_recommendation": "allow", "divergence": false}
```

- **Источник предпосылок.** Предпосылки гейтов проверяются по журналу.
  Пример: допуск AIN-21 для Г-IN — П-1143-44.
- **Закрытый гейт.** Если в журнале уже есть решение по той же редакции,
  гейт не повторяется. Новая редакция требует нового решения.
- **Клиентские данные.** Журнал лежит в песочнице `work/` и не
  коммитится. Экспорт — только sha256 и указатель, как в #506.

### 6.4. Возвраты

1. Оркестратор или рецензент находит причину. Агент **предлагает** точку
   возврата из таблицы
   [«Возвраты маршрута»](../ba-processes/bcreq-manual-process.md#возвраты-маршрута):
   причину, стадию, шаг и основание с локатором.
2. БА подтверждает или выбирает другую точку. Это остановка типа P.
3. Зависимые результаты помечаются устаревшими в `state.json`, их решения
   в журнале — как `superseded`.
4. Тихого отката нет: старые редакции остаются в `work/`.

### 6.5. Чего оркестратор не делает

- не принимает решения гейта за роль: Г-С1, Г-W, Выпуск — только человек;
- не продолжает при `BLOCKED` или открытом `ACCESS_GAP`;
- не правит промпты, контракты, маршруты и навыки;
- не публикует в Jira и Confluence: запись вне песочницы — только через PR
  или вручную;
- не показывает служебные блоки памяти БА, если шаг их не требует
  (П-1143-46).

## 7. Топология MCP и разрешений (ФТ-4)

### 7.1. Серверы

| Канал | Сервер | Режим | Инструменты | Секреты | Если недоступен |
| --- | --- | --- | --- | --- | --- |
| Jira | MCP Atlassian или корпоративный аналог (выбор — BL-132, Р-RT-15) | только чтение | чтение задачи, комментариев, вложений | токен в переменной окружения; в `opencode.json` — только имя переменной | `ACCESS_GAP` → `BLOCKED` на шаге, где нужен источник |
| Confluence | то же | только чтение | поиск и чтение страниц | то же | то же |
| Веб | MCP-сервер поиска и чтения | только чтение | поиск, чтение URL | ключ в окружении | то же |
| БЗ `docs/kb` | нет MCP | ФС | `read`, `grep`, `glob` | — | — |

- Все серверы в `opencode.json` по умолчанию `disabled` и включаются
  локально. Причина — «MCP tools consume model context, so add only the
  servers you need».
- Инструменты записи (создать, изменить, комментировать) запрещены
  правилом `deny` по маске `<server>_*` для записи. Остальное — `ask` или
  `allow` по решению Р-RT-15.
- Встроенные `webfetch` и `websearch` — `deny`. Веб идёт только через
  MCP, единым каналом с локатором.

### 7.2. Разрешения по агентам

| Действие | Оркестратор | Исполнитель шага | Рецензент |
| --- | --- | --- | --- |
| `read`, `grep`, `glob` в клоне | allow | allow | allow |
| `edit` в `work/**` | allow | allow | deny |
| `edit` вне `work/**`: `AGENTS.md`, `contracts/**`, `routes/**`, `skills/**`, `.agents/**`, `.opencode/**`, `opencode.json`, `ssot/**`, `docs/kb/**`, `taxonomy/**` | deny | deny | deny |
| `shell` | ask (только `git status`, `git diff` — allow) | deny | deny |
| `subagent` | `bcreq-step`, `bcreq-reviewer` — allow; прочее — deny | deny | deny |
| `question` | allow | deny (вопросы задаёт только оркестратор) | deny |
| `external_directory` | deny (исключение — внешняя песочница по Р-RT-16) | deny | deny |
| MCP чтение | allow или ask (Р-RT-15) | allow или ask | allow |
| MCP запись | deny | deny | deny |

- Правило по умолчанию — `ask`: «If no rule matches, OpenCode uses `ask`».
  Явный `deny` нужен там, где `ask` нельзя: защищённые пути и запись в
  Jira.
- Smoke runtime запрещает в клоне `runs`, `experiments`, `tools`. Каталог
  `work/` поэтому в `.gitignore` и в исключениях smoke. Альтернатива —
  внешняя песочница (Р-RT-16).
