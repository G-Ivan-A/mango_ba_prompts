## Предлагаемые изменения

### RFC-MCH-P1: Явная фиксация архитектурного слоя в ШАГ 0 промпта glossary

**Промпт:** `prompts/glossary-context-understanding-stepwise.md`

**Что изменить:**
Добавить в ШАГ 0 (Сбор контекста и As-Is) под-шаг фиксации архитектурного слоя
продукта:

```
ШАГ 0. Сбор контекста и As-Is (Подготовительный)
...
N. Зафиксируй архитектурный слой каждой затронутой функции:
   [Функция/настройка] → [Слой-владелец: ЛК ВАТС (настройка) / КЦ (исполнение) / ...].
   Если требование затрагивает оба слоя — явно укажи границу «где настраивается» и
   «где исполняется». Это якорь против смешения слоёв на последующих шагах.
```

**Обоснование:** В кейсе #109 факт Ф10 (настройки распределения — в ЛК ВАТС
[CC, §4.2, с.127], исполнение — в КЦ) пришлось добавлять вручную. Повтор Б1/Б5.

**Риски:** ШАГ 0 удлиняется; при однослойных задачах под-шаг избыточен (пользователь
указывает «один слой»). Частично пересекается с RFC-1025-P1 — см. примечание ниже.

**Тип изменения:** Minor

> **Примечание о дублировании.** RFC-1025-P1 уже предлагает запрос архитектурных
> **компонентов** в ШАГ 0 того же промпта. RFC-MCH-P1 уточняет его в части
> **слоёв настройка/исполнение**. При реализации рекомендуется **объединить** P1
> обоих RFC в одну правку, чтобы не плодить пункты.

### RFC-MCH-P2: Под-шаг (или промпт) «нормализация требования»

**Промпт:** цепочка `understanding` (между glossary и questions)

**Что изменить:**
Ввести явный шаг нормализации сырого требования до постановки вопросов:

```
ШАГ «Нормализация требования»:
1. Разложи требование на атомарные утверждения (что одно утверждение = одна мысль).
2. Для каждого атома отметь тип: потребность / факт-вход / правило / ограничение.
3. Разведи «заявленное решение» и «гипотезу боли» (симптом vs корневая причина).
4. Сопоставь каждый атом с As-Is (есть / частично / нет) — первичный gap-анализ.
```

**Обоснование:** В кейсе #109 декомпозиция (A1–A7), разведение боль/решение и
gap-анализ выполнены вручную — устойчивый разрыв цепочки (повтор после BCREQ-1025).

**Риски:** Может частично дублировать шаг «декомпозиция» в questions-промпте —
нужно решить, делать ли отдельным промптом или под-шагом (открытый вопрос ниже).

**Тип изменения:** Minor (под-шаг) либо Major (новый промпт) — на усмотрение
пользователя.

### RFC-MCH-P3: Отдельный промпт «early-options» (варианты доработки, Раздел 3)

**Промпт:** новый, например `options-solution-design-stepwise` (отделить от
`technical-details-solution-design-stepwise`)

**Что изменить:**
Создать промпт раннего этапа, генерирующий **продуктовые варианты A/B/C** с
плюсами/минусами/сложностью/рисками и опорой на As-Is, БЕЗ детализации ФТ/интеграций
(это остаётся за `technical-details` / Раздел 7).

**Обоснование:** `technical-details-solution-design-stepwise` ориентирован на Раздел 7;
для раннего «Раздела 3» его пришлось адаптировать вручную (убрать детализацию).
Выделенного промпта «варианты доработки» в библиотеке нет.

**Риски:** Рост числа промптов; нужна чёткая граница «Раздел 3 (продуктовый) vs
Раздел 7 (технический)», иначе дублирование.

**Тип изменения:** Major (новый промпт)

## Альтернативы

- **А1 — не вводить новый промпт (P3), а добавить «ранний режим» в существующий
  technical-details.** Плюс: меньше промптов. Минус: смешение раннего и детального
  этапов в одном промпте, риск «съезжания» в Раздел 7.
- **А2 — оставить нормализацию (P2) ручным приёмом БА, задокументировав как паттерн,
  а не промпт.** Плюс: гибкость. Минус: разрыв воспроизводится на каждом прогоне.
