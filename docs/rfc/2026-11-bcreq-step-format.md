# RFC-BCREQ-STEP-FORMAT-001 — цель шага, «Итог шага» и два формата шагов

**Коротко.** В чате 1135-2 БА 66 ходов работал на промптах сайта 2.7.0.
16 проблем чата сводятся к одной верхнеуровневой: **на каждом шаге БА не
видит, зачем запущен промпт, что проверить и нужно ли действие, и вынужден
работать в одном формате взаимодействия**
([анализ](../analysis/2026-11-18-1135-2-chat-step-handoff-analysis.md)).
RFC фиксирует, какие промпты изменены и как, как сохранены оба формата
шагов, какие инструкции обновлены и что из практики переносится на этап 2
(OpenCode). Реализация этапа 1 — [PR #491](https://github.com/G-Ivan-A/mango_ba_prompts/pull/491),
черновики и сайт 2.9.0. Опубликованные промпты `prompts/` не менялись.

### 2.1. Форма итога (п. 1.2 issue)

```text
**Итог шага**

- Выполнен промпт <ID> «<название>»: <что сделано>.
- БА — проверить: <что>. Без решения БА следующий промпт не запускается.
  | Шаг технический, можно проверить (<что>), но не обязательно.
    ИИ-ассистент ожидает ввода промпта <следующий> без обязательного согласования БА выполненных действий.
- Следующий промпт: <ID> «<название>».
```

Технические шаги (14): Ш-0, AIN-01, AIN-03…AIN-10, AIN-12, AIN-15, AIN-19,
AIN-22. Гейты (Ш-2, Ш-5, Ш-В, Ш-Р, AIN-21, AIN-24) техническими быть не
могут: `bcreq_handoff.load()` падает, если их отметить (`NEVER_TECHNICAL`).

## 3. Как доступны оба формата

| Механизм | Где | Поведение |
| --- | --- | --- |
| Переключатель «Декомпозированные шаги» / «Системные (комплексные шаги)» | `site/index.html#step-format-switch`, `site/app.js` (`STEP_FORMATS`, `composeSystemTestKit`) | Меняет карточки раздела «Процессы»; адрес `#processes?track=system` открывает системный формат напрямую (E-09) |
| Строка формата в Ш-0 | `site/app.js`, копирование Ш-0 | Сайт добавляет «Формат шагов: …» к тексту Ш-0; модель формат не спрашивает (ИШ-8) |
| Фасет каталога «Формат шагов» | `prompts.json → filters.formats` | Заменяет фасет stepwise/oneshot; каждый промпт отнесён ровно к одному формату |
| Маршрут | колонка «Следующий» SSOT | Ш-0 → AIN-01 или Ш-А; Ш-2 → Ш-3 после Г-IN; AIN-24 → Ш-3; с Ш-3 маршрут общий |

Формат по умолчанию — декомпозированный: он измерен в #474 и опубликован
как основной. Смешивать форматы внутри раздела 1 нельзя (E-06): Ш-3 проверяет,
что вход пришёл из шага своего формата.

Вид «Полный процесс» (39 классов BCREQ) оставляет поле «Что делает БА»: там
класс — действие БА, а не промпт для копирования (анализ, раздел 6).

Их опубликованные файлы — замороженный архив этапа 1. Блок итога для них

модели, не измерено. Измерение — прогон БА (раздел 8).

## 5. Что не меняется, риски, откат

- **Не меняются:** опубликованные `prompts/*.md`, архив 2.7.0, 39 классов,
  маршрут AIN и его гейты, конституция.
- **Риск: итог удлиняет ответ.** Это три строки и список, только если есть
  что согласовать. Длину ответа измерит прогон БА.
- **Риск: БА пропускает технические шаги.** Это задумано: проверка на них
  по желанию. Гейты защищены `NEVER_TECHNICAL`.
- **Риск: модель пишет итог в начале.** ИШ-1 требует итог последним;
  проверяется прогоном БА.
- **Откат:** удалить блок между маркерами `issue-490:handoff` пересборкой с
  пустым шаблоном; системный формат — удалить `prompts/drafts/system/` и
  перезапустить `generate-pages-data.mjs`. Данные сайта собираются заново.

## 6. Перенос практики на этап 2 (OpenCode)

На этапе 2 ([roadmap](../roadmap.md), [ADR-016](../adr/2026-10-adr-016-ide-client-process.md))
агентный клиент читает пакет правил и файловое состояние задачи. Правила
этого RFC переносятся так:

| Практика этапа 1 | Как на этапе 2 | Что это даёт |
| --- | --- | --- |
| Шаг = промпт для копирования | Шаг = команда или skill пакета (`/bcreq-ain-07`, `/bcreq-sh-3`); два набора команд — два формата | БА не копирует текст; формат — выбор набора команд |
| «Формат шагов» в «Состоянии BCREQ» | Поле в файле состояния задачи | Формат виден всем шагам, не теряется в длинном чате |
| Блок «Итог шага» | Структурированный выход шага (`done`, `check_kind`, `check`, `approvals[]`, `next`); клиент выводит его по шаблону SSOT | Итог нельзя пропустить; П-03, П-04 закрываются средой |
| Гейты и «На согласование БА» | Вызов инструмента, который ждёт ответа человека; решение пишется в файл состояния | Без решения следующий шаг не стартует (ИШ-4) |
| Конституция в начале чата | Правила грузятся на каждом вызове шага | Закрывает П-14: правило не теряется к 144 тыс. токенов |
| «Сначала БЗ, потом вывод» | Обязательный вызов инструмента поиска по БЗ с квитанцией до нормализации | Закрывает П-07 |
| Темп и тон вопросов | Вопросы — отдельная команда (как AIN-16), вызывает её БА | П-12, П-13 — средой, а не просьбой |

Пакет этапа 2 — BL-131, квалификация клиента — BL-132 (P01–P08). Этот RFC не
меняет их триггер: SSOT `bcreq-step-handoff.md` становится одним из входов
пакета. Данные о том, как итог работает на этапе 1, даст прогон БА.
