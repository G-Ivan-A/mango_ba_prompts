# RFC: Таксономия типов задач БА и их артефактов

## Статус: proposed

> **Это предложение, а не изменение.** Ни один прогон и ни один существующий
> артефакт в ходе разбора issue #335 не переоформлялся под предлагаемую
> таксономию. Повышение статуса — по явному решению (см.
> [rfc-process.md](rfc-process.md)).

## 1. Зачем

[ADR-011](../adr/2026-08-adr-011-integration-task-artifacts.md) фиксирует форму
артефактов **интеграционной** задачи. Но в `runs/2026/` лежит 61 прогон, и
интеграционных среди них меньшинство. Если стандарт формы будет один на всех,
он либо окажется избыточным для мелких задач, либо недостаточным для крупных.
Нужно понимать, **какие типы задач вообще встречаются** и какой артефакт каждый
из них выпускает.

## 2. Что показал разбор прогонов

Разобрано 61 значение `process:` и `run_type:` в `runs/2026/RUN-*/metadata.yaml`.

Наблюдения:

1. Поле `run_type` различает только **способ** проведения прогона:
   `execution` (7 прогонов — задача выполнялась) и `statistics` (54 прогона —
   фиксировалась статистика уже состоявшегося диалога с моделью). Оно ничего не
   говорит о **предметном типе** задачи.
2. Предметный тип различим по `process:`, но записан свободным текстом: рядом
   живут `fr-validation-765-headhunter-channel`,
   `Architecture Spike: HH.ru Chats ↔ Mango CC data mapping` и
   `task-1090-human-review-of-twin-links`. Машинно не группируется.
3. Артефакт на выходе повторяется по кругу: `L1/L2/L3`, «вопросы Заказчику»,
   «ФТ», «валидация ФТ», «статистика прогона».
4. Одинаковые по смыслу задачи оформлены по-разному в зависимости от прогона —
   ровно та проблема, которую ADR-011 закрывает для одного типа.

## 3. Предлагаемая таксономия

Пять типов. Тип определяется **вопросом, на который отвечает артефакт**, а не
продуктом, к которому задача относится.

| Тип | Вопрос | Примеры прогонов |
| --- | --- | --- |
| T1. Интеграционная задача | «Можно ли соединить наш продукт с внешней системой и чего не хватает?» | RUN-0055…RUN-0060 |
| T2. Задача контакт-центра | «Как должен вести себя КЦ в этом сценарии?» | RUN-0011, RUN-0032, RUN-0040, RUN-0052 |
| T3. Задача личного кабинета | «Что и как пользователь видит и делает в ЛК?» | RUN-0019, RUN-0027, RUN-0042, RUN-0050, RUN-0051 |
| T4. Задача речевой аналитики | «Что система должна извлечь из разговора и куда отдать?» | RUN-0028, RUN-0033, RUN-0034, RUN-0047, RUN-0049 |
| T5. Процессная задача | «Как мы сами работаем и что в этом сломано?» | RUN-0004, RUN-0005, RUN-0008, RUN-0061 |

Типы T2–T4 покрывают продуктовые задачи и отличаются друг от друга источником
истины и формой приёмки, а не тематикой. T5 выделен отдельно, потому что его
заказчик — команда, а не клиент.

### T1. Интеграционная задача

- **Входные артефакты:** ТЗ Заказчика с нумерованными подпунктами; спецификация
  внешнего API; база знаний собственного продукта.
- **Процесс:** пять шагов ADR-011 (фиксация источников → разбор ТЗ → вердикты →
  техническая модель → таблицы источников).
- **Quality gates:** проверка AI-критиком; соответствие SSOT; читаемость ссылок;
  Human Gate (не блокирует).
- **Результирующий артефакт:** `L1-business-gap-summary.md` + `L4-combined-gap-report.md`.
- **Профиль SSOT:** внешняя спецификация, закреплённая контрольной суммой, плюс
  БЗ продукта. Переписка SSOT не является.

### T2. Задача контакт-центра

- **Входные артефакты:** описание сценария обслуживания; текущая конфигурация
  каналов, очередей и маршрутизации; БЗ продукта.
- **Процесс:** сценарий «как есть» → точки отказа → сценарий «как будет» →
  функциональные требования → пограничные случаи (перевод, таймаут, отказ канала).
- **Quality gates:** каждый шаг сценария имеет ответственную роль; описано
  поведение при отказе; проверка AI-критиком; Human Gate.
- **Результирующий артефакт:** ФТ со сценарием и таблицей пограничных случаев.
- **Профиль SSOT:** БЗ продукта и действующая конфигурация. Внешние API — только
  если сценарий их затрагивает.

### T3. Задача личного кабинета

- **Входные артефакты:** описание экрана или элемента; текущее поведение ЛК;
  UI-паттерны продукта.
- **Процесс:** текущее поведение → изменение → состояния элемента (пусто,
  загрузка, ошибка, права доступа) → влияние на смежные экраны.
- **Quality gates:** перечислены все состояния; проверены права ролей; изменение
  не ломает смежные экраны; Human Gate.
- **Результирующий артефакт:** ФТ по экрану с таблицей состояний.
- **Профиль SSOT:** БЗ продукта и наблюдаемое поведение ЛК.

### T4. Задача речевой аналитики

- **Входные артефакты:** описание извлекаемой сущности; состав данных разговора;
  контракт внешнего приёмника, если выгрузка наружу.
- **Процесс:** что извлекаем → откуда → как размечаем → куда отдаём → как
  измеряем качество извлечения.
- **Quality gates:** определена метрика качества извлечения; описано поведение на
  плохом аудио; согласие на обработку персональных данных учтено; Human Gate.
- **Результирующий артефакт:** ФТ с моделью данных и метрикой качества.
- **Профиль SSOT:** БЗ продукта, контракт приёмника, нормативные требования к
  персональным данным.

### T5. Процессная задача

- **Входные артефакты:** экспорт диалога или прогонов; артефакт, качество
  которого проверяется.
- **Процесс:** измерение → классификация проблем → правило → проверяемость
  правила машинно.
- **Quality gates:** измерение воспроизводимо скриптом; выборка полная, а не
  выборочная; вывод сформулирован как правило.
- **Результирующий артефакт:** анализ в `docs/analysis/` и/или RFC/ADR.
- **Профиль SSOT:** сами артефакты репозитория и логи прогонов.

## 4. Рекомендации по применению

1. Тип задачи фиксируется в `metadata.yaml` отдельным полем (`task_type: T1…T5`)
   в момент заведения прогона, а не постфактум. Существующие 61 прогон
   переоформлять не предлагается — только новые.
2. `run_type` сохраняется как есть: это ортогональная характеристика (как
   проводился прогон), а не тип задачи.
3. ADR-011 применяется к T1 целиком. Для T2–T4 из него берётся только раздел
   «Требование читаемости ссылок»: оно не зависит от типа задачи.
4. Если задача не опознаётся ни как один из пяти типов — это сигнал к расширению
   таксономии через новый RFC, а не к натягиванию ближайшего типа.

## 5. Развитие

- **Шаг 1 (этот RFC).** Зафиксировать типы и их профили.
- **Шаг 2.** Ввести `task_type` в `standards/runs-contract-standard.md` как
  необязательное поле и накопить 10–15 прогонов с ним.
- **Шаг 3.** По накопленным данным проверить, действительно ли профили quality
  gates различаются, и вынести подтверждённые различия в стандарты по типам.
- **Шаг 4.** Сделать `task_type` обязательным и добавить валидатор.

Шаг 3 — точка, где таксономия либо подтверждается измерением, либо
пересматривается. Без него это гипотеза, а не стандарт.
