## 2. Три рекомендованных промпта посекционной генерации

Общие правила промптов вынесены в блок «Общая часть» — его вставляют в начало каждого промпта. Промпты не ссылаются на внешние базы знаний: источники фактов — только входные данные, переданные БА. Продуктовая принадлежность в промптах не определяется.

### 2.0. Общая часть (вставляется в каждый промпт)

### 3.1. Тесты необходимости и достаточности

| Тест | Вопрос | Практика-источник |
| --- | --- | --- |
| Необходимость (necessary) | Если пункт удалить — перестанет ли выполняться проблема/цель 2.x, обязательство перед стороной или ограничение? Нет → пункт лишний | ISO/IEC/IEEE 29148:2018 §5.2.5 (characteristic «Necessary»); BABOK v3 §7.2 (Specify and Model Requirements) |

| Достаточность (complete set) | Покрыта ли каждая способность цели, каждый шаг потока данных и каждый граничный случай? | 29148 §5.2.6 (set «Complete»); BABOK v3 §7.2 |

Пункт **необходим**, если проходит тесты «необходимость» и «трассируемость вверх». Набор пунктов раздела **достаточен**, если проходит тесты «достаточность», «трассируемость вниз», «жизненный цикл» и «каталог граничных случаев». Неоднозначность «необходимых и достаточных» снимается тем, что у каждого пункта есть проверяемый критерий приёмки — это тест «проверяемость».

### 3.2. Как формулировать критерий приёмки

| Тип пункта | Формат критерия | Практика |
| --- | --- | --- |
| ФТ, граничный случай, шаг пайплайна | Gherkin: «Дано {состояние} / Когда {событие} / Тогда {наблюдаемый результат}» | BDD (Given-When-Then); Specification by Example (Adzic) |
| НФТ | метрика + порог + условие измерения | ISO/IEC 25010; Volere fit criterion |
| Термин | термин используется в одном значении во всех разделах; рецензент из каждой стороны интерпретирует одинаково | 29148 (glossary); BABOK v3 §10.20 |
| Граница (включено / не включено) | для каждого результата поставки есть приёмочный артефакт; для каждого исключения — запись о том, кто отвечает | PMBOK (Scope Statement, acceptance criteria), WBS |
| Ограничение | названа сторона, обязательство и что Система делает при его невыполнении | 29148 (constraints); BABOK v3 §10.30 |
| Конфигурационный параметр | для каждого значения описано наблюдаемое поведение | ISTQB (decision table testing) |

Процесс согласования со стейкхолдерами:

1. Критерий приёмки пишется вместе с пунктом, а не после — пункт без критерия не считается готовым (Definition of Ready).
2. Сначала согласуется **необходимость** (матрица трассировки вверх), затем **достаточность** (покрытие цели и каталога граничных случаев), затем **критерии** — три отдельных шага согласования. Так БА в диалоге шёл по разделам (р. 26), но без явных критериев.
3. Приоритет по MoSCoW помечает, какие пункты необходимы для MVP, а какие — кандидаты (например, блок Б атрибутов) (BABOK v3 §10.33 Prioritization).
4. Пункт с критерием «зависит от ответа» получает ссылку на вопрос; он не считается согласованным, пока вопрос открыт.

## 4. Предложения по улучшению

1. Вынести «Общую часть» (2.0) в отдельный файл-контракт и подключать к трём промптам — единый источник сквозных правил RX.1–RX.6.
2. Добавить в шаблон переключатель «новая система / доработка»: от него зависят термины 2.3 («поставка» / «доработка») и применимость «дельты».
3. Требовать в каждом ответе модели блок «Изменения относительно предыдущей версии» — это закрывает самый дорогой класс замечаний БА (р. 30, р. 36, р. 38, р. 40).
4. В шаблон BCREQ-ФТ добавить колонку «Критерий приёмки» к ФТ и к пунктам 4.3 — по формату 3.2.
5. Хранить реестр вопросов отдельно от документа с колонками «адресат» и «на что влияет», ссылаясь на него из пунктов с открытыми значениями.
