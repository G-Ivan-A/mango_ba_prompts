# Ограничения чтения прогона RUN-0073

- **Шкала.** Прогон `statistics`: результат — размеченный реестр ошибок ИИ и кандидаты в эталоны, а не артефакт требований. Приёмки документа БА в экспорте нет (реплика 104 — промежуточная редакция), поэтому `status: draft`, а `success_rate` намеренно не выставлен.
- **Разметка — работа одного разметчика.** Категория, раздел, продукт и происхождение каждого вхождения назначены при фиксации (AI issue solver) и человеком не перепроверены. Достоверность разделена явно: `confirmed` (97) — реакция БА, локатор КБ или прямое правило указывают именно на этот дефект; `plausible` (52) — прямого подтверждения нет. У 18 вхождений `plausible` реакция БА или локатор КБ указаны, но связь с дефектом — вывод разметчика (например, БА молча переписал пункт или возразил против следствия, а не против самой формулировки шаблона-промпта). Выводы о частоте категорий надёжнее читать по столбцу `confirmed` [`../outputs/error-statistics.md`](../outputs/error-statistics.md).
- **Единица учёта — вхождение.** Одна фраза модели может дать два вхождения разных категорий (например, «Валидация HMAC-подписи» — и реализация в функциональном дизайне C01, и ошибочное доменное представление C15). Повторы той же ошибки в новых репликах не схлопываются — так требует issue («Запрещено суммаризировать или упрощать»). Поэтому число вхождений — не число «разных ошибок».
- **«Обнаружено при фиксации»** (57) не означает, что БА ошибку не заметил: он мог не отреагировать на неё в диалоге. Это значит, что в экспорте нет реакции БА, которую можно процитировать.
- **Задержка обнаружения** считается до первой реплики БА, процитированной как реакция; если БА реагировал раньше, но другими словами, задержка завышена.
- **Эвристическая разметка операций БА** в [`../outputs/prompt-usage.md`](../outputs/prompt-usage.md) — по ключевым словам, метки не взаимоисключающие; 23 реплики не распознаны.
- **Токены входа** просуммированы по вызовам и включают переотправку контекста: 2566716 при максимуме 138455 за один вызов — это не объём переписки.
- **BABOK v3 и TM Forum ODA — информативные источники** (правило И5 [`standards/industry-standards-standard.md`](../../../../standards/industry-standards-standard.md)). Номера задач и техник BABOK v3 сверены с оглавлением руководства (2.5 Requirements and Designs, 7.1–7.6, техники 10.18–10.41); сегменты ODA — с моделью компонента ODA (coreFunction с exposedAPIs / dependentAPIs, eventNotification, managementFunction, securityFunction). Сегмент `ODA-IMPL` введён этой записью для реализационных деталей, которых в функциональном дизайне компонента быть не должно; это не сегмент ODA.
- **Основная привязка** (BABOK для разделов ФТ, ODA для функционального дизайна) задана по разделу шаблона, а не по смыслу вхождения: дефект формулировки в разделе 4 считается ODA-первичным, хотя BABOK 7.2 к нему тоже применим (обе привязки есть в реестре).
- **Продуктовая принадлежность и словарь runtime.** SSOT — `taxonomy/products.yaml` runtime на SHA `91406e4`. Сервис-коннектор (71 вхождение) — заказная разработка, класса для неё в словаре нет; ВАТС / VPBX API (24) относится к классу `voice-ucaas`, который помечен `in_slice: false`; CallMentor — внешняя система вне словаря. Значит, большая часть кейсов этого прогона сейчас вне среза runtime — см. вопрос Q2.
- **КБ runtime сверялась точечно**: только по утверждениям модели о VPBX API и Роботе Фил, у которых есть раздел КБ ([`../logs/kb-verification.md`](../logs/kb-verification.md)). Полной сверки всех технических утверждений модели с КБ не было.
- **Вложения не открывались.** Изображение из реплики 6 БА назвал «файл конкурентов», модель ответила, что файла нет (вхождение C07, происхождение `tooling`). Что на изображении — при фиксации не проверялось; вывод «модель не увидела вложение» опирается только на её ответ. PDF Робота Фил (реплика 102) не читался — вместо него использован разбор того же руководства в КБ runtime.
- **Возможности Робота Фил.** Утверждения модели в реплике 103 («нет собственного REST API», «жёсткий лимит», «старые записи будут безвозвратно затерты») помечены как непроверенные (C09) по КБ: у робота есть блок HTTP-запроса (ROBOTFIL §5.6), лимит в документации приведён как пример (ROBOTFIL §7), о перезаписи памяти в §5.20 не сказано. Ответ на вопрос, закрывает ли робот кейс задачи 1123, эта запись не даёт.
- **Ключ API в адресе запроса.** Документированный метод получения ссылки на запись (критерий SC-19) передаёт `vpbx_api_key` в пути URL. Это свойство VPBX API, а не ошибка модели, и вхождением не считается; но требование не писать полный URL в журналы коннектора в документе БА пока не сформулировано — см. Q4.
- **Золотые наборы — кандидаты.** [`standards/evals-contract-standard.md`](../../../../standards/evals-contract-standard.md) запрещает смешивать эталон и факт и требует фиксировать контейнер golden-set решением спока; такого решения нет (пробел #263 в [`pr-ops/BACKLOG.md`](../../../../pr-ops/BACKLOG.md)). Поэтому наборы лежат в записи прогона как кандидаты (`status: draft`) и не являются действующим контрактом — см. Q1.
- **Отбор кейсов в наборы** механический (первое подтверждённое вхождение каждой частой категории, до 8 дефектных и 2 негативных кейсов на набор). Набор GS-373-PRM добран до 5 дефектных кейсов повторными вхождениями единственной категории C19 (шаблон-промпт); в наборе GS-373-PRB ровно 5 категорий на 6 вхождений разделов 1–2, в разделе 1 (глоссарий) вхождений нет — глоссарий покрыт только негативным кейсом.
