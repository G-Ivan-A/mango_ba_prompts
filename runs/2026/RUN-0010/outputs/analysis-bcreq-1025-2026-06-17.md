# Анализ эксперимента BCREQ-1025 (Email-маршрутизация по Точке входа)

Версия: 0.2

Дата: 2026-06-18 (ревизия по итогам ревью PR #108)

## 1. Назначение

Этот документ содержит детальный анализ результатов эксперимента BCREQ-1025 —
второго реального прогона цепочки промптов `mango_ba_prompts` на задаче
маршрутизации email-ответов в Контакт-центре MANGO OFFICE. Анализ выполнен в
режиме `Creative` (нет согласованного стандарта — свобода в методологии) по
требованию [issue #107](https://github.com/G-Ivan-A/mango_ba_prompts/issues/107).

**Цели анализа:**
1. Выявить паттерны ошибок LLM в ходе ~30 итераций согласования.
2. Зафиксировать успешные паттерны (что сработало хорошо).
3. Проанализировать взаимодействие БА + LLM: где тратилось больше всего времени.
4. Сформировать обоснованные предложения по улучшению промптов (→ RFC-1025).
5. Выявить инсайты для онтологии (связь с ADR #003–#010).

**Контекст:**
Задача BCREQ-1025 — маршрутизация email-ответов по «Точке входа» в КЦ: когда
оператор отвечает на входящее письмо, система должна автоматически использовать
почтовый ящик, на который это письмо пришло. Три продуктовых компонента:
ЛК ВАТС (Личный кабинет) ↔ КЦ (Контакт-центр) ↔ Редактор — создавали
архитектурные зависимости, усложнившие формулировку ФТ.

**Участники:**
- **Модель:** qwen3.7 plus, режим — мышление
- **Пользователь:** БА-ИГ

**Источник данных для анализа:** описание эксперимента в issue #107 (ФТ-2),
зафиксированные паттерны ошибок и успехов, сравнение с экспериментом 1027.
Критические замечания по итогам ревью PR (комментарий G-Ivan-A к PR #108)
учтены в версии 0.2 настоящего документа.

## 2. Паттерны ошибок LLM (классификация)

Паттерны сгруппированы в три класса: **структурные** (проблемы формата),
**семантические** (проблемы содержания) и **контекстные** (потеря/путаница
контекста).

### 2.1 Структурные паттерны

#### Б2 — Нарушение глубины иерархии ФТ

**Симптом:** LLM генерировал четырёхуровневую нумерацию `4.x.y.z` (например,
`4.1.1.1`) вместо допустимых трёх уровней `4.x` → `4.x.1` → `4.x.1.1`.

**Причина-гипотеза:** При сложных правилах маршрутизации с множественными
условиями (тип письма → ящик → маршрут → поведение при конфликте) LLM
инстинктивно добавляет уровень, чтобы «разместить» каждое условие. Промпт
`fr-documentation-stepwise` задаёт три уровня, но не содержит явного
**ограничителя** — запрета на 4-й уровень и указания, как обрабатывать
многоусловные правила без углубления.

**Влияние:** Нарушение структуры ТЗ; несоответствие стандарту иерархии ФТ.

**Рекомендация:** → RFC-1025-P4 (явный запрет на 4-й уровень + правило раскладки
многоусловного правила на атомарные `4.x.1`).

#### Б3 — Канцелярит на уровнях 4.x.1, 4.x.1.1 и 4.x.x.x

**Симптом:** Тот же, что Г2 в эксперименте 1027 — тяжёлые канцелярские обороты
на детализирующих уровнях: «Инициация действия осуществляется посредством…»
вместо читаемого «Оператору доступна возможность…». По итогам ревью уточнено:
канцелярит проявляется также на уровне `4.x.x.x` (четвёртый уровень
нумерации), а не только на `4.x.1` и `4.x.1.1`.

**Дополнительный симптом — отсутствие «ВОЗМОЖНОСТЬ»:** При доработке
существующей системы на уровне требований `4.x.x` не используется ключевое
слово «ВОЗМОЖНОСТЬ» (например: «Оператору предоставляется ВОЗМОЖНОСТЬ выбора
источника ответа»). Это существенно для требований уровня расширения
функциональности, где нужно явно отличать обязательное поведение системы от
предоставляемой пользователю возможности.

**Причина-гипотеза:** Правка P2 из [анализа 1027](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/docs/analysis/experiment-1027-analysis.md)
ещё не применена к промпту (RFC-1027-P2 в статусе `proposed`). Повторение той же
ошибки в эксперименте 1025 **подтверждает** необходимость RFC-1027-P2 и усиливает
приоритет реализации. Промпт не предписывает явно использование слова «ВОЗМОЖНОСТЬ»
для задач доработки существующего функционала.

**Влияние:** Снижение читаемости; неоднозначность типа требования (обязательное
vs. возможность); необходимость ручной правки БА на каждой итерации.

**Рекомендация:** → RFC-1025-P3 (подтверждение + усиление: добавить конкретный
пример-эталон для задач маршрутизации; включить правило «ВОЗМОЖНОСТЬ» для
требований к расширению функциональности).

### 2.2 Семантические паттерны

#### ~~Б4 — Путаница ролей~~ (исключён по итогам ревью)

> **Примечание (v0.2):** Паттерн Б4 (путаница ролей Администратор/Оператор/
> Пользователь) исключён из перечня ошибок LLM по итогам ревью PR #108 (комментарий
> G-Ivan-A). Замена ролей была **инициирована пользователем** — модель предлагала
> варианты в пределах допустимого, а не совершала ошибку самостоятельно. Паттерн
> не должен учитываться при приоритизации RFC.
>
> RFC-1025-P2 скорректирован: фокус переносится с «матрицы ролей» на «якорную
> суммаризацию архитектурных границ и запись согласованного контекста».

#### Б5 — Невидимость архитектурных связок

#### Б5 — Невидимость архитектурных связок

**Симптом:** LLM генерировал ФТ для «КЦ» в изоляции, не учитывая, что:
- настройка почтовых ящиков производится в **ЛК ВАТС**;
- маршрутизация в КЦ зависит от этих настроек;
- поведение Редактора при ответе — третье звено цепи.

Архитектурные зависимости «всплывали» только после явных корректировок БА.

**Причина-гипотеза:** Промпт `glossary-context-understanding-stepwise` не содержит
явного шага для фиксации **продуктовых границ и архитектурных связок** (какие
компоненты системы затронуты, как они взаимодействуют). Глоссарий (Раздел 1)
фиксирует термины, но не связи между продуктами. Промпт `fr-documentation-stepwise`
в Шаге 1 суммаризирует контекст, но не запрашивает явно архитектурный контекст
если он не был передан из Раздела 1.

**Влияние:** Генерация ФТ без критически важных зависимостей; необходимость
ретроспективной доработки; итерации на «вспоминание» забытого контекста.

**Рекомендация:** → RFC-1025-P1 (добавить в Шаг 0 промпта glossary явный запрос
архитектурных связок) + RFC-1025-P5 (добавить в Шаг 1 промпта constraints явный
запрос архитектурных зависимостей из контекста).

### 2.3 Контекстные паттерны

#### Б1 — Путаница настроек ЛК ВАТС vs. КЦ

**Симптом:** LLM несколько раз относил настройки ЛК ВАТС к функциям КЦ и
наоборот — повторял одну и ту же ошибку в разных итерациях, не «запоминая»
исправление.

> **Уточнение (v0.2):** По итогам ревью установлено, что критическим замечанием
> является именно **путаница настроек** (какая настройка к какому компоненту
> относится), а не ролей (Б4 — исключён). Это подчёркивает технический, а не
> организационный характер проблемы.

**Причина-гипотеза:** Это проявление «window drift» — в длинном диалоге (~30
итераций) ранние исправления вымываются из приоритетного внимания модели.
Нет механизма «якорного напоминания» — инструкции промпта задают правила один раз
в начале сессии, но не reinforced в критических точках.

**Гипотеза (новая, v0.2):** Явная запись **согласованных результатов** по итогам
каждой фазы генерации в «долгосрочную память» сессии (суммаризация + подтверждение
пользователем → сохранение как «зафиксировано») могла бы предотвратить повторяющееся
забывание. Необходимо исследовать варианты реализации такой долгосрочной памяти
(например, explicit accumulation в инструкции промпта, или паттерн «журнала решений»
внутри диалога).

**Влияние:** БА вынужден повторять одни и те же правки несколько раз; снижение
эффективности.

**Рекомендация:** → RFC-1025-P2 (суммаризация контекста с явной фиксацией
архитектурных границ в начале генерации ФТ; эта «якорная суммаризация» служит
напоминанием для оставшейся части сессии; исследовать механизм долгосрочной памяти
согласованных результатов).

## 3. Успешные паттерны

### У1 — Цепочка 3 промптов работает как единый процесс

Последовательное применение трёх промптов дало цельное ТЗ. Несмотря на то, что
промпты запускаются в разных сессиях LLM (нет автоматического переноса контекста),
механизм ручной передачи данных через явные запросы на Шаге 0/1 каждого промпта
**обеспечивает преемственность**.

**Практический вывод:** Цепочка `glossary → fr → constraints` — это
воспроизводимый паттерн для задач класса BCREQ.

### У2 — `stepwise` для раздела 6 работает лучше, чем `oneshot`

В эксперименте 1027 использовался `constraints-documentation-oneshot`. В BCREQ-1025
— `stepwise`. Результат `stepwise` качественнее: пошаговый майнинг (Шаг 2)
выявил неочевидные ограничения вокруг архитектурных связок ЛК/КЦ/Редактор, которые
oneshot пропустил бы.

**Практический вывод:** Для задач с многокомпонентной архитектурой использовать
`constraints-documentation-stepwise`.

### У3 — Глоссарий как якорь для многозначных терминов

Задача маршрутизации email содержит несколько терминов с бытовым значением, которое
расходится с продуктовым («Точка входа», «Маршрут», «Ящик»). Явное формирование
Раздела 1 на первом шаге предотвратило смешение значений в разделах 4 и 6.

**Практический вывод:** Для задач с нетривиальной терминологией шаг «глоссарий»
критически важен — без него ФТ генерируются в разных понятийных фреймах.

### У4 — Матрица приоритетов в ФТ

В ходе сессии была сформирована матрица приоритетов для функциональных требований,
позволившая Заказчику расставить MVP vs. nice-to-have. Это не предусмотрено явно
в промпте `fr-documentation-stepwise` (только матрица сценариев в Шаге 2), но
возникло органически.

**Практический вывод:** Матрица приоритетов — ценная практика, заслуживает
фиксации как паттерн (не RFC — изменение промпта избыточно; достаточно паттерна).

### У5 — Роли зафиксированы в ограничениях, а не в ФТ

Итоговая архитектура ТЗ: роли (кто что может) вынесены в Раздел 6 (Ограничения),
а в Разделе 4 описаны сценарии без ролевой атрибуции. Это соответствует
рекомендации ADR-009 (подпроцесс П4 — документирование разграничения
ответственности в Разделе 6).

**Практический вывод:** Паттерн «роли → в ограничения» рекомендован к закреплению.

## 4. Анализ взаимодействия БА + LLM

### 4.1 Распределение итераций по промптам

| Промпт | Ориентировочно итераций | Основные причины правок |
| --- | --- | --- |
| `glossary-context-understanding-stepwise` | ~5–7 | Уточнение терминов, фиксация контекста ЛК/КЦ/Редактор |
| `fr-documentation-stepwise` | ~15–18 | Путаница ролей, нарушение иерархии, канцелярит, архитектурные связки |
| `constraints-documentation-stepwise` | ~7–9 | Уточнение границ между компонентами, формулировки ограничений |

**Вывод:** Наибольшая нагрузка на БА — раздел 4 (ФТ). Это согласуется с
результатами эксперимента 1027 и подтверждает приоритет RFC по промпту
`fr-documentation-stepwise`.

### 4.2 Где LLM «запоминал» контекст

**Запоминал (в рамках одной сессии):**
- Термины из Раздела 1 — после передачи глоссария на Шаге 1 промпта FR
  термины соблюдались.
- Базовые правила иерархии (4.x / 4.x.1 / 4.x.1.1) — нарушались реже после
  первой корректировки.
- Факты As-Is из PDF-выжимки — сохранялись корректно на протяжении сессии.

**Не запоминал (повторяющиеся ошибки):**
- Архитектурные границы ЛК vs. КЦ — требовали повторной корректировки.
- Ролевое разграничение — особенно при переходе к новому ФТ.
- Стилистика детализирующих уровней — тенденция к возврату к канцеляриту.

**Вывод:** Контекстное «забывание» — системная особенность длинного диалога, а не
случайность. Промпты должны содержать «якорные механизмы» — повторную активацию
ключевых правил в критических точках сессии.

### 4.3 Наиболее эффективные подсказки БА

По паттерну успешных итераций можно выделить:

1. **Конкретный пример-эталон** («хорошо: "Оператору доступна возможность…",
   плохо: "Инициация действия осуществляется…"») — эффективнее абстрактного
   правила.
2. **Явное указание компонента-владельца** («это настройка ЛК ВАТС, а не КЦ»)
   — быстро перенаправляет генерацию.
3. **Запрос суммаризации** («покажи, что ты понял про архитектуру») — выявляет
   скрытые ошибки контекста до генерации ФТ.

## 5. Инсайты для онтологии (ADR #003–#010)

### ADR-003 (Онтология БА — Артефакт ↔ Процесс ↔ Операция)

**Наблюдение:** Эксперимент подтверждает трёхуровневую модель. Три промпта =
три процесса с явными артефактами:

```
Операция «ingestion/understanding» → Процесс «Раздел 1+2» → Артефакт «Глоссарий + Бизнес-контекст»
Операция «documentation»          → Процесс «Раздел 4»   → Артефакт «Функциональные требования»
Операция «documentation»          → Процесс «Раздел 6»   → Артефакт «Ограничения реализации»
```

**Открытый вопрос для онтологии:** Передача контекста между артефактами (Раздел 1
→ Раздел 4 → Раздел 6) — это операция? Её нет в таксономии 13 операций ADR-004.
Возможно, это «compositing» или «handover» — артефакт прохождения контекста через
цепочку процессов.

**Рекомендация (НЕ изменение ADR):** Рассмотреть введение понятия «контекстный
артефакт передачи» в онтологию как тип артефакта уровня Draft.

### ADR-004 (Таксономия операций)

**Наблюдение:** В эксперименте 1025 задействованы операции:
- `ingestion` (обработка PDF, устных данных, скринкаста)
- `understanding` (формирование глоссария, бизнес-контекста)
- `modeling` (матрица сценариев: Happy Path + альтернативы + исключения)
- `documentation` (разделы 4 и 6)
- `validation` (шаги валидации внутри каждого промпта)

**Соответствие таксономии:** Все использованные операции входят в 13 операций
ADR-004. Новых операций не требуется.

**Дополнительное наблюдение:** Операция «передача контекста между сессиями»
выполняется **человеком** (БА), а не LLM. В таксономии это не выделено явно —
в реальных прогонах это существенная точка трудозатрат.

### ADR-005 (Продуктовая принадлежность / Нейминг артефактов)

**Наблюдение:** В эксперименте явно разграничивались три продуктовых домена:
ЛК ВАТС (`domain_context: lk-vats`), КЦ (`domain_context: cc`), Редактор
(`domain_context: editor`). Модель `domain_context + team_scope + template_ref`
из ADR-005 — рабочая, хотя в данном эксперименте явная метаразметка BCREQ
по доменам не использовалась.

**Практический вывод:** При задачах с многодоменной архитектурой явная
разметка доменов на Шаге 0 промпта может снизить ошибки паттерна Б5.

### ADR-006 (Нейминг промптов)

**Наблюдение:** Все три промпта соответствуют схеме `[домен]-[операция]-[режим]`:
- `glossary-context-understanding-stepwise` ✅
- `fr-documentation-stepwise` ✅
- `constraints-documentation-stepwise` ✅

**Открытый вопрос:** В цепочке нет промпта для явной «передачи контекста» между
сессиями. Если потребность подтвердится в следующих экспериментах, вероятен
новый промпт `context-transfer-stepwise` — что соответствует схеме нейминга ADR-006.

### ADR-007 (Работа с БЗ)

**Наблюдение:** Руководство пользователя КЦ v1.26.04 обработано через механизм
«извлечение фактов As-Is → выжимка → подтверждение → генерация». Механизм работает
корректно (реализован в `glossary-context-understanding-stepwise`, Шаг 0).

**Нюанс:** PDF v1.26.04 — специфичная версия документации. Нет гарантии, что
следующий эксперимент будет на той же версии. Механизм версионирования источников
БЗ в промпте не предусмотрен.

**Рекомендация (НЕ изменение ADR):** При формировании выжимки БЗ указывать
версию источника в явном виде.

### ADR-008 (Отраслевые стандарты)

**Наблюдение:** В ходе эксперимента отраслевые стандарты (TM Forum ODA) явно не
упоминались в ФТ. Шаг 4 промпта `fr-documentation-stepwise` содержит «ODA-Check»,
но в логе это не отразилось как отдельная точка итераций.

**Вывод:** ODA-Check работает как «фоновая» валидация, а не активная итерация —
это ожидаемое поведение для задачи маршрутизации email (домен телефонии/
коммуникаций хорошо покрывается ODA).

### ADR-009 (Процесс BCREQ)

**Наблюдение:** Прогон соответствует подпроцессам конвейера ADR-009:
- П1 (приём/нормализация): Шаг 0 промпта glossary ✅
- П3 (моделирование): Шаг 2 промпта FR (матрица сценариев) ✅
- П4 (документирование): Шаги 3–4 промпта FR + Шаги 2–3 промпта constraints ✅
- Human gate G2 (валидация): ~30 итераций — реализован через диалог ✅

**Открытый вопрос для ADR-009:** Human gate G2 в данном эксперименте
«размыт» по всей сессии (30 итераций), а не является единой точкой. Это
соответствует реальной практике, но расходится с «чистой» моделью одного gate.

**Рекомендация (НЕ изменение ADR):** Рассмотреть концепцию «мягкого gate» —
серии микро-подтверждений — как допустимую реализацию G2.

### ADR-010 (UX GitHub Pages)

**Наблюдение:** Не применимо к данному эксперименту (нет изменений в UI/Pages).

## 8. Дополнительные инсайты (зона свободы)

### Паттерн «Цепочка без проводника»

Три промпта работают как три отдельных агента без явной координации: каждый
промпт начинает с «нуля» (Шаг 0 или Шаг 1 с суммаризацией), предполагая, что
БА вручную перенесёт нужный контекст. При ~30 итерациях это создаёт значительную
когнитивную нагрузку на БА.

**Предложение для будущих экспериментов:** Разработать «промпт-связку» (context
handover) — формальный шаблон для передачи вывода одного промпта как входа
следующего. Это не изменение текущих промптов, а новый артефакт-паттерн.

### Паттерн «30 итераций = сигнал»

Если сессия превышает ~15 итераций, это сигнал о наличии структурных проблем:
либо в промпте (неявные правила), либо в контексте (неполные данные), либо в
сложности задачи (архитектурные зависимости). Метрика `iterations` > 15 —
кандидат для мониторинга качества.

**Предложение:** Добавить в стандарт экспериментов (experiment-log-standard.md)
пороговый индикатор: `iterations > 15 → обязательный ретроспективный анализ`.
