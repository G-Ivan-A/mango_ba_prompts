# Функциональные требования BCREQ-1074

Доработка отчета «Финансы → Расходы на связь» в Личном кабинете MANGO OFFICE.

Статусы утверждений:

- **Подтверждено Заказчиком** — прямо следует из issue #343;
- **Подтверждено БЗ** — следует из указанного раздела руководства;
- **Проектное требование** — формулировка ФТ на основе подтвержденной потребности;
- **Требует решения** — не должно передаваться в разработку до ответа владельца.

## 2. Проблема, цели и задачи

### 2.1. Проблема

Телефонные номера Заказчика используются в разных внутренних проектах. Заказчик
не может получить в ЛК месячную детализацию расходов в требуемом составе для
внутреннего взаиморасчета и контроля бюджета в разрезе УПД. БЗ подтверждает,
что текущий раздел показывает количество, направления, общую длительность и
стоимость звонков и поддерживает фильтрацию, но не подтверждает одновременное
наличие всех семи запрошенных полей в выгрузке.

### 2.2. Цель

Дать уполномоченному пользователю возможность самостоятельно сформировать и
скачать по одному ЛС отчет, достаточный для последующего распределения расходов
Заказчиком между внутренними проектами.

### 2.3. Задачи

1. Добавить формирование детализированного отчета в разделе «Финансы → Расходы
   на связь».
2. Обеспечить выбор ЛС и периода без агрегации нескольких ЛС.
3. Включить в выгрузку заданный набор реквизитов звонка и тарификации.
4. Ограничить действие пользователями с подтвержденным правом доступа.
5. Обрабатывать отсутствие данных явно, не подменяя их вычисленными значениями.

### 2.4. Границы

В scope входят только формирование и скачивание отчета по расходам на связь.
Объединение нескольких ЛС, распределение расходов по внутренним проектам,
создание/изменение УПД, изменение тарификации и бухгалтерский учет Заказчика не
входят в scope.

## 3. Моделирование верхнеуровневых ФТ

### FR-01. Выбор Лицевого счета

Система должна формировать отчет только в границе одного доступного пользователю ЛС.

### FR-02. Выбор отчетного периода

Система должна позволять задать период отчета, включая полный календарный месяц.

### FR-03. Формирование детализации

Система должна формировать строки отчета по звонкам, относящимся к выбранным ЛС и периоду.

### FR-04. Состав данных выгрузки

Система должна включать в отчет семь реквизитов, заданных Заказчиком.

### FR-05. Скачивание и результат операции

Система должна предоставлять сформированный отчет для скачивания и явно сообщать о результате.

### FR-06. Контроль доступа и изоляция данных

Система должна применять действующие права на расходы и исключать данные недоступных ЛС.

## 4. Функциональные требования и сценарии использования

#### FR-01. Выбор Лицевого счета

**Требование:** пользователь выбирает один ЛС из доступных ему. При нескольких
ЛС система не должна формировать агрегированный отчет по всем ЛС; пользователь
повторяет операцию отдельно для каждого ЛС.

**Источник:** issue #343; [LK §2.1](../../../../kb/processed/mango-lk-manual/sections/28-dokumenty.md).

**Статус:** проектное требование; способ переключения ЛС требует проверки UX.

**Критерии приемки:**

1. В запросе формирования указан ровно один ЛС.
2. Каждая строка результата относится к выбранному ЛС.
3. Интерфейс не предлагает режим «все ЛС» для этого отчета.

#### FR-02. Выбор отчетного периода

**Требование:** пользователь задает начало и конец периода; полный календарный
месяц должен быть допустимым периодом. Правила максимальной глубины и закрытого
расчетного месяца требуют решения владельца продукта.

**Источник:** issue #343; выбор произвольного периода подтвержден [LK §2.3](../../../../kb/processed/mango-lk-manual/sections/34-rashody-na-svyaz.md).

**Статус:** проектное требование с открытыми ограничениями.

**Критерии приемки:**

1. Валидный период одного календарного месяца принимается.
2. Дата начала позже даты окончания отклоняется с понятным сообщением.
3. В результат не попадают звонки вне заданного периода по согласованной временной зоне.

#### FR-03. Формирование детализации

**Требование:** после команды пользователя система формирует набор строк по
тарифицируемым звонкам выбранного ЛС и периода. Единица строки, обработка
переадресаций, конференций, нулевой стоимости и корректировок требуют
продуктового решения.

**Источник:** issue #343; текущие возможности по количеству, направлениям,
длительности и стоимости подтверждены [LK §2.3](../../../../kb/processed/mango-lk-manual/sections/34-rashody-na-svyaz.md).

**Статус:** проектное требование; модель строки не утверждена.

**Критерии приемки:**

1. Повторное формирование при неизменных расчетных данных возвращает одинаковый набор строк.
2. Строки ограничены выбранными ЛС и периодом.
3. Если строк нет, система показывает пустой результат, а не ошибку и не строки другого ЛС.

#### FR-04. Состав данных выгрузки

**Требование:** каждая строка содержит колонки в согласованных наименованиях:

1. Номер, инициировавший звонок;
2. Номер абонента;
3. Оператор связи;
4. Длительность звонка;
5. Сумма в рублях;
6. Номер договора;
7. Название услуги.

Для отсутствующего значения используется согласованный пустой маркер; система
не должна угадывать оператора, договор или услугу. Форматы телефона,
длительности, суммы и справочники требуют решения владельца продукта.

**Источник:** issue #343.

**Статус:** состав подтвержден Заказчиком; семантика и форматы требуют решения.

**Критерии приемки:**

1. Выгрузка содержит все семь колонок и не подменяет одну другой.
2. Сумма представлена в рублях с согласованной точностью и знаком корректировки.
3. Пустое исходное значение остается явно пустым/маркированным по контракту.

#### FR-05. Скачивание и результат операции

**Требование:** после успешного формирования пользователь скачивает файл.
Формат файла, имя, кодировка, разделитель, лимит синхронной выгрузки и срок
хранения требуют решения владельца продукта.

**Источник:** самостоятельная выгрузка — issue #343; скачивание документов и
XLS как поддерживаемый пользовательский инструмент — [LK §2.1](../../../../kb/processed/mango-lk-manual/sections/28-dokumenty.md).

**Статус:** проектное требование с открытым контрактом файла.

**Критерии приемки:**

1. При успехе браузер получает один файл для выбранных ЛС и периода.
2. При ошибке пользователь получает сообщение и может повторить операцию.
3. Файл открывается в согласованном табличном приложении без потери телефонных номеров и денежных значений.

#### FR-06. Контроль доступа и изоляция данных

**Требование:** формировать отчет может пользователь, которому доступен раздел
расходов и выбранный ЛС. Конкретная матрица ролей должна быть утверждена: БЗ
подтверждает доступ не только Администратора, но и ряда других ролей.

**Источник:** issue #343 называет Администратора; [Роли §5.5.2](../../../../kb/processed/rolevaya-model-vats/sections/61-razdel-finansy-i-balans-licevogo-scheta.md) подтверждает действующие права просмотра.

**Статус:** требует решения владельца продукта по переиспользованию/созданию права.

**Критерии приемки:**

1. Пользователь без права не может запустить операцию прямым или UI-вызовом.
2. Пользователь не может запросить недоступный ЛС подменой идентификатора.
3. Изменение доступного ЛС изменяет границу результата, не объединяя данные.

### UC-01. Сформировать месячный отчет по одному ЛС

**Актор:** уполномоченный пользователь. **Предусловия:** выполнен вход; раздел
и ЛС доступны. **Основной сценарий:** открыть «Финансы → Расходы на связь» →
выбрать ЛС → указать границы месяца → запустить формирование → скачать файл.
**Результат:** файл содержит только данные выбранного ЛС и периода.

### UC-02. Выгрузить отчеты при нескольких ЛС

Пользователь выполняет UC-01 для первого ЛС, затем выбирает следующий ЛС и
повторяет UC-01. Система создает отдельные файлы без агрегированного отчета по всем ЛС.

### UC-03. Обработать пустой результат или ошибку

При отсутствии строк система сообщает об этом и не подмешивает данные другого
периода/ЛС. При технической ошибке система показывает сообщение без частичного
файла и дает повторить операцию.

## 5. Нефункциональные требования

Не заполняется в рамках issue #343 — заглушка согласно DoD. Производительность,
доступность, аудит, безопасность файла, локализация и объемы должны быть
сформированы отдельным согласованием, а не выведены без источника.

## 6. Ограничения

1. Один файл относится ровно к одному ЛС; без агрегированного отчета по всем ЛС.
2. Объединение файлов и распределение по внутренним проектам выполняет Заказчик.
3. Документ не меняет правила тарификации, договоры и УПД.
4. Источники БЗ описывают версии продукта 1.23/1.26.08; актуальность должна быть подтверждена.
5. Названия и семантика полей не считаются контрактом API до product/SA review.

### Вопросы Заказчику

1. Какой период должен попадать в отчет: календарный месяц, расчетный период УПД или произвольные даты?
2. Требуется ли строка на каждый вызов, тарифицируемое плечо или позицию начисления?
3. Какие форматы файла и денежных/телефонных полей нужны для внутренней системы?
4. Как сопоставлять выгрузку конкретному УПД: номер УПД нужен в файле или достаточно периода и номера договора?
5. Нужно ли включать входящие, исходящие, внутренние, переадресованные, конференционные и звонки нулевой стоимости?

### Вопросы владельцу продукта

1. Какие системные поля являются «инициирующим номером» и «номером абонента» для каждого направления/сценария звонка?
2. Из какого тарификационного источника брать оператора связи и название услуги; что делать при отсутствии значения?
3. Какой договор указывать при нескольких договорах/бланках заказа на одном ЛС?
4. Переиспользуется ли право просмотра расходов или требуется отдельное право выгрузки; какие роли его получают?
5. Каковы максимальный период, объем, модель формирования (синхронная/фоновая), формат, кодировка и срок хранения файла?
6. Как отражать перерасчеты, отрицательные суммы, НДС, валюту и округление, чтобы сумма сверялась с УПД?
