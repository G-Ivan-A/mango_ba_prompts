# BCREQ-1027. Обработано без ответа (ФТ, вариант 2)

Документ фиксирует второй вариант функциональных требований по BCREQ-1027 после
изменения архитектурного решения: вместо отдельной кнопки в карточке обработки
обращения и отдельной колонки в отчете используется настройка канала/виджета,
существующее действие оператора `Завершить обращение` и новый результат

## 2. Исходные данные и бизнес-задача

Текущая логика Контакт-центра описывает ручное закрытие текстового обращения без
единого ответа сотрудника как `Не обработано`. Из-за этого отчеты смешивают два
разных бизнес-сценария:

- обращение действительно не обработано или закрыто по текущим причинам
  `Не обработано`;
- оператор осознанно взял обращение в работу и завершил его без ответа клиенту,
  потому что ответ не требовался.

Цель варианта 2: разделить эти сценарии в результатах обращения, отчетах,
фильтрах, экспорте и API без добавления нового действия оператору и без
добавления новой колонки в `Истории обращений`.

## 3. Описание разрабатываемого решения

### 3.1. Решение верхнего уровня

Система должна предоставить настройку в `ЛК-Диалоги -> Виджет канала`.
Настройка включает новую классификацию ручного завершения обращения без ответа
оператора.

Оператор в `Моих обращениях` продолжает использовать существующее действие
`Завершить обращение`. При закрытии система определяет, есть ли в истории
обращения хотя бы один сохраненный ответ оператора. Если настройка включена и
ответа оператора нет, обращение закрывается с результатом `Обработано без
ответа`, а API-значение результата сохраняется как `result = 8` / `Завершено без
ответа`.

Если ответ оператора был, результат остается `Обработано`. Если настройка
выключена, текущая логика не меняется: ручное закрытие без ответа остается в
старом результате.

### 3.3. Область действия

В scope входят текстовые/диалоговые обращения каналов Манго Диалогов и
Контакт-центра, для которых:

- канал/виджет настроен в ЛК-Диалогах;
- оператор вручную нажал `Завершить обращение`;
- система может проверить сохраненную историю сообщений обращения;
- настройка канала/виджета включена на момент закрытия обращения.

Вне scope:

- звонки и голосовые статусы;
- SMS-сценарии доставки без отдельного решения;
- автоматическое завершение по таймауту;
- обращения, не распределенные на оператора;
- закрытие внешней системой, если оно не является согласованным эквивалентом
  ручного действия оператора;
- результаты `Переведено`, `Спам`, `Запрещена отправка`;
- переоткрытие закрытых обращений;
- пересчет исторических данных.

## 4. Функциональные требования

### 4.1. FR-01. Настройка в ЛК-Диалогах

#### 4.1.1. Размещение настройки

Система должна добавить настройку в карточку настроек виджета/канала в
`ЛК-Диалоги -> Виджет канала` или эквивалентный экран настроек группы каналов,
если продуктовая навигация использует группу каналов как основную сущность.

#### 4.1.2. Тип и состояние

Настройка должна быть чекбоксом с двумя состояниями:

- выключено;
- включено.

Значение по умолчанию для существующих и новых каналов: выключено, если
владелец продукта не согласует другой default отдельно.

#### 4.1.3. Название и подсказка

Рекомендуемый заголовок чекбокса:

`Считать завершение без ответа обработкой обращения`

Рекомендуемая info-подсказка:

`Если оператор завершит обращение без отправленного ответа, в отчетах будет результат «Обработано без ответа». Автоматические закрытия и ошибки отправки не меняются.`

Текст подсказки можно редакционно сократить, но он должен сохранять три смысла:
ручное завершение оператором, отсутствие отправленного ответа и неизменность
автоматических закрытий/ошибок отправки.

#### 4.1.4. Права доступа

Настройка доступна пользователям, которые уже имеют право редактировать
настройки виджета/канала. Новая отдельная модель прав в рамках BCREQ-1027 v2 не
требуется.

#### 4.1.5. Момент применения

Система должна применять значение настройки на момент закрытия обращения.
Изменение настройки после закрытия обращения не должно менять сохраненный
результат закрытого обращения.

### 4.2. FR-02. Определение результата при завершении обращения

#### 4.2.1. Основное правило

При ручном нажатии оператором существующей кнопки `Завершить обращение` система
должна определить результат по алгоритму:

| Условие | Результат |
| --- | --- |
| Настройка выключена, ответа оператора нет | Текущий результат без изменений, для описанного сценария - `Не обработано`. |
| Настройка включена, ответа оператора нет | `Обработано без ответа`, API `result = 8`. |
| Настройка включена, есть хотя бы один ответ оператора | `Обработано`, как в текущей логике. |
| Настройка включена, закрытие завершилось специальным результатом | Специальный результат сохраняется: `Переведено`, `Спам`, `Запрещена отправка` и другие текущие специальные исходы не переопределяются. |

#### 4.2.2. Что считать ответом оператора

Ответом оператора считается только успешное сообщение сотрудника, сохраненное в
истории обращения КЦ/Манго Диалогов.

Ответом оператора не считаются:

- клиентские сообщения;
- автоответы;
- сообщения чат-бота;
- системные и служебные сообщения;
- сообщение при закрытии обращения;
- приглашение оценить работу оператора;
- события доставки, прочтения, набора текста;
- прямой ответ сотрудника во внешнем мессенджере, если он не сохранен в истории
  обращения КЦ/Манго Диалогов;
- неуспешная попытка отправки сообщения.

#### 4.2.3. Приоритет текущих результатов

Новая логика не должна переопределять текущие специальные результаты:

- `Переведено`;
- `Спам`;
- `Запрещена отправка`;
- автоматическое закрытие по таймауту;
- закрытие нераспределенного обращения;
- закрытие внешней системой, если оно не согласовано как эквивалент ручного
  завершения оператором.

#### 4.2.4. Первый ответ

Для результата `Обработано без ответа` система не должна создавать факт первого
ответа оператора. Поля и метрики типа `first_answer`/`Время первого ответа`
должны оставаться пустыми или `null`, если в обращении не было реального ответа
оператора.

### 4.3. FR-03. Отображение в отчетах обращений

#### 4.3.1. История обращений

В `Истории обращений` система должна отображать `Обработано без ответа` в
существующей колонке `Результат`. Новая колонка для этого значения не
добавляется.

Если пользователь скрывает/показывает колонки таблицы, новое значение должно
следовать текущей логике существующей колонки `Результат`.

#### 4.3.2. Исходящие обращения

В отчете или разделе `Исходящие обращения` система должна отображать
`Обработано без ответа` в существующей колонке/поле `Результат`.

#### 4.3.3. Другие места, где отображается результат

Все карточки, истории клиента, dashboards и витрины, которые уже отображают
результат обращения через общий справочник результата, должны получать новое
значение из того же справочника. Если витрина не отображает результат
обращения, добавление нового элемента UI в рамках BCREQ-1027 v2 не требуется.

### 4.4. FR-04. Фильтр и экспорт Истории обращений

#### 4.4.1. Фильтр по результату

Фильтр `Результат` в `Истории обращений` должен включать значение
`Обработано без ответа`.

Фильтрация должна работать вместе с существующими фильтрами периода, группы,
сотрудника, канала, типа обращения, темы и других доступных параметров.

#### 4.4.2. CSV-экспорт

CSV-экспорт `Истории обращений` должен:

- учитывать фильтр `Результат = Обработано без ответа`;
- выгружать новое значение в существующей колонке `Результат`;
- не добавлять отдельную колонку для признака "без ответа";
- использовать тот же текст, который видит пользователь в таблице:
  `Обработано без ответа`.

### 4.5. FR-05. API и enum результата обращения

#### 4.5.1. Новый API-результат

Система должна добавить значение результата обращения:

| Код | API-наименование | UI/отчетная метка |
| --- | --- | --- |
| `8` | `Завершено без ответа` | `Обработано без ответа` |

Код `8` добавляется в enum результата обращения. Код `7` не используется в
рамках BCREQ-1027 v2 и не должен назначаться автоматически только ради
последовательной нумерации.

#### 4.5.2. Поверхности API

Новый enum должен быть поддержан во всех API-полях, где результат обращения
принимается или возвращается как enum. Минимальный набор поверхностей:

| Поверхность | Требование |
| --- | --- |
| `POST /vpbx/cc/appeals/create-closed-appeals` | Параметр `result` должен принимать `8` как валидное значение результата обращения. Обработка `result <= 0` остается текущей. |
| `POST /events/md/onAppealClose` | Событие закрытия обращения должно возвращать `result = 8`, когда обращение закрыто как `Обработано без ответа`. |
| `POST /vpbx/stats/calls/result` | Поле `conversion.result` должно возвращать `8`, если в структуре статистики возвращается обращение с таким результатом. Логика статистики звонков при этом не меняется. |

#### 4.5.3. Манго Диалоги session close

Метод Манго Диалогов `POST /cc/md/session/close` в текущей документации
принимает `session_id` и `abonent_id`, но не принимает `result`.

Требование BCREQ-1027 v2 не добавляет обязательный параметр `result` в этот
метод. Если закрытие сессии через этот метод является серверным эквивалентом
ручного действия оператора для настроенного канала, результат должен
вычисляться на стороне системы по правилам FR-02. Если закрытие трактуется как
закрытие внешней системой, оно остается вне scope новой классификации до
отдельного согласования.

#### 4.5.4. Совместимость API

Существующие значения результата `1..6` не меняются. Внешним потребителям API
следует обрабатывать неизвестные значения enum как допустимые расширения
справочника результата, чтобы добавление `8` не приводило к отказу интеграций.

### 4.6. FR-06. Метрики и аналитика

#### 4.6.1. Обработанные и пропущенные обращения

`Обработано без ответа` должно быть отдельным результатом закрытого обращения.
В агрегатах, где бизнес-смысл метрики - "обращение завершено оператором", `8`
должен учитываться как обработанный подтип и не должен попадать в пропущенные,
неотвеченные или необработанные обращения.

В агрегатах, где бизнес-смысл метрики зависит от факта первого ответа оператора
или SLA первого ответа, `8` не должен считаться отвеченным, потому что реального
ответа оператора не было.

#### 4.6.2. Группировки по результату

Если dashboard, отчет или витрина группирует обращения по результату, система
должна показывать `Обработано без ответа` отдельным бакетом, а не сливать его с
`Обработано` или `Не обработано`.

#### 4.6.3. История и неизменность результата

После закрытия обращения результат `8` должен храниться как результат
обращения. Последующее изменение настройки канала/виджета не должно менять
результат уже закрытого обращения.

## 5. Нефункциональные требования

Раздел не формируется в рамках текущего прогона. По контракту BCREQ-FR
нефункциональные требования выносятся в отдельный блок только при наличии
явного запроса или подтвержденных источников. Для BCREQ-1027 v2 зафиксировано
только функциональное изменение результата обращения, отчетов, фильтров,
экспорта и API enum.

## 6. Ограничения, зависимости и риски

| Область | Ограничение или риск | Требование к согласованию |
| --- | --- | --- |
| История сообщений | Ответы напрямую во внешнем мессенджере не учитываются, если они не сохранены в КЦ. | Зафиксировать как ограничение продукта и поддержки. |
| API-потребители | Интеграции, жестко ожидающие `result` только `1..6`, могут не обработать `8`. | Обновить API changelog и рекомендации интеграторам. |
| Аналитика | Без явного правила разные отчеты могут по-разному считать `8` обработанным или неотвеченным. | Использовать правила FR-06: отдельный результат, обработанный подтип без факта первого ответа. |
| Автозавершение | Таймауты и автоматические закрытия не должны превращаться в `8`. | Проверить при тестировании сценарии автозавершения. |
| Ошибки отправки | Заблокированный канал, запрет отправки и ошибка доставки остаются `Запрещена отправка`. | Проверить исходящие сценарии. |
| Исторические данные | Старые обращения не пересчитываются. | Миграция возможна только отдельным требованием. |
| UI-терминология | UI говорит `Обработано без ответа`, API говорит `Завершено без ответа`. | Маппинг должен быть закреплен в справочнике результата. |

### Матрица приемки

| ID | Сценарий | Ожидаемый результат |

| AC-05 | Сообщение оператора не отправлено из-за ошибки или запрета | Результат специального сценария, например `Запрещена отправка`; не `8`. |

| AC-11 | API `create-closed-appeals` получает `result = 8` | Значение принимается как валидный результат обращения. |
| AC-12 | API `onAppealClose` отправляет событие для обращения с `result = 8` | В событии результата обращения возвращается `8`. |

| AC-14 | Проверяется `first_answer` для результата `8` | Значение пустое или `null`; факт первого ответа не создается. |

### Открытые вопросы для согласования

| Вопрос | Рекомендуемое решение в v2 |
| --- | --- |
| Должна ли настройка быть включена по умолчанию для новых каналов? | Нет, default `выключено` для обратной совместимости. |
| Должны ли исторические обращения пересчитываться? | Нет, только новые закрытия после сохранения настройки. |
| Считать ли `8` обработанным в KPI? | Считать отдельным обработанным подтипом для завершенных оператором обращений, но не создавать факт первого ответа и не включать в SLA первого ответа. |

| Должен ли MD webhook `session/on_closed` получать result? | Не входит в обязательный scope v2; обязательная API-поверхность для результата обращения - API КЦ с `result`. |
