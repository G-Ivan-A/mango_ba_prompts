# Отчёт RUN-0082: golden set этапа 1, Ш-В, три повтора

## Зачем прогон

RUN-0081 (N = 1) не пропустил типизацию гейтов (A): 56/62, но ядро 9/11
против 10/11 RUN-0079. Единственный провал ядра сверх RUN-0079 —
GS-BCREQ-01 по K5, и ту же правку судья RUN-0080 зачёл. Отделить эффект
текста от разброса исполнителя и судьи по одному замеру нельзя. Поэтому
в RUN-0081 рекомендовано: три повтора и решение по медиане (Р-03).
Владелец разрешил бюджет: issue #446, пункт 2.

RUN-0082 меряет **те же тексты** A и D (SHA-256 `adf82663…` и `2e839172…`)
трижды. Каждый повтор — свежие исполнители и свежие слепые судьи. Правило
решения записано и закоммичено до запуска подагентов:
[`preregistration.md`](../../../../experiments/issue_446/run0082/preregistration.md).

## Версии

- golden set: [`golden-set-bcreq-stage1.md`](../../../../standards/bcreq-lessons/golden-set-bcreq-stage1.md), версия 0.1. В наборе 62 кейса: 52 дефектных и 10 негативных, ядро — 11.
- рубрика: [`rubric-bcreq-stage1.md`](../../../../standards/bcreq-lessons/rubric-bcreq-stage1.md), версия 0.1 (K1–K6).
- A: Ш-В v0.1 с 15 подстановками типа гейта и ссылками по SHA — текст A RUN-0081.
- D: черновик Ш-В «по тесту» на реестре 0.4 — текст D RUN-0081.
- база: RUN-0079, версия A (v0.1) — 49/62, ядро 10/11, ложные дефекты 0/10 (N = 1).

## Правило решения (из пред-регистрации)

1. По каждой версии — медиана трёх повторов отдельно по сданным кейсам,
   ядру и ложным дефектам.
2. DEC-427-11 применяется к медианам: «не хуже» RUN-0079 = медиана
   сданных ≥ 49, ядра ≥ 10, ложных дефектов ≤ 0.
3. Тип гейта публикуется, только если A «не хуже» по п. 2.
4. Черновик Ш-В публикуется (П-Ш-В), только если D «не хуже» RUN-0079 **и**
   не хуже медианы A.
5. RUN-0081 — справочный замер, в решение не входит.
6. Частота провала по кейсам ядра — автоматическое второе чтение
   GS-BCREQ-01 и GS-BCREQ-12.

## Решение

| Проверка | Медиана | Порог | Итог |
| --- | --- | --- | --- |
| A не хуже RUN-0079 | 53 / 8 / 0 | 49 / 10 / 0 | **нет** — ядро 8 < 10 |
| D не хуже RUN-0079 | 54 / 9 / 0 | 49 / 10 / 0 | **нет** — ядро 9 < 10 |
| D не хуже медианы A | 54 / 9 / 0 | 53 / 8 / 0 | да |

**Решение по правилу, заданному до прогона:**

1. **Тип гейта в `prompts/` не публикуется** (BL-156б, часть «типизация»).
   `TYPING_APPLIED = False` остаётся; 15 подстановок — в
   `experiments/issue_438/prompt-typing.json`, статус «не применена».
2. **П-Ш-В: черновик Ш-В остаётся в `prompts/drafts/`.** D не хуже A
   (медиана 54 против 53, ядро 9 против 8), но ниже базы RUN-0079 по ядру.
3. В `prompts/` ничего не меняется. Публикуемый набор для теста на сайте —
   v0.1 (см. task statement issue #446).

Проверки пересчитывает `run.py score`, результат — в
[`summary.json`](summary.json), поле `decision`.

## Что показали повторы

### Разброс на одном тексте больше порога

Текст A с типом гейта теперь измерен пять раз: RUN-0080 — ядро 10/11,
RUN-0081 — 9/11, RUN-0082 — 6, 8 и 10 из 11. Сданных — 55, 56, 47, 53, 54.
Размах ядра — 4 кейса из 11 на одном и том же тексте. Порог «ядро ≥ 10»
сравнивает медиану с **одним** историческим замером v0.1 (RUN-0079), у
которого разброс того же порядка, но не измерен. Поэтому «ниже RUN-0079»
не доказывает, что тип гейта ухудшает текст. Это доказывает, что
решение нельзя принять без одновременного контроля: v0.1 без типа (A0)
в тех же повторах и у тех же судей. Плечо A0 исключено из RUN-0082 по
бюджету (пред-регистрация, раздел «Бюджет»).

### Парное сравнение D и A у одного судьи

| Повтор | D − A, сдано | D − A, ядро |
| --- | --- | --- |
| r1 | +4 | +4 |
| r2 | +3 | 0 |
| r3 | 0 | −1 |

У одного судьи D не хуже A в двух повторах из трёх по ядру и в трёх из
трёх по сданным. В RUN-0081 (N = 1) было наоборот: D 51 против 56 у A.
Повторы снимают вывод RUN-0081 «D хуже A».

**GS-BCREQ-12** (вход: «ФТ-2. Система должна обеспечивать корректный и
своевременный роутинг лидов и их апдейт»). Все шесть правок RUN-0082
оставляют два действия в одном ФТ. Пример (A r3): «Система должна
назначать лид ответственному сотруднику… и обновлять статус лида при
назначении». Эталон («в одном пункте два действия») верен, и судьи правы.
Кейс провален во всех семи замерах с RUN-0079. Значит, это не строгость
судьи: Ш-В не требует, чтобы правка неатомарного ФТ делила его на
отдельные ФТ. Человеческое второе чтение для этого вывода не нужно.

**GS-BCREQ-01.** Провальные правки добавляют «учитывать его изменения при
уведомлении». Контекст кейса прямо говорит, что уведомление во входе не
упомянуто, поэтому замечание судьи буквально верно. Кейс провален в трёх
выходах из шести: модель иногда добавляет поведение, иногда нет. Это
разброс одного механизма (правка добавляет без источника), а не ошибка
эталона.

**Общий механизм провалов.** 44 из 63 проваленных критериев во всех
шести замерах — K5 (K2 — 12, K4 — 4, K6 — 2, K1 — 1): модель находит дефект (K1 — 61–62 из 62), но правка
добавляет механизм, объект или поведение без источника («журнал
действий», «уведомление», «передавать в CRM событие») или не делит
неатомарное ФТ. Это точка правки текста Ш-В, общая для A и D.

### Частота провала: остальные кейсы

Устойчиво (3 из 3) проваливаются, кроме GS-BCREQ-12: у A — GS-BCREQ-26,
33, 43; у D — GS-BCREQ-26, 43. GS-BCREQ-26 — всегда K2 (названо «нет
источника», а не «оговорка о несуществующей проблеме»), GS-BCREQ-43 —
всегда K5 (выдуманный механизм интеграции). Остальные 16 кейсов у A и 13
у D проваливаются не во всех повторах. Полный список — `fail_frequency` в
[`summary.json`](summary.json).

## Рекомендации

1. **Р-03: решение по одновременному контролю, а не по историческому
   замеру.** Каждый замер правки `prompts/` включает контрольное плечо —
   текущий опубликованный текст — в тех же повторах и у тех же судей.
   Правило: медиана новой версии не хуже медианы контроля по сданным,
   ядру и ложным дефектам, N = 3. Так делается A/B-тест с одновременным
   контролем; сравнение с одним историческим замером тут не годится.
   Порог 0,95 из прежнего предложения Р-03 на этих данных недостижим ни
   для одной версии (максимум 56/62 = 0,90), поэтому порог — «не хуже
   контроля», а не абсолютное число.
2. **Правка Ш-В «правка без добавлений» (новый пункт BL-156в).** В раздел
   правок Ш-В — правило: правка только удаляет, делит или заменяет на
   `[ТРЕБУЕТСЯ УТОЧНЕНИЕ]` с вопросом в 8.4. Неатомарное ФТ делится на
   отдельные ФТ, по одному действию. Механизм, объект или поведение без
   источника в правку не вносятся. Замер — RUN по п. 1: v0.1 (контроль)
   против v0.1 + правило, N = 3. Оценка — около 0,7 млн токенов.
3. **Тип гейта (BL-156б) — тем же замером.** Плечи A0 (v0.1), A1 (v0.1 +
   тип), N = 3. Оценка — около 0,7 млн токенов. Если совместить с п. 2
   (A0, A1, A2 у одного судьи по три выхода на кейс), то около 1 млн.
4. **Человеческое второе чтение GS-BCREQ-01 и GS-BCREQ-12 не нужно.**
   Повторы ответили: GS-BCREQ-12 — дефект текста, GS-BCREQ-01 — разброс;
   эталоны верны.

## Ограничения

1. Исполнитель и судья — одна модель (`claude-opus-5-5`), хотя и в
   изолированных подагентах.
2. Входы синтетические: прогон меряет удержание правила на фрагменте, а не
   полный документ BCREQ.
3. Нет одновременного контроля A0 (v0.1 без типа гейта): вывод «ниже
   RUN-0079» сравнивает медиану с одним историческим замером.
4. N = 3 — минимум для медианы; доверительные интервалы не оценивались.
5. Человек оценки не подтверждал (`ba_reviewed: false`).

## Вывод

Повторы не пропустили ни тип гейта, ни черновик Ш-В: обе медианы ядра
ниже исторической базы 10/11. Главный результат прогона — не решение
«нет», а измеренный разброс: на одном тексте ядро колеблется от 6 до 10.
Порог DEC-427-11 против исторического N = 1 по ядру работает как
лотерея. Следующий замер должен идти с контролем в тех же повторах.
Единственный устойчивый провал ядра — GS-BCREQ-12 — указывает на
конкретную правку текста Ш-В, а не на судью.
