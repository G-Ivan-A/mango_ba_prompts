# SIM-1106: уведомление о записи исходящего контакта

Ревизия r3, DRAFT_AWAITING_HUMAN. Авторская имитация по историческим данным,
без реальной приёмки. Все ссылки S-* ведут в
[реестр входных источников](../inputs/seed.json). Описания из S-200 —
проектные решения исторического БА, не проверенные текущие свойства продукта.
Рабочая проекция до решения CF-01 использует исключение КЦ из S-56; это
кандидат для обсуждения, без права изменить ранее принятую границу.

## 2. Бизнес-контекст

### 2.1. Контекст

Заказчику нужно уведомлять Абонента о записи при целевом исходящем контакте.
Предпочтительный канал инициирования — Mango Talker. [S-02]

### 2.2. Проблема

В исходном запросе отсутствует подходящий порядок предварительного уведомления.
Кампания автоинформатора не заменяет требуемый сценарий. Юридическая
достаточность уведомления отдельно не оценивалась. [S-02]

### 2.3. Цель

Абонент получает голосовое уведомление до соединения с Оператором при
контакте, для которого предусмотрена автоматическая запись. [S-02, S-142]

### 2.4. Границы

2.4.1. Включено в проект: настройки уведомления в ЛК, целевое воспроизведение,
отдельная запись клиентского плеча и управление ей; документирование,
тестирование и доставка при согласованной реализации. [S-200]

2.4.2. Исключено: прямые входящие вызовы, автоматическое уведомление при
ручной записи, новая ролевая модель, доработка внешнего API и BPMsoft.
КЦ исключён в рабочей проекции до ответа Q-01; обе исходные позиции сохранены.
[S-56, S-110, S-142, S-200]

### 2.5. Продукты и владельцы

ЛК ВАТС — настройки и записи; Mango Talker — контекст инициирования.
Владельцы и затронутость отдельных команд UNKNOWN, D-01. Таксономия S-TAX
даёт Partial для новой функции уведомления; узлы записи существуют, но
новое поведение этим не подтверждено. [S-TAX]

## 5. Описание решения

### 5.1. L1 — проект поведения

Сначала Пользователь с существующим правом настройки выбирает файл из
хранилища, включает уведомление и сохраняет настройки. Новая роль и новая
загрузка не проектируются. Настройка по умолчанию выключена, файл не выбран.
При отключённой базовой записи или ручном режиме настройка недоступна;
причина видна в подсказке. Само изменение доступности не меняет сохранённое
значение переключателя. Это предложения S-200, требующие сверки As-Is.

При ответе Абонента система проверяет включённое уведомление и применимость
автоматической записи к этому контакту. Если записи не будет, сообщение
не воспроизводится. При выполнении условий начинается аудиофиксация плеча,
сообщение получает только Абонент; Оператор ожидает. После завершения
уведомления стороны соединяются. Запись плеча остаётся отдельной от штатной
записи разговора после соединения. [S-142, S-200]

ЗОЗ сохраняет дозвон до Оператора перед дозвоном до Абонента; АПП —
уведомление ответившего Абонента до поиска/соединения с Оператором, как
проект в S-200. Классификация направлений для обоих сценариев требует
проверенного руководства, а не предположения по названию «исходящий».

Хранение и операции используют общие настройки записи. Запись плеча не
передаётся в речевую аналитику. Пользователь может воспроизводить, скачивать
и удалять её; фильтр отображения плеч по умолчанию выключен. Роль и право
переиспользуются, актуальность проверяется по Q-03. [S-110, S-200]

При сбросе Абонентом до соединения вызов завершается и сохраняется записанный
фрагмент. При сбросе Оператором до соединения сохраняется запись плеча.
Отсутствующий/повреждённый файл — открытый выбор Q-02: пропустить уведомление,
завершить вызов либо взять согласованный резервный файл. Ни один вариант
не принят моделью. Внутренняя SIP/RTP/БД-архитектура не проектируется.

## 6. Особенности и ограничения

6.1. Настройка предшествует исполнению, см. 5.1; повторного описания нет.
ЗОЗ и АПП требуют проверки направлений записи, Q-03.

6.2. [CON-01] Единая запись до и после соединения не обещается: плечо
сохраняется отдельно. [S-110] [CON-02] Ручная запись не запускает
автоматическое уведомление; требуется иной согласованный порядок уведомления.
[S-142] [CON-03] Речевая аналитика не получает запись плеча. [S-200]
Эти ограничения исторического проекта должны быть проверены владельцем;
они не объявлены вечными ограничениями всех продуктов Mango.

## 8. Дополнительные разделы

### 8.1. Риски

R-01 кандидат: разные классификации направлений → сообщение не применяется
к ожидаемому контакту → уведомление пропущено. Мера: сверить руководство
и сценарии; владелец UNKNOWN, поэтому вопрос Q-03, а не принятый риск.
Вероятность/влияние не оценены. Юридическая достаточность не подтверждается
техническим текстом, Q-05.

### 8.2. Зависимости

D-01: владелец ЛК/записи и владелец сценария должны подтвердить роли,
направления и границы; блокирует validated delta и оценку; статус pending.
D-02: заказчик выбирает политику ошибочного файла; блокирует FR-03/UC-07.
Ни один статус команды не придуман.

### 8.3. План приёмки

AC-01: дано право настройки и применимая запись; когда Пользователь сохраняет
выбранный файл и включение, тогда состояние доступно для целевого контакта.
Проверка конфигурации; FR-01/02; приёмщик UNKNOWN.

AC-02: даны обе применимые настройки; когда Абонент отвечает, тогда записывается
плечо и сообщение получает только Абонент, Оператор ожидает, соединение
следует после окончания. Наблюдение сценария; FR-03…06; приёмщик UNKNOWN.

AC-03: дано, что запись контакта не выполняется; когда Абонент отвечает,
тогда автоматическое сообщение не играет. FR-03, проверка отрицательной ветви.

AC-04: дано разъединение до соединения; тогда сохранён отдельный фактически
записанный фрагмент плеча. FR-07; проверка артефакта.

AC-05: дано существующее право доступа; когда Пользователь открывает фильтр
плеч и выполняет операцию, тогда доступны только разрешённые воспроизведение,
скачивание и удаление. FR-08; сверка реальной модели прав до исполнения теста.
