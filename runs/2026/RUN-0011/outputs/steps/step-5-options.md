# Шаг 5 — Варианты доработки (Раздел 3)

> **Промпт:** `mango-technical-details-solution-design-stepwise`, применён в **раннем
> режиме** — только продуктовые варианты верхнего уровня, без детального тех-дизайна
> (это был бы Раздел 7). Все варианты — **условные**: окончательный выбор после
> ответов на В1/В3/В4/В5 ([Шаг 3](./step-3-questions.md)).

## Закрываемый gap (из [Шага 2](./step-2-normalization.md))

1. Нет единого межканального счётчика активных контактов (есть только по тексту, Ф3).
2. Нет сквозного приоритета каналов голос>чат>e-mail (Ф8).

## Вариант A — «Расширение существующего лимита» (минимальный)

Превратить текущий текстовый лимит (Ф3) в **единый счётчик активных контактов**, в
который входят и звонок, и чат, и e-mail; приоритет реализовать через уже имеющийся
механизм-чекбокс (Ф5), эскалированный до правила «не давать фон при свободном
реальном времени».

| Аспект | Оценка |
| --- | --- |
| Плюсы | Опирается на существующий параметр (Ф3) и чекбокс (Ф5); быстрый вывод; знакомый UX настройки |
| Минусы | Приоритет — грубый (булева логика, без полноценного ранжирования); слабо решает исключение E1 (звонок при полном лимите) |
| Сложность | **Низкая** |
| Риски | Может не закрыть боль полностью (приоритет «на минималках»); конфликт с независимостью очередей Ф2 |
| Закрывает gap | gap-1 ✅, gap-2 🟡 частично |

## Вариант B — «Единый диспетчер нагрузки с приоритетом» (целевой)

Ввести **межканальную модель загрузки агента**: общий счётчик слотов + диспетчер,
который ранжирует распределение по приоритету голос>чат>e-mail и применяет правило
для E1 (поведение при полном лимите и входящем звонке, `?В5`).

| Аспект | Оценка |
| --- | --- |
| Плюсы | Полностью закрывает оба gap; прямой ответ на боль 2.2; расширяемо на будущие каналы |
| Минусы | Затрагивает оба слоя (ЛК ВАТС + КЦ, Ф10); требует объединить независимые очереди (Ф2) или ввести надстройку над ними |
| Сложность | **Высокая** |
| Риски | Изменение поведения распределения может затронуть текущих клиентов; нужна миграция настроек; больше сценариев тестирования |
| Закрывает gap | gap-1 ✅, gap-2 ✅ |

## Вариант C — «Приоритетное резервирование под реальное время» (компромисс)

Оставить раздельные очереди (Ф2), но ввести **единый лимит** (как A) **плюс
резервирование слота под каналы реального времени**: например, из N слотов хотя бы
один всегда доступен под голос/чат, e-mail заполняет только «остаток».

| Аспект | Оценка |
| --- | --- |
| Плюсы | Гарантирует доступность под голос/чат без полного диспетчера; средняя стоимость; понятно настраивается |
| Минусы | Приоритет реализован через резерв, а не через прерывание (E1 решается лишь частично); чуть сложнее объяснить заказчику |
| Сложность | **Средняя** |
| Риски | При неверной настройке резерва — простой слотов; всё ещё зависит от ответа на В4 (нужно ли прерывание) |
| Закрывает gap | gap-1 ✅, gap-2 🟡 (через резерв, без прерывания) |

## Сравнительная матрица

| Критерий | A (мин.) | B (целевой) | C (компромисс) |
| --- | --- | --- | --- |
| Закрытие боли 2.2 | частично | полно | в основном |
| Единый счётчик (gap-1) | ✅ | ✅ | ✅ |
| Сквозной приоритет (gap-2) | 🟡 | ✅ | 🟡 |
| Сложность/стоимость | низкая | высокая | средняя |
| Риск для текущих клиентов | низкий | высокий | средний |
| Опора на существующее (Ф3/Ф5) | максимальная | частичная | высокая |

## Предварительная рекомендация БА (не решение)

Для проверки гипотезы и быстрой ценности — **A как MVP**, с заложенной эволюцией в
**B** как целевую архитектуру; **C** — если заказчик подтвердит (В4), что нужен
приоритет без прерывания. Окончательно — после ответов на **В1, В3, В4, В5**.

> Это **варианты раннего этапа**, а не Раздел 7. Детальный тех-дизайн, ФТ и
> ограничения — отдельный последующий прогон (вне объёма issue #109).
