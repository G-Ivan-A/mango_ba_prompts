## Главный риск: чат виден только менеджерам-участникам

> ⚠️ **GAP-R1 — High Risk.** Чат по отклику автоматически создаётся у менеджера, ответственного за вакансию, и только он видит чат в своём списке. Событие `CHAT_MESSAGE_CREATED` «присылается менеджеру работодателя по тем чатам, в которых он является **активным участником**» (схема `WebhookActionChatMessageCreated`). Раздела «Чаты **на уровне работодателя**» в API нет — в отличие от откликов, резюме, вакансий и менеджеров, у которых такой уровень доступа документирован. Следовательно, интеграционный аккаунт не получает сообщения по чужим чатам, пока не станет их участником.

Влияние на типовые сценарии КЦ Mango — [L2, §12](L2-gap-matrix.md#12-влияние-gap-r1-на-сценарии-кц-mango):

| Сценарий КЦ | Влияние |
| --- | --- |
| Групповая обработка обращений | Требует, чтобы интеграционный менеджер был участником каждого чата. На стороне HH группы рекрутеров не существует — группа живёт в КЦ. |
| Передача чата между операторами | На стороне HH переключений нет: во внешнюю систему всё уходит от одного участника. Передача — внутреннее событие КЦ, кандидат её не видит. Это **соответствует** §4.7.2 ФТ («от лица компании»). |
| Skill-based маршрутизация | Не затрагивается: маршрутизация выполняется в КЦ после создания Обращения. Ограничение HH влияет только на полноту входящего потока. |

Вывод: ограничение бьёт **по охвату входящего потока**, а не по маршрутизации. Оно устраняется архитектурным обходом (добавление интеграционного менеджера в участники по событию создания чата) либо организационно (интеграционный менеджер назначается ответственным за фильтруемые вакансии). Первый обход опирается на непроверенную гипотезу и подлежит spike, второй гарантирован документацией, но меняет процесс у Заказчика.

## Предпочтительный путь получения сообщений

Из четырёх путей ([L2, §11](L2-gap-matrix.md#11-сравнение-путей-получения-сообщений-и-выбор-для-кц-mango)) для архитектуры КЦ Mango рекомендуется **комбинация «вебхуки + сверка по откликам»**:

1. **`CHAT_MESSAGE_CREATED`** — основной поток реального времени (ФТ-06).
2. **`NEW_RESPONSE_OR_INVITATION_VACANCY`** с `settings.vacancies_only_mine: false` — узнаёт `chat_id`, `vacancy_id`, `resume_id` и `topic_id` в момент появления отклика **по всем вакансиям, к которым есть доступ**, и запускает включение интеграционного менеджера в чат (обход GAP-R1).
3. **Путь 1 (отклики → `chat_id`)** — периодическая сверка: вебхуки в hh.ru «не являются средствами гарантированной доставки», поэтому пропуски должны добираться опросом.
4. **Путь 2 (`get-common-chat-list`)** — только первичная инвентаризация и диагностика: без сортировки и фильтра «изменённые с» он не годится на роль основного потока.
