## 3. ФТ-04 — Фильтрация входящих сообщений по вакансии

**Требование ФТ.** В работу попадают только сообщения по вакансиям категории «линейный персонал»; по прочим вакансиям обращение не создаётся (§4.4.1, §4.4.2).

**Факт документации — фильтровать можно.** `get-common-chat-list` принимает `filter_with_vacancy_ids` («Список идентификаторов вакансий», пример `[1,2,3]`, не более 100 значений) и `vacancy_status` (`all` / `with` / `without`). Элемент списка чатов `ChatsCommonChatBasic` содержит `vacancy_id` (nullable). Событие `NEW_RESPONSE_OR_INVITATION_VACANCY` отдаёт `vacancy_id` в payload.

**Факт документации — классификатора нет.** Признака «линейный персонал» у вакансии в спецификации нет; вывод RUN-0056 (GAP-4) сохраняется.

**Факт документации — вакансии нет в событии сообщения.** `WebhookPayloadChatMessageCreated` содержит `chat_id`, `message_id`, `message_type`, `sender_participant_id`, `role`, `is_current_participant`, `creation_time` — и **не содержит** `vacancy_id`. Фильтрация «на входе» по вакансии невозможна: интеграция обязана вести собственное соответствие `chat_id → vacancy_id`, наполняемое из событий создания отклика и из сверки по откликам.

> ⚠️ **GAP-R5** (уровень: Medium): классификатора «линейный персонал» в API hh.ru нет. Автоматическая фильтрация по формулировке ФТ-04 невыполнима — требуется явный перечень вакансий, выбираемый Пользователем в настройках канала. Дополнительное ограничение: `filter_with_vacancy_ids` принимает не более 100 идентификаторов, что задаёт верхнюю границу перечня в одном запросе. (Источник: спецификация hh.ru, `get-common-chat-list`, параметр `filter_with_vacancy_ids`; признак «линейный персонал» — отсутствует в документации.)

> ⚠️ **GAP-R3** (уровень: Medium): payload события `CHAT_MESSAGE_CREATED` не содержит ни `vacancy_id`, ни `resume_id`, ни текста сообщения. Любое входящее сообщение требует минимум одного дополнительного запроса (`get-chat-messages`), а фильтрация по вакансии — заранее построенного соответствия `chat_id → vacancy_id`. Это влияет на ФТ-04 (фильтр), ФТ-05 (создание обращения) и НФТ по задержке, которых в ФТ нет. (Источник: спецификация hh.ru, схема `WebhookPayloadChatMessageCreated`.)

**Вердикт: Частично.** Фильтрация по перечню вакансий реализуема; по категории «линейный персонал» — нет. Правка ФТ, предложенная в RUN-0056, остаётся в силе.

## 4. ФТ-05 — Создание обращения по первому входящему сообщению и контекст сессии

**Требование ФТ.** Первое входящее текстовое сообщение кандидата по вакансии без активного обращения создаёт Обращение; переносится контекст открытой Сессии; отклики без текста обращений не создают (§4.5.2); TTL сессии — не более 7 дней (§4.5.3).

**Факт документации.** Различить «отклик без текста» и «сообщение кандидата» теперь можно тремя способами: событие `NEW_NEGOTIATION_VACANCY` (появился отклик) отделено от `CHAT_MESSAGE_CREATED` (появилось сообщение); список чатов принимает `filter_has_text_message` («только чаты, в которых есть хотя бы одно текстовое сообщение», доступен работодателю); тип сообщения различается полем `type` (`SIMPLE` / `PARTICIPANT_LEFT` / `PARTICIPANT_JOINED`), поэтому системные записи об изменении состава участников не создадут ложных обращений.

Ключ «Кандидат + Вакансия» соответствует модели hh.ru напрямую: чат привязан к отклику, а «для каждой пары вакансия + резюме может быть только один отклик/приглашение». Требование §4.5.4 (разные вакансии — разные обращения) ложится на модель без допущений.

TTL сессии, автозавершение и распределение обращений — механика Mango Office (паттерн «Авито Работа»), внешних ограничений не имеет.

**Вердикт: Да.** Ограничение остаётся одно и общее — попадут ли сообщения в интеграцию вообще (GAP-R1).

## 5. ФТ-06 — Двусторонняя синхронизация в реальном времени

**Требование ФТ.** Текст и поддерживаемые вложения синхронизируются в обе стороны в реальном времени, без авторизации сотрудника в HH; после ответа оператора статус отклика в HH обновляется (§4.6.2).

### 5.1. Приём в реальном времени

Событие `CHAT_MESSAGE_CREATED` документировано: «Создание сообщения в чате. Событие присылается менеджеру работодателя по тем чатам, в которых он является активным участником» (`WebhookActionChatMessageCreated`). Подписка создаётся методами раздела «Управление подписками на Webhook».

Ограничения доставки, зафиксированные в разделе Webhook API:

- один URL на пользователя в рамках приложения;
- ожидается ответ `2xx` или `409`; если ответа нет в течение **5 секунд**, соединение не установлено или код ответа неожиданный — событие присылается повторно, ретраи идут с увеличением интервала;
- при длительных сбоях разработчику отправляется письмо, а подписка ставится в очередь на блокировку;
- **«Вебхуки не являются средствами гарантированной доставки»**;
- у колбэка в спецификации `security: null` — подпись или общий секрет не описаны.

> ⚠️ **GAP-R4** (уровень: Medium): гарантированная доставка вебхуков не обещана, а альтернативный источник — `get-common-chat-list` — не поддерживает ни сортировку, ни фильтр «изменённые с»; пагинация ограничена `page` 0…50 и `per_page` 1…20, то есть через список достижимо не более ≈1000 чатов. Сверка пропущенных сообщений строится не на списке чатов, а на списке откликов по вакансиям (`get-collection-negotiations-list`). (Источник: спецификация hh.ru, `get-common-chat-list`, параметры `page`, `per_page`; раздел Webhook API.)

Отсутствие подписи колбэка требует, чтобы приёмник проверял подлинность иначе: секрет в URL подписки, ограничение по сети и обязательная перепроверка события запросом к API (что и так необходимо из-за GAP-R3).

### 5.2. Отправка

`POST /common/chats/{chat_id}/messages` принимает либо текст (`text`, до 20000 символов, обязательный `idempotency_key` в формате UUID, необязательный `is_automated`), либо вложение (`file_upload_ids`, **не более одного файла**, тот же `idempotency_key`). Ответ `201`; `409` означает повтор по тому же ключу идемпотентности — это штатный механизм защиты от дублей при ретраях.

Возможность писать проверяется заранее: ответ `get-chat-messages` содержит `chat_states.write_message_state` с полями `allowed` и `reason` (`ARCHIVED_BY_EMPLOYER`, `EMPLOYER_NEGOTIATIONS_LIMIT_EXCEEDED`, `PFP_BLOCK`) и `send_file_state.allowed`. По сравнению с RUN-0056 это существенное улучшение: раньше запрет на переписку обнаруживался только по ошибке отправки (GAP-3), теперь состояние читается до того, как оператор напишет ответ, и КЦ может показать причину.

> ⚠️ **GAP-R6** (уровень: Medium): требование §4.6.1 «синхронизации подлежат текстовые сообщения и поддерживаемые файлы-вложения» шире документированных возможностей: в одном сообщении допускается **один** файл, а пример условий загрузки (`GET /common/chats/files/conditions`) содержит максимальный размер 20971520 байт и типы `image/jpeg`, `image/png`. Перечень типов должен читаться интеграцией во время работы, а не зашиваться, но полагаться на передачу произвольных документов из КЦ в HH нельзя. (Источник: спецификация hh.ru, `chat-message-post`, схема `ChatsCommonMessagePostFileUploadIds`; пример `ChatsCommonFilesConditionsResponse`.)

### 5.3. Статус отклика после ответа оператора

Смена состояния отклика документирована как **отдельное действие**: `PUT /negotiations/{collection_name}/{nid}` (`change-negotiation-action`) изменяет работодательское (`employer_state`) или соискательское (`state`) состояние, а `put-negotiations-collection-to-next-state` переводит отклик на следующий этап с необязательным сообщением. Доступные действия перечислены в самом отклике (`actions[].url`, `actions[].arguments`).

> ⚠️ **GAP-R8** (уровень: Low, был GAP-7): отправка сообщения в чат **не меняет** статус отклика — это требует отдельного вызова. Требование §4.6.2 выполнимо, но ФТ обязано назвать конкретное действие и его аргументы: набор доступных статусов зависит от вакансии и работодателя и запрашивается для каждого отклика. (Источник: спецификация hh.ru, `change-negotiation-action`, `put-negotiations-collection-to-next-state`.)

**Вердикт: Частично** (было «Нет»). Механизмы для обеих сторон обмена документированы; частичность — из-за негарантированной доставки событий, ограничений на вложения и того, что «реальное время» в ФТ не выражено измеримым НФТ.

## 6. ФТ-07 — Склейка сообщений нескольких Акторов в одно обращение

**Требование ФТ.** Сообщения нескольких Акторов одного чата HH собираются в одно Обращение по ключу «Кандидат + Вакансия» (§4.7.1); сообщения из КЦ уходят от интеграционного аккаунта «от лица компании» (§4.7.2); получение событий не зависит от статуса ответственного рекрутера (§4.7.3).

**§4.7.1 — закрывается.** Чат и есть единица «кандидат + вакансия»; `get-participant-list` возвращает участников с ролями `APPLICANT` / `EMPLOYER` / `BOT`, а у соискателя — `resume_id`. Отличать сообщения рекрутеров от сообщений кандидата можно по `sender_display_info.role`.

**§4.7.2 — не закрывается.** Каждое сообщение несёт `sender_display_info` с полями `name` («Имя отправителя сообщения»), `icon` и `role`; способа подменить отображаемое имя на название компании в спецификации нет.

> ⚠️ **GAP-R2** (уровень: Medium, был GAP-6): отправка «от лица компании» не поддерживается — кандидат видит имя менеджера, под которым работает интеграция (`sender_display_info.name`). Обход — выделенный технический менеджер с нейтральным именем; это меняет отображаемое имя, но не природу ограничения. Дополнительно: поле `is_automated` («сообщение создано автоматически, например с помощью AI») позволяет честно помечать автоответы КЦ, и ФТ должно определить, ставится ли этот признак для автоматических ответов канала. (Источник: спецификация hh.ru, схемы `ChatsCommonSenderDisplayInfo`, `ChatsCommonMessagePostText`.)

**§4.7.3 — прямо противоречит документации в исходной формулировке.** Требование «получение событий не зависит от статуса ответственного за Вакансию Рекрутера» выполнимо только при условии, что интеграционный менеджер — участник чата. См. §7 и §12.

**Вердикт: Частично.**

## 7. GAP-R1 — чат виден только менеджерам-участникам (High Risk)

**Формулировка Заказчика (⚠️ Caveat постановки).** Чат создаётся автоматически только для менеджера, ответственного за вакансию; только он видит чат в своём списке. Если в чат пишет другой пользователь, он добавляется в участники.

**Проверка по документации — подтверждается.**

- `WebhookActionChatCreated`: «Создание чата. Событие присылается менеджеру работодателя по тем чатам, в которых он **является участником**».
- `WebhookActionChatMessageCreated`: «Создание сообщения в чате. Событие присылается менеджеру работодателя по тем чатам, в которых он **является активным участником**».
- `get-participant-list`, `put-participant-list`, `get-chat-messages`: ответ `404` — «Чат не найден или не доступен текущему пользователю».
- Существует явная операция добавления участника: `PUT /common/chats/{chat_id}/participants`, тело `{"id": "<идентификатор добавляемого в чат менеджера>"}`, ответ `204`.
- Сообщения типов `PARTICIPANT_JOINED` и `PARTICIPANT_LEFT` фиксируют изменения состава участников в ленте чата — то есть добавление участника **видимо** в переписке.
- В спецификации есть отдельные теги «…на уровне работодателя» для откликов, резюме, вакансий, менеджеров, адресов и комментариев. **Для чатов такого тега нет** — доступ к чатам существует только на уровне менеджера.

> ⚠️ **GAP-R1 — HIGH RISK**: чат по отклику доступен только менеджерам-участникам, по умолчанию — одному ответственному за вакансию; события `CHAT_CREATED` и `CHAT_MESSAGE_CREATED` доставляются только участникам; доступа к чатам «на уровне работодателя» в API нет. Без специального решения канал КЦ получит переписку только по вакансиям того менеджера, под которым подключена интеграция, и цель ФТ §2.2 («обрабатывать обращения силами общей группы рекрутеров») не будет достигнута. (Источник: спецификация hh.ru, схемы `WebhookActionChatCreated`, `WebhookActionChatMessageCreated`; операции `get-participant-list`, `put-participant-list`; отсутствие тега «Чаты на уровне работодателя».)

### 7.1. Митигации

| # | Митигация | Как работает | Статус подтверждения | Цена |
| --- | --- | --- | --- | --- |
| M1 | Интеграционный менеджер назначается **ответственным** за все вакансии, попадающие в фильтр ФТ-04 | Чаты создаются сразу у него; событий и доступа достаточно без обходов | **Подтверждено документацией** (следует из самого правила создания чата) | Организационное изменение у Заказчика: ответственный в HH перестаёт быть «живым» рекрутером; список ответственных нужно поддерживать при заведении вакансий |
| M2 | Подписка `NEW_RESPONSE_OR_INVITATION_VACANCY` с `vacancies_only_mine: false` + автодобавление интеграционного менеджера в чат методом `put-participant-list` | Событие приходит по **всем вакансиям, к которым есть доступ**, и несёт `chat_id`; интеграция немедленно добавляет себя в участники и начинает получать `CHAT_MESSAGE_CREATED` | **Не подтверждено**: спецификация не определяет, доступен ли чужой чат менеджеру для вызова `put-participant-list` (возможен `404`). Гипотеза Г1, проверяется spike | Если гипотеза верна — цена в том, что в ленте чата появится системное сообщение `PARTICIPANT_JOINED`, видимое кандидату |
| M3 | Первое исходящее сообщение отправляет ответственный менеджер, после чего интеграция уже участник | Соответствует правилу «если в чат пишет другой пользователь, он добавляется в участники» | **Не подтверждено** для обратного направления: чтобы написать, нужен доступ к чату | Ручное действие рекрутера на каждый новый чат — неприемлемо для массового подбора |
| M4 | Запрос к hh.ru на доступ к чатам на уровне работодателя | Снимает ограничение полностью | Организационно, срок не контролируется | Внешняя зависимость |

Рекомендация: **M1 как основа договорённости с Заказчиком, M2 как целевая автоматизация после подтверждения Г1**. Строить решение только на M2 до spike нельзя.

### 7.2. Смежное следствие — единая точка отказа

Интеграция целиком живёт под одним менеджерским аккаунтом (`X-Manager-Account-Id`). Блокировка или удаление этого менеджера обрывает канал и, согласно разделу Webhook API, удаляет подписки при отзыве доступа приложению. Требуется процедура смены интеграционного менеджера; в ФТ её нет.

## 8. ФТ-08 — Передача контекста при создании обращения

**Требование ФТ (§4.8.1).** Переносятся: текст сообщений, название вакансии, ссылка на вакансию, ссылка на резюме, id кандидата в HH, ФИО из резюме, телефон при наличии.

**Факт документации.** Всё, кроме контактов, собирается штатно: `resume_id` кандидата — из `get-participant-list` (роль `APPLICANT`) или из payload события отклика; `vacancy_id` — из события либо из соответствия `chat_id → vacancy_id`; история переписки до взятия в работу — `get-chat-messages` c пагинацией (`start_message_id`, `limit` 1…50, `order` `prev`/`next`, флаг `has_more`).

Ограничение по контактам сохраняется без изменений: в анонимных резюме `phones`, `email` и ФИО скрыты, просмотр резюме и контактов квотируется.

> ⚠️ **GAP-R7** (уровень: Medium, был GAP-5): ФИО и телефон кандидата не гарантированы — в анонимных резюме контакты скрыты, а просмотр квотируется. Устойчивый ключ идентификации кандидата — `resume_id` из участников чата, а не телефон. Поведение системы при недоступности контактов в ФТ по-прежнему не описано. (Источник: документация hh.ru по просмотру резюме работодателем; `ChatsCommonParticipant.resume_id`.)

> ⚠️ **GAP-R9** (уровень: Low): тип `chat_id` в спецификации несогласован — в объекте отклика (`NegotiationsObjectsTopicItemCommon`) это `number`, в операциях раздела «Чаты» и в payload вебхуков — `string`. Интеграция обязана хранить идентификатор чата как строку и не приводить его к числу: числовое представление рискует потерять точность и не совпасть с ключом из вебхука. (Источник: спецификация hh.ru, схемы `NegotiationsObjectsTopicItemCommon`, `ChatsCommonChatBasic`, `WebhookPayloadChatMessageCreated`.)

**Вердикт: Частично.**

## 9. ФТ-09 — Автосопоставление кандидата с Адресной книгой

Логика сопоставления — на стороне Mango и реализуема. Вывод RUN-0056 сохраняется и уточняется: приоритет ключей должен начинаться с `resume_id` (устойчив, приходит всегда), затем телефон и e-mail (могут отсутствовать из-за GAP-R7). Порядок ключей в ФТ по-прежнему не задан.

**Вердикт: Частично** — правило сопоставления требует доопределения в ФТ.

## 10. ФТ-10 — Отчётность и выгрузка

Отчёт «История обращений» уже содержит фильтр по каналу; добавление канала HH — типовая доработка. Ограничение RUN-0056 («состав выгружаемых полей зависит от снятия GAP-1») снято: состав полей чата и сообщения теперь известен точно — `creation_time`, `unread_message_count`, `vacancy_id`, `last_message`, роль отправителя, признак `viewed_by_opponent` («факт просмотра сообщения оппонентом»), тип сообщения.

**Вердикт: Да** (сторона Mango, по §4.10.2 — «в отчёты передаются только сопоставимые с API МД поля»).

## 11. Сравнение путей получения сообщений и выбор для КЦ Mango

| | Путь 1: отклик → `chat_id` | Путь 2: `get-common-chat-list` | Путь 3: вебхук `CHAT_MESSAGE_CREATED` | Путь 4: вебхук отклика + добавление участника |
| --- | --- | --- | --- | --- |
| Как работает | `get-negotiation-item` / `get-collection-negotiations-list` по вакансии → `chat_id` → `get-chat-messages` | `GET /common/chats` → `chat_id` → `get-chat-messages` | Подписка на событие → `chat_id`, `message_id` → `get-chat-messages` | `NEW_RESPONSE_OR_INVITATION_VACANCY` (`vacancies_only_mine: false`) → `chat_id`, `vacancy_id`, `resume_id` → `put-participant-list` → далее Путь 3 |
| Задержка | Период опроса (минуты) | Период опроса (минуты) | Секунды | Секунды после включения в чат |
| Даёт `vacancy_id` | Да (запрос строится по вакансии) | Да (поле `vacancy_id`) | **Нет** | **Да** |
| Ограничение масштабирования | Пагинация по каждой вакансии; для работодателя `vacancy_id` обязателен | `page` ≤ 50, `per_page` ≤ 20 → ≈1000 чатов; нет сортировки и фильтра «изменённые с» | Один URL на пользователя; доставка не гарантирована | То же, что Путь 3 |
| Зависимость от GAP-R1 | Отклики видны на уровне работодателя, но `get-chat-messages` — только участнику | Список содержит только чаты текущего менеджера | Только чаты, где менеджер активный участник | **Смягчает GAP-R1**: событие приходит по всем доступным вакансиям |
| Роль в целевой схеме | Сверка пропусков, догрузка истории | Первичная инвентаризация, диагностика | **Основной поток реального времени** | **Входная точка нового чата** |

**Выбор для архитектуры КЦ Mango: комбинация Путей 4 + 3 с Путём 1 в роли сверки.**

Обоснование:

1. **ФТ-06 требует реального времени.** Опрос (Пути 1 и 2) даёт задержку в минуты и расходует лимиты; вебхук — единственный документированный способ узнать о сообщении сразу.
2. **ФТ-04 требует вакансию, а событие сообщения её не содержит (GAP-R3).** Значит, соответствие `chat_id → vacancy_id` должно наполняться раньше первого сообщения — ровно это делает Путь 4.
3. **ФТ-07 §4.7.3 требует независимости от ответственного рекрутера.** Из четырёх путей только Путь 4 работает с настройкой «уведомления о всех вакансиях, к которым есть доступ» (`vacancies_only_mine: false`) и потому не привязан к одному менеджеру на входе.
4. **Вебхуки не гарантируют доставку.** Поэтому Путь 1 обязателен как периодическая сверка: он опирается на список откликов по вакансиям, а не на список чатов, и не упирается в потолок ≈1000 чатов (GAP-R4).
5. **Путь 2 не годится в основные**: без сортировки и фильтра «изменённые с» инкрементальное чтение невозможно — пришлось бы каждый цикл вычитывать весь список.

## 12. Влияние GAP-R1 на сценарии КЦ Mango

| Сценарий КЦ | Что требуется на стороне HH | Влияние GAP-R1 | Блокирует? |
| --- | --- | --- | --- |
| Групповая обработка: обращение принимает группа рекрутеров, а не конкретный сотрудник | Полный входящий поток по фильтруемым вакансиям в один интеграционный аккаунт | Прямое: без M1/M2 поток ограничен вакансиями одного менеджера | Не блокирует **архитектурно**, блокирует **бизнес-цель**, если ни одна митигация не применена |
| Передача чата между операторами | Ничего: в HH участник один и тот же | Нет. Смена оператора не видна кандидату, что совпадает с §4.7.2 ФТ | Нет |
| Skill-based маршрутизация, резервный сотрудник, автозавершение | Ничего: маршрутизация выполняется в КЦ после создания Обращения | Нет | Нет |
| Ответ оператора кандидату | Право писать в чат = участие в чате | Косвенное: тот же интеграционный участник и пишет; дополнительно проверяется `write_message_state.allowed` | Нет |
| Отчётность по каналу | Данные уже в КЦ | Полнота отчётов наследует полноту входящего потока | Нет |

**Ответ на вопрос постановки** («блокирующий фактор или архитектурный обходной путь?»): **архитектурный обходной путь**. Ограничение не запрещает ни один сценарий КЦ, но задаёт обязательное условие развёртывания — интеграционный менеджер должен быть участником каждого обрабатываемого чата. Условие выполняется организационно (M1, гарантировано документацией) или автоматически (M2, требует подтверждения гипотезы Г1). Риск оценивается как **High** именно потому, что в отсутствие обоих решений интеграция выглядит работающей — сообщения приходят, обращения создаются, — но покрывает лишь часть потока, и дефект обнаруживается уже в эксплуатации.
