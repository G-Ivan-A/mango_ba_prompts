# L3 — Заметки по архитектуре интеграции и непроверенные гипотезы

Уровень для архитектора и разработчика. Документ фиксирует целевую схему обмена, следующую из [`L2-gap-matrix.md`](L2-gap-matrix.md), и — отдельно — то, что **не** проверено и требует spike на реальном доступе работодателя. Разделение обязательно: без живого аккаунта hh.ru часть решений остаётся гипотезами, и выдавать их за факт нельзя.

## 1. Целевая схема обмена

```text
                     ┌──────────────── hh.ru ────────────────┐
кандидат ──отклик──▶ │ отклик (negotiation) ─── чат (chat_id) │
                     └───┬───────────────────────────┬───────┘
                         │ NEW_RESPONSE_OR_          │ CHAT_MESSAGE_CREATED
                         │ INVITATION_VACANCY        │ (только участникам чата)
                         │ vacancies_only_mine:false │
                         ▼                           ▼
              ┌───────────────────────── приёмник вебхуков (Mango) ─────────┐
              │ 1. ответ 2xx за < 5 с, обработка асинхронно                 │
              │ 2. по событию отклика: сохранить chat_id→vacancy_id,        │
              │    resume_id; вызвать PUT /common/chats/{id}/participants   │
              │ 3. по событию сообщения: GET /common/chats/{id}/messages    │
              │ 4. фильтр по перечню вакансий канала (ФТ-04)                │
              │ 5. первое текстовое сообщение → Обращение (ФТ-05)           │
              └───────────────┬─────────────────────────────────────────────┘
                              │                 ▲
                    ответ оператора             │ периодическая сверка:
                    POST .../messages           │ get-collection-negotiations-list
                    + change-negotiation-action │ по вакансиям канала → chat_id
                              ▼                 │
                     ┌──────────────── hh.ru ───┴────────────┐
```

Ключевые свойства схемы:

- **Событие — это уведомление, а не данные.** Payload `CHAT_MESSAGE_CREATED` не содержит ни текста, ни вакансии, ни резюме (GAP-R3), поэтому каждое событие обязано порождать запрос к API. Проектировать «доставку по вебхуку» без последующего чтения нельзя.
- **Идентификатор чата хранится строкой** (GAP-R9).
- **Сверка опирается на отклики, а не на список чатов** (GAP-R4): `get-common-chat-list` не имеет фильтра «изменённые с» и упирается в ≈1000 чатов, а перебор откликов идёт по перечню вакансий канала, который и так известен из настроек.

## 2. Гипотезы, требующие проверки на реальном доступе

| # | Гипотеза | Как проверить | Что меняется при опровержении |
| --- | --- | --- | --- |
| **Г1** | Менеджер, не являющийся участником чата, может добавить себя (или другого менеджера) в чат вызовом `PUT /common/chats/{chat_id}/participants`, узнав `chat_id` из вебхука по отклику | Подписаться на `NEW_RESPONSE_OR_INVITATION_VACANCY` с `vacancies_only_mine: false` под менеджером Б; создать отклик на вакансию менеджера А; вызвать `put-participant-list` под Б; ожидать `204` против `403`/`404` | Автоматический обход GAP-R1 (митигация M2) невозможен; остаётся организационная M1 — интеграционный менеджер назначается ответственным за вакансии |
| Г2 | `NEW_RESPONSE_OR_INVITATION_VACANCY` с `vacancies_only_mine: false` действительно приходит по вакансиям чужих менеджеров в пределах работодателя | Тот же стенд: проверить факт доставки события менеджеру Б | Входная точка нового чата отсутствует; Путь 4 вырождается в Путь 1 (опрос откликов) |
| Г3 | Добавление участника не порождает уведомления кандидату, кроме системного сообщения `PARTICIPANT_JOINED` в ленте | Наблюдение со стороны кандидата на стенде | Требуется согласование с Заказчиком по вопросу 2 из [L2, §15](L2-gap-matrix.md#15-вопросы-заказчику) |
| Г4 | Методы раздела «Чаты» имеют лимиты запросов, не описанные в спецификации (GAP-R10) | Нагрузочная проба, наблюдение `429` и заголовков ответа | Нужен адаптивный троттлинг и очередь исходящих |
| Г5 | Условия загрузки файлов у целевого работодателя шире примера из спецификации (только JPEG/PNG до 20 МиБ) | `GET /common/chats/files/conditions` под реальным аккаунтом | Объём ФТ-06 по вложениям сокращается до изображений |

Ни одна из гипотез не проверена в этом прогоне: доступа работодателя к hh.ru у исполнителя нет ([`../inputs/README.md`](../inputs/README.md), раздел «Чего во входе нет»). Г1 — блокирующая для выбора между митигациями M1 и M2 и должна быть проверена первой.

## 3. Приём вебхуков: требования к реализации

1. **Ответ за 5 секунд.** Раздел Webhook API: если ответ не получен в течение 5 секунд, событие присылается повторно. Обработка обязана быть асинхронной: приёмник кладёт событие в очередь и отвечает `200` сразу.
2. **Идемпотентность приёма.** Повторные доставки — штатное поведение. Ключ дедупликации — `message_id` для сообщений, `chat_id` + тип для событий чата.
3. **Код `409` как «уже обработано».** Спецификация допускает `409` наравне с `2xx`, что даёт явный способ сообщить о повторе.
4. **Аутентификация колбэка.** Подпись не документирована (`security: null`), поэтому: секретный сегмент в URL подписки, ограничение источников на сетевом уровне, обязательная перепроверка события запросом к API. Содержимое события не должно считаться доверенным само по себе.
5. **Один URL на пользователя в рамках приложения.** Все типы событий приходят на общий адрес; маршрутизация — по полю `action_type` в теле.
6. **Мониторинг блокировки подписки.** При длительных сбоях hh.ru ставит подписку в очередь на блокировку и уведомляет разработчика письмом — нужен алерт, иначе канал «тихо» замолчит.

## 4. Отправка сообщений: идемпотентность и ошибки

- `idempotency_key` — UUID, обязателен для текста и для вложения. Ключ генерируется один раз на исходящее сообщение КЦ и **переиспользуется при всех ретраях**; иначе повторная отправка создаст дубль у кандидата.
- `409` в ответе означает, что сообщение с этим ключом уже создано; для КЦ это успех, а не ошибка.
- Перед отправкой читается `chat_states.write_message_state.allowed`; при `allowed: false` оператору показывается причина (`ARCHIVED_BY_EMPLOYER`, `EMPLOYER_NEGOTIATIONS_LIMIT_EXCEEDED`, `PFP_BLOCK`), а сообщение не ставится в очередь бесконечных ретраев.
- Вложение: сначала `POST /common/chats/files/upload_links`, затем отправка сообщения с `file_upload_ids`; **не более одного файла на сообщение**, поэтому несколько вложений из КЦ разворачиваются в несколько сообщений.
- Смена статуса отклика после ответа оператора — отдельный вызов `change-negotiation-action`; допустимые действия читаются из самого отклика (`actions[]`), а не зашиваются в код.

## 5. Сверка (reconciliation)

Периодическая задача, закрывающая GAP-R4:

1. Для каждой вакансии из перечня канала — `get-collection-negotiations-list` (для работодателя `vacancy_id` обязателен), собрать `chat_id` и время последнего изменения.
2. Для чатов, где известный локально `message_id` отстаёт, — `get-chat-messages` с `start_message_id` последнего обработанного и `order: next`, повторяя, пока `has_more` истинно.
3. Для чатов, отсутствующих локально, — создать соответствие и, при необходимости, выполнить добавление участника (Г1).

Период сверки — предмет НФТ, которых в ФТ нет ([L2, §15](L2-gap-matrix.md#15-вопросы-заказчику), вопрос 7). Разумная отправная точка для обсуждения — раз в 5–15 минут для активных вакансий канала.

## 6. Учётные записи и доступ

- Все запросы адресуются конкретному менеджеру заголовком `X-Manager-Account-Id`; список доступных аккаунтов — `GET /manager_accounts/mine`.
- Часть методов помечена «Метод требует наличия платного доступа для работодателя» — коммерческая предпосылка интеграции, которую нужно подтвердить у целевого клиента.
- Отзыв доступа приложению удаляет подписки на вебхуки: процедура смены интеграционного менеджера обязана включать пересоздание подписок и повторное включение в чаты.
