# Шаг 3. Валидация НФТ с веб-источниками (эпизод 3, реплики 4–5)

**Реплика 4.** БА вставляет документ НФТ и ставит проверяемую задачу: «Есть такое
исследование, в формате НФТ ниже, проверь его, дай ссылки и сопоставь с
предложением в п. 4». Проверяются три утверждения: НФТ-001 (HTML письма ≤102 КБ,
Gmail), НФТ-002 (подпись ≤30 000 символов, Outlook API), НФТ-003 (письмо ≤20 МБ).

**Реплика 5.** Единственный такт диалога, где модель обращается к внешним
источникам: `web_search` вернул **38 источников**, `web_extractor` — **3
страницы** (Microsoft Learn «Limits for activation and JavaScript API for Outlook
add-ins», Email on Acid «Gmail Email Clipping», officeatwork «Image Size
Requirements for Email Signatures»). Латентность такта — 173 с при среднем 50 с
по остальным.

Результат:

| НФТ | Вердикт модели | Проверка заземления |
| --- | --- | --- |
| НФТ-001 (102 КБ, Gmail) | подтверждено | в выдаче инструмента 12 вхождений «102KB» |
| НФТ-002 (30 000 символов, Outlook) | подтверждено | 5 вхождений «30,000 characters» + `setSignatureAsync` в извлечённой странице Microsoft Learn |
| НФТ-003 (20 МБ) | **частично** подтверждено | в выдаче — «Outlook 20-34MB», «25 MB» для Gmail; модель честно предлагает ориентироваться на 25 МБ |

Детали проверки — [`../../logs/grounding-check.md`](../../logs/grounding-check.md).

**Самокоррекция.** Модель сопоставляет НФТ-002 со своим же предложением из
предыдущего такта и отклоняет его: «предложение "30 КБ" технически некорректно,
если подразумевается хранение изображения внутри подписи», с расчётом «логотип
100 КБ в Base64 = ~133 000 символов → превышение лимита Outlook API в 4.5 раза».
Собственное число из эпизода 2 снято самой моделью, без указания БА.

**Дефект Г3 (риторическое усиление против собственного источника).** Тезис
«❌ 30 КБ (моё предложение) ≠ 30 000 символов (НФТ-002)» построен на различии
единиц, тогда как извлечённая моделью страница officeatwork прямо приравнивает
их: «Outlook API limits the entire signature to 30,000 characters (approximately
30 KB)». Реальная причина превышения — Base64-инфляция изображения, а не
единицы измерения. Коэффициент «~33 %» со сносками `[[31]][[32]]` в выдаче
инструмента не встречается: источники подтверждают рост размера качественно, без
этого числа.

**Оценка эпизода:** принят. Задача «проверь и дай ссылки» выполнена с реальными
источниками, вердикты соответствуют полученному тексту, спорное значение из
эпизода 2 снято самой моделью. Дефект Г3 не влияет на итоговую рекомендацию
(«использовать внешние ссылки вместо Base64»).
