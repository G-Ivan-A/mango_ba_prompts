## 0. Резюме для Заказчика (одна страница)

- **Что просили:** выдавать стороннему сервису РА доступ к записям разговоров так,
  чтобы он мог забирать записи только выбранных сотрудников/групп, не передавая
  единый ключ с полным доступом.
- **Что предлагается:** отдельный **ограниченный API-ключ**, который (1) даёт доступ
  **только** к получению записей разговоров, (2) видит записи **только** выбранных
  сотрудников/групп, (3) **не влияет** на права основного ключа.
- **Границы MVP:** создание, просмотр, отзыв ключа + фильтрация по
  сотрудникам/группам. **Вне MVP** (отдельная оценка): статистика использования
  (В5) и временная деактивация (В6).
- **Что нужно от Заказчика для финализации:** ответы на блокирующие вопросы
  В-МОТИВ, В-СКОП, В-ИЗМ, В-РЕТРО (см. §Открытые вопросы).

## 1. Терминология

Полный глоссарий — [`steps/step-1-glossary.md`](steps/step-1-glossary.md). Ключевые
термины: **основной API-ключ** (полный доступ, не меняется), **ограниченный
API-ключ** (дополнительный, суженная область действия), **область действия ключа**
(разрешённый метод + множество сотрудников-источников), **группа сотрудников**
(единица выбора области).

## 2. Проблема, Цель, Задачи

- **Проблема:** единый API-ключ даёт стороннему сервису доступ ко всем записям всех
  сотрудников и ко всем методам API; сузить доступ нельзя ⇒ интеграция ведётся с
  избыточными правами и риском по ПДн.
- **Цель:** дать возможность выдавать доступ к записям разговоров только по
  заданному перечню сотрудников/групп и только к методу получения записей, не
  затрагивая основной ключ.
- **Задачи:** 2.3.1 создание отдельного ключа · 2.3.2 ограничение метода · 2.3.3
  фильтрация источников · 2.3.4 неприкосновенность основного ключа · 2.3.5 *(опция)*
  статистика · 2.3.6 *(опция)* деактивация. Детали и дерево BCREQ-1069 —
  [`steps/step-2-normalization.md`](steps/step-2-normalization.md).
