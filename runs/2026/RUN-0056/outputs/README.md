# Результаты прогона RUN-0056 — состав и обоснование формата

## Задача

Постановка [#315](https://github.com/G-Ivan-A/mango_ba_prompts/issues/315) требует gap-анализ и оценку технической осуществимости интеграции КЦ Mango Office с чатами HH.ru **и отдельно** требует, чтобы исполнитель сам определил, смоделировал и обосновал формат итоговых артефактов (1–3 уровня), а обоснование положил в этот файл.

## Выбранный формат: три уровня

| Уровень | Файл | Адресат | Вопрос, на который отвечает |
| --- | --- | --- | --- |
| L1 | [`L1-executive-summary.md`](L1-executive-summary.md) | ПО/ПМ, руководитель направления | Делаем или нет, что мешает, какой объём риска. |
| L2 | [`L2-gap-matrix.md`](L2-gap-matrix.md) | БА, системный аналитик, архитектор | Какое требование ФТ чем закрывается в API HH.ru, где разрыв, какой обходной путь. |
| L3 | [`L3-technical-spike-notes.md`](L3-technical-spike-notes.md) | Разработчик, техлид | Что именно проверять в spike, какие лимиты и коды ошибок закладывать в архитектуру. |

## Почему три уровня, а не один

1. **Разные адресаты принимают разные решения.** Решение «участвовать ли в разработке» принимается по вердикту и рискам, решение «как строить канал» — по построчному сопоставлению требований, решение «что проверить первым» — по списку неизвестных. Один документ, обслуживающий все три решения, читается ни одним из адресатов: руководителю он длинен, разработчику — недостаточно конкретен.
2. **Разный срок жизни.** L1 устаревает при смене решения по проекту, L2 — при изменении ФТ, L3 — сразу после выполнения spike. Разделение позволяет обновлять и выбрасывать части независимо.
3. **Разная степень достоверности.** L2 содержит только сопоставление фактов ФТ с фактами документации, L3 — явно помеченные гипотезы, требующие проверки. Смешение проверенного и гипотетического в одном документе — основной источник ложных ожиданий у заказчика анализа.
4. **Прецедент в репозитории.** Прогон [`RUN-0055`](../../RUN-0055/outputs/README.md) уже разделил результат на рабочую матрицу и управленческое резюме, и это разделение было принято. Настоящий прогон продолжает практику, добавляя третий уровень, потому что здесь, в отличие от #313, значительная часть вопросов не решается по документации и должна быть вынесена в план проверок.

**Консолидированный документ для согласования** — L1: он самодостаточен, содержит вердикт, перечень критических гэпов и ссылки вниз по уровням.

## Границы анализа

- Оценивается **техническая осуществимость** — покрывается ли требование ФТ публично документированными возможностями API hh.ru и существующей моделью каналов КЦ Mango Office. Оценка трудозатрат, стоимости, сроков и юридических аспектов (152-ФЗ, соглашение с hh.ru) **не выполняется**.
- Источником фактов об HH.ru является **только** официальный репозиторий документации [`hhru/api`](https://github.com/hhru/api) на коммите `906d7b6`; источником фактов о Mango Office — БЗ репозитория (`kb/processed/`). Утверждения, не подтверждённые этими источниками, помечены как гипотезы в L3.
- Часть документации hh.ru из среды выполнения недоступна по сети; последствия для полноты вердикта зафиксированы в [`../logs/source-availability.md`](../logs/source-availability.md) и повторены в L1.
