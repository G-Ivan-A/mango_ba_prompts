## 1. ФТ-01 — OAuth-авторизация в HeadHunter при настройке канала

**Требование ФТ.** При подключении канала Пользователь авторизуется в HeadHunter из ЛК Mango Office; интеграция работает под выданным доступом.

**Факт документации.** hh.ru реализует OAuth 2.0 с заголовком `Authorization: Bearer ACCESS_TOKEN`; различаются токен приложения и токен пользователя, проверка — методом `/me` [hhru/api, docs/authorization.md], [hhru/api, docs/authorization_for_user.md], [hhru/api, docs/authorization_for_application.md].

**Сторона Mango.** Существующий канал «Авито Работа» подключается ровно этим маршрутом: виджет → «Подключить» → авторизация во внешней системе с выдачей доступа к просмотру и отправке сообщений; при отключении требуется повторная авторизация [LK, §4.5.11.2.2, с.347-352] (`kb/processed/mango-lk-manual/sections/210-avito-rabota.md`).

**Вердикт: Да.** Требование закрывается прецедентом и документированным механизмом.

**Ограничение.** Регистрация приложения-интегратора у hh.ru и получение партнёрского/платного доступа работодателя — организационное условие, не решаемое кодом: методы работы с откликами помечены «Методы требуют наличия платного доступа для работодателя» [hhru/api, docs/employer_negotiations.md].

## 2. ФТ-02 — Подключение и настройка канала HH в ЛК

**Требование ФТ.** ЛК → Текстовые коммуникации → Каналы → Группа каналов; включение/выключение канала; при выключении новые сообщения не поступают, история сохраняется.

**Факт БЗ.** Текущий перечень каналов: «MAX, Вконтакте, WhatsApp, Telegram, Клиентское приложение (по API), E-mail, Авито, Авито Работа» [LK, §4.5.11, `kb/processed/mango-lk-manual/sections/186-nastroyka-kanalov-kommunikacii.md`, строка 31]. Канала HeadHunter в продукте **нет** — требуется разработка нового канала, а не настройка существующего.

**Вердикт: Да** (реализуемо на стороне Mango по существующему паттерну). Это доработка продукта, а не интеграционный разрыв.

**Ограничение-прецедент.** Для «Авито» действует правило «Не следует регистрировать один и тот же аккаунт в разных виджетах Личного кабинета. Действующим будет только канал, созданный последним» [LK, §4.5.11.2.1, с.342-347]. Для HH-канала аналогичное правило (один аккаунт работодателя — один виджет) должно быть зафиксировано в ФТ явно; в текущем ФТ его нет.

## 3. ФТ-03 — Маршрутизация созданных обращений

**Требование ФТ.** Обращения канала HH маршрутизируются на сотрудника или группу единообразно с прочими текстовыми каналами МД.

**Факт БЗ.** Блок «Приём и обработка обращений» (кто принимает — сотрудник, группа или чат-бот; резервный сотрудник/группа; «Распределение обращений») одинаков для каналов «Авито Работа» [LK, §4.5.11.2.2] и «Клиентское приложение» [LK, §4.5.11.2.2, с.335-338]. Требование ложится на существующий механизм без изменений.

**Вердикт: Да.**

## 4. ФТ-04 — Фильтрация входящих сообщений по вакансии

**Требование ФТ.** В работу попадают только сообщения по вакансиям категории «линейный персонал»; по прочим вакансиям обращение не создаётся.

**Факт документации.** Вся работа с откликами/приглашениями ведётся в рамках одной выбранной вакансии, и на пару «вакансия + резюме» существует ровно один отклик/приглашение [hhru/api, docs/employer_negotiations.md]. Значит, идентификатор вакансии в событии присутствует и фильтрация технически возможна.

Однако классификатора «линейный персонал» в документации API нет: справочники профессиональных ролей и категорий, по которым такое разделение можно было бы вывести автоматически, в прочитанной части документации не описаны, а перечень справочников доступен только через недоступную спецификацию.

> ⚠️ **КРИТИЧЕСКИЙ GAP** (GAP-4): в API hh.ru отсутствует документированный признак «линейный персонал» у вакансии, поэтому автоматическая фильтрация по формулировке ФТ-04 невыполнима — требуется явный список вакансий (или их идентификаторов), выбираемый Пользователем в настройках канала. (Источник: Отсутствует в документации)

**Вердикт: Частично.** Фильтрация по конкретной вакансии — да; по категории «линейный персонал» — нет. Требуется правка ФТ: заменить категорию на явный выбор вакансий Пользователем.

## 5. ФТ-05 — Создание обращения по первому входящему сообщению и перенос контекста сессии

**Требование ФТ.** Первое входящее текстовое сообщение кандидата по вакансии, где нет активного обращения, создаёт Обращение; переносится исторический контекст открытой Сессии. §4.5.2: отклики без текста обращение не создают (переключатель, по умолчанию выключен). §4.5.3: сессия закрывается вместе с обращением. TTL сессии — максимум 7 дней, фиксировано. §4.5.4: по разным вакансиям — разные обращения, но один и тот же кандидат маршрутизируется на того же оператора и в тот же Чат с клиентом.

**Факт документации.** Методы чтения сообщений отклика от имени менеджера работодателя существуют, но помечены как устаревшие:

> ‼️ Обратите внимание, что методы для работы с сообщениями в рамках отклика/приглашения от имени соискателя и менеджера работодателя устарели, и новые возможности чатов в них не будут поддерживаться. В связи с этим переписка может некорректно отображаться.
> — [hhru/api, README.md] и [hhru/api, docs/employer_negotiations.md#get-messages]

**Факт БЗ (прецедент).** Переключатель §4.5.2 уже реализован в канале «Авито Работа»: «Отклик кандидата из Авито Работа — включите переключатель, чтобы в работу к сотруднику Контакт-центра попадали только отклики с сообщениями» [LK, §4.5.11.2.2, с.347-352]. Автозакрытие по неактивности («Закрывать неактивный диалог через», значение больше нуля) — там же; TTL 7 дней ложится в существующую настройку.

> ⚠️ **КРИТИЧЕСКИЙ GAP** (GAP-1): публичного API чатов hh.ru в индексе документации нет, а единственные документированные методы работы с сообщениями (в рамках отклика/приглашения) объявлены устаревшими с явным предупреждением, что новые возможности чатов в них поддерживаться не будут и переписка может отображаться некорректно. Требования ФТ-05, ФТ-06, ФТ-07 и ФТ-08 опираются именно на эти методы. (Источник: [hhru/api, docs/employer_negotiations.md#get-messages](https://github.com/hhru/api/blob/master/docs/employer_negotiations.md#get-messages))

**Вердикт: Частично.** Логика создания обращения и жизненного цикла сессии — реализуема на стороне Mango; получение самих сообщений — упирается в GAP-1.

## 6. ФТ-06 — Двусторонняя синхронизация в реальном времени

**Требование ФТ.** Текст и поддерживаемые вложения синхронизируются в обе стороны в реальном времени, без авторизации сотрудника в HH. §4.6.2: после ответа оператора статус отклика в HH обновляется; если обращение закрыто без ответа — не меняется.

**Факт документации — приём событий.** В API есть Webhook API из четырёх операций управления подписками (получить подписки, создать подписку, отменить подписку, изменить подписку), доступных работодателю [hhru/api, README.md]. Перечень типов событий в markdown-документации не приведён — он вынесен в OpenAPI-спецификацию, недоступную из среды прогона.

> ⚠️ **КРИТИЧЕСКИЙ GAP** (GAP-2): состав типов событий Webhook API hh.ru не подтверждён — в markdown-документации перечислены только четыре операции управления подписками, а перечень событий вынесен в OpenAPI-спецификацию, недоступную из среды прогона. Без подтверждения наличия события «новое сообщение в чате» требование ФТ-06 о реальном времени не может быть признано выполнимым: остаётся только периодический опрос устаревших методов. (Источник: [hhru/api, README.md — раздел Webhook API](https://github.com/hhru/api#webhook-api))

**Факт документации — отправка.** Свободная переписка возможна только после приглашения: «После приглашения соискателя вы можете начать с ним свободную переписку» [hhru/api, docs/employer_negotiations.md]; попытка написать без приглашения даёт ошибку `no_invitation` [hhru/api, docs/errors.md — таблица negotiations]. Кроме того, у вакансии есть признак `allow_messages`, которым переписка может быть отключена, и существуют состояния `disabled_by_employer`, `chat_archived`, `archived`.

> ⚠️ **КРИТИЧЕСКИЙ GAP** (GAP-3): отправка сообщения кандидату разрешена только в рамках отклика/приглашения и только при наличии приглашения (`no_invitation`), при этом переписка может быть закрыта признаком вакансии `allow_messages` либо состояниями `disabled_by_employer` / `chat_archived` / `archived`. Сценарий «оператор отвечает на любое входящее сообщение» из ФТ-06 выполним не всегда, а ФТ не описывает поведение системы при этих отказах. (Источник: [hhru/api, docs/errors.md — раздел negotiations](https://github.com/hhru/api/blob/master/docs/errors.md))

> ⚠️ **КРИТИЧЕСКИЙ GAP** (GAP-7): автоматическое изменение статуса отклика при ответе оператора (§4.6.2) в документации не описано — состояния отклика меняются отдельными действиями работодателя, а не как побочный эффект отправки сообщения. Требуется явно определить, какое действие над откликом выполняет интеграция и от чьего имени. (Источник: [hhru/api, docs/employer_negotiations.md](https://github.com/hhru/api/blob/master/docs/employer_negotiations.md))

**Вердикт: Нет** (в формулировке «в реальном времени, для любого входящего сообщения»). Требование выполнимо только после подтверждения событий вебхука и доступа к актуальному API чатов.

## 7. ФТ-07 — Склейка сообщений нескольких Акторов в одно обращение

**Требование ФТ.** Сообщения нескольких Акторов в одном чате HH собираются в одно обращение КЦ по ключу «Кандидат + Вакансия». §4.7.2: сообщения из КЦ уходят в HH от интеграционного аккаунта (от лица компании). §4.7.3: получение событий не зависит от статуса ответственного рекрутера.

**Факт документации.** Ключ «кандидат + вакансия» соответствует модели hh.ru напрямую: «Для каждой пары вакансия + резюме может быть только один отклик/приглашение» [hhru/api, docs/employer_negotiations.md]. Требование ФТ-07 в части ключа реализуемо без допущений.

**Факт документации — от чьего имени.** Работодатель в API представлен менеджерами; методы работают под токеном конкретного менеджера [hhru/api, docs/employer_managers.md]. Способ отправки сообщения «от компании», а не от менеджера, в документации не описан.

> ⚠️ **КРИТИЧЕСКИЙ GAP** (GAP-6): требование §4.7.2 «сообщения уходят в HH от интеграционного аккаунта (от лица компании)» не подтверждается документацией: API работает под токеном конкретного менеджера работодателя, обезличенная отправка «от компании» не описана. Кандидат увидит имя менеджера, под чьим доступом подключена интеграция. (Источник: [hhru/api, docs/employer_managers.md](https://github.com/hhru/api/blob/master/docs/employer_managers.md))

**§4.7.3** — при работе по токену интеграционного менеджера получение событий действительно не зависит от статуса ответственного рекрутера; риск в том, что этот менеджер становится единой точкой отказа (блокировка или увольнение обрывает канал). В ФТ это не описано.

**Вердикт: Частично.**

## 8. ФТ-08 — Передача контекста при создании обращения

**Требование ФТ.** В обращение переносятся: текст сообщения(ий), название вакансии, ссылка на вакансию, ссылка на резюме, данные кандидата (id кандидата в HH, ФИО из резюме, телефон при наличии). §4.8.2: история до подключения канала не импортируется.

**Факт документации.** Вакансия и резюме доступны как объекты отклика; работодатель читает резюме отдельными методами [hhru/api, docs/employer_resumes.md]. Однако:

- В анонимных резюме поля скрываются: `phones`, `email`, `names_and_photo` возвращаются пустыми [hhru/api, docs/employer_resumes.md#hidden-fields].
- Просмотр резюме квотируется: `429 view_limit_exceeded`, `403 quota_exceeded`, `403 cant_view_contacts`, `403 no_available_service` [hhru/api, docs/errors.md — раздел resumes].

> ⚠️ **КРИТИЧЕСКИЙ GAP** (GAP-5): требования ФТ-08 (ФИО и телефон кандидата) и ФТ-09 (сопоставление с Адресной книгой по контактным данным) не гарантируются: в анонимных резюме `phones`, `email` и `names_and_photo` скрываются, а просмотр резюме и контактов квотируется (`view_limit_exceeded`, `quota_exceeded`, `cant_view_contacts`). Поведение системы при недоступности контактов в ФТ не описано. (Источник: [hhru/api, docs/employer_resumes.md — раздел «Скрытые поля»](https://github.com/hhru/api/blob/master/docs/employer_resumes.md))

**§4.8.2** (история до подключения не импортируется) — ограничение снимает нагрузку с интеграции и совпадает с поведением канала «Авито»; противоречий с API нет.

**Вердикт: Частично.** Идентификатор кандидата, вакансия и ссылки — да; ФИО и телефон — не гарантированы.

## 9. ФТ-09 — Автосопоставление кандидата с Адресной книгой

**Требование ФТ.** Кандидат автоматически сопоставляется с записью АК: при отсутствии совпадения — создаётся, при частичном — дополняется, при полном — не обновляется.

**Оценка.** Логика сопоставления целиком на стороне Mango и реализуема. Ограничение — качество ключа: при скрытых контактах (GAP-5) единственным устойчивым ключом остаётся идентификатор кандидата в HH, а не телефон. Это следует зафиксировать в ФТ как приоритет ключей сопоставления; сейчас ФТ порядок ключей не задаёт.

**Вердикт: Частично** — правило сопоставления требует доопределения.

## 10. ФТ-10 — Отчётность и выгрузка

**Требование ФТ.** Канал HH добавляется в отчёт «История обращений» и в «Контроль сотрудников → Текст». §4.10.2: выгружаются только поля, сопоставимые с API МД. §4.10.3: выгрузка — штатными средствами КЦ.

**Факт БЗ.** Отчёт «История обращений» уже содержит фильтр по каналу наряду с фильтрами по оценке клиента, типу обращения, сотруднику, результату, тематике и способу создания [CC, §4.5, с.161-166] (`kb/processed/mango-cc-manual/sections/72-istoriya-obrascheniy.md`). Добавление нового канала в существующий фильтр — типовая доработка.

**Вердикт: Частично** — сторона отчётности закрывается штатно; состав выгружаемых полей зависит от того, какие поля реально придут из HH, то есть от снятия GAP-1.

| GAP-2 (события вебхука не подтверждены) | Периодический опрос списка откликов с использованием `Etag`/`If-None-Match` и ответа `304` для экономии лимитов [hhru/api, docs/cache.md]. | Задержка вместо реального времени; расход лимитов. |
| GAP-3 (нельзя писать без приглашения) | Отправка только в рамках уже открытой переписки; при отказе — информирование оператора текстом ошибки. | Часть сценариев ФТ-06 не поддерживается. |
| GAP-4 (нет признака «линейный персонал») | Явный выбор вакансий Пользователем в настройках канала. | Ручное сопровождение перечня вакансий. |
| GAP-5 (скрытые контакты, квоты) | Ключ сопоставления — id кандидата в HH; телефон дополняется оператором вручную. | АК заполняется не полностью. |
| GAP-6 (отправка «от компании») | Выделенный технический менеджер работодателя с нейтральным именем. | Имя менеджера видно кандидату; единая точка отказа. |
| Все | Канал «Клиентское приложение (по API)» + внешний шлюз как временная схема: услуги «API-Коннектор» и «Открытое API» [LK, §4.5.11.2.2, с.335-338]. | Не даёт нативного канала HH; ограничения hh.ru сохраняются. |

## 12. Риски и ограничения

| # | Риск | Основание | Влияние |
| --- | --- | --- | --- |
| R1 | Устаревание методов сообщений приведёт к некорректному отображению переписки или их отключению. | [hhru/api, README.md] — прямое предупреждение. | Критическое: неработоспособность канала. |
| R2 | Требуется платный доступ работодателя; без него методы недоступны. | [hhru/api, docs/employer_negotiations.md]; ошибки `403 api_access_payment`, `action_must_be_payed` [docs/errors.md]. | Высокое: блокирует продажу без условия у клиента. |
| R3 | Лимиты на переписку: `in_a_row_limit` (подряд), `overall_limit` (всего), `limit_exceeded`, `too_long_message`. | [hhru/api, docs/errors.md — negotiations]. | Среднее: оператор может не отправить ответ. |
| R4 | Квоты на просмотр резюме исчерпываются раньше, чем обрабатываются обращения. | [hhru/api, docs/errors.md — resumes]. | Среднее: контекст обращения неполон. |
| R5 | Отсутствие НФТ в ФТ (§5 пуст): не заданы объёмы, время доставки сообщения, доступность. | ФТ §5 — «-». | Среднее: нечем принимать результат. |
| R6 | Единый интеграционный менеджер как точка отказа. | [hhru/api, docs/employer_managers.md]. | Среднее: обрыв канала при блокировке доступа. |
