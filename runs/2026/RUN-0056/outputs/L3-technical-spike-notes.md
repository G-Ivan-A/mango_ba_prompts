# L3 — Technical Spike Notes: что проверять до оценки трудозатрат

## 2. Подтверждённые ограничения — закладывать в архитектуру сразу

**Авторизация.** OAuth 2.0, заголовок `Authorization: Bearer ACCESS_TOKEN`; различаются токен приложения и токен пользователя; проверка токена — `/me` [hhru/api, docs/authorization.md]. Токен привязан к менеджеру работодателя [hhru/api, docs/employer_managers.md] — нужен процесс перевыпуска при смене сотрудника.

**Платный доступ.** «Методы требуют наличия платного доступа для работодателя» [hhru/api, docs/employer_negotiations.md]. Ошибки отсутствия доступа: `403 api_access_payment`, `403 action_must_be_payed` [hhru/api, docs/errors.md]. Обрабатывать отдельно от прочих 403: это состояние учётной записи, а не ошибка запроса.

**Модель переписки.** Работа ведётся в рамках одной вакансии; на пару «вакансия + резюме» — ровно один отклик/приглашение [hhru/api, docs/employer_negotiations.md]. Это и есть естественный ключ обращения по ФТ-07 — собственный ключ склейки изобретать не нужно.

**Коды отказов переписки** [hhru/api, docs/errors.md, раздел negotiations] — каждый требует собственной реакции интерфейса оператора:

| Код | Смысл | Ожидаемая реакция КЦ |
| --- | --- | --- |
| `no_invitation` | Переписка без приглашения запрещена | Блокировать поле ввода, показать причину |
| `in_a_row_limit` | Превышен лимит сообщений подряд | Отложить отправку, показать причину |
| `overall_limit`, `limit_exceeded` | Превышен общий лимит | Пометить обращение как недоставляемое |
| `disabled_by_employer` | Переписка отключена работодателем | Не создавать обращение |
| `chat_archived`, `archived` | Чат/отклик в архиве | Закрыть обращение |
| `resume_deleted` | Резюме удалено | Закрыть обращение, не обновлять АК |
| `too_long_message` | Сообщение длиннее допустимого | Валидация длины на стороне КЦ до отправки |
| `wrong_state`, `edit_forbidden` | Недопустимое состояние/запрет правки | Логировать, не ретраить |

**Коды отказов при работе с резюме** [hhru/api, docs/errors.md, раздел resumes]: `429 view_limit_exceeded`, `403 quota_exceeded`, `403 cant_view_contacts`, `403 no_available_service`. Контекст обращения должен создаваться и без резюме — иначе исчерпание квоты остановит канал.

**Скрытые поля.** В анонимных резюме `phones`, `email`, `names_and_photo` пусты [hhru/api, docs/employer_resumes.md]. Ключом сопоставления с Адресной книгой должен быть идентификатор кандидата в HH, телефон — необязательное поле.

**Кеширование.** hh.ru поддерживает `Etag` / `If-None-Match` с ответом `304 Not Modified` [hhru/api, docs/cache.md]. Если S2 покажет отсутствие события «новое сообщение», опрос обязан использовать этот механизм — иначе лимиты израсходуются на пустые ответы.

**Признак вакансии `allow_messages`** [hhru/api, docs/employer_negotiations.md] — читать при подключении вакансии к каналу и предупреждать Пользователя, что переписка по ней недоступна.

## 3. Гипотезы (документацией не подтверждены)

- **Г1.** Webhook API содержит событие о новом сообщении. Основание — наличие раздела Webhook API для работодателя; прямого подтверждения нет. Проверка — S2.
- **Г2.** Полезная нагрузка вебхука содержит идентификаторы вакансии и отклика, достаточные для маршрутизации без дополнительного запроса. Проверка — S3.
- **Г3.** Вложения в чатах HH ограничены теми же типами, что и в канале «Клиентское приложение» Mango (изображение, аудио, видео, документы) [LK, §4.5.11.2.2, с.335-338]. Проверка — S4.

Гипотезы Г1–Г3 **не должны** попадать в оценку трудозатрат до проверки.

## 4. Порядок выполнения spike

1. Получить платный доступ работодателя и тестовую вакансию (без этого проверяемо только S1).
2. S1 → если актуального API чатов нет, остальные проверки выполняются на устаревших методах, и результат spike — обоснование отказа/переноса, а не оценка.
3. S2, S3 — определяют архитектуру приёма (вебхук против опроса).
4. S4, S7, S8 — определяют полноту ФТ-06 и ФТ-07.
5. S5, S6 — определяют ёмкость канала и попадают в НФТ, которых в ФТ сейчас нет.
