# Гипотеза: новый процесс БА «Оценка технической осуществимости внешней интеграции»

Постановка [#315](https://github.com/G-Ivan-A/mango_ba_prompts/issues/315) прямо называет прогон тренировкой для выделения нового характерного процесса БА, не описанного в таксономии Mango. Здесь фиксируется гипотеза; изменение [`docs/taxonomy.md`](../../../../docs/taxonomy.md) в состав прогона **не входит** — эволюция таксономии идёт отдельным решением Пользователя (§3 таксономии), и граница прогона запрещает править рабочие артефакты.

## Наблюдение

Работа, выполненная в этом прогоне, не укладывается ни в один из девяти процессов §2 таксономии:

| Существующий процесс | Почему не подходит |
| --- | --- |
| 1. Формирование ФТ/ТЗ | ФТ уже есть; прогон его не создаёт, а проверяет на выполнимость. |
| 2. Валидация ФТ/ТЗ | Валидация проверяет требования на полноту, непротиворечивость и тестируемость **внутри документа**. Здесь проверка идёт **против внешней системы**: требование может быть безупречным по форме и невыполнимым из-за чужого API. |
| 3. Анализ тендерных ТЗ | Ближе всего, но предмет иной: там оценивается соответствие внешнего ТЗ **своему продукту**, здесь — соответствие **своего** ФТ возможностям **чужой** системы. |
| 8. Impact Analysis | Оценивает влияние изменения на свой продукт, а не осуществимость во внешней системе. |
| 9. Risk Analysis | Риски здесь — следствие gap-анализа, а не его метод. |

## Предлагаемый процесс

**Название:** Оценка технической осуществимости внешней интеграции.

**Что включает:** сопоставление требований своего ФТ/ТЗ с фактическими возможностями внешней системы по её официальной документации; фиксация разрывов с обязательной ссылкой на раздел документации либо с пометкой «отсутствует в документации»; выявление обходных путей; формирование перечня проверок (spike) для неснимаемых по документации вопросов; перечень вопросов Заказчику и владельцу внешнего API.

**Ключевые операции** (из §1 таксономии, новых операций не требуется): `research` (изучение внешней документации), `validation` (сопоставление требования с фактом), `risk_analysis` (последствия разрывов), `solution_design` (обходные пути).

**Отличительный признак процесса:** источником истины является документация **третьей стороны**, которую нельзя изменить и в которой нельзя ничего домыслить. Отсюда обязательный для процесса анти-галлюцинационный контракт: каждое утверждение о внешней системе — со ссылкой на раздел документации, отсутствие возможности фиксируется явной пометкой, недоступность источника фиксируется отдельным протоколом.

**Характерный артефакт:** gap-матрица «требование ↔ факт документации ↔ вердикт ↔ обходной путь». В онтологии ближайшие существующие типы — `A26 coverage-matrix` (форма) и `A28 analysis-note` (жанр); отдельный тип артефакта, вероятно, не требуется, но признак «внешний источник истины» должен быть отражён.

## Что подтвердил этот прогон

- Процесс воспроизводим: последовательность «разбор ФТ → изучение внешней документации → построчное сопоставление → маркировка разрывов → обходные пути → spike-план» выполнена целиком и дала результат, пригодный для решения.
- Процессу необходим шаг **фиксации доступности источников** до начала анализа: недоступность части документации hh.ru изменила глубину вердикта по трём требованиям из десяти и должна была быть зафиксирована как ограничение, а не обнаружена по ходу.
- Процессу необходима **трёхуровневая выдача**: решение о разработке, проектное сопоставление и план проверок принимаются разными людьми (см. обоснование в [`../outputs/README.md`](../outputs/README.md)).
