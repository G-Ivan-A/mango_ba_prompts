## 2. Состав артефактов и обоснование выбора

Контракт задачи (§2) оставляет выбор набора документов исполнителю. Выбраны **пять уровней**: L0 задан Заказчиком прямо, L1–L3 отвечают трём различимым аудиториям тендерной оценки, L4 заводит практику статистики по требованиям.

Уровни L0 и L4 добавлены по [дополнению к постановке в комментарии к PR #322](https://github.com/G-Ivan-A/mango_ba_prompts/pull/322#issuecomment-5416675011) от 2026-08-25:

> - другие артефакты для достжени яцелей по решению исполнителя

| Уровень | Документ | Аудитория | Вопрос, на который отвечает | Формат |
|---|---|---|---|---|
| L0 | `L0-customer-form-with-assessment.md` | Заказчик, тендерный комитет | «Что вы ответили по каждой строке нашей формы?» | Дословная форма Заказчика (4 таблицы в одном файле) + одна добавленная колонка |
| L1 | `L1-executive-summary.md` | Бизнес, руководитель направления, тендерный комитет | «Берём или не берём? Что мы точно не сможем?» | Короткий вывод + агрегированные цифры + список красных зон |
| L2 | `L2-feasibility-matrix.md` | БА / архитектор решения | «Какое конкретно требование чем закрывается и на каком основании?» | Матрица построчно по структуре заказчика, со ссылками на источники |
| L3 | `L3-technical-notes.md` | Разработка, пресейл-инженер | «Что проверить у вендора и на пилоте до фиксации обязательств?» | Списки вопросов вендору, spike-проверок и проектных ограничений |
| L4 | `L4-requirements-statistics.md` | БА-методолог | «Как устроены сами требования и можно ли по ним считать статистику?» | Статистика по требованиям: объём, модальность, ответы участника, тематические классы |

Обоснование именно такого деления:

- **Почему матрица (L2) — центральный документ.** Вход — четыре таблицы требований с уже заполненной колонкой «Комментарий участника». Требование «анализ должен явно ложиться НА структуру и требования заказчика» выполнимо только тогда, когда единица анализа совпадает с единицей ТЗ — строкой таблицы. Любая перегруппировка (по темам, по модулям, по рискам) нарушила бы это условие. Поэтому L2 сохраняет исходные `№`, текст требования и ответ участника без изменений и добавляет три колонки: уровень покрытия, подтверждение (SSOT), вывод по исполнимости.
- **Почему L0 воспроизводит форму, хотя есть L2.** L2 — рабочий документ БА: он добавляет три аналитические колонки и тем меняет ширину таблицы, а в шапке Приложения № 3 даёт пояснение к содержанию раздела. L0 не добавляет ничего, кроме одной колонки: шапки листов, порядок и заголовки колонок, нумерация (включая повторяющийся `10.0` и точки в `5.1.`) и текст воспроизведены посимвольно, а сам файл **сгенерирован из `.xls` скриптом**, а не перенесён руками. Это документ для возврата Заказчику в его же форме.
- **Почему нужен L1 отдельно.** Матрица на 101 строку нечитаема для решения «идём в тендер или нет». §2 контракта требует «как минимум один сводный документ с чёткими выводами об исполнимости» — это L1.
- **Почему L4 — практика, а не методология.** Заказчик прямо ограничил статус этого артефакта: статистика на ненормализованных требованиях искажает данные, поэтому определение методологии выносится в отдельный анализ. L4 фиксирует наблюдения по одному ТЗ и перечисляет вопросы, без ответов на которые статистика несопоставима между ТЗ; норматива он не устанавливает.
- **Почему нужен L3 отдельно.** Значительная часть строк закрыта частично или не подтверждена документацией. Эти пробелы — не выводы, а задачи на проверку, и смешивать их с оценкой было бы искажением: L3 отделяет «мы не нашли подтверждения» от «этого нет».

Воспроизводимость L0 и L4: оба сгенерированы скриптами `experiments/issue_319_build_source_mirror.py` и `experiments/issue_319_requirements_statistics.py`; команды запуска приведены в самих документах.

Дополнительно, вне уровней: `inputs/README.md` (трассируемость и хэши вложений), `logs/` (протокол работы, доступность источников, гипотеза процесса для таксономии БА, метрики), `feedback/review-notes.md`.
