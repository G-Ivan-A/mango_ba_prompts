# Гипотеза нового процесса таксономии БА

Формируется по контракту §4 issue #319 для переиспользования паттерна. Гипотеза не вносится в `standards/ba-ontology.md` в рамках данного прогона: контракт прогонов запрещает прогону изменять файлы вне собственного каталога, поэтому включение в онтологию — предмет отдельной задачи.

## Название

**Оценка исполнимости требований заказчика по документации продукта** (рабочий код: `feasibility-assessment-by-docs`).

Отличие от смежных процессов: это не сбор требований и не проектирование решения, а **сверка чужого перечня требований с документированными возможностями продукта** с обязательной трассируемостью каждого вывода к источнику и с явной разметкой пробелов.

## Триггер

Поступила тендерная или предпроектная таблица требований заказчика (чаще всего Excel, часто уже с колонкой ответов вендора), по которой нужно дать обоснованный вывод «исполнимо / исполнимо частично / не исполнимо».

## Входы

| Вход | Обязательность | Примечание |
|---|---|---|
| Таблица(ы) требований заказчика | обязательный | Структура и формулировки неприкосновенны |
| Постановка критериев оценки (фокус, глубина, формат) | обязательный | При отсутствии — процесс останавливается и запрашивается постановка |
| Каскад приоритета источников покрытия | обязательный | Упорядоченный список: основной продукт → смежные платформы → обходные модули |
| База знаний по продукту с указанием версии | обязательный | Версия фиксируется — вывод действителен только для неё |
| Уже заполненные ответы вендора/участника | опциональный | При наличии меняет задачу на перепроверку и фиксацию расхождений |

## Выходы

| Выход | Аудитория |
|---|---|
| Матрица исполнимости построчно по структуре заказчика | БА / архитектор |
| Сводный вывод с агрегированной статистикой и красными зонами | Бизнес |
| Перечень вопросов вендору, spike-проверок и проектных ограничений | Разработка / пресейл |
| Перечень расхождений с ранее данными ответами | Все, кто согласует ответ заказчику |
| Журнал доступности источников | БА (обоснование, почему уровень не присвоен) |

## Ключевые операции

1. **Извлечение постановки** — найти явную инструкцию; при её отсутствии остановиться и запросить, не додумывая намерение.
2. **Приём входа с трассируемостью** — зафиксировать хэши и происхождение файлов, извлечь содержимое дословно.
3. **Разбор структуры входа** — определить единицу анализа (строка требования) и наличие уже заполненных ответов.
4. **Определение шкалы покрытия** — вывести уровни из каскада источников; зафиксировать правило «уровень только при прямом подтверждении».
5. **Сбор доказательной базы по уровням каскада** — последовательно, от приоритетного источника к обходным.
6. **Построчное сопоставление** — «требование ↔ цитата источника ↔ уровень ↔ вывод», без перегруппировки строк заказчика.
7. **Разметка пробелов** — отделить «функции нет» от «подтверждения нет», каждое — маркером с ссылкой на пункт ТЗ.
8. **Агрегация** — статистика по уровням, выделение красных зон.
9. **Фиксация расхождений** с ранее данными ответами.
10. **Расслоение по аудиториям** — L1 / L2 / L3.

## Критерии качества результата

- Каждый положительный вывод сопровождается ссылкой вида «раздел + страница» на источник.
- Каждый пробел размечен маркером и превращён в вопрос вендору или spike-проверку.
- Формулировки и структура заказчика воспроизведены дословно; оценка добавлена, а не подменяет исходный текст.
- Указана версия документации, для которой вывод действителен.
- Ни один уровень покрытия не присвоен «по аналогии» или по маркетинговым материалам.

## Типовые риски процесса

| Риск | Проявление в этом прогоне | Контрмера |
|---|---|---|
| Достраивание отсутствующей постановки | Файл коммуникации не приложен | Остановка + запрос; использование только явного текста задачи |
| Присвоение уровня по маркетинговым заявлениям | twin24.ai заявляет точность 95 % без методики | Уровень не присвоен, заявление вынесено в вопрос вендору |
| Подмена «нет подтверждения» на «нет функции» | 38 строк без подтверждения | Разные формулировки вывода + вынос в L3 |
| Молчаливое согласие с уже заполненными ответами | 11 расхождений | Отдельный перечень расхождений с основаниями |
| Устаревание вывода | КБ v1.26.28 / v1.26.18 | Версия зафиксирована в границах анализа |

## Метрики применимости

Ориентиры, полученные на этом прогоне (102 требования, 2 источника КБ): доля строк с подтверждением — 63 %, доля расхождений с предзаполненными ответами — 11 %. При существенном отклонении от этих значений на следующих применениях процесса стоит проверить полноту базы знаний, а не только качество разбора.
