1. Вложения issue #313 скачаны во временный каталог рабочей станции (`/tmp/att/`), в репозиторий не добавлялись. Провенанс с размерами и SHA-256 — [`../inputs/README.md`](../inputs/README.md).

3. Текстовый слой ТЗ извлечён `experiments/issue_313_extract_pdf_text.py` (`pdfplumber 0.11.10`); 6 страниц, текстовый слой присутствует на всех.
4. Постановка Пользователя восстановлена по репликам экспорта; расхождения с постановкой issue #313 разрешены в пользу issue (текущий контракт задачи приоритетнее формата чата).
5. Каждое утверждение об API сверено с чанком `kb/processed/vpbx-api/sections/*`; построчный протокол — [`verification-log.md`](./verification-log.md).
6. Проверена гипотеза issue #313 о выдуманных параметрах API. **Не подтвердилась:** `dialog_id` — поле Заказчика из ТЗ, сопоставленное с реально существующим `command_id` [VPBXAPI, §3.2.1, с.33]. Ни одного несуществующего параметра или метода в артефакте первичного исполнителя не обнаружено; при этом найдено 10 фактических ошибок в трактовке существующих параметров — они исправлены и перечислены в служебном разделе отчёта.
7. Сформированы два выходных документа; ошибки прогона размещены **только** в разделе «Не для заказчика» в конце основного документа (требование issue #313).

## Наблюдения

- Основной риск оценки — не отсутствие методов API, а расхождение между формой обмена, описанной в ТЗ, и формой, которую даёт API: три поля webhook (`dialog_id`, `duration`, `record_url`) из семи требуют иной механики получения.
- Требование ДОД Пользователя по числу строк в таблицах 5 и 6 расходится со структурой ТЗ. Расхождения выведены «как определит исполнитель с комментарием на изменение» — в соответствии с правилом самого Пользователя.
- Первичный исполнитель ошибался не в существовании сущностей API, а в их семантике (`talk_time`, `disconnect_reason 1110`, код 5008 вместо 429) и в необоснованных числовых утверждениях («~85 %», «100 % выполнимо»). Это иной класс дефекта, чем галлюцинация имён.
