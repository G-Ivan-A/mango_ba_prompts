# Оценка выполнимости ТЗ на тендер: интеграция Utair.Chat (Uta.Chat) с Mango Office

**Предмет оценки.** Техническое задание Заказчика «Техническое задание на интеграцию веб-приложения Uta.Chat, с контакт-центром Mango Office» (6 страниц; провенанс — [`../inputs/README.md`](../inputs/README.md)).

**Вопрос, на который отвечает документ.** Насколько запрошенная Заказчиком функциональность закрывается **стандартными методами публичного REST API ВАТС Mango Office**: без доработок, частично или не предоставляется.

**Что документ не оценивает.** Трудозатраты на фактическую разработку и внедрение интеграционного шлюза на стороне Utair.Chat. Интеграционный шлюз — отдельная разработка силами Заказчика; если она выполняется силами Mango Office, требуется отдельная оценка.

## Дополнительные технические ограничения

Раздел содержит требования и ограничения, которые не выражены в ТЗ как отдельные FR/НФТ, но влияют на реализуемость интеграции. Все ограничения приведены со ссылкой на документацию.

### Разграничение зон ответственности

**Интеграционный шлюз — отдельная разработка на стороне Заказчика.** Настоящий документ оценивает **только возможность реализации интеграции** методами публичного API и **не является оценкой разработки**. Если разработка шлюза выполняется силами Mango Office, она требует отдельной оценки трудозатрат, не входящей в объём настоящей работы.

Заказчик должен реализовать на своей стороне как минимум: приём и валидацию подписи входящих уведомлений; хранение соответствия `command_id ↔ dialog_id ↔ operator_id ↔ channel_source`; вычисление длительности разговора; сопоставление `command_id → entry_id`; асинхронное дополнение системного сообщения ссылкой на запись; обработку кодов ошибок и лимитов частоты.

### Ограничение отправки уведомления о вызове

«При каждом вызове ВАТС передаёт внешней системе уведомление `/events/call` … При этом учитывается расписание приёма вызовов и статус абонента в Контакт-центре. Например, если вызов пришёл во внерабочее время абонента, то уведомление `/events/call` не будет отправлено. Исключение составляет статус "не беспокоить"» [VPBXAPI, §3.1.2, с.22].

Последствие для интеграции: стратегия сопоставления `dialog_id` с итогом звонка, опирающаяся на `/events/call`, не работает вне расписания приёма вызовов оператора. Это ограничение необходимо вынести на этап проектирования.

### В зоне риска

1. **Отсутствие эха `dialog_id` в уведомлении о завершении вызова** [ТЗ, с.4-5 против VPBXAPI, §3.1.6, с.28-31] — прямое требование FR-5 выполняется обходной связкой через `/events/call`.
2. **Неотправка `/events/call` вне расписания приёма вызовов** [VPBXAPI, §3.1.2, с.22] — при работе операторов вне расписания связка из пункта 1 разрывается.
3. **Норматив 2–3 секунды** [ТЗ, с.3] — документацией не подтверждается и не опровергается; требует измерения на пилоте.
4. **Повторная доставка уведомлений (retry)** [ТЗ, с.6] — в документации не описана; компенсируется сверкой через API статистики [VPBXAPI, §3.4.1.1, с.66-69].
5. **Генерация ссылок на записи без авторизации выключена по умолчанию** [VPBXAPI, §3.5.2, с.88] — требует включения в Личном кабинете и учёта временного характера ссылок.
6. **Лимит 4 инициации в секунду на продукт** [VPBXAPI, §1.4.2, с.9] — верхняя граница интенсивности click-to-call.

### Итоговый ответ на вопрос Пользователя

> «Система Mango Office даёт возможность реализовать интеграцию с запрошенными Заказчиком требованиями (с учётом ограничений)?»

**Да, с уточнениями.** Публичное REST API ВАТС Mango Office предоставляет методы, закрывающие ключевой сценарий ТЗ — click-to-call из интерфейса Utair.Chat с последующей фиксацией результата звонка и доступом к записи разговора. Требований, для которых метод в документации не определён вовсе, не выявлено. Четыре функциональных требования покрываются частично и требуют доработки передачи или вычисления параметров **на стороне интеграционного шлюза Заказчика**; два нефункциональных требования по документации API не оцениваются. Ключевое проектное ограничение — сопоставление звонка с диалогом строится через промежуточное уведомление `/events/call`, а не через эхо идентификатора в итоговом уведомлении.

**Формулировка вердикта для тендерного решения: «Исполнимо с уточнениями».**

## Ошибки исполнения: разбор артефакта первичного исполнителя

Проверялась гипотеза постановки [#313](https://github.com/G-Ivan-A/mango_ba_prompts/issues/313): первичный исполнитель (модель `qwen3.7-plus`) мог выдумать параметры API Mango Office, отталкиваясь от наименований параметров Заказчика.

**Гипотеза по `dialog_id` не подтвердилась.** `dialog_id` — поле Заказчика из ТЗ [ТЗ, с.4], а не параметр Mango Office; исполнитель сопоставил его с `command_id`, который действительно определён в `POST /vpbx/commands/callback` [VPBXAPI, §3.2.1, с.33] и в `POST /events/call` [VPBXAPI, §3.1.2, с.19]. Вымышленного параметра здесь нет. Проверка распространена на все параметры и методы, названные исполнителем: подтверждены `from.extension`, `to_number`, `command_id`, `entry_id`, `call_id`, `entry_result`, `disconnect_reason`, `create_time`, `talk_time`, `end_time`, `sip_call_id`, `recording_id`, `general.user_id`, `general.access_role_id`, `general.sips`, `groups`, а также методы `/vpbx/commands/callback`, `/vpbx/result/callback`, `/events/call`, `/events/summary`, `/events/record/added`, `/vpbx/queries/recording/post`, `/vpbx/queries/recording/link/…`, `/vpbx/config/users/request`, `/vpbx/stats/request`. Ни одного несуществующего параметра или метода не обнаружено.

В репозитории **отсутствует зафиксированный процесс оценки исполнимости (выполнимости) ТЗ**: в `standards/` есть `analysis-standard.md`, `bcreq-process-standard.md`, `runs-contract-standard.md` и другие, но стандарта или маршрута для тендерной оценки покрытия требований методами API нет. В соответствии с разделом «Отклонения от постановки» задачи [#313](https://github.com/G-Ivan-A/mango_ba_prompts/issues/313) процесс смоделирован исполнителем и описан в [`../logs/experiment-log.md`](../logs/experiment-log.md); закрепление его в виде стандарта — предмет отдельного решения Пользователя.
