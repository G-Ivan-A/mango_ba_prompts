## 1. Вердикт

**Исполнимо с уточнениями.**

Публичное REST API ВАТС Mango Office (документ «API Mango Office» версии 1.9) содержит методы, закрывающие целевой сценарий ТЗ: инициацию звонка из интерфейса Utair.Chat, получение результата звонка и доступ к записи разговора. Требований, для которых метод в документации отсутствует полностью, не выявлено: из 10 функциональных требований 6 закрываются полностью, 4 — частично; требований с оценкой «Нет» нет.

Оговорки, влияющие на решение:

1. Сопоставление звонка с диалогом (FR-5, Must) реализуется **не тем механизмом, который описан в ТЗ**, и требует проектного согласования.
2. Два нефункциональных требования (норматив 2-3 секунды, соответствие 152-ФЗ) **по документации API не оцениваются** и требуют подтверждения вне её рамок.
3. Оценка **не включает** трудозатраты на разработку интеграционного шлюза — это отдельная разработка на стороне Заказчика.

## 4. Ключевые ограничения, которые нужно объявить до подписания

| № | Ограничение | Последствие для проекта | Источник |
| --- | --- | --- | --- |
| 1 | В уведомлении `POST /events/summary` **нет поля `command_id`** — прямого эха идентификатора диалога в итоговом webhook не существует | Требование FR-5 выполняется связкой в два шага: `command_id → entry_id` через `/events/call`, затем `entry_id → итог` через `/events/summary`. Требует явного согласования с Заказчиком | [VPBXAPI, §3.1.6, с.28-31]; [VPBXAPI, §3.1.2, с.19] |
| 2 | Уведомление `/events/call` **не отправляется вне расписания приёма вызовов** абонента (исключение — статус «не беспокоить») | При работе операторов вне расписания связка из п.1 разрывается: итог звонка приходит, а привязка к диалогу отсутствует | [VPBXAPI, §3.1.2, с.22] |
| 3 | Длительность разговора отдельным полем не передаётся | Вычисляется шлюзом как `end_time − talk_time` при `talk_time > 0` (`talk_time` — момент ответа, а не длительность) | [VPBXAPI, §3.1.6, с.30-31] |
| 4 | Ссылка на запись не входит в итоговое уведомление | Системное сообщение дополняется ссылкой асинхронно, после события `/events/record/added` | [VPBXAPI, §3.1.8, с.32] |
| 5 | Генерация ссылок на записи без авторизации **по умолчанию выключена**, использует иную формулу подписи, ссылки одноразовые и «не должны сохраняться внешней системой» | Требует включения в Личном кабинете; в истории переписки хранится ссылка на шлюз Заказчика, а не на Mango Office | [VPBXAPI, §3.5.2, с.88-89] |
| 6 | Лимит инициаций — 4 запроса в секунду на продукт, 10 суммарно; превышение → HTTP 429 | Верхняя граница интенсивности click-to-call; на стороне шлюза нужна очередь | [VPBXAPI, §1.4.2, с.9-10] |
| 7 | Поля `operator_id` и `channel_source` в ВАТС не передаются | Хранятся на стороне шлюза в привязке к `command_id`; на выполнимость не влияют | [VPBXAPI, §3.2.1, с.33-34] |
| 8 | Поддерживается только TLS 1.2; уведомления приходят с пяти фиксированных IP-адресов | Требования к контуру Заказчика | [VPBXAPI, §1.3, с.8]; [VPBXAPI, §3.1.1, с.16] |

## 6. Границы оценки

Оценивается **только** возможность реализации требований ТЗ стандартными методами публичного REST API ВАТС Mango Office. **Не оценивается**: трудоёмкость и сроки разработки интеграционного шлюза; доработка ПО Utair.Chat; стоимость услуг и лицензий; соответствие 152-ФЗ; миграция с действующей IP-АТС Asterisk. Интеграционный шлюз — отдельная разработка на стороне Заказчика; если она выполняется силами Mango Office, требуется отдельная оценка.

Источники — только база знаний репозитория [`kb/processed/vpbx-api/`](../../../../kb/processed/vpbx-api/index.md), порождённая из официального документа «API Mango Office» версии 1.9, и официальные адреса Mango Office, приведённые в этом документе. Реестр ссылок с адресами чанков — в [`feasibility-assessment.md`](./feasibility-assessment.md#реестр-источников).
