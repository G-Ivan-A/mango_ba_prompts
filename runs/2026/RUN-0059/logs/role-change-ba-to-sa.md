# Смена роли исполнителя: БА → системный аналитик

## Что произошло

Постановка [#331](https://github.com/G-Ivan-A/mango_ba_prompts/issues/331) требует зафиксировать факт смены роли и подумать, как такой процесс стандартизовать в таксономии.

До RUN-0058 включительно прогоны по интеграции HH.ru выполнялись в роли **бизнес-аналитика**: вопрос звучал «покрывает ли API требования Заказчика», результат — вердикты по ФТ, разрывы, вопросы Заказчику, оценка выполнимости. RUN-0059 отвечает на другой вопрос — «как именно данные переходят из системы в систему»: методы, поля, порядок вызовов, идемпотентность, коды ошибок. Это работа **системного аналитика**.

## В чём практическая разница

| Измерение | БА (RUN-0056, RUN-0058) | СА (RUN-0059) |
| --- | --- | --- |
| Вопрос | Выполнимо ли требование? | Как это соединяется технически? |
| Единица анализа | Требование ФТ | Поле и вызов |
| Основной артефакт | Матрица покрытия и разрывов | Матрица маппинга, диаграммы последовательности, примеры JSON |
| Адресат | ПО, руководитель направления, Заказчик | Архитектор, разработчик (+ внутренний бизнес) |
| Критерий качества | Обоснованность вердикта | Однозначность реализации по документу |
| Отношение к неизвестному | Вопрос Заказчику | Маркер «требуется уточнение контракта» + вопрос внутренней команде |

## Что смена роли поменяла в самом прогоне

1. **Появился circuit breaker.** Для БА-вердикта допустимо рассуждение «в общем случае у таких платформ есть…». Для СА-артефакта это недопустимо: имя эндпоинта или поля попадает прямо в код. Отсюда — обязательная проверка `kb/processed` до анализа ([`source-availability.md`](source-availability.md)) и запрет на выдумывание.
2. **Изменился дом артефакта.** БА-результат ложится в уровни L1–L3 по адресатам. СА-результат неделим: диаграмма, строка матрицы и пример JSON читаются вместе.
3. **Изменилась форма фиксации незакрытого.** У БА это «вопрос Заказчику». У СА появился второй адресат — внутренняя команда продукта, и для него потребовался отдельный маркер `⚠️ ТРЕБУЕТСЯ УТОЧНЕНИЕ ВНУТРЕННЕГО КОНТРАКТА MANGO`.

## Предложение по стандартизации (для будущего обсуждения)

Действующий контракт прогонов различает прогоны по **цели** (`run_type`: `execution` или `statistics`), но не по **роли исполнителя**. При этом роль определяет ожидаемый состав артефактов и критерий приёмки — а значит, читателю реестра `runs/README.md` сейчас приходится выводить её из слага.

Возможное развитие таксономии — добавить в `metadata.yaml` необязательное поле `analysis_role` со значениями `business-analysis`, `system-analysis`, `architecture`, ортогональное `run_type`. Тогда:

- реестр прогонов позволяет отобрать все СА-прогоны для сравнения;
- к роли можно привязать чек-лист приёмки (для `system-analysis` — обязательный circuit breaker по источникам, обязательная матрица маппинга, обязательная маркировка непокрытых контрактов);
- цепочка «БА-прогон → СА-прогон → ADR» становится видимой через `related_runs` и роль, а не через чтение содержимого.

Ограничение предложения: поле не должно превращаться во второй `run_type`. Шкала успеха остаётся за `run_type`; роль отвечает только за состав артефактов и чек-лист приёмки. Изменение стандарта в этом прогоне **не выполняется** — постановка просила зафиксировать соображение, а не менять контракт; правка `standards/runs-contract-standard.md` требует отдельной задачи и обсуждения с владельцем стандарта.
