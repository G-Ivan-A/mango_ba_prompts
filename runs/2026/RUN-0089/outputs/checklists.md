# Чек-листы мета-стандартов разделов 1–8

## Раздел 1 (01-glossary.md)

- S1.1 Каждый предметный термин разделов 2–6 есть в разделе 1, и каждый термин раздела 1 используется в разделах 2–6.
- S1.2 Определение — одно предложение «родовое понятие + отличительный признак», без синонимов.
- S1.3 Термины БА и Заказчика перенесены дословно, связь с термином продукта имеет локатор.
- S1.4 Каждый термин сверен со словарями профиля; для С1–С3 есть блок расхождения с рекомендацией.
- S1.5 Ни один термин не заменён на индустриальный без решения БА.

## Раздел 2 (02-business-context.md)

- S2.1 Есть 2.1–2.4; 2.1 называет актора и ситуацию; 2.3 — одна фраза.
- S2.2 2.2 и 2.3 используют формулировки Заказчика; риски и числа имеют источник.
- S2.3 2.4.1 и 2.4.2 атомарны; 2.4.1 включает документацию, тестирование и вывод в эксплуатацию.
- S2.4 Ограничения платформы и версий — в 2.4.2 (кроме задач старой структуры).
- S2.5 Предложения ≤20 слов, раздел ≤250 слов, нет стоп-слов КС5.
- S2.6 При ≥2 продуктах заполнен 2.5 по классификации Mango.

## Раздел 3 (03-functional-requirements.md)

- S3.1 Вариант (В-Д или В-Н) указан и соответствует флагу Промпта 0.
- S3.2 Каждое ФТ проходит Ф1 (для В-Д), Ф2, Ф3, Ф4.
- S3.3 ФТ верхнего уровня 3–7 либо есть «Обоснование отклонения 5±2».
- S3.4 Каждое ФТ — по формуле «Система должна …» с субъектом и объектом.
- S3.5 Индустриально значимые ФТ вынесены в отдельный блок с источником и не вошли в список без решения БА.
- S3.6 Каждый пункт 2.4.1 покрыт ФТ или помечен «→ раздел 5».

## Раздел 4 (04-non-functional-requirements.md)

- S4.1 Каждое НФТ имеет характеристику, метрику, порог, условие и источник.
- S4.2 Нет НФТ без входного источника; при отсутствии НФТ — пустой раздел и ≤5 вопросов.
- S4.3 НФТ не дублирует ФТ и не описывает архитектуру.
- S4.4 Формулировки — бюрократический стиль, без размытых слов.

## Раздел 5 (05-solution-description.md)

- S5.1 Уровень (`L1` или `L1+L2`) указан и выбран БА.
- S5.2 Каждое ФТ раздела 3 есть в таблице трассировки; нет строк L2 без строки L1.
- S5.3 L1 не содержит методов API, форматов, БД и имён сервисов; ≤900 слов.
- S5.4 L2 содержит дельту API с типом изменения и обратной совместимостью (если API меняется).
- S5.5 Стыковые ФТ описаны в L1 один раз, в L2 — по сторонам стыка с контрактом.
- S5.6 Доменные подпункты — только в 5.2.x по профилям композиции.

## Раздел 6 (06-implementation-constraints.md)

- S6.1 6.1 и 6.2 разделены; пустой подраздел помечен «нет».
- S6.2 Каждый пункт 6.2 — «ограничение · источник · последствие».
- S6.3 Каждый пункт 6.1 ведёт к пункту раздела 5.
- S6.4 Ограничения платформы и версий — в 2.4.2 (кроме задач старой структуры).
- S6.5 Раздел ≤250 слов, предложения ≤20 слов.

## Раздел 7 (07-use-cases.md)

- S7.1 Каждый UC заполнен по шаблону и имеет класс.
- S7.2 Матрица UC × ФТ: покрытие ФТ 100 %, нет UC «влияет» без ФТ.
- S7.3 UC «не влияет» сохранены с меткой.
- S7.4 Прогон 2 содержит граничные кейсы по граничным значениям, классам эквивалентности и переходам состояний.
- S7.5 Стыковые ФТ имеют UC, проходящий через оба продукта.

## Раздел 8 (08-supplementary.md)

- S8.1 Каждый риск 8.1 имеет причину, последствие, меру и владельца.
- S8.2 Каждая зависимость 8.2 указывает, что блокирует.
- S8.3 Каждый критерий 8.3 проверяем и ведёт к ФТ или НФТ.
- S8.4 Открытые вопросы собраны в 8.4, решения — в 8.5 со ссылкой на человека.
