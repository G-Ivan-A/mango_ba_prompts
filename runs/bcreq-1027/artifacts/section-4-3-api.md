# BCREQ-1027. Раздел 4.3: API-методы

## 4.3. API-методы

4.3.1. Система должна передавать через API Контакт-центра аналитический признак способа завершения взаимодействия `с ответом` / `без ответа` для каждого текстового Обращения, которому по правилам п. 4.1 присвоен результат `Обработано`.

4.3.2. Система должна расширить событие `POST /events/md/onAppealClose` полем `completion_method`. Поле должно передаваться в корне JSON-объекта события вместе с существующим полем `result` и не должно заменять значение результата Обращения.

| Вложенность 1 | Вложенность 2 | Вложенность 3 | Вложенность 4 | Тип | Описание | Примечание |
| --- | --- | --- | --- | --- | --- | --- |
| `completion_method` |  |  |  | string/null | Аналитический признак способа завершения текстового Обращения. | `with_response` - Обращение завершено с ответом Клиенту; `without_response` - Обращение завершено без ответа Клиенту; `null` - признак неприменим или не заполнен для данного результата. |

4.3.3. Система должна определять значение `completion_method` для текстовых Обращений следующим образом:

| Условие завершения Обращения | Значение `result` | Значение `completion_method` |
| --- | --- | --- |
| Оператор завершил Обращение стандартным действием `Завершить` после отправки хотя бы одного сообщения Клиенту. | `Обработано` | `with_response` |
| Оператор завершил Обращение действием `Завершить без ответа`. | `Обработано` | `without_response` |
| Обращение завершено с результатом `Переведено`, `Спам`, `Не обработано`, `Истекло время ожидания ответа`, `Отправка запрещена` либо относится к нетекстовому каналу. | Текущий результат Обращения | `null` |

4.3.4. Система должна расширить метод `POST /vpbx/cc/appeals/create-closed-appeals` необязательным входным полем `completion_method`, чтобы внешняя система могла передать признак для закрытого текстового Обращения, созданного через API.

| Вложенность 1 | Вложенность 2 | Вложенность 3 | Вложенность 4 | Тип | Описание | Примечание |
| --- | --- | --- | --- | --- | --- | --- |
| `completion_method` |  |  |  | string/null | Аналитический признак способа завершения текстового Обращения, создаваемого в статусе `Закрыто`. | Допустимые значения: `with_response`, `without_response`, `null`. Значения `with_response` и `without_response` допустимы только при `result = 1` (`Обработано`). При некорректном значении Система должна возвращать существующую ошибку неверных параметров API. |

4.3.5. Система не должна менять существующие значения поля `result`, правила авторизации API, формат подписи запроса, идентификаторы Обращений и порядок отправки события `POST /events/md/onAppealClose`.

4.3.6. Система должна сохранять `completion_method` в аналитических данных Обращения так, чтобы значение, установленное при закрытии Обращения в интерфейсе или переданное через `POST /vpbx/cc/appeals/create-closed-appeals`, было доступно в API-событии закрытия и в API-представлениях закрытого Обращения, где уже передается поле `result`.

4.3.7. В обязанности Исполнителя не входит доработка внешних систем, которые получают событие `POST /events/md/onAppealClose` или вызывают `POST /vpbx/cc/appeals/create-closed-appeals`; внешние системы самостоятельно используют новое поле `completion_method` после обновления API-документации.

## Резюме изменений

- Текущая заглушка п. 4.3 заменена на конкретное аддитивное расширение API: добавляется поле `completion_method`, но существующий результат Обращения `result` не переопределяется.
- API-пример из вложения использован только как формат описания метода и таблиц параметров; поля статистики звонков и QM из примера не включены в скоуп BCREQ-1027.
- As-Is правила закрытия Обращений не переписаны в требования; текущие API-методы использованы только как точки расширения для целевого To-Be поведения.
- Раздел 3 не формируется. Разделы 1, 2, 4.1, 4.2, 4.4 и 6 не воспроизводятся в этом артефакте.
- При включении текста в полный ФТ нужно согласовать п. 6.1.4: передача признака через API в п. 4.3 является отдельным целевым исключением из ограничения на прочие отчеты, витрины, модули и интеграции.
